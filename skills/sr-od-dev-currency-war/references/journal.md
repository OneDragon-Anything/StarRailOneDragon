# 状态流水(journal)

状态容器怎么设计字段、值怎么写入,见 [game-state.md](game-state.md);本篇管**写入之后账本这一侧**:每次写入怎么落成一行、怎么落盘、谁能读、什么时候清理。

## 1. 状态流水是什么

- 流程侧唯一落盘流 = `state/journal.jsonl`,单文件追加(JSONL),行内 `run_id` 字段切段归局。per-run 分文件方案已否决。
- **每次状态写入记一行**:行 = 改了什么 + 渠道签名 + 版本号 + **写入后的完整状态快照**。
- **行行自足**:任何一行单独可读,判读不需要回溯前面的行。这是查询模型的根基。
- 遥测落盘共两份产物:状态流水(本篇)、缺陷台账(存废待裁,挂账板 §二.17)。曾设计的策略侧决策行文件(strategy/decision_trace.jsonl,逐帧记录策略计数增量)已裁定废弃删除——它只写不读(无判读/渲染消费方),且从未投产。

## 2. 一行记录从产生到消失(完整过程)

1. **状态变化发生**:观察 / 动作逻辑 / 派生逻辑三个渠道之一调用唯一写入口(渠道概念见 game-state.md 写入规范)。
2. **组行**:写入口在同一临界区内,先变更状态、后组装一行——分配版本号(本局段内自 1 连续递增)、嵌写入后完整快照、附渠道签名(§4)。
3. **进内存缓冲**:行先进内存缓冲,不逐行写盘——同步关键路径零 open/write。
4. **批量落盘**:缓冲满阈值(`DEFAULT_FLUSH_EVERY`,单一源 = kernel/cw_state_journal)写一次盘;局收尾时无论缓冲多少,收尾单点统一写盘(§7)。
5. **被读取**:判读 / 装配 / 策略回溯按行直接读;跨行对照靠行间差分(§8)。
6. **被清理**:每次进程装配时滚动清理,按局段整体淘汰,三道闸按序判定(§9)。

## 3. 行结构:两种行型

查询不分行型——两种行在流内等价,任一行自足。

- **写入行**:`v`(版本号)/ `ts` / `run_id` / `row='write'` / `field`(本次写入的字段寻址)/ `after`(新值)/ `same_value` / `state`(写入后完整快照)/ `sig`(渠道签名)/ `note` / `evidence_refs`。
- **观察事件行(obs_event)**:零状态变更的观察证据落行——拒读仲裁、失读保留证据、popup、类型直定冲突、获得链 diff 等。同样占版本号、内嵌当时 state。`event` 词是登记清单非全量(在用 obs_conflicts 写入位置逐点并入 + 新登记项);全量 miss 不保留证据行(在用纪律)。
- 归属注记:obs_event 仲裁行 `field='gold_delta'`(备战帧账实金对账证据行)属**观察对账域,非回执域**——与已退役的回执扩展键无涉,判读勿混。

## 4. 渠道签名(ChannelSig)

三族概念与写入规范见 game-state.md;本节是签名的完整字段面。

**渠道族封闭集**(写入源有且只有三个):

| family | 谁 | mode 取值 |
|---|---|---|
| `obs` | 画面 op 观察 | `read`(真读)/ `carried`(失读沿用)/ `prior`(先验)/ `synthesized`(sim 合成) |
| `logic_action` | 动作 op 逻辑计算 | 恒 `compute`(买卖扣金/升级/回执写入位置等) |
| `logic_hook` | 状态容器内部派生逻辑 | 恒 `compute`(节点推进派生/效果推进/局终收尾/接管中继) |

carried / prior / synthesized 是 obs 族内子模,**不是第四源**。

签名字段(每次写入必带):

- `family` + `mode`:必填;族构造期过封闭校验(`CHANNEL_FAMILIES`,集外即报错),缺签名 = 调用期显式报错,全行 actor 非空。
- `actor`:写入者身份(画面 op 类名 / 观察汇聚模块 / 动作 op 类名 / 派生规则登记名 / 接管协议 / 局终收尾)。
- `screen` / `frame`:画面建档名;carried 行必带 `frame`(沿用来源帧键)。
- `quality`:字段级质量标记 `{字段名: 标记}`,记录「这个值是怎么读到的」(如 hp=real_read / settlement_fresh / same_node_carried / prior;商店卡 cost=badge / roster / roster_fallback)。首写字段须登记申报值域。
- `group_id`:一次逻辑计算的打包组标识(动作 = `act:<op类名>@<seq>`,派生 = `hook:<登记名>@<序>`)。

## 5. 版本号

1. **单点分配**:写入口同一临界区内,先变更、后落行。
2. **局段内自 1 连续单调**,不重不漏;跨局唯一性由 `(run_id, v)` 保证;流内行序 = 版本序(版本号 ≠ 物理行号)。
3. **全序性前提 = 单写者**(单线程 op 链);多线程化必须先加锁,硬前置。
4. **单版本事务**:一次逻辑写入(观察组 confirm / 动作写入 / 派生管线一次触发)各产一行、各占一个版本;观察事件行也占版本。**派生连带更新共享同一版本号、一笔行落账**(行载荷标注 derived 清单)——若派生各占版本、或逐字段多行,策略侧的版本钉会指到从未被决策消费过的中间态,两形态废除。
5. **读取**:`current_version()` 只读;策略侧钉 `state_ref = (run_id, v)`,回溯直接读该行,行缺失 = `unverified`,不猜。

段界三个特殊窗口:

- **局间旧 id 驻留窗**:一局收尾后、下一局 run_id 还没铸造时,写入口上游有写缓冲垫着,新段铸造后按原顺序补写,补写行带原始 ts。
- **历史段补写窗**:给历史段补行走专用装配通道,不经运行时写入口。
- **恢复局重基线窗**:恢复局每段状态容器重新基线化——这是「版本号自 1」的前提。

## 6. 行内快照与序列化

- **state 快照**:写入后完整统一状态(JSON 安全化),含逐字段来源注记 `gs_prov`(source 非观察态、或带 evidence 的字段入注记——单行可判「gold 是真读还是沿用」)。
- **序列化规范化**:effects 按 spec id 排序、receipts 按窗序——同态同形,离线 diff 可比。
- **键名即值形契约**:节点序位键 = `node_pos`(值 `[p, r]` JSON 数组)、顶层水位键 = `node_hist_pos`(同值形)、effects 登记时点键 = `acquired_key`;离线判读按 (位面, 轮) 键取列。
- **派生原子生效**:派生规则在单版本事务内按固定次序完成(节点判定→类型→效果推进),派生字段与原始变更同行可见;派生出错 = 整笔回滚保留证据。
- **效果域捕获声明**:效果账本域(effects)保持就地可变的 inventory 方法域,不设专用写入入口、不设专用域行——效果变化随每行全量快照自带。效果的内容语义(声明式建模/计数器/写入两分/事件映射)归 [effect-inventory.md](effect-inventory.md)。

## 7. 落盘

- **形态**:内存追加 + 规范化序列化;磁盘批量 flush(阈值 `DEFAULT_FLUSH_EVERY`,单一源 = kernel/cw_state_journal)。
- **收尾统一落盘**:run 收尾单点(telemetry close_run)先把缓冲批量落盘再返回。若局终行与段尾行留在缓冲,紧随的档案装配读盘会漏行;收尾落盘把丢失窗上界收敛到收尾时点(单一源 = kernel flush_pending)。
- **宽容消费契约**:批量 flush 可能产生半行/坏行 = 逐行跳过 + 坏行计数留痕;一切消费方(判读命令行 / 装配器 / 哨兵)统一按此消费,禁把半行当合法行解析。
- **局外拒写**:run_id 为空 = 拒写(`StateJournal.append` 局外门与写入口双门)。
- **体积**:单行全量快照,显著大于增量式设计;压缩候选必须保行自足。

## 8. 读取:谁能读、怎么读

- **查询模型**:按行直接读(单行自足);跨行对照 = 行间差分(人读 / 离线),无机制化重放;完备性核查(节点推进数 / 效果递减伴生性等)归判读侧离线派生,不设系统机制。
- **读向隔离**:决策输入禁读状态流水。运行时控制面确需读流水的入口属例外,须在消费点注释显式申报豁免——不设集中枚举清单(清单会随调用点漂移,集中维护必失真)。

## 9. 寿命:滚动清理三道闸

- **触发时点** = 装配前置:生产装配趟 `install_state_telemetry` 调 `enforce_journal_retention`(单一源 = kernel/cw_state_journal)。该时点写入方未启动,零并发窗;每次进程装配触发一次。
- **清理单元 = run 段整体**,禁切半段——段内版本序完整是 state_ref 版本钉解析的前提。
- 三道闸按序判定,命中即入淘汰集:

1. **实机段龄窗**(常量 `JOURNAL_RETENTION_DAYS`,跨期语料窗):只适用实机形态段(run_id 铸造口径 `REAL_RUN_ID_RE` 分型)。跨期语料窗的承诺适用范围 = 实机对局语料。
2. **非实机段龄窗**(常量 `JOURNAL_NONLIVE_RETENTION_DAYS`):sim 批段与 harness 段——全消费面(判读过滤 / 档案装配 / 哨兵)均不采信,保留价值 = 批后隔日复查判读,短窗足够;非实机段是账面体积的主要来源。
3. **体积兜底窗**(常量 `JOURNAL_MAX_BYTES`):前两道清完后在用文件仍超上限,按段末时间从最老段继续淘汰(**不分型**,实机段也在淘汰序内),直到 ≤ 上限或只剩不可清段。容量失控(如压测日异常积累)可击穿闸 1 的承诺窗——此时保留窗的下限语义让位于容量约束,被清段经 manifest 记录保考古。

- **通用护栏**:活跃段(段末行最新)永不清理;无 ts 段不判龄不清理(宁保留不误删);坏行 / 无 run_id 行原样保留(宽容契约,清理面不判定);被清段逐段追加写 `journal.retirement.jsonl`(`archived_out` 注记,`reason` 键辨「哪道闸清的」);文件重写 = 临时文件 + 原子改名;state_ref 钉解析失败 = 查 manifest 辨「清理 vs 丢数据」(行缺失 = unverified 不猜,schema 既有口径)。
- **伴生流联动**:缺陷台账随本趟段裁决联动清理——触发点唯一 = journal 装配趟,台账侧只跟随不自设清理周期(双源漂移禁令)。

## 10. 常开与装配

- **无条件常开**:无开关、无装配条件分支(影子双写方案已推翻)。
- **生产装配两路**:
  1. app 装配段显式接通;
  2. 局状态容器单例建立点兜底——`game_state_of` 建立路径注入 run 归属读取函数并触发 kernel `ensure_journal_assembly`(幂等)。GameState 构造器零装配逻辑:画面解析草稿的状态容器直构路径,结构性不可能触发遥测。
- **两路汇合的注入聚合入口** = `establish_new_match` 状态容器建立点——它是「CwEntryStart 进对局前移」与「CwLoop handle_init 兜底」两个生产调用方的公共入口。
- **装配归属**:遥测数据的保存是状态容器(game state)的职责;run 领取层 telemetry `ensure_run_started` 不负责装配。
- **旁路覆盖**:`run_operation` 直调 CwLoop 的接管 / 续跑不经 app 装配段,由兜底路 ② 覆盖。写路径不因账本存在与否分支,行落盘以 sink 在场与 run_id 在场为准——缺实例 = 行不落,诚实缺失。

## 11. 硬约束

1. **禁旁路直写**:状态写入只能走唯一写入口,禁直摸字段 / 直摸效果域 inventory。
2. **渠道族封闭集**:族构造期校验(`CHANNEL_FAMILIES`),集外即报错。
3. **域准入白名单**:逐字段以实码写入位置全集核源,禁凭概念断格。
4. **读向隔离**(§8)。

## 12. 策略计数的承载

- 策略私有计数(`cw4_counters`,策略器状态字段)不进状态容器快照,状态流水里没有它。
- 它的落盘载体 = 局终聚合(局终域行载荷 `MatchFinal.cw4_counters`,局终一行总账)——判读与复盘渲染按此读。
- 曾设计的逐帧载体(策略侧决策行文件)已废弃:只写不读,判读链全部走局终聚合。
