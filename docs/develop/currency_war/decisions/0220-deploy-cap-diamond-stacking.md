# 0220 deploy cap 合法域反转:宝钻可叠加,cap<level 才是真异常

## Status

accepted(2026-08-22;局38 判读驱动,用户指出后台单位/新角色假设)

## Context

局38 r2 起 `deploy_cap_vs_level` 观察冲突留证反复触发(cap=5, level=3,域外 +2),
跨 5 局存活 5 shots(19:13-00:56)。原域检查(审计 #15,D-53 知识)假设
`cap ∈ {level, level+1}`(单宝钻封顶)。用户提出假设:后台特殊单位(佩佩类)/
新角色未识别可能改变人口。

排查三假设:
1. **新角色未识别** → 排除:局38 OCR 全部角色名(赛飞儿/万敌/远坂凛等)在
   CHARACTERS roster 全覆盖(74 人);佩佩 MISSING 正确(投资策略发放物,
   非部署角色);
2. **后台单位加 cap(领航员/佩佩)** → 排除:领航员=姬子·启行独立羁绊
   (trait 3007,「加入流派羁绊+复制装备」),与部署位无关;佩佩=投资
   发放物(招财狗「每佩佩+1 金」),无人口效果证据;
3. **宝钻叠加** → 命中:装备注册表官方效果原文「拥有宝钻可以使团队规模
   上限+1,**无论是否被角色穿戴**」(cw_equipment_data)= 按拥有计数可叠加;
   cw_back_layout 五组实测早有「lv4+1宝钻=cap5」先例;局38 r2 的 +2 =
   两宝钻,自洽。

## Decision Drivers

1. 域检查的目的(审计 #15)是「cap 作 level 的第三独立源,检测 level 读错
   (M38 毒化天敌)」——该目的只约束**下界**;
2. 假警报占 [cw!] 通道(跨 5 局响),违背「需关注=真需介入」的日志纪律。

## Considered Options

- **A. 域放宽到 level..level+2**:拍脑袋新上限,再叠 3 宝钻又假响 → 弃。
- **B. 删掉域检查**:丢失 cap<level 的真读错检测(下界有鉴别力) → 弃。
- **C. 反转+分级(选定)**:cap<level → 留证「不可能向」(真异常);
  cap>level+1 → debug 级记宝钻数(cap-level,人口/板深模型可用信息),
  不再占 [cw!]。

## Decision

选 C。`prep_director` 审计 #15 域检查反转;`_read_deploy_paddle`/
`read_deploy_cap` docstring 补叠加语义(官方原文引用);recognizer D-50
告警保留(其行为在叠加语义下仍正确:cap>level 均意味着后排按 max(6,cap)
取布局),文案改「宝钻×N 叠加」。

## Consequences

- 假警报消除(宝钻叠加是常态合法态);cap-level 现为可消费的宝钻数信号;
- 策略侧未来可用宝钻数(如人口规划/经济模型),已在 debug 日志暴露;
- D-50 的「+1 封顶」旧表述作废。
