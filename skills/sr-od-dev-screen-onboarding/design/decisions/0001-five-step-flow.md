# 0001. 五步流:客观 → 主观 → 建档 → 缺口 → 建模

- **Status**: accepted
- **Date**: 2026-08-04(形式化;原始实践 2026-07 初)

## Context
每张新画面要做「识别 + 建档 + 建模」,顺序混乱会漏:只看 OCR 漏图形按钮(`打开游戏` 右下 4 圆圈按钮 OCR 只零碎识出一个 `C`);不做缺口分析就盲目建模(不知道哪些已建模、哪些缺)。

## Decision Drivers
- **不漏元素**:客观(识别器视角) + 主观(人视角)双视角互补。
- **建模有据**:基于缺口建模,不盲目堆模板。
- **可重复**:同一流程套每个新画面。

## Considered Options
1. **线性 OCR → 建档**:简单,但漏图形按钮 / 状态图标(OCR 盲区)。
2. **客观 → 主观 → 建档 → 缺口 → 建模**(选中):双视角 + 缺口驱动建模。
3. **建模优先**:先建模板再建档,顺序倒置、无缺口依据。

## Decision
选 2。五步:
1. **客观识别**(`analyze_screen`):匹配画面 / area / 全量 OCR。
2. **主观理解**(多模态 vision):布局 / 图标 / 状态 / 模态性。
3. **建档**(doc):何时出现 / 状态流转 / 识别特征 / 可交互元素 / 识别快照。
4. **缺口分析**:对照「匹配 area」与「可交互元素 / 识别特征」,显式化已知 / 未知。
5. **主动建模**:基于缺口截模板 / 入 screen_info。

**前置 / 分支**:
- 玩法画面(有独立目标 / 资源 / 循环的 app)在前加「先搜攻略 / wiki 理解机制」前置(2026-07-28 补;玩法理解在先,读代码 / 画面才高效,避免凭代码猜流程、漏画面)。
- 无匹配(`screens=[]`)时走**兜底画面**(loading / 对话 等通用画面,无固定文字特征但结构固定),按结构 + 位置 area 判定 + 建档(不必精准 screen 匹配)(2026-07-12 补;某入口建档时 interact NPC 触发对话 `screens=[]`,发现这类通用画面 analyze 必无匹配但结构固定)。

## Consequences
- **正向**:不漏元素;建模基于缺口有据;流程可重复。
- **负向**:五步对简单画面偏重 → 按规模缩放:单画面走 §1-§6 常规;重 app(app 有 ≥3 子玩法、各独立画面)走 app 维度(见 [ADR-0006](0006-heavy-app-dimension-onboarding.md))。
- **边界**:OCR 盲区(图形按钮)由第 5 步主动建模补;状态判断由代码 + 第 2 步客观描述结合(见 [ADR-0004](0004-vision-required.md))。
