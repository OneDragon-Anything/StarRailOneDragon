## 核一·无前提

### F1【必修】道具详情弹窗错归 B-1 类——⑤ 的屏名委托对它结构性不可达，且删 miss 委托后失去唯一处理路径

- 位置：design.md §2.2（B-1 清单「道具详情弹窗(0e3)」）、§2.1 ⑤/⑥。
- 证据：
  1. `_od_merged.yml` 实测：货币战争-道具详情弹窗 **NO_IDMARK**；`cw_idmark_audit_report.md` 亦将其列为 5 个无 id_mark 屏之一；design.md §1.3「明确不解决」自己也列出了「道具详情弹窗」属无 id_mark 屏——**设计内部自相矛盾**（§1.3 说它建档识别不可达，§2.2 却把它当作可经 ① 屏名委托的画面）。
  2. `screen_utils.py:477-488`：无 id_mark 的屏 `get_match_screen_name` 恒不返回 → 该屏帧在 ⑤（屏名 ∈ 委托名单）永远不命中，必落 ⑥。
  3. 现状 miss 链 streak==2 委托 CwLoop（`cw_entry_exit.py:121-131`），CwLoop 0e3 分支用 OCR「聘用书」接住它——这是它**当前唯一**的处理路径。设计 ⑥ 明确删除该委托，理由「落到⑥的未建档画面委托对局循环同样无力」对该屏不成立（loop 有 0e3 现成分支，恰恰有力）。
  4. 后果：道具详情弹窗出现时只剩战斗 X 兜底——点的是「货币战争-战斗」档的右上 X 坐标，在道具详情弹窗上效果未知；battle_x 的 until（战斗暂停标识）不出现 → retry → 节点 fail，有界但弃局失败。
- 修复建议：道具详情弹窗移出 B-1，与 战斗结算/备战-补给锁定 同列「备忘档（无 id_mark，⑤ 不可达）」，并补一句其真实去处（⑥ X 兜底是否有効 / 或 miss 链保留一次按锚委托）；⑥ 的论证句「能落到此的只剩清单外（未建档/过渡帧）」同步改写——落到 ⑥ 的还有 4 张已建档无 id_mark 屏（战斗/战斗结算/补给锁定/道具详情弹窗），「备忘档或被 B-1 单锚接住」的说法同样不成立（B-1 委托入口在 ⑤，靠屏名，无 id_mark 屏进不去）。

### F2【必修】landing 3.2 完成判据 ⑤ 与设计 §2.1 ⑥ 直接相反

- 位置：landing.md §3.2 判据⑤「认不出帧 → miss 链与战斗兜底行为**与现状一致（回归）**」 vs design.md §2.1 ⑥「**删除**现有 miss 链中『委托一次 CwLoop』步骤」。
- 证据：`cw_entry_exit.py:121-131` 现状 streak==2 委托 CwLoop；设计明令删除。二者只能有一个成立。验收者按 landing 判据⑤验「与现状一致」会把正确实现（已删委托）判为不达标。
- 修复建议：判据⑤改写为「认不出帧 → miss 链**无 CwLoop 委托**（streak 计数与战斗兜底阈值不变），连续未识别按计数进战斗 X 兜底」。

### F3【必修】B-1 末两张的「落地批验证其在派生集内」——实测已可判定为「不在」，且补登记路径无阶段承载、超出 3.2 文件面

- 位置：design.md §2.2 B-1（备战-角色信息提示、备战-装备详情浮窗）；landing.md §3.2。
- 证据：
  1. 实测运行 `cw_overlay_registry.derive_clearable()`：派生集仅 {积分奖励, 中断挑战弹窗, 武装箱弹窗}，**不含**该两屏。设计预留的「不在则补登记」分支必然触发。
  2. 「补登记」动的是 `cw_overlay_registry.py` / `cw_screen_prep.py` 的注册表来源，而 3.2 文件面 = cw_entry_exit.py / cw_loop.py(停机位段) / cw_screen_state.py / 测试——补登记必然越界。
  3. 该验证没有出现在 3.2 或 3.3 任何完成判据里（3.2 六条行为锁、3.3 实机判据均未涵盖）——「落地批验证」是悬空承诺，违反写作硬规则 2（实现者无需再设计：实现者撞到时不知停手还是自行拍板）。
- 修复建议：设计定死处理方式（两屏的关闭动作如何落地：扩注册表 spec / 还是给 CwEntryExit/委托链加专用分支），并把它写进 3.2 完成判据 + 扩 3.2 文件面；或在 3.2 判据里显式写「验证两屏在派生集内，不在则按 §X 补登记（文件面含 …）」。

### F4【建议】prep_exit 对免战帧的点击坐标来源未写明

- 位置：design.md §2.1（A 类判定）/ §2.3（3.2 边界「任何建档 yml」不动）。
- 证据：实测免战档仅 2 个 area（标识-跳过, 标识-前台区域），**无「按钮-退出对局」**；备战退局发起节点点的是（货币战争-备战, 按钮-退出对局）。免战帧进 ③ 后跳备退局发起，点击坐标只能复用备战档（跨屏用档）——依据归档帧「布局同备战」成立，但设计没写这一句，实现者要自行拍板「复用坐标」还是「免战档补 area」（后者动 yml，违反 3.2 边界）。
- 修复建议：§2.1 A 类段补一句「免战帧复用备战档『按钮-退出对局』坐标（归档帧图证布局同备战）；不在免战档重复建档」。

### F5【建议】委托名单与新增路由状态的结构/落点未定

- 位置：design.md §2.1 ⑤「屏名 ∈ 委托名单（B-1/B-2 类）→ 跳『委托对局循环』或『敌人信息关闭』节点」。
- 证据：⑤ 里 B-1 与 B-2 的分流机制（逐屏 dict？B-2 单屏特判？）、新路由状态常量名、名单常量放 cw_entry_exit 还是 cw_screen_state，§2.3 只写「新增路由状态与两个节点」。单文档设计按规范应达「实现者无需再设计」深度——此项是可推断的浅层空白，不阻塞但建议一句话定死（如：B-2 为单屏特判 dict，B-1 = ① 返回的其余对局中屏名，即「非 A、非退出链、非大厅即委托」，无需维护 B-1 名单本体——这正好兑现「表外画面零维护」的 §2.4 承诺）。
- 修复建议：明确「委托 = ① 返回非 None 且不命中 ②③④ 的兜底分支」而非又一张 29 屏名单——若落地成显式 29 屏名单，则新建档画面漏登即复发，与 §2.4 放弃理由自相矛盾。

### F6【建议】战斗结算删委托后的兜底路径未交代

- 位置：design.md §2.2 备忘档、§2.1 ⑥。
- 证据：CwLoop 3b 分支可消化结算系画面（0e 注释「落到 3b『下一页』回大厅」实测在码）；战斗结算无 id_mark → ⑥ → X 兜底点「货币战争-战斗」档坐标，效果未知，失败有界但慢。备忘档只写「落 C 类兜底域（认不出）」未点明 X 对结算屏可能无效。
- 修复建议：备忘档补一句战斗结算的预期路径与可接受性（X 无效 → battle_x retry→fail 有界，或登记实机观察项）。

### F7【存疑】备战子态浮层帧上 ① 的屏名区分度

- 位置：design.md §2.1 ③（A 类 = 屏名判定）。
- 证据与疑点：备战与备战-开商店的 id_mark 存在同帧双命中可能（0n 注释实证「购买经验/出战在浮层下透出命中」）；若 ① 在开商店帧返回「备战」，③ 会在商店浮层在场时直接退局——与现状双锚穿透同形（现状注释自认「子态浮层不遮左上门形退出图标……实机验证项」），非本次回归，但设计把停机位判据从「穿透双锚」改为「屏名 ∈ A 类」后，该行为是否变化取决于 60 屏审计是否覆盖了「备战 id_mark × 开商店帧」这一对的互斥。若已覆盖则无发现；建议 3.3 实机验证顺手带一句。
- 注：免战点门形弹窗的未验证假设设计已规范登记（§2.1 + 3.3），不重复计分。
