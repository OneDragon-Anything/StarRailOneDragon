# 迭代文档规范（changes/ 篇）

> 定位：定义双层文档流中 `changes/<迭代名>/` 下的文档构成与写法。目标：设计文档足以指导实施——
> 任务书从它派生（指针化，不再自带判据）、reviewer 对照它验收、对抗审以它为攻击对象、账本阶段以它为单一源。
> 迭代的**流程顺序与任务书序列**（①设计批→②设计对抗批→③落地批→正本更新）见 od-dev-agent-autonomous-mode
> skill 的 orchestration.md「派出时」；本文只管**文档本身**。目录约定见项目 `AGENTS.md`「文档规范」。
> 术语：**总纲/详设** = 设计的概览文档/详细设计文档（详设存 `details/` 目录）；**阶段** = 一个可独立
> 派工、独立验收的实施批，对应账本一个任务。

## 1. changes/ 文档构成（两类文档 + 一个索引）

```
changes/<迭代名>/
├── README.md          # 索引:文档清单 + 流程进度(串起下面所有文档)
├── design.md          # 迭代设计·总纲(必有)
├── details/<主题>.md   # 迭代设计·详设(按需,可多份)
└── landing.md         # 迭代落地(唯一一份:阶段拆分与验收 + 正本更新清单)
```

- **分工一句话**：设计文档回答「系统应该变成什么样」；落地文档回答「怎么落地」（把设计映射为可派工、可验收的阶段序列）；README 回答「有哪些文档、走到哪一步」。
- **设计文档可能多份**（方案复杂时总纲+详设分开），**落地文档只有一份**。
- **引用寿命分层**（细化 AGENTS.md「禁引 changes/」铁律）：代码与正本文档**禁引** changes/ 内容（长期引用，维持禁令）；**迭代内工件**（任务书指针/账本 criteria/验收对照）引用总纲/详设/落地文档**合法**，寿命 = 迭代——收尾时正本已更新自足、任务全部终态，引用自然失效。

## 2. 设计文档（总纲 design.md + 详设 details/<主题>.md）

### 2.1 总纲（§0–§2）

- **§0 元信息**：迭代目标（对应当期目标编号/用户裁定指针）；状态 `草案 → 对抗审中 → 定稿`（定稿才可派落地批）；文档清单（详设一行一条）。
- **§1 问题与动机**：现状症状；根因归层（表示/约定/流程/语义）；解决到哪、**明确不解决什么**（防范围外溢）。
- **§2 方案**：系统级变化（读一遍知全貌）；详设划分与**跨详设接口契约**（唯一必须在总纲定死的深度内容——各自演化接口就会对不上）；单文档方案（无详设）此处即完整设计，深度要求与详设相同。

### 2.2 详设（三部分）

1. **问题与约束**：本主题边界条件；引用总纲划给本篇的接口契约。
2. **方案**：结构/接口/数据流/边界，深度标准 = 实现者无需再设计。
3. **关键取舍**：备选方案 + 为何放弃（正本化时进动机段）。

### 2.3 阅读体验与划分判据

- 总纲读一遍知全貌；实现某个阶段只读总纲 + 该阶段指向的详设即可动手。
- 实现某个阶段要跨多份详设拼凑 = 划分不当（回总纲调整划分或合并详设，不是 worker 的问题）。

## 3. 落地文档 landing.md（唯一一份）

### 3.1 阶段拆分与验收（账本阶段的唯一源）

每个阶段一个小节（`### 3.x <阶段名>`），按实施顺序排列，七件：

```markdown
### 3.1 <阶段名>
**范围**：<做什么；边界——明确不含什么>
**设计依据**：<design.md §X / details/<主题>.md+节>
**文件面**：<本阶段允许动的文件/目录>
**依赖**：<前置阶段，无则空>
**优先级建议**：<0..10>
**完成判据**：
- <行为对照设计文档哪节>
- <§12 通用工程门（引用，不复述）>
**验收凭据形式**：<测试名 / 画面对照 / 数字对照>
```

- **阶段粒度**：一个阶段 = 一个可独立验收的 worker 批；判据依赖另一阶段未完成部分 = 划分不当（排进依赖，或重新划分）。
- **阶段小节 = 账本唯一源**：立任务 = 照阶段小节内容 `dag.py add`（criteria 预注册指向本节）；设计改 → 小节改 → 账本跟着改，禁止两处各自演化。
- **固定末阶段 = 正本更新**：每个 landing.md 必含，判据 = §3.2 清单清零——迭代收尾由此成为流程终点，不是「记得就做」。每阶段交付后按交付流程派 reviewer 验收（验收不是独立阶段，是每阶段的固定动作）。

### 3.2 正本更新清单

每行：正本文档：节 ← 本迭代哪个阶段导致。由固定末阶段「正本更新」消费，清单清零 = 收尾完成。

## 4. README.md（索引）

只做两件事——**串文档、记进度**；不放判据、不放松散笔记：

```markdown
# <迭代名>

## 文档
- 设计总纲:[design.md](design.md)
- 详设:[details/<主题>.md](details/<主题>.md)（无详设删本行）
- 落地:[landing.md](landing.md)

## 进度
- 迭代设计:<草案/对抗审中/定稿>
- 设计对抗:<未开始/进行中/收敛> · 报告=[attack.md](attack.md)
- 落地:<阶段 x/y done>（明细见 landing.md）
- 正本更新:<未开始/清零>
```

- 进度只写在 README（一处）；设计/落地文档正文不写进度（无状态纪律）。

## 5. 写作硬规则（三条，各带卡点）

1. **依据就地标注**（无依据必攻）：每个关键主张在旁边写明依据（来源文档+节 / 直调数据表 / 已证命题）；依据跟着结论走，不设集中清单（集中清单 = 第二抄本，必漂移）。
   - 卡点：对抗审——无依据标注的主张默认为攻击目标（攻击者不用找弱点，未标注 = 弱点自带坐标）。
   - 防的事故：设计信任二手转述而与游戏真值不符，公式自洽但对抗两轮抓不住。
2. **实现者无需再设计**（定稿门槛）：实现者遇到的每个语义选择都能在设计或其引用的权威源里找到答案；「看情况/待定/酌情」= 未定稿。
   - 卡点：①定稿试读——对抗审假自己是实现者，逐阶段问「凭这份能开工吗」；②交付契约段停手令——worker 撞到设计未回答的问题：停手，回任务书指认的设计依据章节提请修订，禁自行拍板（自行拍板 = 在未过对抗审的语境做设计决策，绕过全部审查）。
   - 防的事故：worker 在无审查语境自行设计 → 实现与设计意图分叉 → 验收时整批返工。
3. **无过程叙事**：不写谁审的、第几轮攻击、上稿改了什么；过程住对抗报告与账本，进度只住 README。
   - 卡点：形式检查——「本轮/修订后/已改」类措辞即打回。
   - 防的事故：叙事让每次阅读付出与读者无关的注意力，且「第 N 轮」类引用随 changes/ 清理全部死亡。

## 6. 生命周期与引用寿命

```
草案(按模板起稿) → 对抗审中(②设计对抗批:总纲/详设/landing.md 一并攻——
                        依据/试读/阶段可验收性/接口契约)
→ 定稿(攻击收敛+试读过) → 立阶段任务(照 landing.md 逐阶段 dag.py add)
→ 落地批×N(每阶段交付即对照判据验收) → 正本更新批(固定末阶段)
→ README 进度收尾 → 设计文档留 changes/ 待生命周期清理
```

- 定稿门槛 = 攻击收敛 + 试读过；「带开放问题的定稿」不存在（未决 = 停在草案/对抗审中，状态由总纲 §0 表达）。
- 实现期设计修订：landing.md 阶段小节变更 → 账本同步；受影响在飞阶段按打回路由处理。

## 7. 设计对抗的攻击面（三核：无前提 / 规范遵循 / 治本）

对抗审三核并重；本节是核二/核三的卡点细则；核一（无前提）的角度由攻击者自己找，禁预设焦点。

### 核一·无前提攻击

- **总纲**：详设合集是否覆盖 §1 全部改动（边界完整性）；跨详设接口契约是否明确；landing.md 阶段与设计是否一致（设计依据指向真实存在、判据可验证）。
- **详设**：试读（实现者无需再设计）；依据就地标注逐条攻；对齐权威源逐项核。
- **通用**：无依据标注的主张必攻；结论只看证据，不看论证说服力；零实质发现 = 合法结论。

### 核二·规范遵循（对照已制定规范逐项核，每个发现给规范出处）

- 本规范：四节齐、阶段小节七件齐、写作硬规则三条（依据标注/无需再设计/无过程叙事）。
- 相关领域 skill 规范（按迭代主题定，如策略类 = strategy-work 各硬门）。

（项目 AGENTS.md 为 always-on 自动加载，不入清单——核它不需提醒。）

### 核三·治本核验（对 §1/§2 攻，根源两问）

- §1 的归层结论成立吗——现象的根真的在这一层（表示/约定/流程/语义）？
- §2 修的是根还是症状——说不清治本 = 打回；症状修法必须显式声明战术权衡 + 排期根治。
- 同族问题第二次出现 = 该升架构级设计件（跨件半问）——本迭代是否又在逐件修？
