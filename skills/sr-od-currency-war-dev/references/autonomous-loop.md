## 1. 写入 AGENTS.local 的自主推进纪律(登记镜像)

> 自主推进节由通用模板生成(围栏固定文本+CW 纪律条);固定文本之外,CW 增补写入 AGENTS.local 的纪律行=下方代码块全文(整块照抄进指令文件的自主推进节)——**新增须用户逐条批准**;镜像与实际写入保持一致(改任何一侧时同步另一侧):

```markdown
- **实机判读与早停**:局终了 = 实机监控角色按「单局复盘协议」派复盘子 agent(协议=`sr-od-currency-war-dev` skill references/match-review.md;数据=对局档案 `--match <game_id>` 直读,产出落 `replay/matches/reviews/<game_id>.md` 供策略审查角色消费)——编排者只裁决与记档,不自己做复盘。**重大修复 commit 后=无条件早停在跑旧代码局重开**(素材价值趋零);通关门等早停条件=sentinel 脚本组事件触发;连续 3 局不同根因=停下做架构层反思,禁止逐局打补丁
- **改货币战争策略**(细则单一源=`sr-od-currency-war-dev` skill 的 references/strategy-work.md):
  - 修改任何策略前,一定先读玩法文档(玩法研究/证明集/设计文档;清单入口=strategy-work「改策略前」;策略命题权威=math_proofs 证明与 sim/实机实证,未证口述按待证假设对待,ADR-0482)——没读就改=凭猜
  - 动手前必须明确本次修改是治本而非打补丁,说不清就是补丁,停下按根源两问走
  - 策略修复方案能用数学证明的尽量用数学证明——能算能证的一律优于拍死值(细则=strategy-work.md「决策规则数学先行」硬门)
  - 引入策略开关先过「策略开关的生命周期」门——唯一合法理由=行为输入未就绪+开臂判据挂账,禁悬置默认关(细则=strategy-work.md「策略开关的生命周期」节)
  - 旧测试锁拦路时先判锁再判改——**锁红≠改动错**,可能是锁钉着已被新设计取代的旧语义:先对照设计出处重推锁语义是否仍是当前意图,禁为保绿机械跟绿或回退好改动(判据与手法=strategy-work「锁的存在性纪律」)
- **模拟常开**:始终保持有子 agent 在跑模拟测试,找出货币战争策略的问题与优化方向(先阅读 sr-od-currency-war-dev skill 的 references/sim-testing.md「找问题」三步主线;一批交付即补派下一批)——不必等漫长的实机验证
- **实机运行时先武装哨兵**:起实机对局前,先把哨兵脚本三件跑起来(脚本=`sr-od-currency-war-dev` skill 的 scripts/ 目录;武装命令口径与重武三步入口=`sr-od-currency-war-dev` skill 的 references/runtime-ops.md「哨兵脚本组」节;报警怎么消费=`sr-od-currency-war-dev` skill 的 references/autonomous-loop.md §3)——不武装=对局卡死/断流没人报,烧几十分钟才发现
- **不干等实机**:实机运行期间禁止干等,实机在跑 ≠ 无事可做——判读上一局、跑 sim 批、改下一版策略这些离线可做的事照常推进,按派发盘点提醒派子 agent 并行工作
```

写入准则:动作判断本身完整写进指令文件,指针只作细则入口——不是拿一句「见某 skill」代替内容。

## 2. 定时任务增补角色:实机监控 + 策略审查

以通用四角色(值守兜底/派发盘点/回顾/子 agent 审计)为基线建网,提示词模板整块照抄 od-dev-agent-autonomous-mode references/reminder-net.md;CW 增补两个角色:

| 角色 | 间隔 | 类型 | 盯什么 |
|---|---|---|---|
| 实机监控 | ~10min,与通用角色错峰 | 自执行+派单 | 只管实机:哨兵脚本存活、对局/空窗、局中卡死巡检、**局终派单复盘子 agent(单局复盘协议)**、等待期不空转(见下模板) |
| 策略审查 | ~45min,与通用/实机错峰 | 派 agent | 派干净上下文子 agent:消费各局复盘报告的候选修复项作病灶输入,做策略修改审查八问(逐局复盘已由实机监控局终派单完成,本角色不做实盘分析;见下模板) |

### 实机监控

提示词模板(建定时任务时整块照抄):

```markdown
⚠️ 自主推进执行提醒:你在自主推进模式中。这条不是要回复的消息,是系统发来的待执行检查指令,现在执行。

【实机监控】当前任务:请按下述步骤严格执行。

1. 哨兵脚本还活着吗?
2. 在打局还是空窗?
3. 打局中,逐项巡检:
   - **时长巡检**:本局已进行多久(起点=对局档案 index 的 start_ts 或当前 run 段起始时间)——超过 ~50 分钟(阈值占位,待效率剖析批校准)在汇报里标记时长异常;极端长局常是半卡死/低效形态
   - **卡死巡检**:最近 10 分钟日志里同一句警告反复出现、又没有买卖上阵动作 = 卡死,停局处理
4. 局终了 → **派一个子 agent 按「单局复盘协议」复盘本局**(后台异步,不占本监控回合;不自己 inline 做,不用旧的四问)。子 agent 开工令必含:
   - 执行协议 = sr-od-currency-war-dev skill references/match-review.md 全文(阶段 1 阅读理解 → 阶段 2 逐节点四步**每节点出结论** → 阶段 3 位面三问);
   - 数据入口:本局的对局档案(主 agent 已按局拆分;字段面见协议阶段 2);判读工具 = telemetry-reading「查询工具」节;
   - 产出 = 逐节点结论清单 + 位面三问总答 + 候选修复项,每条带轮号证据,异常条目带来源定位;**报告落盘** `.debug/temp/currency_war/replay/matches/reviews/<game_id>.md`(子 agent 直接写文件,供策略审查角色消费)。

   结论回来由编排者(本监控)裁决与记档,裁决先**分诊**:**感知/运行时 bug**(识别误判/gate 误杀/死数据)→ 防线=fixture 帧锁+回放对拍+哨兵,别为此扩 sim;**策略行为病** → 治本修复,且修代码之外必须固化成 sim 检查项(先验形态在 sim 内可达,不可达走构造账本锁)或单帧锁——只修不复盘=再交学费;新检查须过守卫移除验证(临时去掉被检守卫重跑小批,违规必须涌现;全量基线 100% 命中=伪检查)。有异常 → 先确定异常来源,再找出治本的修复方案,然后将方案的实施状态记录到进度账本中合适的位置;同一个问题出现两次 → 必须走到治本方案这步,不许再当单局异常放下;单局结论不留。

每步结论必须带本轮工具输出的证据(哨兵存活=进程行原文,日志判读=引到的那几行,局终=结算数据摘录),拿不出当轮输出=没查过,不算数。汇报局中进展时,必须说这局的达成进度:打到第几轮、进的哪个阶段、阵容凑齐了多少、金的进出正不正常——不许拿血量充当进展(血量高低不等于打得好坏),血量只在跌破报警线以下才值得提一句。实机对局由 server 自动跑,不占用你的时间和子 agent 额度;且在跑的局用的代码在开局时已定型,等待期间做任何事(sim 批/下一版策略/文档)都不影响它在跑的结果。**「等实机跑完再说」永远是错的**:改下一版策略、跑 sim、审上局判读,都是现在就能做且该做的事。一切正常时一行结论,不写别的。(细则源=sr-od-currency-war-dev skill references/runtime-ops.md「哨兵脚本组」节)
```

### 策略审查

提示词模板(建定时任务时整块照抄):

```markdown
⚠️ 自主推进执行提醒:你在自主推进模式中。这条不是要回复的消息,是系统发来的待执行检查指令,现在执行。

【策略审查】当前任务:请按下述步骤严格执行。

1. 派一个干净上下文的子 agent 做策略审查(先当轮真扫:①`.debug/temp/currency_war/replay/matches/reviews/` 下未消化的各局复盘报告(实机监控局终派单的产出,其候选修复项=本步病灶输入);②账本任务行效果结论;③commit 记录——确认有无可处理对象;新报告与新修改都没有 → 写一行「本轮扫过,无新复盘报告、无新修改可审」即结束)
2. **子 agent 的开工令必含**(子 agent 编号承接上一步):
   1. 先读再动工:① sr-od-currency-war-dev skill 全文(入口分诊→单一源地图→当次涉及的域主线);② strategy-work.md(§2 策略骨架/§4 验证纪律,含「策略开关的生命周期」节);③ 玩法文档:按 docs/game/currency_war/research/README.md「策略相关文档」节的基线清单全读(阅读顺序也在该节);④ research/math_proofs.md 命题索引(证明对照用)
   2. **策略审查**(八问,逐项给「过/不过+依据」,判据全部锚定上述文档,不许自由发挥;各局复盘报告的候选修复项是本步的病灶候选输入):
      - 治本核对:病灶因果链画到根了吗?修的是根因层还是症状层?症状缓解有显式声明+排期吗?
      - 机制辖域核对:这个根因,现有代码/文档里的既定机制是否已管辖或部分管辖?(读 skill 与玩法文档可判)
      - 证明对照(ADR-0482):修改声称的依据是哪条已证命题(math_proofs P 编号)或哪组实测/sim 分布数据?直觉假设未证明前不构成依据,须先立命题或走 A/B 验证
      - 判据对照:效果结论用的指标来自权威判据吗?有没有拿末端量(hp 这类)当优化方向?
      - 波及面:动了哪些决策消费点?测试锁跟上了吗?同族消费点查过吗?
      - 数学证明核对:最近的策略修改,能不能用数学证明?能 → 立命题进 math_proofs 证明(按 strategy-work「决策规则数学先行」:能算能证优于拍死值);暂不能 → 写明卡点什么(缺机制参数/缺真值/非经济维度),需要补的采集挂账进进度账本
      - 开关审查:最近的修改引入了策略开关吗?存量默认关开关有悬置的吗?——判据=strategy-work「策略开关的生命周期」节:开关唯一合法存在理由=行为改动的输入还没就绪,且落码时必须带开臂判据挂账(什么数据、什么阈值才开);默认关若「开臂前置已消失或永不满足」且「概念已定谳」=该进清理批的死开关;「悬置开关」(已 A/B 判决却用默认关挂起)禁——结论必须三选一兑换,不留悬案
      - 旧锁存在性核对:最近的策略修改有没有被旧测试锁拦路/被迫绕行?拦路的锁先判锁再判改——**锁红≠改动错**,对照设计出处重推锁语义是否仍是当前意图(判据=strategy-work「锁的存在性纪律」);发现钉着已被取代旧语义的锁 → 立改写/删除项进进度账本,禁为保绿机械跟绿或回退好改动;同时查最近的锁更新有没有「只跟绿没重推语义」的洗白嫌疑

**派出前的编排者自查**(不在子 agent 清单里——它看不到其他子 agent 的活动):该根因是否已有别的在飞批在管?是→协调或等,不重复立案。

结论三种:「无新复盘报告且无新修改可审」(第 1 步当轮真扫过)、「通过」(各问全过+论证齐)、「打回/立修正批」(哪项不过+建议)。各局复盘报告的候选修复项与审查发现的问题当场立项进进度账本;跨局反复出现的「做得好」决策模式由编排者从复盘报告中提炼,沉淀进进度账本对应位置供策略设计引用。
```

### 派发盘点·CW 领域版(整块照抄本块;基于通用版 od-dev-agent-autonomous-mode references/reminder-net.md,改动说明见块后)

```markdown

【派发盘点】当前任务:请按下述步骤严格执行。

1. **先查还有没有空余的派发名额**:看当前 agent 额度上限和正在运行的子 agent 数(子 agent 状态清单)——还有空槽 → 继续第 2 步找活派;额度已满 → 直接跳到第 6 步记录,本轮不派
2. **重新检索进度账本找待办**:**当轮真执行检索并读结果**,以读到的为据——`progress.py summary <迭代目录>` 拿聚合+未完成态,或 grep 状态词(进行中/锁定/待激活/部分过/未做,只扫 进度.md,归档与流水不入检索);不要凭会话记忆里的待办状态派活;账本随时会被并行批更新,记忆里的「没有待办」不是看过的证据。有该做的 → 马上派(任务行写入也走 progress.py write)
3. 进度文件外重新找活:继续从下面的来源里找**现在就能派、不依赖任何进行中任务**的活。**每个来源都要本轮真的打开文件/执行搜索来看,以本轮读到的内容作答**——上一轮的结论、记忆里的状态一律不作数,代码和文档随时在变,「跟之前一样」不是看过的证据:
   - 欠的债:代码 TODO/到期没还的临时补丁、没跟上代码的文档、复杂逻辑缺「为什么」注释
   - 算法效率:上一个操作结束到下一个决策执行完成的延迟,是否慢到使用者看到自动化卡顿
   - 测试等待:开发过程是否每次都花大量时间等测试跑完
   - 重复手工:每次都手敲的命令序列、固定的多步操作
   - 该测试锁住但没锁的行为;复制粘贴的重复逻辑(该抽公共)
   - 攒够没消化的样本、该清理的临时文件
   - 踩了没记档的坑

5. 结论为零候选(非额度满)且当前仍有空槽 → 派一个**干净上下文的找活子 agent**快速找有什么能做(视野兜底,与第 4 步的 sim 产能兜底可同轮先后派)。任务书三件:①当前自主推进的目标与进度入口路径(运行时从 AGENTS.local.md「目标」「进度入口」字段抄全文,别凭记忆转述);②找活方法引用 sr-od-currency-war-dev skill references/autonomous-loop.md「派发盘点·CW 领域版」第 2、3 步,让它照着来源与方法找——指针写全文件与节名,别只写步骤号(子 agent 看不到这条提醒);③产出=候选清单,每条带出处与理由,只找不派。候选回来由编排者逐条裁决
```

### sim 批组织细则(承接 sim-testing 的批怎么组织;判据与做法=sim-testing「找问题」主线)

- **交付完整性 = 指纹 + 可运行的检查项**:问题较大的要留下回归——sim 批自己把检查项写进检查网(检查网可改,策略/sim 语义仓不可改);同类问题出现 ≥3 次 = 上升架构审查立案,不再点修。
- **批间互证**:没有批次的结论是不被检验的——编排者转述 worker 数字前先核原始口径;worker 论断 = 可推翻假设,选题优先审计前批的主导性论断(推翻与确认同等有价值)。
- **效果徘徊期的标准动作 = 两批并行**:一批走 sim-testing「找问题」三步主线(结构化),一批自由探索(无预设任务书,自带问题意识;负面结果也是产出,唯一纪律=证据链+对照玩法文档);两批都不改码(诊断与修分离),优化点清单汇入「周期改进」作派发弹药。
