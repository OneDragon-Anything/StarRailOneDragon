# 板面格子结构(部署空间机制)

> **性质**:对局内上场名额与前后排格子数的机制事实。来源=**用户口述(最高权威)**,2026-08-26 run 26 崩坏局后澄清。
> 版本基准:V4.4(4.5 更新无相关修复条目)。

## 规则(口述原文,2026-08-26)

> 「lv8 不是后台有 8 个,这个是错误的,lv8 是说总共可以上 8 个角色。正常情况下,就是固定的前台 4 个,后台 6 个,如果有钻石,或者召唤物,后台才会变多。」

拆解为三条机制事实:

1. **等级决定的是「总共可上场人数」(deploy_cap),不决定格子数**——lv8 = cap 8 人(前台+后台合计最多 8 人上场)。
2. **格子数正常恒定:前台 4 格 + 后台 6 格**;等级升高(人口扩展)是「往同样的格子里填更多人直到 cap」,不是「长出新格子」。
3. **后台格数只在两种情况下变多:钻石 / 召唤物(系统单位)**——即 8 格后台(393-1529 带)的触发条件是「钻石或召唤物存在」,与 level 无关。

## 对旧模型的勘误(推翻 ADR-0281 的 level 驱动模型)

`cw_back_layout.py` 现行模型「level≥7 → 后排 8 格」**归因错误**:其唯一实证(「lv7-8 → 8 格,狸猫局交互实拍」)的局**本身带召唤物(狸猫)**——8 格来自召唤物,不是来自 lv7+。按本篇口述,无召唤物/钻石的 lv7/8 局后排仍是 6 格。

**影响面**(run 26 = lv8 无召唤物局实证崩坏):
- 按错误的 8 格坐标拖拽 → 拖向不存在的 7/8 号格被游戏拒绝(白拖/弹回);
- `read_deployed_chars` 按 8 槽读人 → 把背景误读为空槽或错位身份;
- 板满门/围栏的空位计算(len(back)=8)全部失真 → 散牌填位与 cap 判定错乱。

**正确驱动因子判定**(供修法):后排格数 = 6(基线) | 8(当且仅当局内有钻石或召唤物/系统单位)。level 只进 cap,不进布局选档。

## 证据等级

- 本篇三条规则:`[口述]` 最高权威(用户 2026-08-26,亲见 run 26 崩坏后澄清)。
- 8 格与召唤物关联:口述 + 狸猫局实拍(交互定名)双重印证。
- 「钻石使后台变多」的具体格数(8?):口述未给数,按狸猫局 8 格实证暂记 8,**待钻石局实拍核实**。
