# sr-od-dev-currency-war · 设计总览

## 定位

货币战争(Currency War)自动化的**开发·维护·自主推进操作手册**,项目内 dev skill(跟仓库走,不独立发布)。回答三件事:代码架构与铁律是什么(SKILL.md §1)、任务从分诊表哪一行进入(§2 入口分诊)、知识在哪与行为变更怎么同步文档(§3 单一源地图+§4)。

## 边界

- **不管**:新玩法从零搭建(od-dev-write-application)、迭代流程与迭代内进度(od-dev-run-iteration)、停机钩子生命周期(od-dev-stop-hooks)、画面建档(od-dev-screen-onboarding)、写单个 op(od-dev-write-operation)——CW 场景下按 SKILL.md 入口序路由到它们,本 skill 不复述其内容。
- **不管**:游戏机制知识本身(在哪查由单一源地图指路)、策略的具体行为语义(strategy/01-07 是源)。
- 面向**已存在的 CW app**;若 CW 被推倒重写,本 skill 随之修订。

## 构成

- `SKILL.md`:导读 + 入口分诊表(任务→对应域,路由到各域 references 主线)+ 单一源地图(全部指针的集中地)+ 文档同步(细则按节下沉 references)。
- `references/sim-testing.md`:模拟测试专属说明(边界+找问题三步主线(统计→筛坏指标→挑局复盘);A/B 归 strategy-work「验证」)。
- `references/telemetry-reading.md`:实机局数据判读方法论(判读流程与先定标准步骤、查询工具、观察面全量清单、视图覆盖矩阵、采集缺口)。
- `references/runtime-ops.md`:实机运维细则(启动与重启、早停判据、局间交接序、残局画面清单、监控栈与哨兵脚本组)。
- `references/data-collection.md`:数据采集全景(生成器族、图鉴实采、运行时钩子、建模增量层、钩子统一使用与产物路径)。
- `references/version-update.md`:版本更新 CW 域适配方法(场景判型扩充/换赛季重做、按域依赖顺序的 checklist 与验收判据、换赛季特有面、已知坑;总流程挂 sr-od-dev-version-update-adaptation 路由表)。
- `references/compo-knowledge.md`:阵容知识工程(证据三层、三笔账、提炼/修订/版本重跑流程)。
- `references/strategy-work.md`:策略工作统一说明(策略是什么与方法主线、改前、开关落地、验证、单帧测试)。
- `references/autonomous-loop.md`:CW 分场景自主推进编排细则(四场景模型、场景的确定与线的叫法/跨场景通用编排:窗口所有权串行、停止操作汇报纪律、问题处置循环、传话纪律、进度登记/各场景节:实机探索局+修复线→app 自动流程跑局→sim 对拍→策略迭代线/领域叠加件:核心面清单与共享资产枚举的 CW 映射;通用框架单一源=od-dev-agent-autonomous-mode 的需求线流水线)。
- `references/screen-tracking.md`:画面识别与动作 op 的追踪文件(货币战争长期追踪目录里的一份记录文件:路径/格式/谁在什么时候写/什么不记在这里)。
- `design/`:本文件;ADR(why)仅经用户命令创建(默认无)。

## 与其它约定层的分工

- 全局/项目 AGENTS:always-on 通用纪律(工作流级);本 skill 只管 CW 特定操作,通用部分不复述。
- `docs/`:知识与设计本体;本 skill 是「怎么消费/维护它们」的操作规程。
- `.debug/progress/` 根下的存量迭代目录:历史运行状态,只读封存;新迭代的进度住 `.temp/changes/` 迭代目录(tasks.md,规范见 od-dev-run-iteration)。
- 货币战争的长期追踪目录 `.temp/tracking/currency-war/`:不在版本控制里,放跨会话长期保存的本地文件,现在是两份记录文件(待跟进事项、画面识别与动作 op);记法见 `references/screen-tracking.md` 和 `references/autonomous-loop.md` §2.5。

## 动机记录

- **§1.4 参数规范(用户裁定)**:动作原语最初按 kernel 会话语义设计参数(名称定位/槽位缺省走 game state 现算),暴露三类缺口——名称在重复实体下定位歧义(实拍:装备栏同名多条)、个别分支 game state 缺席即断言崩溃、参数 dataclass 缺 `from_dict` 导致 MCP JSON 通道构造不出(实机局 agent 无法调用穿装 op)。裁定:执行路径零 game state 依赖、参数三分法(固定槽位/半固定/动态坐标)、名称降级语义参数、坐标新鲜度归调用方、迁移按 op 切四角色子代理流水线(设计→review→实施→review)。刻意不采纳:op 落点前校验(违反动作 op 纯机械契约,新鲜度归调用方纪律)、按名称定位(重复实体歧义不可解)。
- **自主推进形态重写为实机探索期(用户裁定)**:旧形态(定时任务提醒+实机监控角色+哨兵报警消费接入+模拟常开+局终自动派复盘)服务 server 自动跑局时代,已整体废弃;新形态 = 编排者派实机探索 agent 按玩家 skill 亲自玩、遇问题停止操作并汇报,走诊断→设计→对抗评审(每轮全新子 agent)→实现与 review→实机验证循环(缺动作 op 的发现不经过诊断,直接立修复线),编排者全程只调度与传话不做技术判断。刻意不采纳:在旧文档上保留定时任务模板待将来恢复使用(用户裁定需要时重写,不留尾巴)。
- **自主推进文档按场景组织(用户裁定)**:编排方法跨场景相同(编排者职责/窗口所有权/处置循环/挂账与归位),一个场景一份文档、换期整体重写会让这些恒定件被反复重抄、方法无稳定落点;四个场景(版本适配摸索/流程框架适配/投资策略与环境 sim 适配/策略实现)只决定优先事项与对应场景节,文档不整体重写、各场景节就地维护。场景由用户开启自主推进时说明,编排者不按证据判定、不自行切换:线表表头只抄用户的原话,不随证据更新。刻意不采纳:按日历时间分期(能力未就绪即切换会让场景错位);编排者按追踪文件等证据判定场景并自动切换;维持单场景文档+换期整体重写。
- **场景一的范围(用户裁定)**:场景一只管画面建档与识别、动作 op。各域数据的更新(注册表、成批生成识别模板)是版本适配时做一次的事,不在场景一里预先排;只有实机探索中发现某一项内容识别不到(比如缺模板),才立修复线去补。画面上的操作没有动作 op 时,探索 agent 用鼠标把当前画面摸清楚后停在它上面、不往后打:画面留着,新动作 op 写完就能在它上面验证。知识文档在场景一只记待裁知识队列、不直接改,诊断结论是知识修正时不立线、探索线不等它:玩家 skill 的知识文档由用户把关,等裁定不该挡住探索。停在半路的对局留着、修复线期间不放弃:放弃对局收不回来,现场又是验证修复的场景。不做事先的盘点:不到游戏里看,光翻文件看不出缺了什么;目标由用户开启自主推进时说明,缺口在实机局里发现一条记一条,追踪文件开局时不预先建画面章。每局不另派子 agent 核对报告、整理发现、出下一局计划:实机探索 agent 自己在单局报告里写清发现、每条该去哪,编排者照报告登记;下一局任务书的四个字段照固定的记录填(目标 = 用户说明的目标,顺带取证 = 待跟进事项文件里等实机取证的条目,顺路验证 = 等实机验证的修复线,难度 = 可解锁的最高难度)。派要操作游戏窗口的活之前不另做画面识别,也不设「画面停在一局中间而占用表没有持有者」的专门规则。刻意不采纳:没有动作 op 时用鼠标打完整局再补(画面过去后只能等它随机再出现);在场景一里按域预先排数据更新线;开局先派一个不进游戏的盘点任务,预先扫出缺口清单和数据差异清单;每局另派一个判读子 agent 核对报告数字、整理发现、出下一局计划;派发前识别当前画面,发现来历不明的现场就登记待裁。
- **长期追踪目录(用户裁定)**:画面识别、动作 op 的情况要持续跟进,是跨会话的长期记录;开工前不该为了解它们读很多内容。做法:货币战争的长期追踪目录(`.temp/tracking/currency-war/`,不在版本控制里)放两份长期保存的文件——待跟进事项文件(寿命超过单个迭代的待办)和追踪文件(按画面分章,记识别核对的日期和结论、每个动作用的是哪个 op、该画面的缺口)。任务书只给路径,不抄内容:实机探索 agent 打到哪个画面读哪一章。记录只写日期和结论,不复述画面文档和画面档里已经写着的细节(两处都写,迟早不一致)。不是画面的缺口(流程缺陷、机制缺失)不进追踪文件,归待跟进事项文件。刻意不采纳:每次自主推进开工新建一张缺口矩阵、把没覆盖的格子原文抄进每一份任务书(每次开工新建一份,以前开工时记下的读不到;任务书越写越长);开工前按文件盘点一遍、预先建好全部画面章(不进游戏看不出缺了什么);记录里写明每次核对了哪些内容(和画面文档形成两份说法)。
- **场景一的运转细节(领域设计,不是用户裁定)**:
  - 有没有动作 op,按顺序看两处。先看追踪文件里这个画面那一章的动作一栏:这一步后面的括号里是 op 名,就有。括号里是「鼠标点击」、动作一栏里没有这一步、这个画面还没有章的,再看玩家 skill 对应画面文档的操作表:这一步「用什么」写的是 op 名(用 run_operation 调用的)就有;写的是鼠标点击或拖拽的、操作表里没有这一步的、这个画面还没有操作表的,就没有——这些步骤没有给 agent 调用的动作 op,bot 自动流程接不上。括号里写「鼠标点击」不直接算没有:括号记的是这一步上一次实际用了哪个,按它直接下判断,会在同一个画面重复停下、重复立线。新动作 op 做出来以后,由修复线把操作表那一格和追踪文件里这一步都改成 op 名:不改,下一个探索 agent 判断这一步还是没有动作 op,会在同一个画面再停一次。
  - 完成条件里带一条「用户说明的目标达到过」:不带的话,一局打完没报缺口,追踪文件里一条缺口都没有,「每条缺口都已处理」自动成立,场景一会被判完成。
  - 缺口的建议处置(立修复线 / 现在探不了)由实机探索 agent 在单局报告里写,编排者照抄:不写,这个技术判断会落到编排者头上。
  - 缺口并进已有修复线,只在那条线没过定稿时成立;过了定稿就另立一条线:过了定稿再并,等于绕开设计修订的门,而编排者没有「派设计修订」的机械规则。
  - 闪退、掉线以后对局多半转成挂起存档:恢复时先看模式选择画面有没有「继续进度」,有就续同一局,没有才记中止;启动工具只登到大世界,进货币战争交给重派的探索 agent。
  - 探索 agent 的建档按画面建档 skill 的完整步骤做,含测试仓的归档图和 id_mark 测试:不这样做,局里建档不算完成;留给后面的线补又没有固定的线来接。合并缓存是写档时重生成的派生文件,里面混着所有人的改动,谁都不单独提交。
  - 修复线连续 3 局没遇到而转去等裁定时,它对应的缺口条目同时登记进待跟进事项文件:不然这几条一直留在追踪文件里,完成条件一直不满足,编排者会一直派下一局。
  - 中途停下的报告(叫停、连接断开、闪退以后重开)和局终报告一样要登记:一局一派,子 agent 交了报告就结束,这一份不登记,里面的发现就没人再报。
  - 修复线往立绘库、装备库加了模板,或者改了已有的模板,要重启 MCP server:这几个库读进服务进程以后不再重读,不重启新模板不生效,修对了也会验证不达标。
