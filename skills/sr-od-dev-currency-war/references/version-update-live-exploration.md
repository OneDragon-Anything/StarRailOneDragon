# 货币战争实机探索期作业方法(CW 域)

> 定位与分工:本文档 = 货币战争新版本实机探索期的作业方法——怎么跑实机探索局、怎么把探索产出变成四层覆盖。分工一句话:编排机制(编排者职责/窗口所有权/单局限令机制面/问题处置循环)归 [autonomous-loop.md](autonomous-loop.md);版本适配总流程(判型/各域适配明细/换赛季战役组织)归 [version-update.md](version-update.md);玩法操作与对局决策归玩家 skill `sr-od-currency-war`;本文档只写作业方法本身。适用前提 = 游戏版本更新后的实机探索期(自主推进下就是场景一,见 autonomous-loop.md §3)。读者 = 实机探索期的编排者与实机探索 agent:编排者派局前读 §2-§3 与 §5,实机探索 agent 开工前读 §4 与 §6。局间循环:版本适配流程按 §5 走;自主推进下按 autonomous-loop.md §3.5 走。

## 1. 探索期目标口径

主目标 = 四层覆盖链闭合(自主推进场景一的完成只看前三层,见本节末条)。四层按依赖序:

| 层 | 内容 | 覆盖判据 |
|---|---|---|
| 画面建档 | bot 会遇到的画面建档到 screen_info | 画面能被识别框架认出(产物形态见 od-dev-screen-onboarding) |
| 画面识别 | 已建档画面的关键读数接入识别器 | `analyze_screen` extras(结构化读数扩展)能读出该画面的关键数值 |
| 动作 op | 自动打一局用得上的动作有对应动作 op | 该不该有,按 autonomous-loop.md §3.4 的三个问题判。该有的里面,玩家 skill 对应画面文档的操作表这一步「用什么」的主做法写着 op 的类名(用 run_operation 调用的)算有,其余算没有 |
| 游玩指导 | 玩家 skill 有该画面的决策知识 | 玩家 skill 对应玩法文档覆盖该画面的决策面 |

- **标杆 = 商店的买卖闭环**:商店画面上买、卖这一组动作四层全部在役(建档可识别 / extras 可读数 / 买卖的动作 op 可执行 / 玩家 skill 有买卖的决策指导)。新画面与新节点的覆盖验收以它为参照:前三层缺任何一层 = 未闭合,缺口登记进追踪文件(画面识别与动作 op 的追踪文件,§2.1);第四层缺了,记进待裁知识队列(§5 第 4 步)。商店画面上不在买卖这一组里的动作(比如免战跳过),该有动作 op 而还没有的,照常登记缺口,不算在标杆里。
- **目标来自用户,缺口边做边记**:实机局任务书由用户说明的目标驱动(§2.3)。追踪文件里已知的缺口只带路径:实机探索 agent 打到哪个画面,读那一章,顺手核对章里的缺口(§2.1)。禁不带目标进局。
- **机制/数据取证顺带,不占主目标**:待跟进事项文件上等实机取证的条目(定位见 SKILL.md §3「待跟进事项」行)在单局任务书里以顺带清单携带,主线始终是覆盖缺口;取证结论按 §6 可靠性纪律处理。
- **自主推进场景一的完成只看前三层**:第四层(游玩指导)是知识文档,要等用户裁定。它的缺口登记进待裁知识队列或待跟进事项文件,不卡场景完成(见 autonomous-loop.md §3.1)。玩家 skill 的指引不够用的地方,记进玩法指引的不足文件(§4.5),也不卡场景完成。

## 2. 开局与追踪文件

探索期的目标来自用户开启自主推进时的说明。缺口在实机局里发现,发现一条记一条(§2.1)。各域数据的更新(注册表、成批生成识别模板)是版本适配时做一次的事,归 version-update.md 的清单,不在探索期里排;探索中发现某一项内容识别不到(比如缺模板),才立修复线去补(autonomous-loop.md §3.6)。

### 2.1 画面识别与动作 op 的追踪文件

前三层的覆盖情况记在追踪文件里:按画面分章,每章记识别核对的日期和结论、每个该有动作 op 的动作有没有动作 op、这个画面的缺口。路径、格式、谁在什么时候写,单一源 = [screen-tracking.md](screen-tracking.md);本节只写探索期怎么用它。

- 新缺口从哪来:实机探索 agent 在局里发现的——没建档的画面、认不出的内容、该有动作 op 而还没有的动作。局里发现一条,编排者记一条。
- 追踪文件长期保存,随局更新。实机探索 agent 打到哪个画面,读哪一章,章里有缺口的顺手核对(自主推进下怎么给它路径,见 autonomous-loop.md §3.3 第 9 项)。四个字段的来源见 §2.3。
- 自主推进下由编排者登记和更新,规则见 autonomous-loop.md §3.2,登记的时机见其 §3.5;版本适配流程里也由编排者在局间循环登记(§5 第 3 步)。

### 2.2 版本配置什么时候查

版本适配流程里,实机局开工前先离线研究:

1. 拉官方攻略广场配置快照(plaza config,拉取命令见 version-update.md §2 第 2 步)——角色/羁绊/装备/投资的官方名单与效果文本;
2. 查 wiki 三源交叉(米游社 wiki / 国际服 wiki / BWIKI,接口入口 = skill `sr-od-official-api`);
3. **随机池类取证(概率/出现规则/池构成)先查配置再耗实机窗**——纯统计推断会被结构盲区骗。结构盲区 = 样本覆盖不到的规则结构(低概率档/隐藏门控/跨局状态),统计上不可见但真实存在;配置与 wiki 先给出结构假设,实机局只做验证。
4. 判据(版本适配流程里):实机局开工前配置研究已完成一轮;实机读数与配置矛盾的点才是高价值发现,优先排进任务书。
5. 自主推进场景一不把这一步排成单独的任务:它属于版本适配时做一次的事(version-update.md §2)。探索中要用到配置时(比如核对一个随机池的概率),再按上面三条查。

### 2.3 实机局任务书的字段

- 单局任务书的四个字段:局内目标(打到哪里/验证什么)、顺带取证清单(本局顺路可取的条目)、顺路验证清单(等实机验证的线里本局顺路能验的)、难度。
- 排序判据:覆盖缺口优先,机制取证次之;每局只背一个主目标,顺带清单只收顺路可取的条目,不要求绕路取证。
- 自主推进下,四个字段的来源是固定的记录,编排者照着填进任务书(autonomous-loop.md §3.3 第 7 项)。

## 3. 派发纪律

单局限令和难度的机制面归 autonomous-loop.md §3.3,一窗一 agent/占用先登记归 autonomous-loop.md §2.2,不在本节重复;本节写执行侧增量,每条附为什么。

1. **任务书完整重申纪律**:每次派发的任务书必须完整重申全部纪律条款(单局限令/停止纪律/最高难度/结算存档义务),不得以「按上次任务书」「同前」指代。为什么:子 agent 会话上下文压缩会丢早期纪律条目,被压缩掉的纪律等于没有纪律,任务书是纪律的唯一可靠载体。
2. **派发前查占用**:派发任何会占用游戏窗口的活之前,先查占用表(谁、从何时起、干什么)和线表,确认没有别的实机线在推进。完整的派发前检查见 autonomous-loop.md §2.2。为什么:同一窗口两个操作者会互相干扰——点击落进对方操作的画面、画面被抢,且事后无法从运行记录区分是谁的操作。
3. **实机占用先登记再派**:占用表登记(谁/从何时起/干什么)先于派发动作完成。为什么:登记是窗口互斥的唯一事前凭据,事后归因防不住并发。

## 4. 单局作业规范

实机探索 agent 每局执行以下规范:版本适配流程里,全部条款并入任务书;自主推进下,开工前读本节,任务书不复制(autonomous-loop.md §3.3 第 1 项)。

### 4.1 结算画面必存档

每场战斗的结算画面截图存档。用途:留证。版本适配流程里,单局报告的数字以结算画面为凭据逐项对账(§5 第 2 步);自主推进场景一不做对账,截图只留证。截图放当前线的子目录,文件名列进单局报告的证据文件清单。

### 4.2 逐局记录

单局报告按固定栏目记这一局的结果:走到哪(节点进度,如位面-节点号)/难度(当局难度档)/照哪条阵容线打(没照具体阵容线的写「没定」)/怎么结束的(胜负与终止原因)/局内目标(本局目标达到 / 未达到)。为什么只记这几样:看一局,要看的是它打到哪、照什么打的、怎么结束的。栏目缺失 = 报告不完整:版本适配流程里,编排者打回补齐;自主推进下一局一派,子 agent 交了报告就结束,不打回——中途停下的(这一局还会重派),编排者把缺的那一栏写进重派任务书的附加信息节,让接手的实机探索 agent 补写;局终的报告缺了哪一栏,在线表里实机探索线那一行的备注栏记「〈报告文件名〉缺〈栏名〉」,不补写。中途停下的报告里还没发生的栏目写「未到」,不算缺失。

### 4.3 新画面先建档再操作

遇到未建档画面,先按 od-dev-screen-onboarding 建档,再继续操作。画面上有这一局必须做、操作表里没写的一步时,把这个画面摸清楚以后停在它上面,不往后打(见 autonomous-loop.md §3.4);必须做的步骤,操作表里写了的,照操作表用鼠标做、继续打;不是必须做的动作,操作表里没写就不点。为什么:在未知画面操作 = 误点风险 + 现场证据丢失;建档本身也是覆盖链第一层的推进。

### 4.4 遇问题停手留证

下面是总则;场景一里各种情况各自的处置,以 autonomous-loop.md §3.4 的表为准,表里写「继续」的照表做。操作不生效/画面异常时:停止一切游戏操作 → 截图留证 → 报编排者等待处置。疑似机制变化不算故障:不停手,把现象和证据记进单局报告的「知识发现」,继续打。机制细则 = autonomous-loop.md §2.3,任务书整段并入。局内各种情况各自的处置见 autonomous-loop.md §3.4。

### 4.5 打法照玩家 skill 的指引

实机探索 agent 自己打局(不跑 application)时,照下面办:

- 打法照玩家 skill `sr-od-currency-war` 的指引,加上自己的判断。指引不会讲到每一种情况,没讲到的自己判断。
- 读什么、什么时候读,照 `sr-od-currency-war` 入口文件的规定。
- 遇到下面三种情况,记一条「玩法指引的不足」:
  - 要做判断,觉得难,`sr-od-currency-war` 里没有指引;
  - 有指引,但觉得不适合现在的情况;
  - 照着做了,效果不好。
- 记完接着打,不停手。

记在哪、一条怎么写,见 autonomous-loop.md §3.7。修复线做实机验证、要打一段对局的,也照本节办。

为什么打法不写在开发 skill 里:打法只住在玩家 skill。开发 skill 另写一套打法要求,两处会各说各的。

## 5. 局间循环

每局终了到下一局派发之间按固定序列走,每步产出是下一步的输入。自主推进下每一步由谁做、条件怎么分叉、中途停下时怎么走,见 autonomous-loop.md §3.5;分工一句话:第 1 步归实机探索 agent,第 2 步在自主推进场景一里不做,第 3、4 步的登记归编排者,第 5 步由编排者照记录填。本节只写每一步怎么做:

1. **单局报告**:实机探索 agent 每次停下都发报告,构成见 autonomous-loop.md §3.3 第 6 项。
2. **机械对账**:报告里的数字逐项和凭据(截图文件名、帧号)比对,不依赖报告者转述。判据:数字对不上 = 记为疑点,不采信报告原文;后面的登记一律用截图上的数。谁做:版本适配流程里由编排者另派一个子 agent;自主推进场景一不派——编排者不做判断,单局报告里的数字照报告登记。
3. **登记两份长期保存的文件**:画面核对的结果照单局报告更新追踪文件([screen-tracking.md](screen-tracking.md) §3);待办与候选结论登记进待跟进事项文件(定位见 SKILL.md §3「待跟进事项」行),条目格式见 autonomous-loop.md §2.5:实机发现类条目编号顺延(删掉的编号不复用),每条附证据指针(截图文件名)。
4. **知识发现去向**:实机探索期的知识文档等用户裁定,不当场回填。发现由编排者转登待裁知识队列(格式见 autonomous-loop.md §3.7)。用户裁定后派知识文档线,候选知识逐条核实:官方配置、wiki、以前实机局留下的截图,三样里有一样对得上才回填知识卡。判据:对不上的候选不进知识卡,去向按 autonomous-loop.md §3.7「核实的三种结果」;核实通过 = 更新知识卡,队列里对应条目删除。
5. **下一局任务书**:按待跟进事项文件开放项、等实机验证的线重排(回到 §2.3),派发前过 §3 纪律。追踪文件只带路径,内容不抄进任务书。自主推进下,四个字段照固定的记录填(§2.3)。

**知识卡** = 玩法知识的最小归档单元:玩家 skill `sr-od-currency-war` 的玩法文档(单画面卡与总览篇)与 `docs/game/currency_war/research/` 知识篇。归位分层判据见 SKILL.md §3。

## 6. 知识可靠性纪律

1. **帧号制度**:候选实录与机制结论必须附帧号。帧号 = 帧时点的可回查标识,实证形态 = 截图文件名(编排细则里叫证据指针)或遥测流水时点。判据:无帧号 = 不可回查 = 不入档;口头转述无帧证的内容只作线索。
2. **单样本知识先核实再入契约**:仅出现一次的观察读数不入消费契约(注册表条目/知识卡的确定性结论)。核实路径 = 第二来源(官方配置、wiki、以前实机局留下的截图)任一命中;三样都没有,才设计实机取证(再打一局取证)。为什么:单样本含观察误报的可能,误报入契约会随下游消费放大成系统性错误。
3. **知识源被质疑时暂停下游写入**:某知识卡或数据点被质疑后,先核实,再继续以其为依据写入新条目。为什么:基于未核实源的写入会把单一错误扩散成引用链。
4. **自己写错了要自纠**:改知识文档的 agent 发现自己此前写入的知识卡有错,直接修正该卡,并同步检查该错误的其他消费点。自主推进场景一例外:知识文档等用户裁定(autonomous-loop.md §3.7),发现写错只记进单局报告的「知识发现」,不直接改。

## 7. 长跑与上下文压缩对策

本节只适用于版本适配流程里一个子 agent 连打多局的跑法。自主推进场景一是一局一派,不适用;那边靠每次自足的任务书(autonomous-loop.md §3.3)。

子 agent 长跑时,上下文压缩会丢纪律条款与早期明细。对策三条:

1. **累积报告模式**:发现子 agent 回报内容缺失(早期局明细/纪律条款丢失)= 压缩已发生;此后其回报改为累积模式——覆盖多局的累积账 + 候选名单整体重发,不依赖其会话记忆拼单局明细。
2. **关键结论即时落盘**:每局的关键结论(逐局记录/候选结论/待跟进事项)在局间循环内落盘(待跟进事项文件/追踪文件/知识卡);落盘完成的结论才视为已保存。为什么:会话记忆跨局不可靠,落盘是唯一持久层。
3. **任务书自足**:每个任务书自含全部纪律与目标(§3),任何环节不引用「会话内此前说过」的内容。

## 8. 数据源优先级

取证优先级从高到低:**官方配置 > wiki 三源 > 项目注册表(代码内注册表与 `knowledge/` 事实常量)> 实机统计推断**。

- 实机局首先是覆盖手段,玩法上的新发现顺带收集。要专门弄清某个机制或数值时,先查官方配置与 wiki(§2.2);两者都查不到才设计实机取证,取证按 §6 附帧号。
- 实机统计样本与官方配置冲突时,以官方配置为准复核读数——先查读数链(OCR/识别/转述环节),确认读数无误再上报矛盾;禁直接按样本改配置结论。
