# 历战余响挑战机制概览（正本）

周本挑战的自动化分层与共享件契约。实现单一源在代码；数值阈值只写常量名不写数字。

## 1. op 家族与职责分层

| op | 位置 | 职责 | 起点 → 终点 |
|---|---|---|---|
| `ChallengeEchoOfWar` | `challenge_ehco_of_war.py` | 周本 app 编排：run_record 语义、`on_battle_success` 回调记账归 app 层 | 任意（自行传送）→ 大世界 |
| `ChallengeEchoOfWarCore` | `challenge_echo_of_war_core.py` | 纯参数挑战循环（`team_num`/`plan_times`/`support`），不读计划、不导航；内部成功/失败计数属性代替回调（回调破坏 MCP 反射契约） | 挑战副本-历战余响·挑战态 → 按 status 落挑战画面或大世界 |
| `ChallengeEchoOfWarByName` | `challenge_echo_of_war_by_name.py` | 带 mission 语义的入口：按名/ID 解析 + 计划配队解析 + 导航与收尾 | 任意可控画面 → 大世界 |

分界原则：**配置换算必须有 mission 语义，归包装层；核心保持 mission 无关**（起点已就位，不知道自己是哪个本）。配队计划是单一源，无 override 参数——双轨配队源必然漂移。

## 2. 包装层契约

- `mission` 解析：周本计划 `mission_id` 精确匹配优先，关卡中文名互相包含匹配兜底；多命中抛 `ValueError` 带候选列表，零命中带可选值清单。
- 配队固定查 `EchoOfWarConfig.plan_list` 该关卡项（配置初始化全量补齐保证必存在）；`support='none'` 在包装层翻译为 `None`（`ChooseSupportInTeam` 只认 None，编排层翻译先例为开拓力 app），核心另做 `None`/`'none'` 兜底归一防线。
- `team_num=0` = 沿用当前编队：合法但需显性化——运行日志提示当前编队可能是上个玩法残留（周本败场照扣开拓力）。
- 节点链：回大世界 → 指南传送 → 委托核心（status 全名单显式分支）→ 收尾回大世界。**核心成功分支终点恒为大世界、对外终态恒「已返回大世界」**（收尾不按落点分支，对外契约单一）；核心 fail 原样透传、不收尾导航（画面停原地交调用方处置）。
- 次数耗尽分支清 `ctx.echo_of_war_run_record.left_times`（镜像周本 app 同款记账职责——带 mission 语义层的正当动作）。
- 运行日志打印计划配队/消耗预估与实际消耗（记账缺口由日志承载），供调用方向用户汇报。

## 3. 核心循环要点

- 入口画面级判定（`check_and_update_current_screen` 只认「挑战副本-历战余响」），不符显式失败，禁逐 area 试命中推断。
- 三弹窗防线（开拓力补充/本周次数耗尽/阵亡取消）在点击挑战后、开始挑战后、再来一次后三处重放；无弹窗重试等待（弹窗迟到），预算耗尽=下一阶段已就绪，经 `无对话框` fail 边承接。
- 战斗失败走共享失败继续件（见 §4）；连败达阈值（家族口径，与开拓力侧现值一致）判停放弃，退出落挑战画面。
- 主等待窗超时不清场：沿「执行超时」fail 边转战斗超时收尾节点继续观察至结算（防战场残留污染后续 app 入口导航，家族先例 use_trailblaze_power 同名节点）；二次观察窗内仍无结算才是真死锁，经「执行超时」边转战斗卡死终局落自定义失败文案。
- 等待窗常量单一源在 `use_trailblaze_power`（`WAIT_RESULT_TIMEOUT_SECONDS`/`WAIT_RESULT_CLEANUP_TIMEOUT_SECONDS`，贪饕侵蚀机制把花萼战斗拖长是该口径的根因）；结算交互（退出关卡/再来一次）另设 `RESULT_SETTLE_TIMEOUT_SECONDS` 交互级封顶——「点击恒成功但锚恒不出现」的 until 无界等待防线。
- 对外出口 status（模块层常量）：`已完成计划次数`/`超时胜利已退出`/`连败放弃`/`本周次数耗尽`/`开拓力不足`/`有阵亡角色已复活` 六类 success，`不在历战余响挑战画面`/`战斗超时无结算` 两类 fail。内部路由 status（弹窗取消、`无对话框`、战斗态值、超时收尾分流）不对外。

## 4. 共享失败继续件 `ResumeFromBattleFail`（challenge_mission 包）

职责 = 把画面从「战斗失败画面」单跳交还到「挑战画面」，**只做画面恢复不做重试/退出决策**（重试预算与退出落点是各 op 真差异，决策归调用方）。

- 失败画面现状 = 「大世界-战斗失败」独立建档的新形态：无「退出关卡/再来一次」结算按钮，点空白区域继续回挑战画面；旧结算形态（战斗画面带结算按钮）在部分副本类型仍可能存在。
- 入口两态分流防误伤：新形态锚在场 → 点空白继续；仅旧结算锚在场 → 直接点退出关卡（不空等）；两态各自连等封顶，转态前先验对方锚在场，不在场直接显式失败（防按「未找到按钮」路径耗尽预算落框架默认文案）。
- 挑战态锚用「挑战副本·挑战按钮」通用几何（花萼/周本帧均命中）；节点预算 5、超时 = `RESUME_TIMEOUT_SECONDS` 兜底窗。
- 消费方：周本核心失败分支（现行）；开拓力侧 `UseTrailblazePower` 失败消费点、光锥/角色手动路径的接入随各自迭代落地（落地前这些路径遇战斗失败有卡死风险，属已声明缺口）。

## 5. 花萼共用口径（零新建）

花萼不抽挑战核心：行迹侧花萼缺料手动刷 = 既有 `FarmLightConeMaterialOp` 委托链（材料反查 → 副本直达 → 委托 `UseTrailblazePower(skip_transport=true)`）；自动场景（一条龙体力计划）配队走体力计划编排层既有代码。理由：花萼挑战循环已有完整实现，再抽一份与体力计划机制重复建库；真正可下沉的部分（失败继续件、弹窗防线家族）已在 challenge_mission 共享层，花萼侧经后续迭代接入即可。

## 6. 识别依据

周本挑战画面独立建档 `challenge_echo_of_war.yml`（id_mark = 标题-历战余响 + 挑战按钮；弹窗组镜像自挑战副本同 rect）；失败画面 `normal_world_battle_fail.yml`（标题-战斗失败 + 点击空白区域继续 id_mark，点击区-空白继续为纯定位点击区）；战斗结算/战斗失败检测走 `battle.yml` 与 `battle_screen_state`。挑战按钮点击复用 `ClickChallenge` 的「挑战副本」通用几何（两形态按钮同位）。
