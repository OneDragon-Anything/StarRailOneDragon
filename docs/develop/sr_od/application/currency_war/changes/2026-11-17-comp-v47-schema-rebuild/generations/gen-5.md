## 3. 缺陷清单

严重度定义：**阻塞** = 消费代码或落库数据写不了；**歧义** = 两种读法各自能写但行为不同；**轻微** = 文档没写清，补一句即可。

### D1【阻塞】计数口径特例表被要求存在，却不在 17 字段清单里

- **现象**：写 Q6 部署档位计数器与 V4（EXACT 恰等校验）时需要机器可读的口径源。原则 4 写明「EXACT/召唤复合走库层口径特例表+出处指针」，但字段清单（17 = 条目 3 + 阶段 8 + 过渡 2 + 库级 4）里没有这张表——库级 4 项是 FILLER_PRIORITY / CROSS_PHASE_KEEP_EQUIPS / OFF_ROSTER_EQUIP_CARRIERS / ECONOMIC_BONDS。消费方要么硬编码设计文档文字（违反单一源纪律），要么自建平行表（第二源必漂移）。
- **根因**：schema 内部自相矛盾——原则 4 要求表存在，字段清单漏收录；N5 只把「注册表 count_mode 扩枚举」挂给注册表批，库侧表本身的归属悬空。
- **修订提案**：库级公共表增第 5 项 `COUNT_MODE_EXCEPTIONS: dict[羁绊名, tuple[口径, 出处指针]]`（初值 = {'少女乐队': ('EXACT', simple_desc 原文), '双龙吟': ('召唤复合', trait 原文+尾注)}），字段数 17→18；V4 校验与部署计数器以它为唯一口径源。注册表扩枚举（N5）落地后本表保留为库侧投影或退役，归注册表维护批裁定——但落库前必须有它。

### D2【歧义】让位序的全序值域未声明，V11 校验不足以防局部序写法

- **现象**：写 Q3 卖牌比较器「人口满 → 卖让位序最大者」，比较对象跨 core 与 support（D1 刃线假设 core={刃:1,…}、support={风堇:2,千冶·刃:5,缇宝:6,符玄:7}）。core 值与 support 值是否同一可比空间，v4 字段 5/6 未写；字段 5 的「主 C 让位序全名单最小」暗示全序，但字段 6 未重申，且 V11 只校验 min(core)≤min(support)——落库者把 support 写成独立局部序（如 support={花火:1,星期日:2}，min=1，与 core min=1 满足 ≤）时校验照过，「花火与主 C 并列最小」的消费预期被破坏。
- **根因**：让位序的坐标系声明缺失（值域 = 阶段名单共享全序，还是两字段各自局部序）；V11 只覆盖两个 min 的相对关系。
- **修订提案**：字段 5/6 docstring 明示「core 值与 support 值在同一阶段名单的全序值域内可比；让位序小 = 重要，大值先让位」；V11 增补「core∪support 同值并列仅允许出现在 core 内的主 C 双 C 制（其余并列报错）」。纯文档 + 校验判据修订，无字段增删。

### D3【轻微】凑件与点名成员的让位先后无规则

- **现象**：人口满时场上 = 点名成员（core∪support）+ 凑件（FILLER_PRIORITY 来的，不在名单）。卖谁？自然预期是凑件先让（可替换），但 schema 让位序只覆盖点名成员，这条规则没有写。
- **根因**：让位序的管辖域声明只写了名单内，名单外成员的让位规则缺一句。
- **修订提案**：Q3 消费文档补一句「名单外成员（凑件/打工残留）让位优先级恒低于名单内成员；名单外之间按凑件序逆序（序大先让）」。

### D4【歧义】代持规则「低序辅助」方向不明，且真实代持者分两类

- **现象**：写 Q4 代持实现时，「归属未到由低序辅助代穿」的「低序」无参照系——按「大值先让位」的字面，序小 = 重要，代持给重要辅助？案例代入显示代持者实际分两类：**稳定成员**（知更鸟代持永动机至昔涟到场、景元代穿遐蝶装后转出）与**弃子**（幻造巨铠先给云璃穿、卖云璃时先转装给万敌；A2 打工组带镜流装备打工后卖掉换钱）。单一「低序」规则两个方向都覆盖不了，且弃子类代持还隐含「卖人之前先转装」的操作时序。
- **根因**：代持者选择规则被压成一个方向词，而它实际是策略层自适应决策（稳定者代持 = 降低转移成本；弃子代持 = 装备随人走打工）。
- **修订提案**：v4 字段 9 的代持句改为「代持/接力 = 策略层通用规则（归属未到由**当前在场非归属成员**代穿，到位即转移；代持者选择与『卖人前先转装』时序归策略层运行时）」——把方向词撤掉，明确归策略层；Q4 消费文档落库时给两类代持的判据（终局名单内成员优先稳定代持，名单外打工件允许弃子代持）。

### D5【歧义】合成闸与「已选线定向合成」的分叉未写明

- **现象**：CROSS_PHASE_KEEP_EQUIPS 语义 =「过渡期唯一允许主动合成的成品集」，初值 {火力风暴潮, 永动机, 蓄能帆}。D1 刃线代入：打工甲（幻造巨铠）在**转线判定之前**就要合成（帖证「拿到幻造巨铠再转反击」「云璃/万敌/瓦尔特带甲打工」），巨铠不在白名单 → 合成闸拦截，D1 的标准打法被自己的库规则禁掉。同理 C 击破线的双鞋风扇（反重力皮靴+光速螺旋桨）、F 饭店线的未唱名面具都是线特定保值件。
- **根因**：字段 15 的闸语义没写「已选定终局线」的豁免分叉——白名单管的是**未选线期**的通用保值合成，已选线后的定向合成应按该线 equip_assign 内序走。
- **修订提案**：字段 15 语义补一句「本表管未选线期（过渡库活跃）的提前合成；已选定终局线后，合成按该线当前阶段 equip_assign 内序执行，不受本表限制」。同时 Q8 出口站「1 件合成装」判据的消费口径 = 本表 ∪ 已选线 equip_assign 首件，一并写明。

### D6【歧义】need_star 在「单形态多节奏」线与「即用线成员」上的登值口径无判据

- **现象**：三组真实案例：
  1. A1 那刻夏（127 帖，T-5 判定**单形态多节奏**、不拆条）：追三线（卡 5-6 级搜到 3 星）与 2 星即用线（速升 8/9）并存，「两条线都不改变装备与人选」。need_star={'那刻夏':3} 还是 {'那刻夏':2}？登 3 = 永远有追星压力（即用线被拖着刷），登 2 = 追三线的承诺丢失（永远 2 星停手）。H2 飞霄（0.68 三星率 + 帖证二星即用线）、B1 狼尊（67% 三星但 1/3 胜局 1-2 星通关）同款。
  2. A4 双 C 制同条目内：那刻夏追三 + 阿格莱雅「1-2 星即用、3 星锦上添花」——即用线成员登几？登 1（1 星也能用）会错过顺手升星，登 2 则「锦上添花」的 3 星永不追，「未列 = 无追星义务」又把 1 星当成达标口径。
  3. 拆条判据只覆盖名单/档位差异（V8 重构），**星级路线差异不在拆条判据里**——C 线拆两条是因为节奏互斥 + 帖量带落格，A1 双线帖量同簇不落格。
- **根因**：need_star 定义了「停手线 = 目标上限承诺非必达；止损归策略层」，但没定义**登值判据**（多节奏线登哪一档、即用线成员登不登）。「承诺上限」与「止损下限」之间没有说清登的是哪一头。
- **修订提案**：文档层明示登值判据，建议口径：「need_star 登**帖间主流停手线**（A1 主流＝追三线 → 登 3；A4 阿格莱雅主流 2 星 → 登 2）；低于承诺的提前停手（即用线/经济不足）一律归策略层止损，高于承诺的追星不发生」。判据写入字段 10 docstring；H1 双峰（星级差异是峰差之一）已按帖量带拆条，不受此影响。

### D7【歧义】V8 名单⊇不变量与普遍的「功能位轮换 / 线内打工」冲突，退役候选语义死化

- **现象**：V8 =「新阶段名单 ⊇ 旧名单且档位非降」。三组真实案例按字面全部触发拦截：
  1. A1 单形态内：阶段 1 白露（前期生存位）→ 阶段 2 风堇（帖间明写「踢白露」）——同功能位轮换，名单减换；
  2. A1/H1：知更鸟（阶段 2 代持启动）→ 昔涟（阶段 3 顶轴）——启动件交接，若两人分属不同阶段的名单即减换；
  3. A2 打工组：那刻夏/瓦尔特/景元**在选定镜流线之后**带镜流装备打工（阶段 1 在板），终盘卖掉换钱（阶段 3 不在名单）——线内打工成员，名单减换。
  这三类是终局阵容的普遍现象（19 篇里至少 A1/A2/A4/H1/F 五篇有实证），全部走「import 报错 → 显式裁决」会让落库批被裁决点淹没，且「选拆条 vs 确认特例」的裁决口径没有成文（帖量带是聚类期两形态分立判据，不是阶段间减换的裁决判据）。连带死语义：字段 6「阶段名单差集=退役候选」在名单⊇不变量下差集恒空——那句消费读法只对「V8 放行的特例」有意义，正文没写。
- **根因**：V8 把「core 身份的单调性」和「support 板凳的流动性」压成同一条不变量；真实的阵容演进里 core 确实单调（主 C 不换），support 天然有轮换窗口。
- **修订提案**：V8 拆成硬软两层——**硬不变量**（机器拦截）：core 键集单调增 ∧ faction_core 档位非降 ∧ ceiling 非降；**软注记**（落库批人工过账，不拦截）：support 名单允许增减换，减换项须注记归类（功能位轮换 / 启动件交接 / 线内打工退役之一）；字段 6「阶段名单差集=退役候选」改为「soft 减换项 = 退役候选（Q3 卖牌读这里）」。这样 A1/A2 直接落库，白露→风堇走软注记，真正的重构（名单大换血）仍被硬不变量外的帖量带拆条判据接管。

### D8【歧义】FILLER_PRIORITY 候选域的排除域（全库点名者 vs 本条目点名者）未定义

- **现象**：写 Q2 凑件推荐：候选域 =「注册表成员 − 点名者」。镜流案例代入：镜流是 A2 的 core、同时是 A1「纯凑云上五骁挂件」（多数局）与「少数局追 3 星二 C 变体」——按**全库点名者排除**，镜流不在云五凑件序候选里，A1 凑云五 2-3 档少一个帖证高优候选；按**本条目排除**，A1 消耗时差集掉 A2 的点名才对——但凑件表是库级单表（一张序管全库），它在静态表内无法感知「当前消费条目」。
- **根因**：排除域是条目相关概念，表是全局结构，两者错位没有声明。
- **修订提案**：字段 14 语义改为「每羁绊登**全量成员**的凑件序（含他线条目点名者）；消费时按当前条目 core∪support 差集后取序」——表登全量、消费做减法，镜流在云五凑件序里可以排前，A2 消费时自动被差集排除。

### D9【轻微】need_star / char_positions 键域未声明，「键域收口」校验未列明收什么

- **现象**：字段 9 equip_assign 键域声明完整（名单 ∪ OFF_ROSTER_EQUIP_CARRIERS ∪ 注册表 is_hide），字段 10 need_star 与字段 11 char_positions 的键域没写——B4 案例代入：开拓者佩千星星徽后算三星计数（帖 6），他不是条目名单成员，need_star 键能不能是开拓者（要不要为他立追三目标）？欢愉阿哈（OFF_ROSTER 载体）要不要登站位？V1-V11 里的「键域收口」四个字没说收哪几个字段的键域。
- **根因**：三字段键域声明不一致（一个写了两个没写）。
- **修订提案**：统一声明——need_star 键域 = 名单（佩徽者待实机取证后定，先挂开放问题 4）；char_positions 键域 = 名单（OFF_ROSTER 载体不在上场面板，无需站位；腾荒 back 由注册表兜底）；「键域收口」校验列明覆盖字段清单。

### D10【轻微】巡海任命派生锚点在「主 C 后台线」失效

- **现象**：V11 注「core 首键 = 终盘主 C（巡海任命派生取首键）」。D1 刃线代入：刃全程坐后排（帖证），而巡海任命「任命 1 名**前台**角色」——派生锚点取到刃则任命目标不合法。A1（不死途任命那刻夏，前台 ✓）是锚点的正例，D1 是反例。
- **根因**：派生锚点把「让位序首键」与「任命合法目标（前台）」划了等号，主 C 站位不恒为前台。
- **修订提案**：派生规则补一步过滤：「任命目标 = core 首键 ∩ 前台；首键在后台时（D1 类），任命 = 策略层按前台成员自适应（帖证无一致口径，落库批注记）」。写进 V11 注释与 Q6 消费文档。

### D11【轻微】双龙吟「选连击分支」的跨羁绊计数溢出未入口径特例表键域

- **现象**：口径特例表（原则 4）只登了双龙吟**自身**的召唤复合计数（饮月 1 人即 2 档）。但「双龙吟强化选连击后龙单位计入连击数」（A1「冲 7-8 档顶配的拼档手段」、A2/A4「2 双龙吟 6 连击 = 8 连击」三篇多帖互证）意味着**连击**羁绊的 TOTAL 计数也会被双龙吟在场+局内分支选择改变——Q7 连击 8 档成型判定、Q2 连击凑档推荐在该场景下口径漂移。分支机制本身[社区待实机]（开放问题 4 已挂「双龙吟选连击分支」取证），但**口径特例表的键域设计**（只管羁绊自身计数 vs 含跨羁绊溢出）可以先定。
- **根因**：口径特例表键域按「羁绊」粒度设计，跨羁绊溢出是「羁绊对」粒度的事件。
- **修订提案**：D1 的 `COUNT_MODE_EXCEPTIONS` 值结构预留「溢出条目」类目（如 ('溢出', 载体羁绊, 目标羁绊, 条件, 出处)）；实机证实分支机制前先登记占位行（条件标注待实机），避免证实后连击判定静默漂移。

### D12【歧义】成型判据完整式未在 v4 正文成文（档齐即成型 vs 档齐且点名件在板）

- **现象**：写 Q7 成型判定。v4 字段 7 faction_core 写「AND 成型身份档」，库级规则 3 的 Q7 消费契约写「成型只停定向搜牌与凑档采购」——但「档齐」可以由凑件凑出（连击 4 档全用凑件、黄泉不在板）。H1 代入：梦境 4 + 群攻 4 档齐而黄泉未到手——按「档齐即成型」会误停定向搜牌（黄泉是 44/44 唯一主 C，帖证成型判据=「黄泉+千冶·刃到手即停手」）。comp-definition 方法论文档里有完整式（「成型 = AND 档 + 点名件在板；form_progress 唯一折法」），但 v4 正文没有重申——两文档是不同文件，落库者只读 schema 时拿到的是半截判据。
- **根因**：成型判据的表达式分布在两个文档（v4 字段 7 只有一半，comp-definition 有完整式），违反正本自足原则。
- **修订提案**：v4 字段 7 语义行补全：「faction_core AND 档 ∧ core 点名件在板 = 成型判据完整式（Q7 消费唯一读法，与 comp-definition 成型层语义对齐）」；或并入库级规则 3 的 Q7 契约首句。

## 4. 总评

### 4.1 完成度估计

**约 85%**。依据：17 字段骨架 + 3 构件 + V1-V11 的结构层经四轮独立复现收敛，本轮从消费侧走查未发现任何「字段缺失导致写不了代码」的结构缺口（唯一阻塞项 D1 是把已成文的口径表落进字段清单，属遗漏不是设计缺陷）；八问 5 够用 3 勉强 0 不够，三个勉强的根因全部是**判据/语义成文度**（让位序值域、合成闸分叉、need_star 登值），修订都是文档与校验判据层动作，不动骨架。

### 4.2 最严重的三个问题

1. **D7（V8 名单⊇ vs 功能位轮换/线内打工）**：19 篇里至少五篇的落库第一批就会触发 import 拦截，裁决口径又没有成文——落库批会被自己的校验卡死，或被迫批量记特例把校验架空。

3. **D1（计数口径特例表无字段位）**：部署计数器与 V4 校验器的唯一口径源悬空，硬编码文字或自建平行表都会埋下双源漂移。

### 4.3 是否可以开始落库
