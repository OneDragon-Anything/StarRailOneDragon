# 自主推进编排细则(CW 分场景)

> 读者 = 自主推进会话的编排者(负责派活和登记的主 agent)。开线派发前、处理子 agent 汇报时读。
>
> 读法:先按 §1 确认当前场景(用户开启自主推进时会说明),再进 §3-§6 里对应的场景节。
>
> 分工:开启和停止自主推进的做法,以及通用框架(编排者职责、线的调度与放行、挂机〔用户不在场,由 agent 自己推进〕时和平时有什么不同、失败后怎么重派、游戏窗口的占用互斥、传话纪律〔编排者在用户与子 agent 之间如实转交、不加工〕),单一源是公共 skill od-dev-agent-autonomous-mode 的 SKILL.md;任务书模板是它的 references/line-templates.md。迭代流程和迭代内进度的单一源 = od-dev-run-iteration。本文件不复述这两份,只写两样:CW 在各场景下的不同做法(§3-§6),CW 对通用框架的补充(§7)。
>
> 名词:线 = 一条独立推进的需求(公共 skill 叫需求线),下文用「线」。待裁登记 = 公共 skill 定义的文件(pending-decisions.md),放等用户裁定的事项,下文直接用这个名字。自主工作文件夹 = 公共 skill 定义的文件夹,放线表这些登记文件(本项目的位置见 §2.5)。单局报告 = 实机探索 agent 每次停下时交的报告(构成见 §3.3 第 6 项)。局账 = 单局报告里记这一局各项结果的那一节。待跟进事项文件 = 货币战争专用的待办文件(§2.5)。追踪文件 = 画面识别与动作 op 的追踪文件,按画面分章,记三样:识别核对(把 MCP 画面识别的结果和自己看截图读出来的逐项比)的日期和结论;动作一栏(画面上每个动作上次用的是哪个 op 还是鼠标,最近一次用着正常的日期);这个画面的缺口(§3.2)。
>
> 适用前提 = 货币战争自主推进的任何场景。

## 1. 场景模型

CW 自主推进分四个场景。场景 = 开启自主推进时设定的一组「这段时间要关注什么」。方法骨架跨场景不变(§2+§7),场景只决定优先事项:编排者让当前线按对应场景节运转。

| 场景 | 主要目的 | 优先事项 | 完成条件 |
|---|---|---|---|
| 场景一 版本适配摸索期 | 把新版本的画面认得全、点得动:画面建档与识别、动作 op。玩法上的新发现靠实机局收集 | 实机探索局 → 修复线 | 三样缺一不可:用户说明的目标达到过;修复线都已收口或在待裁登记里;三层的缺口都已补上或登记挂账。细则见 §3.1 |
| 场景二 流程框架适配期 | 把场景一的识别成果与动作 op 接入 app 自动流程 | app 自动流程跑局循环(run→暴露缺口→修→再跑);策略可以坏、随机乱选——不看对局成绩,只看流程推进与缺口收敛 | app 自动流程能稳定打完整局(端到端不卡死) |
| 场景三 投资策略/环境 sim 适配期 | 投资策略与环境效果在 sim 里建模到位 | sim 与实机对拍 | 对拍一致 |
| 场景四 策略实现适配期 | 策略实现 | 策略迭代线(真实策略代码迭代) | 策略成绩达标(用户判) |

术语注:sim = 项目内置的单局模拟器(`src/sr_od/application/currency_war/sim/`,只模拟环境,不评判策略);对拍 = sim 局与实机局跑同一对局内容后逐项比对读数。

**场景的确定**:

- 场景由用户在开启自主推进时说明。编排者不按证据判断现在处在哪个场景,也不自行切换。
- 编排者把用户说明场景的原话整句抄进线表表头(线表 = 公共 skill 的线登记表),包括用户有没有说「接着做下一个场景」。中断重开的会话以这行记录为准接续。
- 上一个场景完成、用户说过「接着做下一个场景」→ 表头另起一行,写「按用户原话〈…〉顺延进入场景 N」,旧行保留。
- 场景的完成条件满足时,按表头记的原话处理:
  - 说过「接着做下一个场景」→ 按上表顺序进入下一个场景。场景四是最后一个:它完成时,在待裁登记写一条「四个场景都已完成,等用户说明」。
  - 没说过 → 在待裁登记写一条「本场景已完成,等用户说明下一个场景」,不自行开始下一个场景。
  - 这两条待裁登记没有对应的线。待裁登记的模板每条要写线名,这两条的线名一栏写「场景收尾」。
  - 场景一完成以后进入场景二怎么做,见 §4 开头的说明。

**开启清单在本领域怎么填**(公共 skill 的开启清单照走,只有下面两处不同):

- 「确认需求入口」这一步:需求入口 = 用户开启时说明的目标和场景的原话,加上本文件对应的场景节(场景一就是 §3)。用户只说了场景、没有说明目标 → 登记待裁请用户补,不自造目标(公共 skill 这一步的规则)。
- 「立线并派首个探索」这一步:场景一按 §3.2 的「场景一的开启清单」走。

**跨场景恒定项**(任何场景都成立):

- §2 通用编排与 §7 领域叠加件在所有场景生效;
- 知识文档线和挂账修复线是跨场景常驻的线型,任何场景都可立(§6.2);场景一里知识文档线只在用户裁定知识发现以后才立(§3.7);
- 推进模式缺省串行(§7 第 1 项)。

**线的叫法**(本文件出现四种线。立了迭代的线,迭代内每一步怎么走都一样,见 od-dev-run-iteration;实机探索线只走到探索这一步,见 §3.2):

| 线型 | 做什么 | 定义在 |
|---|---|---|
| 实机探索线 | 实机探索 agent 亲自打对局,收集画面和机制上的发现 | §3.2、§3.3 |
| 修复线 | 改识别代码、补识别模板、改动作 op、补完没做完的建档 | §3.6 |
| 知识文档线 | 只改知识文档,不进游戏 | §6.2 |
| 策略迭代线 | 改策略代码 | §6.2 |

从待跟进事项文件里取条目来修的线叫挂账修复线,它是修复线的一种(§6.2)。

## 2. 通用编排(跨场景不变)

本节条款对所有场景生效。两个通用术语:**验证载具** = 当前场景用来暴露缺口、验证改动的运行形态(场景一=实机探索局,场景二=app 自动流程跑局,场景三=sim 对拍局,场景四=策略迭代线的实机验证局;细则见各场景节);**执行 agent** = 当前线操作验证载具的那个子 agent。在飞 = 已经派出去、还没交活的。

### 2.1 编排者职责

- 编排者做的事分三类,都是机械动作:
  1. 派子 agent;
  2. 登记记录文件。通用框架定义的三份:线表、占用表、待裁登记。货币战争另有三份:待跟进事项文件(§2.5)和追踪文件(§3.2),这两份长期保存;待裁知识队列(§3.7),场景一才有。登记的内容照子 agent 报告的原文抄,不加工。
  3. 按本文件写的固定步骤做的几件事:武装资产哨兵(§2.2);重启 MCP server(§3.6);对局丢失后的恢复(§3.8);子 agent 被中断以后替它提交文件(§3.8)。
  
  通用框架的单一源是公共 skill,本文件不展开。
- 判断类动作,编排者要么按本文件写的机械规则做,要么交给对应的子 agent 在它交付的固定节里给结论。两边都没有依据 → 登记待裁,线转等待(公共 skill §2-②)。
- 编排者不做三类事:技术判断(方案倾向、归因结论、评审意见,一律由对应的子 agent 产出);亲自写代码与文档;操作游戏(§3.8 固定步骤里的 open_game 除外,它只负责把游戏打开并登到大世界)。
- 为什么:编排者夹带技术倾向会污染对抗评审与用户裁决——这是本流程要防的第一件事。
- 例外:用户明确指名要编排者亲手做某事时,以该指令为准。

### 2.2 窗口所有权(串行铁律)

- 一个游戏窗口同一时间只归一条线,由这条线在飞的 agent 操作。编排者登记「谁、从何时起、干什么」于占用表(occupancy.md)。
- 操作窗口的动作 = 点击/拖拽/输入等驱动游戏的操作;只读识别(analyze_screen)不算占用。
- 派发任何会操作窗口的活之前,做派发前检查:
  1. 查占用表。窗口已有持有者 → 把新活排队,不派第二个。两种情况不算别人占用:持有行就是本次要派的这条线自己的;接管窗口的是同一条线的诊断 agent 或实机验证 agent(§2.4)。
  2. 查项目 MCP 运行状态(get_run_status)。运行状态是「运行中」→ 排队。
  3. 登记占用表:谁、从何时起、干什么。登记先于派发。
  - 为什么:两个 agent 同时驱动同一窗口会互相干扰(点击落进对方操作的画面、画面被抢),且事后从运行记录难以区分是谁的操作——防患只能靠事前登记,不靠事后归因。
- **资产哨兵**:资产哨兵是一个后台脚本,盯着识别模型、立绘库这些运行时资产还在不在,缺了就报警。做法见 runtime-ops.md「哨兵脚本组」表。
  - 每个会话(包括接手中断的会话)第一次派实机探索 agent 之前,先查它还在不在(查旧的办法见同一张表)。在,就不用再管;不在,按 runtime-ops.md 同一节的「重新启动三步」武装(把它放到后台跑起来)。武装以后,把后台任务的编号记进线表备注栏。
  - 它报警退出(证据在 asset_hit_alert.md)→ 编排者把报警原话转给在飞的实机探索 agent,让它停止操作、交报告;登记待裁(附证据文件路径),实机探索线转等待。资产怎么恢复由用户定(同一张表「只报不修」一栏)。
  - 用户叫停时不用专门停它:它是长驻脚本,随会话走。
- 交接协议:交出方交窗时报告四项现场信息(下文叫现场四项)——当前画面 / 对局进度 / 血量与金币 / 未了事项。接管方开工第一步先识别当前画面(analyze_screen),和交接报告核对。
  - 核对范围:当前画面必须一致。对局进度、血量与金币,画面上读得到的时候核。未了事项只用来接手,不核。
  - 对不上的出口有两个。当前画面和对局进度都对不上 → 现场视为不可信,按 §2.3 停止操作汇报纪律报编排者派诊断,不先动手。只有当前画面不同、对局进度对得上的(比如断线重连以后回到了备战画面)→ 接着打,在单局报告里写明。
  - 这条协议整段写进接管方的任务书。
- **MCP server 重启执行权归编排者**(本领域规定);执行/诊断/实机验证 agent 禁自行重启。重启前先查运行状态,没有运行中的 run 才重启。重启办法见项目入口文件 §6。四步确认、改动集中纪律见 runtime-ops.md「启动与重启」节;场景一怎么适用见 §3.6。

### 2.3 停止操作汇报纪律(任务书必含)

- 遇到问题(操作不生效 / 画面异常 / 疑似机制变化 / op 报错)的动作顺序:
  1. 停止操作:一切游戏操作停下,游戏窗口状态保持原样,不试图自行修复或退出当前画面;
  2. 保存证据:截图留档 + 一句话描述 + 发生时间;
  3. 汇报:现象 + 证据 + 发生时点报给编排者,然后等待。
- 禁止:自行改代码;自行绕过问题继续跑(把问题藏进「看起来跑通」);未经交接就把游戏窗口丢在当前状态。
- 为什么:现场就是诊断的证据;修了、绕了、清了,证据就没了,同一个问题还会再来一次。
- 场景一的例外以 §3.4 的表为准:表里写「继续」的几种情况不停手。它们要么是知识发现,要么玩家 skill 给了自己读图的做法,都不是要绕过去的故障。

### 2.4 问题处置循环

**循环全貌**

1. 执行 agent 停止操作并汇报 → 编排者派**诊断 agent**定位根因。一份报告里有多条未闭环问题,一次只派一个诊断 agent:任务书把全部未闭环问题列上,它的报告逐条给处置建议。诊断任务书的要素如下(通用层没有这个模板,CW 自持):
   - 输入:当前线的报告。场景一 = 这一份单局报告;中途停下的那份带着现场四项,局终的现场四项填「无」。另带本线此前的诊断报告(有就带上)和追踪文件的路径(「处置建议」第 5 样要指认里面的缺口条目)。
   - 权限:代码只读。游戏操作:现场还在(出问题的画面还停在游戏窗口里)才可以复现;现场不在了,不进游戏、不开新局,只凭报告、截图和代码定位。
   - 报告:格式用 od-dev-run-iteration 的探索报告格式(判断结论 / 活跃迭代影响 / 现状 / 没摸到的现状 / 澄清记录 / 问题定义)。「现状」一节写复现步骤和证据,「问题定义」一节写根因。另加两节:「处置建议」;「结束时的现场四项」(动过游戏窗口才写)。
   - 「处置建议」逐条写五样:
     - 处置方式(第 2 步四个值里选一个,必附字段);
     - 合并建议(并入哪条已有的线,或新立);
     - 现象指认(和本线哪一份此前的诊断报告是同一现象,没有写「无」);
     - 修正办法(给下一个执行 agent 看的做法,有才写);
     - 对应追踪文件里哪个画面的哪几条缺口(不对应任何一条写「无」)。
   - 查不清也是合法结论:凭现有证据定位不了根因的,报告结论写「查不清,要等现场」,不硬选处置方式。
   - 落点:报告落 `<自主工作文件夹>/<线名>/`。回信不超过 10 行:结论一行(处置方式,或「查不清」)+ 报告路径。
2. 诊断产出固定节「处置建议」,编排者照派:
   - 先改追踪文件:照第 5 样找到那几条缺口。处置方式是立线建议、单点修复单的,状态改成「等修复线」。结论是「查不清」的,按下一小条登记,状态改成「已登记待跟进事项」。处置方式是知识修正、环境处置的,和写「无」的,删掉那几条状态是「等诊断」的缺口(这次的问题不是画面上的缺口)。它指的画面和缺口原来记的画面不一样,把缺口挪过去(记法见 screen-tracking.md)。
   - 结论是「查不清」(场景一)→ 编排者把这条问题登记进待跟进事项文件,标「等现场再现」。以后每局任务书的附加信息节带上它;实机探索 agent 再遇到就停下来,现场留给诊断。诊断报告写出以后,编排者删掉这条「等现场再现」的条目:结论不是查不清的,问题有了处置建议,照建议走;还是查不清的,原样再登记一条,由诊断熔断计数。
   - **知识修正**(知识文档要改;附目标文件指针+生效方式):立知识文档线(小迭代:步骤少、文档短的迭代,内容是修正知识文档)走 od-dev-run-iteration,收口后让原执行 agent 继续工作。场景一例外:知识文档等用户裁定,不立线,登记进待裁知识队列(§3.7),原执行 agent 不等这一条;编排者把「修正办法」原文放进重派任务书的附加信息节。画面档、模板要改的,不算知识修正,按单点修复单或立线建议走(修复线的范围含补完建档,§3.6)。
   - **单点修复单**(改哪+判据):编排者拿「改哪」对照当前线 landing 文件首节的影响面申报(§7 第 5 项)。影响面申报 = 落地申报文件(landing.md)的第一节,声明本线会改哪些文件;下文说的「申报面」就是它。在申报范围里的 = 线内任务(当前线迭代 tasks.md 加任务,不立新线),派线内修复任务(实现+验证)后继续;不在申报范围里的,和没有迭代目录的线(如场景一的实机探索线)一样,按立线处理;
   - **立线建议**(线名+改哪+判据+优先级+原文切片〔从报告里原样抄出来的一段话〕):立新线走 od-dev-run-iteration 完整生命周期 → 实现并过了 review → 改了运行时代码的重启 MCP server(§3.6)→ 实机验证(复现原故障场景确认已修;什么时候验见各场景节,场景一=§3.6)→ 让原执行 agent 继续工作;
   - **环境处置**(重启/重试+可复跑检查命令):执行者是编排者。
     - 动作限于三种:重启 MCP server、重新打开游戏、重派原执行 agent。每种做一次。
     - 检查命令由编排者跑,限于不操作游戏的命令(git、pytest、查日志这类)。要操作游戏的检查,写进重派任务书交实机探索 agent。
     - 场景一里对局停在半路时,「重新打开游戏」不直接做:那等于放弃对局,改为登记待裁。
     - 做完还不行 → 登记待裁。场景一里对局丢了怎么恢复,见 §3.8(不派诊断,按固定步骤走)。

   建议字段缺失=格式缺陷打回重交;**诊断熔断**:编排者按「现象指认」连起来的链条计数,同一现象第 3 次=登记待裁(pending-decisions.md),线表等待条件记「等待裁定」,其他线继续。
3. 循环期间原执行 agent 保持停止状态等待。线表里这条线的「在飞 agent」一格改记诊断 agent,「当前步骤」不变。编排者按公共 skill 的放行规则(其 §4.1)接其他排队线;窗口可能被诊断/实机验证 agent 按 §2.2 接管,窗口归谁以编排者的登记为准。诊断 agent 不立线;它用窗口期间,占用表仍记在原线名下,备注「诊断 agent 在用」。

**诊断报告当修复线的探索报告用**:按处置建议立线时,立项与设计任务书里的「探索报告」填诊断报告的路径,修复线不另派探索。为什么:诊断已经把现状和代码两边都摸清,再派一次探索是重复劳动。本领域和迭代 skill 有一点不同:迭代 skill 写的是把探索报告移进迭代目录;这里复制一份进迭代目录、改名 explore.md,原报告留在原处(后面的诊断和线表还要引用它)。没经过诊断的修复线(§3.6),自己的探索报告照迭代 skill 的做法移进迭代目录。「缺动作 op」不经过诊断,见 §3.6。

**各角色边界**

| 角色 | 游戏操作 | 代码 | 说明 |
|---|---|---|---|
| 执行 agent | 可 | 只读 | 按任务书操作当前场景验证载具(场景一=亲自玩货币战争);遇问题停止操作并汇报;问题处置交编排者另派(§2.4) |
| 诊断 agent | 现场还在才可(复现) | 只读 | 定位根因,不改代码 |
| 设计 agent | 不操作 | 只写设计稿 | 设计与实现分开,防同一个 agent 既定方案又自己验收 |
| 对抗评审 | 不操作 | 只读 | 每轮起全新的、没读过前几轮讨论的子 agent——看过前几轮讨论就会被已有思路带偏,挑不出真问题 |
| 实现 agent | 不操作 | 写 | 按设计稿落地;与设计稿对不上的地方报告编排者,不自作主张改设计 |
| 实机验证 agent | 可(复现验证) | 只读 | 验证后把窗口停回已知稳定状态(大厅或备战画面)再归还;要把窗口交还给半路对局的原执行 agent 时,停在验证结束时的画面归还,并在报告里附现场四项(§3.6) |

**传话纪律(约束编排者本人)**:用户消息与子 agent 问题原样转交、不加工、不筛选——通用框架定义,单一源 = od-dev-agent-autonomous-mode §4.3「传话原样」;CW 增量一条:设计争议需要用户裁决时,把双方论点原样并列转达,不排序、不建议。

### 2.5 进度登记与跨会话接口

- 自主推进不设总的任务清单文件。当前线还有哪些事没做完,记在下面这些地方:画面识别、动作 op 的缺口记在追踪文件(§3.2),哪个场景发现的都记这里;其余待办记在待跟进事项文件(本节下文);等用户裁定的知识发现记在待裁知识队列(§3.7)。编排层的登记(线表/占用表/待裁登记)= 通用框架定义的自主工作文件夹(SR 项目惯例 .debug/temp/ 下 autonomous/<开工日期-主题>/)。
- 追踪文件和待跟进事项文件不放自主工作文件夹,会话结束了也留着(位置见 screen-tracking.md §1 和本节下文)。待裁知识队列放自主工作文件夹。三份都由编排者照子 agent 的报告登记。只有一处例外:修复线做出新的动作 op 时,由修复线自己改追踪文件的动作一栏(§3.6)。
- 推进期间子 agent 做迭代时,按 od-dev-run-iteration(完整迭代 skill)的 tasks.md 格式在迭代目录内登记进度;编排者不替子 agent 记迭代进度。
- 待办登记:货币战争专用的待办文件 = `.temp/tracking/currency-war/待跟进事项.md`(定位见 SKILL.md §3「待跟进事项」行)。它是运行时产生的文件,不进版本控制;文件不存在就按「没有未竟项」处理,第一次登记时新建。
  - 条目写四样:事项、证据指针(截图文件名)、状态标签、编号。编号顺延,删掉的编号不复用。
  - 状态标签五种:等实机取证 / 已取证 / 等现场再现 / 等用户裁定 / 等随机遇到。
  - 立过修复线或迭代目录的条目,再写「改哪、判据是什么」,照它的申报抄。从追踪文件转登的条目,写上画面名,抄缺口条目原文和证据;追踪文件里那条缺口的状态后面写上这个条目的编号(写法见 screen-tracking.md §2)。编排者不自己编技术内容。
  - 迭代做多大,由设计 agent 在设计文档里定。
  - **完成即删**:条目闭环(清偿/实证/裁决定谳)时当场把该条目从待跟进事项文件删除——文件里只留开放项,禁留「已完成/已清偿」划线态或存档句堆积;有长效价值的裁定结论随 commit message 或知识文档固化,不靠文件留尸。为什么:文件混入完成态会让后来者把已完结条目当活待办盘,文件越长真待办越难找。
- 发现的归档:知识类结论落对应知识文档或画面档(分层判据见 SKILL.md §3;场景一先记待裁知识队列,见 §3.7);过程叙事不进本 skill。

## 3. 场景一:版本适配摸索期

### 3.1 目的与完成条件

- 目的:把新版本的画面认得全、点得动。基础有两块:画面建档与识别、动作 op。玩法上的新发现靠实机局收集。
- 不属于本场景的事:
  - 更新各域的数据(角色、羁绊、装备这些注册表,以及成批生成识别模板)。这是版本适配时做一次的事,走 version-update.md 的清单,不归自主推进。探索中发现某一项内容识别不到(比如缺模板),才立修复线去补(§3.6);
  - 提升对局成绩、调策略(场景四,§6);
  - 单局复盘。它的输入是 bot 自动打局留下的运行记录;本场景的对局由实机探索 agent 自己手动打,没有这种记录;
  - 改写知识文档。本场景里知识文档等用户裁定(§3.7)。
- 完成条件有三样,缺一不可:
  1. 用户开启自主推进时说明的目标,至少有一局写明已经达到;
  2. 线表里的修复线都已收口,或只剩登记在待裁登记里的;
  3. 追踪文件(§3.2)里每条缺口都已删除(修好并实机核实过),或已登记进待跟进事项文件。
  
  范围 = version-update-live-exploration.md 第 1 节四层覆盖表里的前三层。第四层(游玩指导)是知识文档,不卡本场景完成。
- 三样都看记录,不看编排者的印象:第 1 样看单局报告的「局账」;第 2 样看线表;第 3 样看追踪文件和待跟进事项文件。

### 3.2 有哪几类活,按什么顺序推

| 类别 | 进不进游戏 | 做什么 | 改哪些文件 |
|---|---|---|---|
| 实机探索线 | 进 | 实机探索 agent 按玩家 skill 亲自打,一局一派 | 建档内容、画面文档前两章、玩家 skill 入口列表加一行、单局报告 |
| 修复线 | 验证时进 | 改识别代码、补识别模板、改动作 op、补完没做完的建档 | 代码、测试、模板资产、画面档、画面文档(前两章,和「操作」章)、设计正本 |
| 诊断 agent(一次性任务) | 现场还在才进 | 定位一个问题的根因,给处置建议 | 不改文件,只写诊断报告 |

- **实机探索线**:一开始只立这一条。它停在迭代的探索这一步。产出是单局报告和上表列的文件,不做设计与实现;要改代码、补模板的发现都另立修复线。
- **修复线**:探索中发现要改代码、补模板才能解决的问题才立。什么时候立、怎么走,见 §3.6。
- **诊断 agent**:不立线,做完即止。任务书要素见 §2.4。

**追踪文件** = `.temp/tracking/currency-war/画面识别与动作op.md`,长期保存,不随会话或迭代重建。它按画面分章,每章记三样:这个画面最近一次识别核对的日期和结论;每个动作用的是哪个 op 还是鼠标点击,最近一次用着正常的日期;这个画面的缺口。格式和记法见 [screen-tracking.md](screen-tracking.md)。

- 缺口的状态四种:等诊断;等修复线(该立修复线,或已有修复线在跟——包括动作 op 已经做出来、等实机验证);等用户裁定;已登记待跟进事项(现在探不了,卡在什么条件上写在待跟进事项文件里,这里只留编号)。每种什么意思、怎么写,见 screen-tracking.md §2。
- 第四层(游玩指导)的发现记在待裁知识队列(§3.7),不进追踪文件。
- 开局时编排者不预先建章:第一次核对哪个画面,才建哪个画面的章。没有章的画面不算缺口。
- 之后什么时候更新、谁来写,见 screen-tracking.md §3。

**推进顺序**(串行,§7 第 1 项):修复线和知识文档线都排在两次派发实机探索 agent 之间(§3.5)。

**场景一的开启清单**(按顺序做;公共 skill 开启清单的四步都在里面,最后一步是自验):

1. ☐ 确认需求入口:用户说明的场景和目标,整句抄下来。只说了场景、没说目标 → 先做完第 2 步,在待裁登记里登记请用户补,然后停下等用户,不往下走。
2. ☐ 建自主工作文件夹,复制线表、占用表、待裁登记三份模板。两处要填:
   - 场景原话抄进线表表头(§1「场景的确定」):线表模板的标题下面加一行「场景(用户原话):〈…〉」。
   - 并行度:用户当次明示了并行就按用户的,没明示取 1(§7 第 1 项)。向用户报一句。
3. ☐ 接手中断的会话时(已有同主题的文件夹):按公共 skill 核对三份文件。另外把追踪文件里标着「卡在用户叫停」的缺口,状态改回「等修复线」;待跟进事项文件里对应的条目删除(叫停时登记的,§3.8)。
4. ☐ 立实机探索线:登记线表,建 `<线名>/` 子目录。
5. ☐ 派第一局之前做三件事:查占用表和运行状态;查资产哨兵还在不在,不在就武装(§2.2);登记占用表。
6. ☐ 拼任务书,派实机探索 agent(§3.3)。分两种:
   - 占用表里有留存的半路对局(持有行标着「用户叫停」)→ 先把最后一份单局报告里还没处理的发现照路 B 第 2、5 步处理(该立修复线的立修复线,用户已经裁定的知识发现派知识文档线),再拼续打的任务书:按路 A 第 3 步第 4 小步更新,附加信息节带「叫停后恢复」的说明(§3.8)。交接记录写了「现场未知」的,任务书带公共 skill 的接棒前言。
   - 没有 → 拼下一局的任务书;还没有打过的,照 §3.3 拼第一局。
7. ☐ 自验:场景原话在线表表头;线表里有实机探索线;占用表有登记;资产哨兵在岗;探索 agent 已派。有缺回那步重做。

### 3.3 实机探索任务书构成

任务书以公共 skill 的 references/line-templates.md §1 探索模板为基,逐字复制并填实例位,再并入下面第 1-9 项。

模板库头注规定领域增补只加条目。探索模板却是按「摸清现状、不推进游戏」写的,它的步骤、报告格式都和「打完一局」对不上。所以本领域在任务书开头加下面这句声明,模板其余条款照常有效:

> 声明:本任务书里,模板的第一行,和「步骤」「顺带取证」「禁止事项」第一条、「报告」「回信」,由 sr-od-dev-currency-war 的 references/autonomous-loop.md §3.3 的条款替换;其余条款照常有效。

替换的对照:

| 模板里的 | 替换成 |
|---|---|
| 第一行(「开工前先读 od-dev-run-iteration 第 1 章」) | 第 1 项「开工前读什么」 |
| 「步骤」一节(含里面「不做消耗性、不可逆的游戏内操作」那一句) | 第 1 项「步骤」和「消耗性操作」那一段 |
| 「顺带取证」一节 | 第 7 项的顺带取证清单、顺路验证清单 |
| 「禁止事项」第一条(不改任何代码与文档) | 第 5 项 |
| 「报告」「回信」两节 | 第 6 项 |

四个字段(局内目标、两个清单、难度)写进任务书的「需求」节。

并入的条款:

1. **操作依据与步骤**:
   - 开工前读什么(替换模板第一行):开工前先读玩家 skill `sr-od-currency-war` 全文,再读 version-update-live-exploration.md 的 §4(单局作业规范)和 §6(知识可靠性纪律)。进游戏的授权已含在自主推进授权内,不用再问用户。用户不在场:问题原样记进报告,不等回复。
   - 任务书不复制玩家 skill 的内容,实机探索 agent 也不依赖编排者的会话历史。
   - 步骤(替换模板「步骤」一节,下面的文字照抄进任务书):

     ```
     按玩家 skill 打这一局。局内遇到情况,按本任务书并入的「局内遇到情况怎么处理」处理。
     每到一个画面,做两件事:
     - 把画面识别的结果和自己读图对一遍;每做一个动作,记下用的是哪个 op 还是鼠标点击、有没有生效。
       这些写进单局报告的「画面核对」。
     - 读「画面识别与动作op」追踪文件里这个画面的那一章(路径在附加信息节里;没有这一章就跳过)。
       章里有缺口的,顺手核对,核的是这条缺口现在还在不在:
       画面建档那一层的,看这个画面认不认得出;画面识别那一层的,看识别结果和自己读图还对不对得上;
       动作 op 那一层的,按并入的「没有动作 op」怎么判断看。
       还在的,记进「缺口」;不在了的,在「画面核对」这个画面那一条后面写一句。
     开工先识别当前画面(只读),分四种情况:
     - 在货币战争大厅 → 开新局。
     - 在一局中间的画面(接管已有对局)→ 先按并入的交接协议核对现场,对得上就从停下的画面继续。
     - 已经在货币战争的开局流程里(模式选择、难度确认这些画面;上一局对局丢了以后会停在这里)
       → 按任务书的目标走。
     - 在大世界或别的玩法 → 按玩家 skill 的导航办法进货币战争,走到模式选择画面。
     走到模式选择画面时,上面几种情况都一样:
     - 任务书写明开新局:没有存档 → 开新局。是「进行中」形态(有存档)→ 不点任何东西,
       停下回报编排者(开新局要先放弃旧局,放弃对局要用户点头)。
     - 任务书写明接着打:是「进行中」形态(有存档)→ 点「继续进度」,续的是上一局,算同一局。
       没有存档 → 回报编排者「对局已丢」。
     打完这一局,或者按表中途停下 → 停止操作,提交,发单局报告,然后等待。
     ```

   - 模板里「不做消耗性、不可逆的游戏内操作」这一条,在本领域指对局之外的东西:晶球、门票、充值、放弃对局都不碰。对局里正常的买牌、刷新、出战是打一局的一部分,不算。
2. **关注清单**:这一次要关注的内容。由实机探索 agent 开工时自己起草,写进单局报告;每次派发各有一份。起草的输入四样:用户开启自主推进时说明的目标(任务书「需求」节);附加信息节里上一份单局报告「没看到」的条目和待裁知识队列(第 9 项);待跟进事项文件的未竟项(路径在附加信息节里);玩家 skill 玩法文档里当期值得核对的面。每条注来源,零来源的条目不进清单;每条写清「关注什么、观察到什么算值得关注、怎么记录」,以及对应哪个画面(按玩家 skill 的画面名写;哪个画面都不是的写「跨画面」)。
   - 关注清单只管这一局。这一局没看到的条目,由编排者照原文抄进下一局任务书的附加信息节(第 9 项),下一局起草关注清单时从那里取。
   - 待裁知识队列里已有的发现,这一局再遇到,不算新发现:在单局报告的「知识发现」里写「同队列 K-N,本局再次出现」,附证据指针。编排者只在原条目上追加证据指针。
3. **并入任务书的其他条款**:§2.3 停止操作汇报纪律整段并入(含场景一例外);§3.4(局内遇到情况怎么处理)整段并入;接管已有对局时,§2.2 交接协议整段并入。
4. **现场交接信息**:接管已有对局时写三样:交出方(最后一个动过窗口的 agent)报告的现场四项(当前画面 / 对局进度 / 血量与金币 / 未了事项);它的报告路径;这一局此前全部单局报告的路径。局账和关注清单接着这些报告续记。
5. **文件面**:实机探索 agent 不经用户裁定能写的只有三样,不动 `src/` 下的代码。
   - 建档内容:按 od-dev-screen-onboarding 的完整步骤做,包括它的测试仓部分(往 sr-od-test/ 归档本画面的截图、跑 id_mark 准确性测试)。其中画面档的 area、id_mark 经 MCP 写档工具写;模板文件按画面建档 skill 裁出来、放到模板目录。
   - 画面文档的前两章(画面简介、建档 area 说明),写法见画面建档 skill「画面文档」节。新画面的前两章全写。已建档画面的前两章,只改和建档 area 有关的描述;讲游戏机制、交互效果的句子发现和实际不一样,只记进「知识发现」,不改。
   - 新画面在玩家 skill 入口文件(SKILL.md)的「各阶段与画面的处理方案」列表里加一行。加在它所属的阶段分组下;是某个主画面的子态,就用二级缩进排在主画面下面。只加画面名,不改别的行。

   模板「禁止事项」里的「不改任何代码与文档」,在本领域按本条执行(见上面的替换声明)。以下内容不写:
   - 画面文档的后两章(「操作」章、「识别后要做的决策」章);
   - 玩家 skill 的知识文档(references/ 下的玩法说明、决策手册、阵容图鉴、机制各篇)和 `docs/game/currency_war/research/` 各篇;
   - 删除任何文档。

   知识上的新发现不直接改文档:写进单局报告的「知识发现」,由编排者照原文抄登记进别的文件(下文叫转登,§3.7)。
6. **交付**:
   - 报告叫**单局报告**,各节以本项为准。报告和证据截图一起放 `<自主工作文件夹>/<线名>/`。文件名 `match-<局号>-<序号>.md`:局号按开新局的先后从 1 数起;接着打同一局的报告沿用同一个局号,序号从 1 顺延。还没开新局就停下的(比如模式选择画面有存档),用下一个局号,序号 1。各节:
     1. 停下方式:局终 / 中途停下 / 中止。中途停下的写原因,七选一:没有动作 op / 有要查原因的问题 / 模式选择画面有存档 / MCP server 连不上 / 游戏掉线 / 游戏闪退 / 用户叫停。
     2. 局账:深度、难度、环境、词条、终局、晋升、晶球(含义见 version-update-live-exploration.md §4.2),另加一栏「局内目标」:达到 / 未达到(差在哪)。中途停下的报告里还没发生的字段写「未到」。
     3. 关注清单逐条覆盖状态:每条写对应哪个画面(按玩家 skill 的画面名)。结果是下面三种之一,前两种附证据指针:
        - 看到了,没问题;
        - 看到了,有问题(问题另记进「缺口」或「未闭环问题」);
        - 没看到。
     4. 缺口:缺什么一眼看得出的记这里——画面没建档、某类内容认不出、操作没有动作 op。每条写画面名、缺哪一层(画面建档 / 画面识别 / 动作 op)、证据指针、建议处置(立修复线 / 现在探不了〔写明卡在什么条件上〕)。
     5. 顺带取证和顺路验证的结果:采到的项写数值和证据指针;每条顺路验证写达标 / 不达标 / 没遇到,附证据指针。
     6. 知识发现:玩法上和文档不一样、或者文档里没有的内容。每条写建议去处(待跟进事项文件 / 待裁知识队列);去处是待裁知识队列的,再写建议落点(改哪份文档的哪一节)。建议去处怎么选:证据还不够、要再打一局才能核实的,写待跟进事项文件;证据够、只是等用户裁定改不改文档的,写待裁知识队列。
     7. 「缺动作 op」:有才写。画面名;每个操作(玩家 skill 操作表里这一步写的是什么、点了会怎样、哪些没点);证据指针。
     8. 未闭环问题:要查原因的现象记这里——读不出数、动作 op 没生效或点错位置、认错画面。只列还没处置的。
     9. 遗留。
     10. 晶球余额。
     11. 证据文件清单:截图文件名,结算截图也在内。
    12. 画面核对:先写报告日期(年-月-日)。这一局到过的每个画面一条。写画面名;识别核对(一致 / 有不一致,有不一致的写一句是什么,详情在「缺口」或「未闭环问题」);用过的动作逐个写(动作名、用的是哪个 op 还是鼠标点击、正常 / 不正常);这个画面在追踪文件里原有的缺口,现在还在不在。到了画面没做动作的,动作写「无」。
     - 中途停下时另加两节:现场四项(当前画面 / 对局进度 / 血量与金币 / 未了事项)、这次写的文件清单。
     - 局终那份:第 3、12 节汇总本局全部结果;第 4、6、8 节只列前面几份报告没报过的。
   - 回信不超过 10 行:停下方式一行(中途停下的带原因)+ 局内目标达到没有一行 + 有没有「缺动作 op」一行 + 未闭环问题数一行 + 本局新报的缺口数一行 + 顺路验证有没有不达标一行 + 报告路径。
   - 提交:每次汇报之前(中途停下、局终、中止都算),先提交这次派发里写的文件,提交完再发报告。
     - 提交范围:建档文件、模板资产、画面文档、玩家 skill 入口列表加的那一行、测试仓里的归档图和 id_mark 测试。测试仓是独立的仓库,单独提交。
     - 提交规则按项目入口文件的提交规范:逐文件点名;提交前核对该文件的改动全是这次派发写的。
     - 文件里有别人的改动 → 不提交该文件,文件名记进「遗留」。
     - 合并缓存 `_od_merged.yml` 不提交:它是写档时自动重生成的派生文件,里面混着所有人的改动。记进「遗留」,由用户按惯例从分文件重新生成后统一提交。
7. **单局限令(每次派发最多一局)**:
   - 任务书写明本局的四样:局内目标、顺带取证清单、顺路验证清单、难度。每次派发都照当时的记录重新填,编排者不自己判断:
     - 局内目标 = 用户开启自主推进时说明的目标(原话),每一局都一样;
     - 顺带取证清单 = 待跟进事项文件里标「等实机取证」的条目;
     - 顺路验证清单 = 线表里等待条件是「等实机」的修复线,每条写线名 + 它 landing 文件「验证需求」节的路径;
     - 难度按第 8 项。
     - 某一样没有内容,写「无」。
   - 实机探索 agent 打完这一局,或按 §3.4 中途停下以后,就停止操作、发单局报告,然后等待。不获得连续打多局的授权。
   - 局终以后把画面收回大厅;中途停下时画面留在原地不动。接着打同一局不算新的一局(§3.5 路 A)。
   - 局间怎么走见 §3.5。
   - 为什么:局间每一步都由编排者放行,进度才抓得住;连续打多局会让探索方向失控,局间新出现的待办也插不进来。
8. **难度**:
   - 用当前可解锁的最高难度。
   - 最高难度不可达(未解锁、条件不足)时,用可达的最高难度,并在单局报告里写明可达的难度和解锁路径。
   - 为什么默认往高了打:高难度才会出现的画面和机制,低难度局碰不到。它和血线保守(version-update-live-exploration.md §4.5)各管各的:难度管能看到什么,血线管能走多远。
9. **附加信息节**:编排者照抄、不加工。
   - 每次派发都带:待裁知识队列全文和队列文件路径;待跟进事项文件的路径;追踪文件的路径。追踪文件只给路径,不抄内容:实机探索 agent 打到哪个画面,自己读哪一章(步骤见第 1 项)。第一局时队列文件还没有,写「无」。
   - 有才带:诊断报告里给的修正办法(§2.4);待跟进事项文件里标「等现场再现」的问题(再遇到就停下来,现场留给诊断);上一份单局报告的关注清单里「没看到」的条目(原文,实机探索 agent 起草关注清单时从这取,第 2 项);恢复类的说明(§3.8,连不上、掉线、闪退、叫停四种,各有一段原话)。

### 3.4 局内遇到情况怎么处理

实机探索 agent 在局内遇到下表的情况,按表处理;表里没有的,按 §2.3 停止操作并汇报。本节整段并入实机探索任务书。

| 遇到的情况 | 实机探索 agent 做什么 | 这一局 |
|---|---|---|
| 进了没建档的画面 | 先按 od-dev-screen-onboarding 建档、写画面文档前两章,再继续。画面上有操作没有动作 op 的,按下一行处理 | 继续 |
| 画面上的操作没有动作 op | 停在这个画面,用鼠标把它摸清楚,该建档的建档。能点到哪一步见下面的界线。摸完就停手汇报,不往后打 | 停在这个画面 |
| 画面上某一项内容认不出(识别结果里有一项标成认不出,比如商店一个槽位的 kind 是 `unknown`) | 自己读图,继续打。记进「缺口」,缺的那一层写「画面识别」 | 继续 |
| 画面识别读不出数(这个画面有字段说明〔extras_doc〕,读数〔extras〕却是空的) | 先等几秒重新识别;仍然读不出,按玩家 skill「通用注意事项」第 5 条的应急做法继续(存图、自己读图)。把现象记进「未闭环问题」。没有注册识别器的画面,读数本来就没有,不算这种情况 | 继续 |
| 疑似游戏机制和文档写的不一样 | 不停手。把现象和证据截图记进「知识发现」,继续打 | 继续 |
| 识别出的画面名和实际画面不符,或读数和画面上的数字对不上 | 按 §2.3 停止操作并汇报 | 停在这个画面 |
| 动作 op 点了没生效、点错位置,或 op 报错 | 先重新识别画面。按玩家 skill「通用注意事项」第 1、3、4 条排除状态原因(按钮置灰、商店面板没收起、坐标和槽号取自旧读数、弹窗挡住)。然后用同一个动作 op 重发一次。重发不生效 → 按 §2.3 停止操作并汇报。重发成功以后:查到了状态原因的,不用记;没查到原因的,记进「未闭环问题」(原因没查,以后还会出现) | 重发成功:继续;否则停在这个画面 |
| MCP server 连不上,或游戏掉线 | 停止操作,把能保存的证据保存,向编排者汇报。停下方式写「中途停下」,原因写明。对局还在不在,留给重派以后的 agent 识别(§3.8) | 中途停下 |
| 游戏闪退 | 把能保存的证据保存,向编排者汇报。停下方式写「中途停下」,原因写「游戏闪退」。对局还在不在(有没有存档),等游戏重新打开以后看(§3.8) | 中途停下 |

- 「没有动作 op」怎么判断,按顺序看两处:
  - 先看追踪文件里这个画面的动作一栏(路径在附加信息节里)。这一步后面的括号里写的是 op 的名字 = 有动作 op,不用再看第二处。
  - 括号里写的是「鼠标点击」,动作一栏里没有这一步,或者这个画面还没有章 → 看玩家 skill 对应画面文档的「操作」表。这一步「用什么」写的是 op 的名字(用 run_operation 调用的)= 有动作 op(上一次只是用了鼠标)。下面三种算没有动作 op:写的是 `click`、`drag` 这类鼠标操作的;操作表里没有这一步的;这个画面还没有「操作」表的。
  - 为什么括号里写「鼠标点击」不能直接算没有:括号记的是这一步上一次实际用了哪个。这一步有 op、上一次用了鼠标,是可能的。
  - 判断结果写进单局报告的「画面核对」和「缺动作 op」,由编排者登记进追踪文件(§3.5);实机探索 agent 不自己改追踪文件。
- 为什么「没有动作 op」停在这个画面:画面留着,动作 op 写完、MCP server 重启以后,可以直接在这个画面上验证;往后打了,画面就过去了,只能等它随机再出现。
- 「摸清楚」能点到哪一步,界线如下:
  - 可以点:点了以后画面还在的——切换页签、打开弹窗或详情、选中一项、再点取消关掉。
  - 不可以点:一点就会离开这个画面的——推进到下一个节点、出战、确认领奖这类。这些只建档,把位置和预期作用写进「缺动作 op」一节,留给验证的时候点。
  - 拿不准某个按钮点了会不会离开画面 → 不点,记进「缺动作 op」。
- 没点的按钮,建档怎么算:没点的按钮,建档到这里算告一段落。画面文档「建档 area 说明」的「交互效果」一栏写「未点,预期作用是…」;画面档的 goto_list 不填。
- 和画面建档 skill(od-dev-screen-onboarding)的三条硬规则冲突,以本表为准。任务书里写明下面三条豁免,实机探索 agent 不用自己权衡:
  - 它 §3.4「交互类 area 必须 click 实锤」:会离开画面的按钮不点,没有点击记录也算建档告一段落;
  - 它 §3.5「跳转关系落 goto_list 是硬要求」:没点的按钮不填;
  - 它 §3.3「强制探索协议」的第 2 步「系统找出口」:不执行,出口留给实机验证的时候点。
- 补录落在哪一步:实机验证 agent 点过这些按钮的,验证报告里写明点了哪些、点后到了哪个画面。修复线在正本更新这一步补录:把「交互效果」一栏改成实测结果,goto_list 用写档工具补上,写进本线的落地申报(§3.6)。
- 「认不出某一项」「读不出数」为什么可以继续:玩家 skill 已经给了自己读图的做法,不继续会白白丢掉这一局能盖到的内容;问题记下来,停下以后照样处置。
- 「中途停下」以后怎么收:见 §3.5 路 A 和 §3.8。
- MCP server 连不上、游戏掉线、游戏闪退这三种,只写在「停下方式」的原因里,不记进「未闭环问题」。它们不是要诊断的故障,由编排者按固定步骤恢复(§3.8)。

### 3.5 局间流程

实机探索 agent 停下并汇报以后,看单局报告的「停下方式」,分三条路。

**路 A:中途停下(这一局没打完)**

1. 停下原因是 MCP server 连不上、游戏掉线、游戏闪退 → 不派诊断。先按第 5 条登记,再按 §3.8 的固定步骤恢复。恢复以后直接走第 3 步的第 4 小步(重派)。
2. 停下原因是用户叫停 → 按 §3.8「用户叫停」处理。
3. 其余原因(先按第 5 条登记,再走下面四小步):
   1. 报告里有未闭环问题 → 走 §2.4 派诊断。报告里同时有「缺动作 op」的,也先派诊断:未闭环问题和缺的动作 op 可能是同一个原因。诊断报告到了,按它的合并建议决定缺的动作 op 并进哪条线。
   2. 没有未闭环问题,只有「缺动作 op」,或者建议处置是「立修复线」的缺口 → 不派诊断,直接立修复线(§3.6)。
   3. 立起来的修复线按 §3.6 走到验证通过,或者转成顺路验证(现场不在了的时候)。修复线自己的探索报告认为不用改代码的 → 登记待裁(附报告路径),线表等待条件记「等待裁定」,这一小步停在这里等裁定。
   4. 重派实机探索 agent 接着打这一局。重派任务书 = 原任务书,下面几处更新:
      - 四个字段(局内目标、两个清单、难度)按当时的记录重新填(第 7 项)。停下这段时间新走到「等实机验证」的修复线,这时才进得了任务书;
      - 现场交接信息(第 4 项):现场四项取自动过窗口的最后一个 agent 的报告。诊断 agent、实机验证 agent 动过窗口的,取它们的报告;都没动过,取最后一份单局报告;
      - 附加信息节(第 9 项)更新,其中带两句:「从停下的画面继续」;修复线给这个画面接上了新动作 op 的,「这个画面的这一步已经是动作 op〈名字〉」(§3.6)。
4. 停下原因是「模式选择画面有存档」→ 登记待裁(附报告路径),线表等待条件记「等待裁定」。用户裁定以后,把裁定原话写进重派任务书的附加信息节,重派实机探索 agent。
5. 中途报告怎么登记(第 1、3、4 条共用):照路 B 第 2-4 步里登记的部分做,三样:
   - 追踪文件(路 B 第 3 步);
   - 待裁知识队列、待跟进事项文件(路 B 第 2 步);
   - 顺带取证和顺路验证的结果(路 B 第 2、4 步)。

   登记这一步不派活:不派诊断、不立修复线、不派知识文档线。第 3 条的派活在登记以后按它的小步走。第 1 条恢复以后不派:没闭环的问题由这一局后面的单局报告接着报(「未闭环问题」只列还没处置的);顺路验证不达标的,记进那条修复线在线表的备注栏。这两样都等下一次停下或者局终,再按对应的路处理。

**路 B:这一局结束(局终)**(按顺序做,最后一步是自验)

1. ☐ 收这一局的全部单局报告,以局终那份为准。
2. ☐ 处置这一局的发现:
   - 未闭环问题 → 走 §2.4 处置循环;
   - 「缺口」里建议处置是「立修复线」的、「缺动作 op」→ 立修复线,或并入已有的修复线(§3.6);
   - 「缺口」里写明现在探不了的 → 登记待跟进事项文件,状态标签「等随机遇到」。追踪文件里这条缺口的状态在第 3 步一起改;
   - 知识发现 → 编排者照每条的建议去处登记(§3.7):进待裁知识队列,或登记待跟进事项文件;
   - 顺带取证采到的项 → 把数值和证据指针照报告抄进待跟进事项文件的对应条目,状态标签改成「已取证」。之后由谁拿它改代码或文档,登记待裁由用户定;
   - 这一轮新立或并入的修复线,走到「等实机验证」或收口。
3. ☐ 照单局报告更新追踪文件(记法见 screen-tracking.md):
   - 第 12 节「画面核对」,报告写到过的每个画面,按顺序做四样:
     1. 这个画面还没有章的,新建一章。
     2. 识别核对那一行,改成报告日期和报告写的结论。
     3. 报告写用过的动作:动作一栏里还没有这一步的,加一行;写正常的,这一行的日期改成报告日期,括号里用的是哪个 op 还是「鼠标点击」照报告写的改。
     4. 报告写不正常的动作:日期不改。它的问题按下面「未闭环问题」那一条处理。
     
     报告写某一章原有的缺口已经不在了的,删掉那一条缺口。
   - 第 4 节「缺口」、第 7 节「缺动作 op」→ 写进对应画面那一章的「缺口」小节,状态「等修复线」。已经有一条说的是同一件事,只改状态,不另起一条。报告写这一条现在探不了的,按第 2 步登记进待跟进事项文件;这里的状态写「已登记待跟进事项(编号 N)」,N 是那个条目的编号。
   - 第 8 节「未闭环问题」→ 每个问题在报告写的那个画面的「缺口」小节里先写一条,状态「等诊断」,缺什么照报告写的现象写。诊断报告到了以后按 §2.4 第 2 步改。
   - 原来标「已登记待跟进事项」的缺口,这一局又遇到了(第 4 节里有它),待跟进事项文件里那一条标的是「等随机遇到」→ 删掉那一条待跟进事项,缺口的状态改回「等修复线」。
   - 第 3 节「没看到」→ 不动追踪文件,按第 9 项抄进下一局任务书。
   - 第 9 节「遗留」里的文件名(合并缓存除外)→ 记进线表备注栏。以后给这个画面立修复线时,写进任务书的附加信息节,由修复线的探索 agent 核对:改动全属于那次建档的,由修复线提交;混有别人改动的,不动。
4. ☐ 顺路验证的结果照单局报告处理(§3.6)。达标与否以报告写的为准,编排者不另核。
5. ☐ 待裁知识队列里有用户已经裁定的 → 派知识文档线(§3.7),走到收口或等待。
6. ☐ 按条件决定下一步:
   - §3.1 的完成条件都满足 → 按 §1「场景的确定」处理;
   - 其余 → 编排者拼下一局的任务书(第 7 项),派发前过 §2.2,派下一局。验证通过的修复线,剩下几步(全局对照、正本更新、收口)排在派下一局之前。
7. ☐ 自验:这一局报告里的每条发现都有去处——追踪文件、待裁知识队列、待跟进事项文件、线表,四份文件里至少一份记了它;线表和占用表是最新值。有遗漏回去补。

**路 C:中止(对局丢了)**

1. 这一份中止报告和这一局此前的各份单局报告,照路 B 第 2-4 步登记(内容以最后一份完整的单局报告为准)。
2. 开新局 = 派下一局:四个字段照记录填,派发前过 §2.2。

实机探索线什么时候停,由用户决定(§3.8):编排者不因为「连着几局没盖到新条目」自己收线。

为什么修复线排在下一局前面:串行模式下实机探索线和修复线不能同时走;先修再打,下一局用的就是修过的识别和动作 op。

### 3.6 修复线与等实机验证

- **什么时候立修复线**:来源两个,都照报告写的办,编排者不自己判断:
  - 实机探索 agent 的单局报告:「缺动作 op」一节;「缺口」一节里建议处置是「立修复线」的;
  - 处置循环的处置建议(§2.4):单点修复单、立线建议。

  例子:局里发现某类内容认不出,报告的建议处置是立修复线,查出来是缺模板。
- **修复线的范围**:改识别代码、补识别模板、改动作 op、补完没做完的建档(比如没点的按钮的跳转关系)。
- **立线分两种**:
  - 经过诊断的,按 §2.4 走,诊断报告当探索报告。
  - 没经过诊断的(单局报告的「缺动作 op」和「缺口」里报的):直接立线,按通用流程从探索这一步开始。探索任务书照通用模板;画面留在现场不动,修复线的探索 agent 只读识别、不操作。
- **线名**:按画面归并的,线名用画面名。按诊断的立线建议立线、诊断另起了线名的,用诊断起的线名,线表备注栏记「对应画面:<画面名>」。以后同一个画面再报缺口,按备注栏找这条线。
- **攒批(按画面归并)**:一个画面一条修复线。同一个画面又报了缺口,按已有的那条线在哪个状态办:
  - 还没进定稿(还在探索、立项与设计、对抗这三步)→ 并进去。编排者把新缺口的报告原文切片记进线表备注栏;这条线定稿以前的每一张任务书,附加信息节都带上它(这一步在飞的,直接转话)。并进设计由设计 agent 做,对抗 agent 不做。不同画面的缺口各立各的线。
  - 在等待裁定(诊断熔断、规则没覆盖)→ 不另立。把新缺口的原文追加进同一条待裁登记,等用户一起裁。
  - 已经进了定稿这一步,或者过了定稿(在定稿、实现、review、等实机验证,或者已经收口)→ 不并,另立一条线,线名加序号(比如「商店-2」)。
  - 诊断报告的合并建议说要并入某条线的,同样看那条线在哪个状态。诊断给的是单点修复单、在场景一按立线处理的,也照这三条找该并的线。
- **最小形态**:改哪和判据都能逐字指出来的小修复,迭代可以很小(设计一页 + 任务一行),门一个不少。够不够小,由设计 agent 在设计文档里定。
- **半路的对局留着**:诊断、实现期间,游戏窗口停在现场不动,占用表把窗口记到这条修复线名下。不替用户放弃对局。为什么:放弃对局收不回来;现场还在,修复就能在它上面验证。
- **重启 MCP server**:
  - 要不要重启:看这条线 landing 文件首节「影响面申报」的「共享资源面」有没有「重启」标记(§7 第 4 项)。要重启的,实现完成并过了 review 以后,由编排者重启(§2.2)。
  - 场景一的实现任务书另加一条回信增补,写明三样:
    1. 本线改没改 `src/sr_od/` 下的运行时代码;
    2. 本线动没动模板文件(加了还是改了,在哪个目录);
    3. 本线改动直接影响的测试有哪些(测试文件路径)。
  - 什么改动要重启,三种之一:
    1. 改了运行时代码;
    2. 往立绘库、装备库里加了模板;
    3. 改了已有的模板文件。
  - 什么改动不用重启:只改了画面档、测试、文档;或者只新加了立绘库、装备库以外的模板。
  - 为什么模板分三种:立绘库(`assets/template/cw_character_avatar`)和装备库(`assets/template/currency_war/` 下的 `equip_plaza`、`equip_legacy`)第一次用到时整库读进 MCP server,之后一直用内存里的那份,新加的模板不重启读不到。别的模板读进内存以后也不再重读,所以改了已有的要重启;没用到的模板不在内存里,新加的用到时才读盘,不用重启。
  - 什么时候重启:画面停在半路时立的修复线,等它们都到了验证点,合并成一次重启,派一个实机验证 agent 一次验完。同现场还有修复线在实现的时候,先到验证点的那条不先重启,等它到了再一起。
  - 重启前确认(runtime-ops.md「启动与重启」节)有三项在本场景这样判,其余照做:
    - 「游戏在大厅」不要求:中途停下的时候,对局可能停在半路。
    - 「工作区干净」:本线申报面里的文件都已提交,就算过。工作区里别的会话的改动不挡重启,编排者把剩下的文件名记进线表备注栏。
    - 「全量测试 0 失败」:全量测试有失败时,只跑回信增补第 3 样列的直接影响的测试。这些全过 → 把全量里失败的测试名记进线表备注栏,照常重启。直接影响的测试也有失败 → 不重启,回 §2.4 处置循环。为什么放宽:工作区里有别的会话的改动,它们的测试挂红不该挡住本线的重启。
  - 重启以后:编排者调一次 get_run_status,调通了才算连接恢复,才能派下一个 agent。调不通 → 按所在环境的办法重连 MCP 客户端再调;仍不通 → 登记待裁。
  - runtime-ops.md 的「改动集中纪律」(局中不改代码)针对的是 MCP server 自己在跑的对局。实机探索 agent 自己打的对局,它停下以后就可以改代码并重启。
  - 为什么自己打的对局不受重启影响:重启脚本只结束 MCP server 自己的进程,游戏是独立进程;重启后新的 MCP server 第一次用到游戏时会重新找到游戏窗口。
- **等实机验证的修复线**:实现完成、过了 review 以后,线表记等待条件「等实机」(线表模板里的「等实机」,就是本文件说的等实机验证)。收口这一步的任务书加一句,两种时机都用:回信里写明本线修掉了追踪文件里哪个画面的哪几条缺口,验证时哪些识别核对和动作是正常的,并附验证报告的路径。编排者在验证达标时已经照验证报告更新过追踪文件(下面「验证结果怎么处理」);回信里这两样用来核对更新有没有漏。验证分两种时机:
  1. 现场还在(出问题的画面还停在游戏窗口里):重启以后立刻派实机验证 agent,在这个画面上验。同现场还有修复线在实现的,等它们都到了验证点再重启、再派(见上一条「什么时候重启」)。
     - 主验证和次要验证:线表里先记「等实机」的那条线是主验证。同一个现场其余等实机验证的修复线,进验证任务书的「次要验证」一节。
     - 验证任务书开头加一句声明,替换模板「禁止事项」的第二条:「本任务书里,模板『专跑趟次不做消耗性 / 不可逆的游戏内操作』这一条,替换为——允许执行被验的动作 op,它会改变对局,这就是验证本身;和验收标准无关的操作不做。」
     - 附加信息节带五样:交接协议(§2.2)整段;交出方的现场四项和报告路径;同现场其他等实机验证的修复线(每条写线名和验收标准,模板「次要验证」一节的填法);追踪文件里这个画面那一章的原文;这个画面上标了「未点」的按钮清单(§3.4)——验证时点到了哪个,报告里就写明点了哪些、点后到了哪个画面。
     - 验完把窗口停在验证结束时的画面归还,报告里附现场四项。验完交还实机探索 agent(§3.5 路 A 第 3 步)。
  2. 现场不在了(出问题的画面不在游戏窗口里:这一局已经结束,或者对局已经往前走、回不到那个画面):编排者每局拼任务书时,把等实机验证的修复线写进「顺路验证清单」(§3.3 第 7 项)。实机探索 agent 顺路遇到就验:对照那条线的验收标准,把结果写进单局报告。编排者照报告处理。

- **验证结果怎么处理**(两种时机相同):
  - 达标 → 清掉线表的等待条件,派后面几步(全局对照、正本更新、收口)。编排者同时照验证报告更新追踪文件:删掉本线修掉的缺口条目;验证时用着正常的动作、核对一致的识别,日期改成验证那天。
  - 不达标 → 回 §2.4 处置循环。
  - 没遇到 → 在线表这条线的备注栏记一局。连续 3 局没遇到 → 做三样:
    1. 登记待裁,线表等待条件记「等待裁定」;
    2. 把它对应的缺口条目登记进待跟进事项文件,状态标签「等用户裁定」;
    3. 追踪文件里这几条的状态写「等用户裁定」。
    
    用户裁定以后:要修的,这几条改回「等修复线」,删掉待跟进事项文件里对应的条目;不修的,两处都不动(完成条件按「已登记进待跟进事项文件」算,§3.1)。
    
    怎么数「连续 3 局」:局终报告算一局,中途停下的报告不算;中间出过一次不达标的,重新从 0 数。
- **动作 op 接上以后改操作章和追踪文件**:修复线实现新的动作 op 以后,在实现这一步里(排在实机验证之前)做两处改动。实现任务书的附加信息节带上追踪文件的路径。
  - 第一处,玩家 skill 对应画面文档的「操作」章:把这一步「用什么」改成新 op 的名字和用法。
    - 画面文档已经有「操作」章的:只改「操作」章里对应的那一格,别的章不动。操作表里没有这一步的,加一行。
    - 画面文档还没有「操作」章的(新画面:前两章是实机探索 agent 写的,后两章没人写):新建「操作」章,只写接上动作 op 的这一步。「识别后要做的决策」章仍然不写。
  - 第二处,追踪文件里这个画面的动作一栏(记法见 screen-tracking.md):这一步的括号里改成新 op 的名字,日期写「还没用过」;动作一栏里没有这一步的,加一行。
  - 为什么必须改、必须排在验证之前:不改追踪文件,下一个实机探索 agent 按 §3.4 判断这一步还是没有动作 op,会在同一个画面再停一次,还会按攒批规则另立一条重复的线。不改操作表,它查不到这个 op 的用法,只能照旧用鼠标。
- 修复线的申报面不得碰策略面(§7 第 2 项)。

### 3.7 文档维护与待裁知识队列

- 本场景里,实机探索 agent 不经用户裁定就能改的只有三样(§3.3 第 5 项):建档内容、画面文档的前两章、玩家 skill 入口列表加一行。修复线改设计正本,走它迭代的正本更新步;给新画面接上动作 op 时,新建或修改画面文档的「操作」章(§3.6)。
- 其余知识文档一律不改,删也不改:
  - 画面文档的「识别后要做的决策」章;「操作」章只有修复线按 §3.6 能改;
  - 玩家 skill 的知识文档(references/ 下的玩法说明、决策手册、阵容图鉴、机制各篇);
  - `docs/game/currency_war/research/` 各篇。

**待裁知识队列** = `<自主工作文件夹>/pending-knowledge.md`,放等用户裁定的知识发现。

- 谁写:编排者。实机探索 agent 把知识发现写进单局报告的「知识发现」;编排者照原文转登,不加工。
- 每条四项:编号(K-1、K-2 顺延,删掉的编号不复用)、发现内容、证据指针、建议落点(改哪份文档的哪一节)。已经入队的发现再次出现,只在原条目上追加证据指针,不另起一条。
- 知识文档线排在两次派发实机探索 agent 之间,和修复线一样(串行,一次只推一条线)。
- 用户裁定以后:编排者先把裁定原话记在这条队列条目下面,再派知识文档线(小迭代)按裁定更新。知识文档线不进游戏,核实靠第二来源:官方配置、wiki、以前实机局留下的截图,三样里有一样和这条发现对得上,才写进文档。
- 核实的三种结果,各有收场:
  - 对得上 → 更新知识文档。更新线提交后,删除队列里对应的条目。
  - 第二来源证明它不对 → 知识文档线回报编排者;编排者把这一条从待裁知识队列移到待裁登记(一个事项只挂在一处),由用户再定。
  - 三样都查不到、要再打一局才能核实(知识文档线走到哪一步查到,都按这条办)→ 知识文档线回报编排者;编排者把这条发现登记进待跟进事项文件,标「等实机取证」,删除队列条目。这条知识文档线不结束,线表等待条件记「等实机」。顺带取证采到以后,编排者清掉等待条件,重派它的立项与设计这一步,附上采到的证据。
- 用户裁定「不改」→ 删除队列条目,不立线。
- 用户一次裁定好几条 → 合并成一条知识文档线。
- 证据还不够、要等实机取证的发现不进这个队列:登记待跟进事项文件,由顺带取证清单携带。
- 可靠性纪律见 version-update-live-exploration.md §6。

### 3.8 收尾与中断

- 实机探索线什么时候停,由用户决定。§3.1 的完成条件满足时,编排者照 §1「场景的确定」报告。除此之外,编排者不自己判断「再打下去没收获」而收线。

**用户叫停**(按顺序做;之后接着做公共 skill 停止清单的其余步骤)

1. 把用户的原话转给此刻持有游戏窗口的 agent(实机探索 agent、实机验证 agent 或诊断 agent),让它停止操作、交报告。实机探索 agent 交的是单局报告,附现场四项和这次写的文件清单;先提交这次派发写的文件,再发报告。
   - 转话以后 10 分钟没有交报告 → 用中断手段中断它。
   - 中断导致文件没提交,分两种:
     - 报告里有「这次写的文件清单」的:编排者只按清单逐文件点名提交,提交说明写线名和「叫停时未完成」。同样先核对该文件的改动全是这次派发写的,混有别人改动的不提交。
     - 没有清单的:编排者不替它提交。把工作区里还没提交的路径(`git status` 的输出)全部记进线表备注栏,标「未经核对」。下次开启重派时,让新的实机探索 agent 核对:改动全是那次派发写的才提交。
2. 收到报告以后,最后一份单局报告照路 B 第 2-4 步**登记**:追踪文件、待裁知识队列、待跟进事项文件、顺路验证的结果。叫停时只登记、不派活:不派诊断、不立修复线、不派知识文档线。这几样留到下次开启再做(§3.2 开启清单第 6 步)。
3. 最后一份单局报告里有未闭环问题的:登记进待跟进事项文件,状态标签「等现场再现」。追踪文件里这几条「等诊断」的缺口,状态改成「已登记待跟进事项(编号 N)」。下次开启时它们跟着任务书的附加信息节走(§3.3 第 9 项);实机探索 agent 再遇到就停下来,现场留给诊断。
4. 对局停在半路 → 对局留在原地,不放弃。占用表的持有行保留,交接记录写明现场四项(取自最后一个动过窗口的 agent 的报告)和「用户叫停」。那个 agent 被中断、没交报告的,交接记录写「现场未知」。线表「在飞 agent」一格记「停止时中断」。为什么不放弃:放弃对局收不回来,做之前要用户点头。
5. 追踪文件里的缺口条目,分三种:状态是「已登记待跟进事项」「等用户裁定」的不动(叫停以前就卡住了,待跟进事项文件里已经有条目)。有修复线在跟的不动。其余的,登记进待跟进事项文件,状态标签「等随机遇到」;追踪文件里这几条的状态写「已登记待跟进事项(编号 N),卡在用户叫停」。
6. 汇总给用户时,待裁登记和待裁知识队列两份都汇总。
7. 自验:没有在飞的 agent;线表、占用表、待裁登记、追踪文件是最终值;最后一份报告里的发现都登记了;待裁已汇总。有缺回那步重做。

- 线表里实机探索线怎么记结束:用户叫停 → 线不结束,「在飞 agent」一格记「停止时中断」,下次开启接着推。用户明说这条线不要了(砍单)→ 移入「已结束线」,注明砍单。场景完成 → 注明收口。

**对局丢了或者连接断了以后怎么恢复**(由编排者按固定步骤做,不派诊断)

恢复类的说明有四段。按上一份报告的停下原因选一段,原话写进重派任务书的附加信息节:

- MCP server 连不上:「上一份报告是因为 MCP server 连不上停下的,游戏画面没动过。先识别画面,按并入的交接协议核对现场,对得上就从停下的地方接着打。」
- 游戏掉线:「上一份报告是因为游戏掉线停下的。先识别画面,有重新连接的提示就点它;连不上就停下回报。连上以后按并入的交接协议核对现场,对得上就从停下的地方接着打。」
- 游戏闪退:「上一份报告是因为游戏闪退停下的。按玩家 skill 进货币战争,走到模式选择画面。是「进行中」形态(有存档)→ 点「继续进度」,续的是原来那一局,按并入的交接协议核对现场,对得上就从停下的地方接着打。没有存档 → 对局已经丢了:写一份单局报告,停下方式写「中止」,回报编排者。」
- 用户叫停:「上一份报告是因为用户叫停停下的。先识别画面,按并入的交接协议核对现场,对得上就从停下的地方接着打。」

核对现场时,续局以后进度比记录的早(闪退以后回滚到了前一个节点)也算对得上:接着打,在单局报告里写明。

1. MCP server 连不上 → 重启(§2.2)。
2. `check_game_window` 显示窗口无效 → `open_game`。它只负责把游戏打开、登到大世界,到不了货币战争大厅。
3. 重派实机探索 agent(任务书按 §3.5 路 A 第 3 步第 4 小步更新),附加信息节加上面对应的那段恢复类的说明。之后按原因分三种:
   - MCP server 连不上:它核对现场,对得上就接着打。
   - 游戏掉线:它先识别画面,有重新连接的提示就点它;连不上,停下回报。编排者再重派一次;还连不上 → 登记待裁。
   - 游戏闪退:它按玩家 skill 进货币战争,走到模式选择画面。有存档 → 点「继续进度」,续上原来那一局;没有存档 → 回报编排者「对局已丢」。
4. 收到「对局已丢」→ 这一局记「中止」,走路 C(§3.5)。
5. 某一步做不成 → 登记待裁。

恢复期间,占用表的持有行保留在实机探索线名下,备注「恢复中」。

## 4. 场景二:流程框架适配期

> 本节只立了骨架:目的、验证载具、缺口的去处。进入本场景时立哪些线、由谁发起第一局,本节没有写——编排者在待裁登记写一条「已进入场景二,怎么开工等用户说明」,不自行立线。

### 4.1 目的与完成条件

- 目的:把场景一的识别成果与动作 op 接入 app 自动流程——对局由流程框架自主推进,不再靠 agent 逐帧代理操作。
- 优先事项:app 自动流程跑局循环——「跑一局→暴露缺口→修→再跑」。
- 策略无关性:本场景策略质量不设标准(可以坏、可以随机乱选)——流程框架的验证看「对局推进与缺口收敛」,不看胜负与成绩;对局成绩与策略调优是场景四的事(§6)。
- 完成条件:app 自动流程能稳定打完整局(端到端不卡死)。满足以后怎么办,见 §1「场景的确定」。

### 4.2 验证载具与工作节奏

- **验证载具 = app 自动流程跑局**:经项目 MCP 工具发起 run_standalone_app(货币战争);一次 run 一局,run 结束即停——与场景一「一局一停」同型,载具不同;逐局发起,不获多局连续授权(局间机械步进的理由同 §3.3 第 7 项)。
- 跑局暴露存量识别/建档/流程缺口 = 常态,暴露即覆盖工作在生效,逐条登记(§4.3)后继续。连续两局零登记 → 登记待裁(已知的缺口可能都补完了,下一步等用户说明)。本节没有「重新找缺口」的做法,编排者不自己找。
- run 卡死/中途停止 → 按 §2.3 停止操作汇报纪律处置,走 §2.4 问题处置循环;run 跑完但暴露读数/行为缺口 → 不停线,按 §4.3 登记缺口后继续下一局。

### 4.3 缺口分诊与修复路由

- 按缺口类型路由:
  - 识别缺口(建档过期/OCR 能力不足/模板缺失)→ 画面建档与识别修复走 od-dev-screen-onboarding;
  - 流程缺陷(重试语义/分发接线/循环结构)→ 小修复批(线内单点修复攒批实现与验证,每条带「改哪+判据」);
  - 机制缺失(动作 op 缺失/机制建模缺)→ 立线走 od-dev-run-iteration(迭代形态按挂账条目的改哪与判据是否逐字可指,口径见 §6.2)。
- 缺口记账:画面识别、动作 op 的缺口,记进追踪文件里该画面的「缺口」小节(§3.2);其余缺口逐条登记待跟进事项文件(定位见 SKILL.md §3「待跟进事项」行),条目写明「改哪+判据」。修复批从两份文件的开放条目取活逐个清偿,完成即删(登记与删除纪律见 §2.5)。
- 根因不明的缺口先走 §2.4 处置循环(诊断 agent 定位)再归入上述路由;修复改运行时代码的,重启窗纪律按 §7 第 4 项。
