## 1. 阶段模型

CW 自主推进分四个阶段。方法骨架跨阶段不变(§2+§7),阶段只决定优先事项:编排者先判定当前阶段,当前线按对应阶段节运转。

| 阶段 | 主要目的 | 优先事项 | 退出判据(进入下一阶段条件) |
|---|---|---|---|
| 阶段一 版本适配摸索期 | 画面识别与动作 op 适配;玩法理解靠实机探索补充 | 实机探索局+覆盖缺口收敛 | 画面识别与动作 op 适配完成——覆盖审计缺口清零或仅余已登记进挂账的缺口 → §4 |
| 阶段二 流程框架适配期 | 识别与 op 接入 bot 自动流程 | app 自动流程跑局循环(run→暴露缺口→修→再跑);策略可以坏、随机乱选——不看对局成绩,只看流程推进与缺口收敛 | app 自动流程能稳定打完整局(端到端不卡死) → §5 |
| 阶段三 投资策略/环境 sim 适配期 | 投资策略与环境效果在 sim 里建模到位 | sim 与实机对拍 | 对拍一致 → §6 |
| 阶段四 策略实现适配期 | 策略实现 | 策略线(真实策略代码迭代) | 策略成绩达标(用户判) |

术语注:sim = 项目内置的单局模拟器(`src/sr_od/application/currency_war/sim/`,只模拟环境,不评判策略);对拍 = sim 局与实机局跑同一对局内容后逐项比对读数。

**阶段判定**:按能力就绪度,不按日历时间。证据 = 覆盖审计状态(阶段一;口径见 version-update-live-exploration.md「覆盖审计」节)/ app 自动流程稳定性(阶段二)/ sim 对拍状态(阶段三)。编排者据证据判定当前阶段,在线表表头记一行「当前阶段=阶段 N+判据指针」;中断重开的会话以表头记录为准接续,不重判。

**跨阶段恒定项**(任何阶段都成立):

- §2 通用编排与 §7 领域叠加件在所有阶段生效;
- 挂账修复线与知识文档线为跨阶段常驻支线(线型定义见 §6.2;任何阶段都可立,不只阶段四);
- 推进模式恒为串行(§7 第 1 项)。

## 2. 通用编排(跨阶段不变)

本节条款对所有阶段生效。两个通用术语:**验证载具** = 当前阶段用来暴露缺口与验证改动的运行形态(阶段一=实机探索局,阶段二=app 自动流程跑局,阶段三=sim 对拍局,阶段四=策略线的实机验证局;细则见各阶段节);**执行 agent** = 当前线验证载具的在飞操作者。

### 2.1 编排者职责

- 编排者只做机械动作(派子 agent+记录三份文件,通用框架单一源,本文件不展开),不参与决策:判断类动作机械规则化,或交由对应子 agent 在其交付固定节中产出,无判据可依登记待裁、线转等待(od-dev-agent-autonomous-mode §2-②;下文「自主模式」即指该 skill)。
- 编排者不做:技术判断(方案倾向、归因结论、评审意见一律由对应角色子 agent 产出)、亲自写代码与文档、亲自操作游戏。编排者夹带技术倾向会污染对抗评审与用户裁决——这是本流程要防的第一件事;用户明确指名要编排者亲手做某事时,以该指令为准。

### 2.2 窗口所有权(串行铁律)

- 一个游戏窗口同一时间只归一个 agent;编排者显式登记「谁、从何时起、干什么」于占用表(occupancy.md)。
- 占用窗口的动作 = 点击/拖拽/输入等驱动游戏的操作;只读识别(analyze_screen)不算占用。
- 派发任何会占用窗口的活(载具操作/诊断/实机验证)之前:先查窗口登记与项目 MCP 运行状态(get_run_status);窗口已有持有者就把新活排队,不派第二个。
  - 为什么:两个 agent 同时驱动同一窗口会互相干扰(点击落进对方操作的画面、画面被抢),且事后从运行记录难以区分是谁的操作——防患只能靠事前登记,不靠事后归因。
- 交接协议:交出方交窗时报告现场信息四项——当前画面 / 对局进度 / 血量与金币 / 未了事项;接管方开工第一步先识别当前画面(analyze_screen),与交接报告逐项核对,对不上=按遇问题停止纪律报编排者派诊断(现场视为不可信),不先动手。
- **MCP server 重启执行权归编排者**(通用框架规则;CW 重启运维细则=runtime-ops.md「启动与重启」节——重启前四步确认/对局中守卫拒绝/改动集中纪律);执行/诊断/验证 agent 禁自行重启。

### 2.3 停止操作汇报纪律(任务书必含)

- 遇到问题(操作不生效 / 画面异常 / 疑似机制变化 / op 报错)的动作顺序:
  1. 停止操作:一切游戏操作停下,游戏窗口状态保持原样,不试图自行修复或退出当前画面;
  2. 保存证据:截图留档 + 一句话描述 + 发生时间;
  3. 汇报:现象 + 证据 + 发生时点报给编排者,然后等待。
- 禁止:自行改代码;自行绕过问题继续跑(把问题藏进「看起来跑通」);未经交接就把游戏窗口丢在当前状态。
- 为什么:现场就是诊断的证据;修了、绕了、清了,证据就没了,同一个问题还会再来一次。

### 2.4 问题处置循环

**循环全貌**

1. 执行 agent 停止操作并汇报 → 编排者派**诊断 agent**定位根因(诊断任务书要素:输入=当前线局终报告(阶段一=单局报告,§3.3 第 7 项)+现场交接四项/游戏操作可现场复现但代码只读/交付固定节「处置建议」四值枚举/报告落 <工作文件夹>/<线名>/,回信≤10 行=处置建议一行+报告路径;通用层无此模板,CW 自持)。
2. 诊断产出固定节「处置建议」(四值枚举,字段必附),编排者照派:
   - **知识修正**(机制理解错 / 操作方法错 / 画面建档缺口;附目标文件指针+生效方式):立知识文档线(小迭代:补画面档/修正知识文档)走 od-dev-run-iteration,收口后让原执行 agent 继续工作;
   - **单点修复单**(改哪+判据):属当前线申报面内的=线内任务(当前线迭代 tasks.md 加任务,不立新线),派线内修复任务(实现+验证)后继续;
   - **立线建议**(线名+改哪+判据+优先级+原文切片):触设计意图或跨多文件=立新线走 od-dev-run-iteration 完整生命周期(实机验证=复现原故障场景确认已修)→ 重启 MCP server(运维细则见 [runtime-ops.md](runtime-ops.md))→ 让原执行 agent 继续工作;
   - **环境处置**(重启/重试+可复跑检查命令):按 occupancy 规则机械执行。
   建议字段缺失=格式缺陷打回重交;**诊断熔断**:同一现象第 3 次=登记待裁(pending-decisions.md),线转等待,其他线继续。
3. 循环期间原执行 agent 保持停止状态等待,所在线登记暂停(等处置,恢复点=诊断结论指针),编排者按取活规则接其他排队线;窗口可能被诊断/验证 agent 按 §2.2 接管,窗口归谁以编排者的登记为准。

**各角色边界**

| 角色 | 游戏操作 | 代码 | 说明 |
|---|---|---|---|
| 执行 agent | 可 | 只读 | 按任务书操作当前阶段验证载具(阶段一=亲自玩货币战争);遇问题停止操作并汇报;问题处置交编排者另派(§2.4) |
| 诊断 agent | 可(现场复现) | 只读 | 定位根因,不改代码 |
| 设计 agent | 不操作 | 只写设计稿 | 设计与实现分开,防同一个 agent 既定方案又自己验收 |
| 对抗评审 | 不操作 | 只读 | 每轮起全新的、没读过前几轮讨论的子 agent——看过前几轮讨论就会被已有思路带偏,挑不出真问题 |
| 实现 agent | 不操作 | 写 | 按设计稿落地;与设计稿对不上的地方报告编排者,不自作主张改设计 |
| 实机验证 agent | 可(复现验证) | 只读 | 验证后把窗口停回已知稳定状态(大厅或备战画面)再归还 |

**传话纪律(约束编排者本人)**:用户消息与子 agent 问题原样转交、不加工、不筛选——通用框架定义,单一源 = od-dev-agent-autonomous-mode §4.3「传话原样」;CW 增量一条:设计争议需要用户裁决时,把双方论点原样并列转达,不排序、不建议。

### 2.5 进度登记与跨会话接口

- 自主推进不设总的任务清单文件:当前线的任务面由对应阶段节的登记载体承载(阶段一=关注清单,§3.3 第 2 项;阶段二起=跨迭代挂账文件的缺口记账,§4.3);编排层登记(线表/占用表/待裁登记三份文件)=通用框架定义的自主工作文件夹(SR 项目惯例 .debug/temp/ 下 autonomous/<开工日期-主题>/)。
- 推进期间子 agent 做迭代时,按 od-dev-run-iteration(完整迭代 skill)的 tasks.md 格式在迭代目录内登记进度;编排者不替子 agent 记迭代进度。
- 待办登记:货币战争专用的待办文件 = `.debug/progress/CW跨迭代挂账.md`(定位见 SKILL.md §3「跨迭代挂账」行);条目写明「改哪、判据是什么」——这两样是立线定迭代形态时要对照的原料,入口写齐 = 初判纯文字对照,不强制格式。**完成即删**:条目闭环(清偿/实证/裁决定谳)时当场把该条目从跨迭代挂账文件删除——文件里只留开放项,禁留「已完成/已清偿」划线态或存档句堆积;有长效价值的裁定结论随 commit message 或知识卡固化,不靠文件留尸。为什么:文件混入完成态会让后来者把已完结条目当活待办盘,文件越长真待办越难找。
- 发现的归档:知识类结论落对应知识文档或画面档(分层判据见 SKILL.md §3);过程叙事不进本 skill。

## 3. 阶段一:版本适配摸索期

### 3.1 目的与退出判据

- 目的:画面识别与动作 op 适配;玩法理解靠实机探索补充——用真实对局摸清新版本的画面、机制、与旧版本的差异,收集问题。提升对局成绩与策略调优不属于本阶段(策略线见 §6)。
- 优先事项:实机探索局+覆盖缺口收敛(覆盖审计口径 = version-update-live-exploration.md「覆盖审计」节)。
- 退出判据:画面识别与动作 op 适配完成——覆盖审计缺口清零或仅余已登记进挂账的缺口 → 进入阶段二(§4)。

### 3.2 运转形态(串行实机探索局)

- 运转形态只有一条主线:编排者反复派实机探索 agent(=阶段一的执行 agent)亲自玩货币战争——玩法知识与操作方法按游玩 skill `sr-od-currency-war`(面向玩家的 skill),经项目 MCP 工具执行;每次派发以一局为限(单局限令,§3.3 第 7 项),实机探索 agent 打完当前局即停止汇报,编排者按局间机械条件映射处置(见 §3.3 第 7 项)。实机探索 agent 遇到问题就停止操作(停止一切游戏操作、保持游戏窗口状态原样,向编排者汇报后等待处置,细则见 §2.3);编排者按 §2.4 走问题处置循环;处置完让实机探索 agent 继续工作。
- 推进模式:串行(恒定口径见 §7 第 1 项)。探索产出开迭代是默认去向(自主模式 §2-③:挂机下不设「小改直做」出口)——知识产出(补画面档/修正知识文档)与问题修复都立线走 od-dev-run-iteration,最小形态=设计一页+任务一行,门一个不少。

### 3.3 实机探索任务书构成(CW 实例差异,逐项并入模板实例位)

任务书以 od-dev-agent-autonomous-mode skill 的 references/line-templates.md §1 探索模板为基复制(实例位照填),再按本节条目 1-8 增补 CW 条款(领域增补规则见该模板库头注);CW 实例差异:

1. **操作依据**:游玩 skill `sr-od-currency-war`(面向玩家的 skill)——实机探索 agent 的玩法知识与操作方法从它取;任务书不复制其内容,实机探索 agent 也不依赖编排者的会话历史。
2. **关注清单**:本次要关注/验证的内容——由实机探索 agent 开工步自起草(输入:用户当期指令原文、跨迭代挂账文件未竟项、游玩 skill `sr-od-currency-war` 的玩法文档中当期值得核对的面;仍空=按操作依据 skill 的玩法机制文档自选关注点并如实申报来源),每条注来源,零来源条目禁入;每条写清「关注什么、观察到什么算值得关注、怎么记录」。本线(探索任务)的终止判据=交付固定节「清单逐条覆盖状态」全为已覆盖(凭据随附)或用户叫停。
3. **停止操作纪律**:§2.3 整段并入任务书。
4. **现场交接信息**:接管已有对局时,写明交出方(= 上一个持有窗口的 agent,见 §2.2 交接协议)报告的现场信息四项(当前画面 / 对局进度 / 血量与金币 / 未了事项)。
5. **文件面**:探索产物只写知识归档(知识文档/画面档,分层判据见 SKILL.md §3)与探索报告,不动任何代码。
6. **交付**:探索报告与证据截图落自主工作文件夹的当前线子目录(`<工作文件夹>/<线名>/`),回信格式按通用模板。
7. **单局限令(每次派发最多一局)**:任务书写明本局的局内目标(打到哪里/验证什么)与顺带取证清单——由判读批(=判读单局遥测与报告并出下一局规划建议单的子 agent 委派)按跨迭代挂账文件+单局报告给「下一局规划建议单」(判读批任务书要素:输入=跨迭代挂账文件+单局报告;操作依据=本 skill references/telemetry-reading.md;交付=下一局规划建议单,字段=局内目标+顺带取证清单;报告落 <工作文件夹>/<线名>/;回信≤10 行=建议单要点+路径。通用层无此模板,CW 自持),编排者照抄进任务书;实机探索 agent 完成本局(终局或中止)即停止操作、把画面收回大厅待命位、向编排者发单局报告(局账/取证发现/遗留/晶球余额),然后等待——**不获得多局连续授权**。局间处置=机械条件映射:报告有未闭环问题→转问题处置循环(§2.4);无问题且关注清单未全覆盖→判读批出下一局规划建议单,照抄续派;清单全覆盖→结束本线的窗口占用。为什么:局间机械步进 = 编排者控制进度的抓手,连续多局授权会让探索方向失控且局间新待办无法插入。
8. **最高难度默认**:实机探索局默认选择当前可解锁的最高难度——探索目标是暴露新版本问题(画面/机制/策略),难度压力越大暴露面越广,低难度局验不出策略与经济模型的压力面。若最高难度不可达(未解锁/条件不足),如实报告当前可达难度与解锁路径,编排者记档进关注清单,解锁后再探索最高难度。新版本初未达最高难度属常态:随解锁逐步上难度,难度选择写进每局任务书。

## 4. 阶段二:流程框架适配期

### 4.1 目的与退出判据

- 目的:把阶段一的识别成果与动作 op 接入 bot 自动流程(app)——对局由流程框架自主推进,不再靠 agent 逐帧代理操作。
- 优先事项:app 自动流程跑局循环——「跑一局→暴露缺口→修→再跑」。
- 策略无关性:本阶段策略质量不设标准(可以坏、可以随机乱选)——流程框架的验证看「对局推进与缺口收敛」,不看胜负与成绩;对局成绩与策略调优是阶段四的事(§6)。
- 退出判据:app 自动流程能稳定打完整局(端到端不卡死)→ 进入阶段三(§5)。

### 4.2 验证载具与工作节奏

- **验证载具 = app 自动流程跑局**:经项目 MCP 工具发起 run_standalone_app(货币战争);一次 run 一局,run 结束即停——与阶段一「一局一停」同型,载具不同;逐局发起,不获多局连续授权(局间机械步进的理由同 §3.3 第 7 项)。
- 跑局暴露存量识别/建档/流程缺口 = 常态,暴露即覆盖工作在生效,逐条登记(§4.3)后继续;连续两局零登记 = 覆盖审计过期,回审覆盖审计清单后再继续。
- run 卡死/中途停止 → 按 §2.3 停止操作汇报纪律处置,走 §2.4 问题处置循环;run 跑完但暴露读数/行为缺口 → 不停线,按 §4.3 登记缺口后继续下一局。

### 4.3 缺口分诊与修复路由

- 按缺口类型路由:
  - 识别缺口(建档过期/OCR 能力不足/模板缺失)→ 画面建档与识别修复走 od-dev-screen-onboarding;
  - 流程缺陷(重试语义/分发接线/循环结构)→ 小修复批(线内单点修复攒批实现与验证,每条带「改哪+判据」);
  - 机制缺失(动作 op 缺失/机制建模缺)→ 立线走 od-dev-run-iteration(迭代形态按挂账条目的改哪与判据是否逐字可指,口径见 §6.2)。
- 缺口记账:暴露的缺口逐条登记跨迭代挂账文件(定位见 SKILL.md §3「跨迭代挂账」行),条目写明「改哪+判据」;修复批从开放条目取活逐个清偿,完成即删(登记与删除纪律见 §2.5)。
- 根因不明的缺口先走 §2.4 处置循环(诊断 agent 定位)再归入上述路由;修复改运行时代码的,重启窗纪律按 §7 第 4 项。

## 5. 阶段三:投资策略/环境 sim 适配期

> 本节先立骨架:进入本阶段时按当期需求就地细化本节(阶段模型落地后本文不再整体重写,各阶段节就地维护)。

### 5.1 目的与退出判据

- 目的:投资策略与环境效果在 sim 里建模到位——sim 局与实机局跑同一套循环/op/策略只换环境(SKILL.md §1.3 铁律),环境面失真会直接污染阶段四的策略结论,故先对拍再开工策略线。
- 优先事项:sim 与实机对拍。
- 退出判据:sim-实机对拍一致 → 进入阶段四(§6)。

### 5.2 方法单一源

- sim 测试方法单一源 = [sim-testing.md](sim-testing.md)(sim 能信什么/找问题三步/种子段分配纪律/单局复盘素材采集);本节不复制其内容,进入本阶段时以「先知道边界」节为对拍口径基线。
- 对拍差异的处置:走 §2.4 处置循环分诊,缺口登记跨迭代挂账文件(§4.3 同口径)。

## 6. 阶段四:策略实现适配期

### 6.1 目的与退出判据

- 目的:真实策略代码迭代——阶段一至三的产物(画面档/动作 op/自动流程/sim 建模)是既有地基,本阶段在其上做策略实现与调优;策略工作的方法主线与验证阶梯 = strategy-work(分诊表「改策略/迭代算法」行),本节不复制。
- 优先事项:策略线(线型见 §6.2)。
- 退出判据:策略成绩达标——达标口径由用户判,编排者不自判。

### 6.2 线型三类

- **策略迭代线**:完整生命周期(设计→循环对抗→实施→实机验证→正本更新→收口);探索段跳段判据=设计开工前确认本线目标面已被既有探索产出覆盖,逐条指认出处才跳(覆盖审计缺口矩阵的已覆盖格/知识文档结论/画面档,覆盖审计口径见 version-update-live-exploration.md「覆盖审计」节)——指认不了按完整生命周期走探索;阶段一的探索产出通常已满足。
- **挂账修复线**(跨阶段常驻支线,§1;任何阶段都可立,不只本阶段):多为小迭代(单点修复+判据机械+不触核心面);挂账条目的改哪与判据逐字可指=可走最小形态——设计一页+任务一行,门一个不少。
- **知识文档线**(跨阶段常驻支线,§1):纯文档迭代,无实机段。

### 6.3 推进模式与设计批规范路径

- 推进模式:缺省串行(恒定口径与并行启用口径见 §7 第 1 项)。
- 设计批规范路径:策略迭代线按 od-dev-run-iteration 走双层文档流——迭代目录 = `.temp/changes/active/<立项日期-主题>/`,正本区 = `docs/develop/sr_od/application/currency_war/`。

## 7. 领域叠加件(通用 skill 的 CW 映射)

通用层机制自含完整默认形态,本节只写 CW 的映射与增量(分层边界见 od-dev-agent-autonomous-mode 的 design/overview.md「边界」节:领域操作归领域 skill):

1. **推进模式映射**:CW 自主推进各阶段=串行模式(游戏窗口与 MCP server 单跑道,独占资源天然串行——并行度取值恒为 1)——本领域缺省串行,用户当次明示并行时按通用层取值序生效(实机与 MCP 单跑道的互斥由占用表把关,不随线数放宽);公共 skill 未提供并行启用判据的领域定义位,本领域亦不定义,要开并行由用户当次明示。
