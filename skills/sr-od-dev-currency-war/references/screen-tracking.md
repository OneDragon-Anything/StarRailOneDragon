# 画面识别与动作 op 的追踪文件

> 定位:货币战争的长期追踪目录里的一份记录文件。它按画面分章,记三样:这个画面的识别最近一次核对是什么时候、结论是什么;画面上每个该有动作 op 的动作有没有动作 op、最近一次用着正常是什么时候(判不准、后来判了不用做的动作也记一行;某一次实际用了什么,记在单局报告里,不记在这里);这个画面还有哪些缺口。
> 动作 op(本文件和 exploration.md 的叫法)= 实机探索 agent 能用 run_operation 单独调用的一次动作。开发 skill 入口文件 §1.2 按代码目录把给 agent 单独调用的叫「动作原语」、把一条龙内部用的叫「动作 op」,那是讲代码怎么分层;这里只看能不能单独调用。新做一个动作 op 该放哪一层,按 od-dev-write-operation。
> 读者:登记它的编排者,查它的实机探索 agent 和修复线。编排者、实机探索 agent、修复线、单局报告都是 [autonomous/orchestrator.md](autonomous/orchestrator.md) 里的叫法;实机探索 agent 的工作方法在 [autonomous/exploration.md](autonomous/exploration.md)。同目录另一份文件(待跟进事项)的条目怎么写,见 orchestrator.md §2.5。

## 1. 文件在哪,怎么用它

- 路径:`.temp/tracking/currency-war/画面识别与动作op.md`。它不在版本控制里,会话结束了也留着。
- 怎么用:打到哪个画面,读哪一章,不通读全文。按画面名找二级标题,只读那一章。
- 文件不存在 = 还没有核对过任何画面。第一次登记时新建,文件头照 §2 写。
- 换了客户端版本:编排者在文件头「记录对应的客户端版本」下面加一行,写新版本号。旧记录不删。之后每个画面第一次被打到时,识别核对照常做,日期会更新成新版本下的日期。实机探索 agent 先发现的,写进单局报告的「遗留」,报给编排者。不在自主推进里的时候,谁先发现谁加。

## 2. 格式

文件头:

```markdown
# 画面识别与动作 op(货币战争)

> 打到哪个画面,就看哪一章。没有章的画面 = 还没核对过。
> 记录对应的客户端版本:v4.7。
> 怎么记:开发 skill `sr-od-dev-currency-war` 的 references/screen-tracking.md。
```

一个画面一章。一章有三样:识别核对一行、动作一栏、缺口小节。下面是一章完整的样子(日期和报告文件名是示意):

```markdown
## 货币战争-备战-开商店

- 识别核对:2026-11-24,一致。
- 动作:
  - 买牌(`CwBuyShopCardBySlot`):2026-11-24 用过,正常。
  - 买经验(`CwBuyXpRepeat`):2026-11-23 用过,正常。
  - 刷新商店(`CwRefreshShopByClick`):2026-11-24 用过,正常。
  - 收店(`CwToggleShopPanel`):2026-11-24 用过,正常。
  - 卖备战席角色(`CwSellBenchBySlot`):还没用过。
  - 免战跳过(鼠标点击):还没用过。
  - 商店锁定(不用做动作 op):2026-11-26 判,一条龙的代码不点它。

### 缺口

- 动作 op:「免战跳过」这一步该有动作 op、还没有,操作表里写的是鼠标点击。2026-11-24 发现。证据:match-3-1.md。状态:等修复线。
```

识别核对对不上、缺口是另外两层时,识别核对那一行和缺口小节这样写(还是示意):

```markdown
- 识别核对:2026-11-24,有不一致,见下方缺口。

### 缺口

- 画面识别:标题下方的数字读成「S0」。2026-11-24 发现。证据:match-4-1.md。状态:等修复线。
- 画面建档:各费用档的出现概率没有建读数区。2026-11-24 发现。证据:match-4-1.md。状态:等修复线。
- 画面建档:按钮「详情」没有建 area,要等这个画面出现第二槽已解锁的形态才能建。2026-11-25 发现。证据:match-5-1.md。状态:等现场再现(等这个画面出现第二槽已解锁的形态)。
```

缺口小节没有缺口,写一行「- 无」。

记法:

- **章**:画面名用玩家 skill 入口文件(SKILL.md)「各阶段与画面的处理方案」列表里的名字。列表里二级缩进的子画面,也各算一个画面,自己一章。新章插在哪,跟着那个列表的顺序。
- **识别核对**:把 MCP 画面识别(analyze_screen)返回的画面名和读数,和自己看截图读出来的逐项比。对得上写「一致」。有对不上的写「有不一致,见下方缺口」,并在缺口小节写一条「画面识别」。
- **动作一栏**:只列该有动作 op 的动作,一行一个。该不该有,按 [exploration.md](autonomous/exploration.md) §3.2 的三个问题判;只是看的动作不列。动作名用玩家 skill 画面文档「操作」章里这一步的名字(表格用「目标」一栏,编号列表用每条开头的短语);操作章里没有这一步的,用单局报告里写的名字。操作章加了一步、删了一步,或者某一步该不该有变了,动作一栏跟着改,谁来改见 §3。三个问题判不准、后来判了不用做的,也记一行;别的判过不用做的不记。
- **动作名后面的括号**写操作章给这一步指定的做法:op 写类名;用鼠标的(点击、拖拽)都写「鼠标点击」。括号只表示这一步有没有动作 op:是 op 名 = 有;是「鼠标点击」= 该有、还没有。这一次实际用了什么,记在单局报告里,不改括号。括号里是「不用做动作 op」= 这一步判不准、后来判了不用做;冒号后面写判的日期和理由,不写使用日期。「鼠标点击,未判」= 这一步还没判过该不该有,是旧记法转过来时留下的;读到它怎么办,见 [exploration.md](autonomous/exploration.md) §3.3。
- **日期**:只留最近一次照括号里的做法做、并且正常的日期,抄单局报告第 11 节写的报告日期。这一局用着不正常的,日期不改,问题写进缺口小节。还没用过的写「还没用过」。
- **缺口小节**:一条写四样——缺什么、发现的日期、证据、状态。缺什么的开头先写它属于哪一层,三层:画面建档 / 画面识别 / 动作 op;还没查出属于哪一层的,开头写「待查原因:」,查出来以后改成那一层。证据 = 记着这件事的单局报告或验证报告的文件名。动作一栏里括号是「鼠标点击」的,这里要有一条「动作 op」;括号是「鼠标点击,未判」的不用。
- **缺口的状态**五种,都写在这一行里,不转登进别的文件:
  - 等诊断(报了要查原因的问题,诊断报告还没到);
  - 等修复线(该立修复线,或者已经有修复线在跟——包括动作 op 已经做出来、等实机验证。已经有线在跟的,括号里写线名,比如「等修复线(货币战争-备战-开商店)」:同一条缺口再报上来,靠它找到那条线);
  - 等现场再现(括号里写卡在什么条件上。现在探不了的,实机探索 agent 再报到它、或者等的外部条件变了,改回「等修复线」。开头是「待查原因」的,是没诊断完的问题:再遇到就停下,现场留给诊断,状态照诊断报告改);
  - 等用户裁定(登记过待裁。裁定要修的,改回「等修复线」,立线或并线的办法见 orchestrator.md §5.3 第 2 步;裁定不修的,改成「不修」);
  - 不修(用户裁定不修,括号里写裁定日期。再报上来不派活)。
- **缺口修好并且实机核实以后**,当场删掉那一条。
- **只写日期和结论**:核对了哪些内容、动作具体怎么做,定义在画面文档和画面档里,这里不复述。
- **不预先建章**:第一次核对哪个画面,才建哪个画面的章。没有章的画面不算缺口。

## 3. 谁在什么时候写

| 什么时候 | 谁写 | 写什么 |
|---|---|---|
| 实机探索 agent 交了单局报告以后 | 编排者 | 照报告第 11 节「画面核对」更新到过的画面;照「缺口」「未闭环问题」写缺口。步骤见 [orchestrator.md](autonomous/orchestrator.md) §5.4 |
| 要查原因的问题,诊断报告到了以后 | 编排者 | 按诊断报告「处置建议」的第 5 样,改对应那几条缺口的状态。见 orchestrator.md §2.4 第 2 步 |
| 登记过待裁的缺口,用户裁定以后 | 编排者 | 照裁定改状态:要修的改回「等修复线」;不修的写「不修」(§2) |
| 修复线的实机验证达标以后 | 编排者 | 删掉修好的缺口;验证时正常的动作、一致的识别核对,日期改成验证那天。见 orchestrator.md §6.6 |
| 修复线做出新的动作 op,编排者重启 MCP server 以后 | 编排者 | 照实现报告:动作一栏里这一步,括号里改成新 op 的类名,日期写「还没用过」;动作一栏里没有这一步的,加一行。见 orchestrator.md §6.7 |
| 修复线判了一步不用做动作 op;用户裁定某一步不用做 | 编排者 | 照探索报告或者用户的裁定:动作一栏里给这一步加一行(原来有这一行的,改括号),括号写「不用做动作 op」,冒号后面写判的日期和理由;对应的缺口删掉。见 orchestrator.md §6.8 |
| 玩家 skill 的操作章加了一步、删了一步,或者某一步「用什么」变了 | 编排者 | 照改操作章的那份报告,或者单局报告「遗留」里写的「括号和操作表对不上」,动作一栏跟着加一行、删一行、改括号 |
| 用户叫停 | 编排者 | 叫停时改什么,见 orchestrator.md §7.1 |
| 不在自主推进里,编排者以外的会话在实机上核对过某个画面、用过某个动作 | 做核对的那个会话 | 照 §2 写 |

## 4. 什么不记在这里

- 画面建档、画面识别、动作 op 三层的缺口记在这里,不管是哪个场景、哪条线发现的。
- 别的待办记进同目录的 `待跟进事项.md`:流程缺陷、机制缺失、要等实机取证的机制问题、等用户裁定的家族级议题。
- 缺口卡住了(现在探不了、等用户裁定),只改这条缺口自己的状态(§2),不转登进 `待跟进事项.md`。
- 等用户裁定改不改知识文档的发现,记进待裁知识队列(orchestrator.md §5.6),不在这里。
- 玩家 skill 的指引不够用的地方,记进同目录的 `玩法指引的不足.md`([exploration.md](autonomous/exploration.md) §6.4),不在这里。

## 5. 边界

- 为什么长期保存、为什么任务书只带路径:design/overview.md「动机记录」。
- 任务书里怎么给路径:orchestrator.md §4.3。
- 哪些动作该有动作 op、有了没有怎么判断:[exploration.md](autonomous/exploration.md) §3。追踪文件里这一章的动作一栏只列该有的,和判不准、后来判了不用做的:括号里是 op 的名字 = 有;括号里是「鼠标点击」= 该有、还没有;括号里是「不用做动作 op」= 判不准、后来判了不用了。

## 6. 旧记法的条目怎么读、怎么转

### 6.1 按旧记法写的待跟进事项条目怎么读

待跟进事项文件里按旧记法写的条目,分节存放、每一节自己编号、多数没写状态标签。

- 条目里写着等实机确认、等实机逐局顺带这类说法的,都算「等实机取证」;写着等外部条件的,算「等外部条件」。
- 它的编号在全文里不唯一,引用时写「节.号」(比如「一.11」)。
- 编排者第一次改到某一条旧条目的时候,给它补上状态标签。编号不动:追踪文件和别的登记正按这些编号引用它,重排会对不上。

### 6.2 状态引用着待跟进事项的旧条目怎么读、怎么转

追踪文件里状态写着「已登记待跟进事项(…)」、括号里是待跟进事项编号的缺口,是按旧记法记的:卡住的条件写在待跟进事项文件里那个编号的条目上(旧条目的编号写「节.号」)。

- 怎么读:要看它卡在什么条件上,读待跟进事项里那一条;那一头的状态标签就是它现在的状态。
- 怎么转:编排者第一次改到这条缺口的时候(照单局报告更新、诊断报告到了、用户裁定以后),先转成现行记法再改。照待跟进事项里那一条:
  - 标「等实机取证」「等随机遇到」「等外部条件」「等现场再现」的,状态写「等现场再现」,条件抄进括号;后面写着「卡在用户叫停」的,状态写「等修复线」;
  - 标「等用户裁定」的,状态写「等用户裁定」,待裁登记里没有这一条的补登记一条;
  - 证据缺的从那一头抄;
  - 那一条是专为本条缺口登记的(条目里抄着这条缺口的原文),转完删掉;别的条目不动。
