# 恢复局机制重整（每次运行重建 + 开局方式事实化）迭代设计（总纲）

## 0. 元信息

- **迭代目标**：删掉恢复局三字段状态机的「跨运行记忆」职能，重整为「每次运行从干净状态开始 + 开局方式事实化 + 探针接管局必裁」——消除挂账板 §二.7⑥ 的两个失活场景，顺带删字段。
- **用户裁定集（2026-11-19 讨论，本设计的规范来源）**：
  1. **接管是最佳情况，不分模式**：残局（重跑遇到的半途局）一律接管；接管靠画面探查 + 补采（现有备战特殊逻辑本职），**能补多少补多少，补不到就算了**；
  2. **接管不靠记忆**：不记录之前的信息，每次运行从画面重新认识局面；
  3. **每次运行都应该重建**（Match）；
  4. **停点分模式**：`is_debug=True` 停屏等诊断（维持现语义）；False 弃局重开（走交接批退出交接回大厅重开）；
  5. **挂起局弃局重开**维持既定语义（模式选择-进行中 → 委托退出 op → 回大厅重开）；
  6. **debug 判断用框架现成的** `env_config.is_debug`（不自造模式字段）。
- **关联账**：挂账板 §二.7⑥（本批销账目标）；§二.7⑦ `_snap`（无关，不在范围）；交接批 design §2.6（max_rounds「非退出触发」语义按裁定 4 修订，随本批）；loop→exit 交接批正本（loop.md §6 出口表 max_rounds 行随批订正）。
- **状态**：草案（待对抗审）

## 1. 问题与动机

### 1.1 现状机制与两个失活场景（挂账 §二.7⑥）

恢复局检测现状 = `CurrencyWarMatch` 流程态三字段动态状态机（`is_new_match` / `resume_probe_pending` / `locked_resume`〔+`locked_round` 遥测、`locked_sync_done` 配对证据位〕），写入节奏 per-run（loop `handle_init` 每次 execute 重判/重置），裁决链 = 备战画面 op b 查（候选过判 → 探针点击商店验可开性 → 锁定确认/撤回）。失活场景：

1. **跨 run 重入锁定帧**：上次运行探针确认锁定（`locked_resume=True`）后未走完即停；同进程重跑 → `handle_init` 重置 `locked_resume=False` → 第 0 查失活 → 常规链发商店动作 → 点击落空空转至哨兵。**已确认的裁决结论不能跨运行存活，重跑等于白确认**。
2. **停点命中后再跑探针永久失活**：停点停在备战屏 → 同进程再跑 → `was_new=False`（容器续用）→ `resume_probe_pending=False` → 探针永不触发。

**病根**：「每换工人重写这一栏」的重置节奏，把**已确认的局级事实**（这局是残局——客观不变）也当 run 级状态抹掉了。修补方向（字段跨 run 存活/分层生命周期）都要在动态状态机上继续加约束；本轮讨论裁定走重整路线（§2）。

### 1.2 调查补充的接管全景（2026-11-19，重整判据的事实基础）

进入对局的全部路径与现状处置：

| 路径 | 画面序列 | 现状处置 | 新局/接管 |
|---|---|---|---|
| 大厅点开始 → 无保存局 | 难度确认 → 简报 → 投资环境 → 备战 | 正常新局链；三屏 = 新局确凿信号（`_discard_stale_once` 弃旧建新） | 新局 |
| 大厅点开始 → **有保存局** | 「继续进度」弹窗 → 直达备战 | 点掉弹窗推进；旧容器合法续用 | **接管**（游戏保证同一物理局，信息最全） |
| 大厅点开始 → **挂起局** | 模式选择-进行中 | 委托退出 op 结算回大厅 → 重开新局 | 弃局重开（既定语义） |
| 半局直撞 | app `_in_match` 命中，跳过入口链 | loop 兜底建容器 → 探针裁决 | 接管 |
| 残留大厅 | 死按钮态 | 关X + F 重进新鲜大厅 | — |

游戏锁定语义（`cw_resume_lock.py` 实测申报）：进过战斗后游戏 exe 异常退出重进继续该局 → 备战屏锁定「只能出战」（商店按钮零响应）。锁定唯一可观测特征 = 商店可开性 → 探针（识别性点击）是唯一裁决手段。

### 1.3 「新局 vs 接管」的判定信号（重整核心，替代内存字段）

**游戏流程自己会说**：新局链专属画面（难度确认/模式选择/简报/投资环境）出现 = 新局；没经过这些画面就到了备战（继续进度直达 / 半局直撞 / 停点重跑重建）= 接管。判定落成 `opened_via` 开局方式事实字段（§2.2），**建立时一次写入、运行内不变**——不再是动态状态机。

新局永不探针（游戏锁定的前提是 exe 异常退出重进，自己开局的新局不可能锁）；接管局必探（含继续进度路径——游戏 exe 重启过的保存局可能带锁）。

## 2. 方案

### 2.1 语义收敛表

| 场景 | 重整后处置 |
|---|---|
| 正常开局（入口链见过新局画面） | `opened_via=new_game`，永不探针，正常打 |
| 接管局（直撞/继续进度/停点重跑重建） | `opened_via=takeover`，首个备战相位探一次：锁定 → 出战接管；非锁定 → 带缺口正常接管（补采照旧，补不到算了） |
| 挂起局（模式选择-进行中） | 弃局重开（既定语义不动） |
| 停点（跑满 max_rounds） | `is_debug=True`：停屏等诊断（留局，采样照做）；False：弃局重开（走 `CwEntryExit` 退出交接回大厅 → 重开新局） |
| 接管局停 1-1 备战 | 照常探针（不省点击——判据最少优先；无锁则探针必「可开」走常规，结果正确） |

### 2.2 字段收敛

**新字段**（宿主不变 = `CurrencyWarMatch` 流程态区，传播路径不变 = `ctx.cw_match` → `CwScreenPrep` 读）：

- `opened_via: str`（`'new_game'` / `'takeover'`）——**容器建立时一次写入**：入口链新局确凿信号处（`_establish_match_once` 调用点）建 → `new_game`；loop `handle_init` 兜底建 → `takeover`；继续进度直达备战不经建容器段 → 同走兜底建 → `takeover`（探针覆盖，锁定检得出）。

**删除**：

- `is_new_match`——「新局/续局」判别职能由 `opened_via` 承接；消费方（SettlementState 新局标记注入 / 战斗帧恢复检测门 / 恢复候选判定输入）逐个迁移（§2.5 盘点）。
- `resume_probe_pending`——探针门改为 `opened_via == 'takeover'` ∧ 本次运行未探（去重标志，§2.3）。

**保留（降格为本次运行内工作态，申报语义变化）**：

- `locked_resume`——锁定确认后的多帧直达标志（确认 → 出战段直达 → 出战成功解除）。运行结束随容器重建作废，不再有「跨运行记忆」期望。
- `locked_sync_done`——出战同步步证据位。配对不变量（与锁定确认/发出核同帧配对写）是否可随「必裁」简化，设计阶段核对 `prep_actions` 发出核读侧后定；初版倾向保留不动（改动面控制）。
- `locked_round`——遥测对照用，随锁定确认写入保留；是否并入 `locked_resume` 场景由落地定（纯遥测字段，去留不涉行为）。

### 2.3 探针裁决链重构（`CwScreenPrep` 段1 b 查）

- **触发门**：`opened_via == 'takeover'` ∧ 本次运行该容器未探过（去重标志一次写，替代 `resume_probe_pending` 的挂起/撤回两态翻转）。`new_game` 永不进探针分支。
- **裁决流程保留**：候选过判条件（`resume_candidate` 纯函数）保留轮次/位面输入作**裁决记录**用途还是删除，落地时定——初版倾向保留（轮次读数进遥测，判据本身不再门控触发）；探针点击（商店可开性）与 `probe_resolve` 两分支结论不变。
- **裁决处置**：锁定 → `locked_resume=True` 直达出战段（现状链）；非锁定 → 收店恢复 → 常规接管（heavy 观察 + 接管补采照旧，信息缺失接受）。
- **接管失效写**（`_invalidate_tracked_on_takeover`）：现状挂在「候选过判即写」——重整后挂「探针分支进入即写」（接管局必经），时点语义不变。

### 2.4 每次运行重建的落地

- **语义**：loop `handle_init` 每次执行时，容器若是**本次运行开局所建**（入口链建，`opened_via=new_game`）→ 保留；否则（残留自上次运行 / 不存在）→ 弃旧建新（`takeover`）。
- **「是否本次运行开局所建」判据**（实现候选，设计阶段定稿）：候选 a = 容器记建立时 run 归属（比对当前 run）；候选 b = 入口链建容器时置一次性标志（app/ctx 运行内存活，天然 per-run）。倾向 b（不引 run 比对，标志天然运行内）。
- **正常流不受影响**：一次运行 = 入口链建容器（new_game）→ loop handle_init 见「本次运行所建」→ 保留 → 跑局。异常重跑 = 上次运行容器残留 → 重建（takeover）→ 探针接管。两个失活场景推演消解：场景 1（重跑重建 → 必探 → 锁定重裁决 ✓）；场景 2（停点后再跑 → 重建 → 必探 → 商店可开 → 常规接管续打 ✓——停点局重跑从「探针失活」变「正确接管」，且信息缺失按裁定接受）。

### 2.5 消费方盘点清单（设计内逐项落地，此处登记入口）

- `is_new_match` 消费方：SettlementState 新局标记注入（`handle_init`）/ 战斗帧恢复检测门 / `resume_candidate` 输入——逐个改 `opened_via` 判据或删；
- `discard_stale_match_container`（新局确凿信号处弃旧防线）：与 §2.4 重建的分工——入口链信号处弃旧（三屏出现时，入口链发起）+ handle_init 兜底重建（非本次运行容器），两道不冲突（发起方不同、时序不同），防线保留；
- `cw_game_state` 接管相关面：`prep_substate` 四档注释（「恢复锁定」档零现役写入方——随本批复核归档）、接管失效写锚定字段、接管补采编排——语义不变，注释宿主名随字段改名同步；
- 交接批 design §2.6 + 正本 `loop.md` §6 max_rounds 行：停点语义按裁定 4 修订（`is_debug` 分叉）；
- 停点弃局重开的衔接：停点出口（日常模式）→ `round_success` 交 app → 交接节点按异常交接形态调 `CwEntryExit`（复用交接批机制，零新机制）——app 三形态判定表 max_rounds 行按模式分叉修订。

### 2.6 测试面（概要，landing 细化）

- 字段收敛回归：`opened_via` 三路径写入断言（入口链新局 / loop 兜底 / 停点重跑重建）；
- 探针触发门：`new_game` 永不探 / `takeover` 必探一次（去重）/ 探针两分支结论（锁定出战 / 非锁定常规）；
- 两个失活场景的回归用例（重跑重建后锁定重裁决；停点后再跑探针照跑）；
- 停点分模式：`is_debug` 两分支（halt 交回 / 弃局走交接）；
- `locked_sync_done` 配对不变量（若保留）既有断言不回归。

### 2.7 sim 面

- sim 直驱 loop（不经入口链）→ 容器由 sim 驱动器/handle_init 建立 → `opened_via=takeover`？——**注意**：sim 局是完整新局，若标 takeover 会误触探针分支（sim 识别面下探针点击行为待核）。落地时核 `establish_new_match` 的 sim 调用方（cw_strategy_manager 直建路径）补 `new_game` 打标或 sim 驱动器显式传参。**此项为已知落地面，勿漏。**
- sim 决策确定性 → 探针分支在 sim 全量回归中的可达性 = 0（新局标 `new_game` 后），既有 sim 回归零影响。

### 2.8 关键取舍

1. **重整而非修补**：字段跨 run 存活/分层生命周期都是在动态状态机上加约束；重整把「跨运行记忆」职能整体删除，用流程事实字段（一次写入）+ 画面驱动必裁替代——状态机复杂度净减。
2. **接管优先，补不到算了**：不做「恢复完整上下文」的执念；接管信息缺失 = 接受面（接管补采兜画面可观察部分）。
3. **停点 debug halt 保留**：验证模式采样依赖留局，`is_debug` 分叉零新概念。
4. **探针判据最少化**：接管局停 1-1 照探（不省一次点击），换触发门只看 `opened_via` 一个条件。
5. **`locked_sync_done` 初版不动**：配对不变量是发出核正确性约束，与探针触发门解耦；简化机会留给后续批（改动面控制）。
