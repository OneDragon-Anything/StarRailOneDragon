# 新玩法自动化开发 playbook(OneDragon 框架)

把「自主开发一个新玩法的自动化」拆成可复现的阶段。每阶段有判据,全程守「**看(analyze)→ 动(click/key/run)→ 等(sleep)→ 验**」循环。**别凭猜硬写** —— 凭猜只覆盖一种情况、漏另一种,必回归。

> 本 skill 是从「货币战争」自动化开发中提炼的**通用**方法论(试验场);遇新的可通用经验就往里加一条(增量维护)。

## 总流程(按序,每阶段达标再进下一个)

| 阶段 | 做什么 | 达标判据 |
|---|---|---|
| 0 | **先验现实约束** | 确认玩法常驻/限时、能实机、未过期 |
| 1 | **玩法建档(理解玩法)= 一切的起点** | 能口述机制 + 一局流程 + 决策点 |
| 2 | **找结构同构兄弟 + 读现有代码** | 找到可复用骨架,定下复用/丢弃清单 |
| 3 | **画面建档(核心环节)** | 每画面定识别方式(OCR/CV/YOLO)+ screen_info/模板 |
| 4 | **设计:范围 + 前置 + op 链 + 配置** | 定自动化范围/前置条件 + op 链 + 配置项 |
| 5 | **实现**:先零件后整体 | 每个零件单独 `run_operation` 实测过 |
| 6 | **验证**:串成 app 端到端跑 | `run_standalone_app` 跑通 |
| 7 | **策略设计**(若有决策) | 客观指标 + A/B,迭代到目标胜率 |
| 8 | **事件长尾**:遇预料外补逻辑,循环到稳定 | loop 覆盖已知全部事件类型 |
| 9 | **测试 + 文档 + 成文** | ruff 干净 + sr-od-test + docs/game |

## 阶段 0:先验现实约束(最易漏)

钻机制前先确认这个**外部依赖**现在还在不在、能不能碰:
- 常驻 or 限时?限时玩法可能已结束 → 只能做"研究 + 骨架",**没法实机验证**。
- 能实机打开吗?(客户端版本、入口是否还在)
- 有无反作弊 / 锁光标 / 全屏独占等限制(影响 controller 能否操作)。

> 机制再懂,对象过期了也白搭。这是 agent 最容易跳过的「现实约束前置检查」。

## 阶段 1:玩法建档 —— 先理解玩法(一切的起点)

> 面对全新玩法,**第一件事是搞懂玩法本身(玩法建档)**,不是急着写代码。机制不清就自动化 = 给错误的流程写代码。

- **先搜官方 + 攻略/wiki**,理清:**类型**(肉鸽 / 自动战斗 / 手动 / 节点制)、**一局流程**、**决策点**(玩家在哪 step 做选择)、**自动 vs 手动**部分、胜负 / 奖励规则。
- **实机跟一遍**(或看视频):亲手把一局走通,边走边记每个画面的进入 / 退出条件 + 该画面"玩家要做什么"。这个**实操过程本身就是画面建档的开始(阶段 3)**。
- 输出:一段机制口述 + 画面清单(每屏:怎么进、怎么判定、怎么出、玩家在此做什么)。

## 阶段 2:找结构同构的兄弟,而不是从零设计

在 `src/sr_od/` 找一个**结构同构**的已有玩法复用骨架:
- 肉鸽推进 + 选择决策 + 自动战斗 → 参照 `sim_universe`。
- 体力刷本 + 配队 + 自动战斗 → 参照 `trailblaze_power`。
- 大世界寻路 → 参照 `world_patrol`。

**复用对的、丢掉不对的**(如节点制玩法用不上大世界 `move_v1/v2` 寻路)。看 `ApplicationFactory` 怎么注册、`SrApplication` 怎么编排 `Operation`、配置怎么走 `YamlConfig`。

> 面对 unfamiliar 玩法,杠杆是"在既有代码里找结构同构的兄弟"。比从零设计省一个数量级,也符合项目"先复用现有 Application/Operation 模式"的硬约束。

## 阶段 3:画面建档(核心环节)

> **画面建档是整个自动化流程的核心环节** —— 它决定每一步怎么识别、要不要 screen_info、要不要裁模板图,进而决定整个流程能不能流转。**画面建档 / 逻辑设计时,就该想好每一步要识别什么、用什么手段**(文字 → OCR;固定 UI / 图标 → screen_info + CV 模板;动态 / 稀有 / 多实例目标 → YOLO)。把各种**子态**都建档好,识别方式自然清楚,screen_info 和模板图也就知道怎么弄了。马虎建档 = 后面每步都在猜,回归不断。

> **主动把玩法的每一个画面都建档,不只是"op 当前要点哪"的画面(通用经验)**。玩法流程**经过**的每一个画面(入口 / 备战 / 各类事件选项 / 战斗 / 各结算子页 / 失败 / 大厅回归…)都要建档(画面 doc + screen_info area),**哪怕当下看不出它有什么用**。原因:**你是在建档 / 熟悉的过程中才逐渐明白每个画面的作用** —— 信息源、决策点、反馈信号往往在建档时(读三层:截图 / screen_info / 代码)才浮现;事前用"用不用得到"过滤,会漏掉后来才显价值的画面(典型:结算屏的阵容价值 / 总经济 / 伤害统计 —— 既是策略反馈信号又是 A/B 客观指标,但只在建档读数据时才意识到它的价值)。判据:**玩法流程经过的画面 = 都要建档**(每画面定识别方式 + 存 fixture),别只建 op 当前直接交互的画面。

判定"当前在哪个画面"是自动化的地基。优先级:
1. **文字 → OCR**(`analyze_screen` 的 `ocr_texts`,1080p 直出坐标)。OCR 关键词**选画面独有的**,别用会出现在多个画面的子串(如"羁绊"既在战斗屏也在大厅"羁绊链路"→ 误匹配)。
   - **⚠️ 中文关键词 LCS 误匹配(反复踩坑,2026-08)**:框架 `round_by_ocr` 默认 `lcs_percent=0.5`(LCS 最长公共子序列 / 目标长度 ≥ 阈值)。**中文关键词若与别的画面文字共享 2+ 字子串,就会在 0.5 误匹配** —— 不是"子串包含",是"子序列比例"。例(货币战争实跑):`选择伙伴`↔`请选择投资策略`(共享「选择」2/4=0.5)、`投资策略`↔`投资环境`(共享「投资」2/4=0.5,且两个都是合法屏 → 投资环境屏被先检查的投资策略分支吞)、`返回投资策略选择`↔`请选择投资策略`(共享「选择投资策略」6/8=0.75)。**症状**:loop 卡在某屏 round_wait 循环、handler 不触发(日志无子 op 执行)、或派发到错误 handler。**判据**:卡死 + OCR 明明有关键词但 handler 不跑 → 查 `round_by_ocr` 关键词是否与同屏/邻屏文字共享 2+ 字。**修**:该 `round_by_ocr`/`round_by_ocr_and_click` 调用传 `lcs_percent=0.7~0.9`(真匹配 1.0 不受影响,假匹配 0.5 被杀);或用更长/更独有关键词(如全标题「请选择投资策略」)。**别只改一个就收工** —— 同 loop 里所有中文关键词都可能踩,逐个审共享子串。
2. **固定 UI 元素 → screen_info**(写 `assets/game_data/screen_info/<screen>.yml`,pc_rect 坐标)。坐标怎么来见 skill `sr-od-dev-ui-region-detect`(稀疏独特找 vision、密集网格找 CV、文字找 OCR;vision 必须用原生 grounding 格式)。
3. **状态/选中/计数 → vision 兜底**,但 vision 的状态推理不可信,只信客观描述;坐标对错用数值对拍 ground truth。

**建档只写 docs + screen_info,别改 screen_info 原内容**(pc_rect 占位是待填不是坏数据)。详见 skill `sr-od-dev-screen-onboarding`。

**每个状态都建档 + 存 fixture(防回归地基)**:早期接触玩法**很多画面没见过** —— 每碰到一个新状态就:① 截代表图存 fixture(项目 test 目录 / `.debug/`);② screen_info 建该画面 area;③ 写针对该 fixture 的测试。**别凭 1-2 张图写整个流程** —— 一个流程通常有多种状态(不同子界面 / 事件选项 / 阶段切换 / 结算页…),只见过一两种就下结论 / 写代码,必然漏状态、回归不断。不认识的画面别猜,先 `analyze_screen` + vision 看清(vision 取坐标必须用原生 grounding 格式,见 CLAUDE.md)。

## 阶段 4:设计(范围 + 前置 + 拆 op + 状态机 + 配置)

- **先定自动化范围**:核心目标是**帮使用者完成大量游戏日常**(每日重复、量大的),其次才是极端复杂场景(成就 / 挑战 / 极限难度)。日常没稳之前别钻极端场景。
- **前置条件**:自动化可能有前提 —— 使用者需先解锁某玩法 / 完成某任务 / 达到某等级。把这些列清楚(写进 doc + 配置说明),别假设所有人一开始就能跑。
- 把一局拆成**可独立验证的 Operation**(每个 op 一个职责:一类画面 / 一类动作)。
- 主循环画成**状态机**:每轮读屏 → 按优先级匹配画面 → 分流处理。
- 配置(难度选择、策略开关、优先角色…)走 `YamlConfig` 子类 + GUI setting card(`YamlConfigAdapter`),别散落硬编码。

## 阶段 5:实现 —— 先零件后整体

> **激进拆成多个小 op,每个 op 只负责一个特定操作(一类画面 / 一个事件 / 一个动作),别写巨型 op(通用经验)**。工程化好的代码 = 很多个职责单一的小 op,而不是一个塞满分支的大 op。理由(前期尤甚):**按 op 执行(`run_operation '<op_id>'` 单独跑)能最快定位每一步的问题** —— op 粒度小,失败就锁在那一个 op 的那一步,修那一步、单独重跑该 op 确认、再往下走;不用每次跑整条 app 才撞到问题、再从一堆内联分支里猜哪步坏了。
> - **反例(别这样)**:主循环 op 的 `loop()` 里内联 N 个事件 handler(选择伙伴 / 巨星 / 遭遇 / 投资策略 / 结算…)→ 任一 handler 坏了,都得跑整局才碰到,且无法 `run_operation` 单独复现 → 只能靠实机手动 click 一步步试(慢、浪费)。正确:每个事件 = 独立 op(`HandleEncounterNode` / `HandleMegastar` / `HandleSettlement`…),主循环按画面分流 `run` 各 op;坏了单独跑那个 op 定位。
> - **判据**:op 的某个方法(如 `loop`)里 if-elif 分支 ≥ 3 个不同画面/事件 → 拆成独立 op;一个 op 超过 ~80 行 / 职责含"或"(买牌**或**选人**或**结算)→ 拆。
> - 拆完仍守「先零件后整体」:每个小 op 单独 `run_operation` 实测通过,再串成 app 主循环。

- 每个 op 单独 `run_operation` 实测通过,再串成 app。
- Operation 用 `@operation_node` / `@node_from` 编排状态机;`round_by_ocr_and_click` / `round_by_ocr` 做画面判定 + 重试。
- **TDD 从入口(逻辑先于运行时)**:入口流线性(大厅→…→备战),每步输入 = fixture、输出 = 检测/动作明确 → **先写 fixture 测试断言期望,再实现/改**。存量 op 先补**刻画测试**锁现状;新改先写期望测试再改。⚠️ TDD 锁的是**逻辑回归**(检测对 / 该点哪 / 纯函数),**锁不住运行时 bug**(click 时序被截图吞、MCP 异步、真机 OCR 抖动)→ 绿测试 ≠ 实机能跑,仍靠阶段 6 实机验。流程 op(跨多屏)用 `add_mock_screenshot` 喂**序列 fixture** 测整条推进。
- **每步实机验证**(短闭环:分钟级 跑→看→改→再跑)是快速推进的关键。
- **实现-测试流水线:写一个 op → 后台测 → 等待时写下个(通用经验,别串行干等)**:实现期不要"写完一个 op → 干等它测完 → 再写下一个"(串行浪费等待时间)。改成**写完一个 op 立刻 `run_operation '<op_id>'` 后台跑(`block=false`)测试它,趁后台测试的等待时间写下一个 op**;然后 `get_run_status` 查前一个结果,有问题就修、没问题继续往下。**实现与测试重叠,等待时不闲着**。
  - 判据:只要**跑道空**(无 op 在跑)且**有待测 op** → 立刻后台提交测试,自己转去写下一个;op 跑完(成功 / 失败)再回来收尾。
  - 约束:单跑道(同时只能一个 op 在跑)+ LLM 并发 ≤ 2;后台 op 期间**别再起第二个 op**(撞跑道报错),写代码 / 读文档 / 沉淀经验这些不占跑道的活随便做。
  - 配合「激进拆小 op」(上条):op 越小、单个测试越快、流水线越顺;巨 op 测一次耗时久,流水线优势发挥不出来。

## 阶段 6:验证 —— 串成 app 端到端

- `SrApplication` + `XxxAppFactory`(注册进 `ApplicationFactory`),`run_standalone_app('<app_id>')` 端到端跑。
- 跑通 = 能从入口走到结算回大厅,不卡死、不死循环。

## 阶段 7:策略设计(有玩家决策的玩法)

- **用客观指标衡量**(到第几轮 / 剩多少血 / 多少金币 / 激活几层羁绊 / 胜负),别凭感觉。
- **A/B 对比**(如"升等级 ×8 vs ×16")比直觉可靠;优化找**甜点**不是极端化。
- **"打不过"先精确诊断卡在哪一步**(警告?锁阵?出战禁用?被某个机制阻塞?),别笼统归因"策略差" —— 往往一个具体小动作(升等级 / 卖弱角色)就破墙。
- **策略要给配置口**(优先角色 / 阵营偏好 / 激进度),别写死,让使用者调。

## 阶段 8:事件长尾 —— 边玩边重构

肉鸽 / 多分支玩法**事件类型巨多**,没法一次写全。方法论:
- **loop 跑,卡在哪个事件,就读屏 + 加一个 handler,再跑。**
- 兜底:任何匹配不到的状态走 fallback(点空白 / ESC),避免死循环。
- 每跑深一点冒新事件是常态,别指望一次覆盖。

## 调试纪律:bot 卡死/失败 —— 先读日志,不够就补日志

bot 卡死 / 死循环 / op 失败时,**先读日志再动手**,别凭猜改或盲点坐标:
1. **读日志**(`.debug/sr_od_mcp/main_server.log`):看卡住时**实际 OCR 到什么、走到哪个节点、决策状态**(等待/重试/失败)。日志常直接暴露根因(OCR 没读到关键锚点 / 节点循环 / 命中错屏)。
2. **日志解释不了 → 工程缺日志,补日志**:若日志只记 OCR、没记「点了什么坐标 / click 是否成功 / 走了哪个分支」,就在**决策点补日志**(记 OCR 摘要 + 点击坐标 + click/分支结果)+ **临时存图**(`screenshot()` 落盘到决策点)。否则下次同样卡住还是黑盒,改了也不知道为什么好/坏 —— **不可观测 = 不可维护**。
3. **结合日志 + 搜/合理猜玩法**:日志给客观事实,玩法知识给假设方向(「会不会要多次确认」「会不会有前置条件没满足」「会不会是 bug#1 吞 click」),两者结合形成假设再验证。
- **反例(别这样)**:bot 卡住 → 不看日志,直接盲点坐标试,没成又换坐标 —— 既定位不了根因,改了下次还卡。

### 预料之外的画面 → 调研"怎么交互进来的" + 建档(通用经验)

bot 跑到一个**代码没预期 / 没 handler 的画面**(如点卡开出角色详情、误点进设置、过渡叠层)时,**别只 ESC/handle 掉它就完事** —— 先**调研"代码哪个动作交互进来的"**:
1. **回溯入口**:看日志/截图,定位**上一步代码点了什么**导致进这个屏(哪个 click/nav、点的是 UI 的哪个元素)。例:bot 点投资环境卡想选中,但点中了卡上的**角色立绘** → 游戏开角色详情(点立绘=查看角色,游戏通用交互)。
2. **建档该画面**:记**入口(从哪来:什么动作/条件触发)+ 出口(怎么回/推进)+ 为何出现**(游戏机制,如"点角色立绘=查看角色信息")。进 screen doc / insights,后续一见这屏就知道根因 + 代码怎么修(避开误触元素)。
3. **修代码不再误触**:根因是"代码的 click 落到了会触发别的交互的元素上" → 调 click 目标(避开该元素,点同卡的非触发区),或调整交互顺序。
- **判据**:遇未建档/未预期的屏 → 先问"代码上一步点了啥 → 落到哪个 UI 元素 → 游戏对该元素有什么交互" → 建档 + 改 click 避开。只 ESC 不调研 = 同样的误触下次还发生(黑盒)。
- 这是「事件长尾」的深化:长尾不只是"遇新事件加 handler",而是**搞清每个意外屏的入口链**(代码动作 → UI 元素 → 游戏交互),建档后从源头修(改 click 不误触),而非 endlessly 加 ESC handler。

### 自动化开发不确定性 → 开发时预留日志 + 截图开关(前期快速定位,验证后去掉)

自动化开发(game 交互)比普通软件**不确定性大得多**:UI 变 / 时序抖动 / 加载延迟 / bug#1 → **TDD 锁不住运行时问题**(TDD 只能锁纯逻辑)。故功能开发时:
- **关键决策点预留充足日志 + 临时截图开关**(OCR 摘要 / 点击坐标 / 分支结果 / 前后截图)→ **前期跑失败一次就能定位根因**,不用反复重跑猜。验证通过后**逐步去掉**(减运行时开销)。
- **初期接触玩法时尤其要堆满日志 + debug 截图(通用经验,信息密度论)**:**刚接触一个玩法、对机制 / 画面 / 时序理解最浅的阶段,每次实跑的"信息密度"必须拉满** —— 每个决策点(买 / 选 / 升 / deploy / 事件分支)都记:OCR 到什么、评估了哪些选项、选了哪个、为什么、点了哪、结果如何,关键分支**存 debug 截图**。目的不只是"失败时定位根因",更是**让一次实跑暴露尽量多的问题**(策略漏洞 / OCR 误读 / 坐标漂移 / 漏事件),而非每次只测一种情况 —— 否则「跑一次只为找一个问题」极浪费时间,且很多问题要跑很多次才偶然碰到。**判据:实跑后看日志就能复盘整局每个决策点发生了什么**(不用重跑猜);做不到 = 日志不够,补。这条与「用真实策略实跑」配合:逻辑越真(非占位 naive)、日志越全 → 一次跑暴露的问题越多、越接近最终形态。
- **等待时别闲着**:bot 跑/等加载/等刷新期间,**同时做别的事**(自检类似坑 / 预写日志 / 补画面建档 / 沉淀经验),别纯 sleep。
- 日志编码注意:Windows server stdout 可能用 locale(GBK)→ 日志 mojibake → 强制 UTF-8(`sys.stdout.reconfigure`)。

### 重复的手动操作 → 尽早建成 op(别手动重复)

开发/测试中**手动做了 2+ 次的导航序列**(如退出对局:Esc→放弃→结算3页→大厅;或进入某玩法入口),**尽早建成 op**(放 `operations/`,用 `run_operation` 一键调用)。好处:① 不用每次手动点 N 个按钮(省时省力);② 可复用(bot 刷开局/测试/回滚都用);③ op 有重试/超时/日志(比手动可靠)。判据:**同一个手动操作做了 2 次 → 第 3 次前建成 op**。

## 阶段 9:测试 + 文档 + 成文

- `sr-od-test/` 加测试(纯逻辑部分:策略评估、OCR 解析、数据类;fixture 截图 → 期望输出)。
- **测试覆盖具体画面,不只是纯逻辑**:每个 reader/op 测试用**真实截图 fixture**(每状态 1-2 张典型)断言具体输出;改 reader/解析前把所有相关状态 fixture 跑一遍 → 改完重跑 → **无回归才提交**。只测纯逻辑(无截图)防不住"某状态 OCR 读不到 / 读错"的回归。
- **TDD:测试前置**(见阶段 5):新 reader / op / 改 → 先写 fixture 测试再实现;改前跑、改后跑,锁回归。刻画测试(存量 op)+ TDD(新改)搭配 fixture 覆盖。
- `docs/game/gameplay/<play>.md` 写玩法 + bot 流程 + 踩坑。
- 改动同步 `docs/develop/`(若涉及框架)。

## 通用硬约束 / 框架级踩坑(遇过就记,反复发作)

1. **`before_screenshot` 会移鼠标 → 吞掉紧接的 click(bug #1)**:框架每个 op 轮次开始自动截图,截图前把鼠标移到角落;紧接的 `controller.click` 被游戏判成"拖拽"而落空。**症状:同坐标 op 点不中、手动 `click_game` 一发即中**。缓解:关键 click 前 `active_window()` + `sleep(0.5)` 让鼠标 settle,且 click 之间不要再截图。
2. **MCP click/key 异步**:立即返回但 ~1s 后才落地;`analyze` 前必须 `sleep ~1.5s`,否则截到点击前画面 + 乱导航。
3. **OCR 关键词选画面独有**(见阶段 3)。
4. **ONNX session 异步调用走 `gpu_executor.submit`**,别并发直调多个 session。
5. **配置生效**:server 启动时读进内存缓存,GUI 改配置 / 手改 yml / 改 op 代码都不自动跟随 → 经 daemon 重启 server 生效(客户端无需重连);只有改 MCP 元信息(增减 method / instructions)才需客户端 /mcp 重连。
6. **录屏走 MCP 后端**(`record_screen`,Session 1),别从服务会话(Session 0)Bash 起 ffmpeg(BitBlt 录不到交互桌面)。
7. **MCP server 日志默认 GBK → mojibake 不可读**:daemon 用 `subprocess.Popen(stdout=log_file)` 启 server,server 的 Python stdout 用 Windows locale(GBK)写 → 进 UTF-8 文件变乱码(op 名/OCR 全 mojibake,无法日志诊断)。修:server 入口(`sr_od/backend/entry/server.py` main)起手 `sys.stdout/stderr.reconfigure(encoding='utf-8')`。验证:`.debug/sr_od_mcp/main_server.log` 按 utf-8 能解码 + Read 工具显示正常中文。日志不可读 = 无法用「读日志」方法论诊断,优先修。

## 知识维护:边干边补

凡是文档没写、或与实际矛盾、而你在干活时又需要它 —— 就是知识缺口,补上:
- 能查官方文档 / 工具说明的 → **先查,别凭猜试错**(API / 模型用法 / 坐标系 / grounding 格式,查文档比反复试错快得多)。
- 能确定答案的 → 提议补进 docs(只补会重复用到的)。
- 确定不了的 → 问用户。
- **遇工具 / API / 模型行为反常,先查文档** —— 这条比任何具体技巧都重要。
- **游戏数据 / 描述 / 原生数值,优先官网(米游社)和游戏内(图鉴 / 词条)** —— 这些是权威源;只有"攻略 / 玩法技巧"这类主观总结才信第三方网站(bwiki / NGA / b 站)。原生数据别从攻略转手抄(易错 / 过期)。

## 证据纪律(验证 / 下结论别凭单点)

> 反复发作的坑:**凭单张截图 / 单次推断就下结论**,然后写进代码 / docstring / 文章,后来被多样本打脸。三条:

1. **验证 OCR 读取器 / 运行时行为,跨多样本,别凭一张图**:跑实机后先看 telemetry / 日志的**统计分布**(如 `grep -o '"<field>": [0-9]*' file | sort | uniq -c`),不要只看一两条或一张图。`analyze_screen`(全屏 OCR)和读取器里的**区域 OCR**(`get_ocr_result_list(rect=...)`)可能行为不一致 —— 前者命中不代表后者命中,要分开验(全屏命中是"该处有字",不等于"区域 OCR 读得到")。**异常值(garbage)是信号**:读取器读出明显越界的值(如本该是小整数的计数读成几百)= 误读,别忽略。
2. **逻辑推断也要交叉验证,别拿未证实假设当论据**:例"某读数不可能是 X,所以读到 X 必是 bug" —— 但可能有你没考虑的情况(对象根本没变化 / 处于你没见过的状态 / 你的机制理解错了);该用**客观佐证**(日志 / 结算数据 / 多样本)而非"我觉得不可能"。结论立在硬证据(诊断 + 代码流)上。
3. **写 docstring / 结论 / 文章前**分清"多样本观察到"还是"单次推断";单次的标"待核实",别写成既成事实。
