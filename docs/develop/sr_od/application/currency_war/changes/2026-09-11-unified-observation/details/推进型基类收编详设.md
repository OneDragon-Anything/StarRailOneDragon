# 推进型基类收编详设(CwProgressionScreenOp → CwScreenOpBase 只读/导航变体)

## 问题与约束

- 本篇辖域 = 阶段二:第二画面 op 基类 `CwProgressionScreenOp`(`_progression_base.py`)重挂 `CwScreenOpBase`;11 个子类(aha_equip_pick / consumable_overlay / emblem_detail_popup / interrupt_dialog / item_detail_popup / next_button / plane_detail / prep_locked_return / refresh_odds_popup / role_detail_overlay / shop_card_detail)零改动随之收敛。
- 总纲划给本篇的接口契约 = design.md §2.1-3(变体五段映射)、§2.2 契约 1-5。
- 硬约束:**空决策形态合同逐字保留**(`_progression_base.py` 模块 docstring 在案)——纯推进画面零策略器问询、零期望态、零决策行;节点预算 = 1 次推进 + 1 次重入裁决(`node_max_retry_times=2`);验证废除形态(重入锚不在 = 已离开本画面 → success;首发锚 miss = 误分发 → fail 交回);journal/决策帧留证归 dispatch 包装(`cw_loop._dispatch_screen_op`)不进基类。
- 子类覆写面(2026-09-11 grep 实测):11 子类仅覆写 `entry_ok` / `progress_once` / 类常量(`SCREEN_NAME`/`ENTRY_AREA`),**无 `handle` 覆写**——变体骨架是单一共享体,收编只需动 `_progression_base.py` 一个文件。

## 方案

### 1. 基类改挂

```python
class CwProgressionScreenOp(CwScreenOpBase):   # 原: SrOperation
```

- `__init__(ctx, op_name, screen_name=None, entry_area=None)` 签名不变;内部 `CwScreenOpBase.__init__(self, ctx, op_name=op_name)`(适配器位缺省 None),随后原有字段赋值原样(`_screen_name`/`_entry_area`/`_advanced_once`)。
- 子类构造调用(`super().__init__(ctx, ...)` 或 `CwProgressionScreenOp.__init__`)零改动。

### 2. 变体五段映射(handle 顶部分流 + 钩子缺省实现)

`handle` 顶部加装配点分流(表达式同总纲契约 1),缺省 None = 现役骨架逐位执行;`run_lifecycle()` 走五段,映射如下(每段 = 现 `handle()` 骨架对应半的转录,`_progression_base.py` :92-109):

| 五段 | 变体形态 | 现役骨架对应半 |
|---|---|---|
| observe | `entry_ok(self.last_screenshot)` 判定:miss + 未推进 → 早退 round_fail(误分发交回外循环重判);miss + 已推进 → 清旗标、早退 round_success(wait=1,重入裁决出口) | `handle` 锚 miss 两分支(:93-98) |
| reconcile | 空申报(空决策形态无对账面) | —— |
| decide | 空申报 = **本屏无策略消费**(B4 选项②原语义;不是缺省缺位,是合同声明) | —— |
| act | `progress_once()`;False → round_fail(推进动作未落地);True → 置 `_advanced_once`;免锚形态(空 `ENTRY_AREA` 且未覆写 `entry_ok`)→ 发出即 success 交回;否则 round_retry(wait=1) | `handle` 推进半 + 免锚分支(:99-108) |
| on_outcome | 无登记件(注册表缺席 = 零动作;推进型无 §6.4 收编面) | —— |

- 段迹:五段各留一字段名(基类 `_lifecycle_mark`),旧路径不写迹——与已迁屏同纪律。

### 3. 子类与消费面零改动论证

- 分流判据缺省 None → 生产恒走现役骨架(模块槽 `observation_source`/`action_sink` 生产不装配,`cw_game_ports` 安装协议);11 子类的 `entry_ok` 覆写(如 `consumable_overlay` 双锚其一形态)在两条路径同样被调用。
- 参数化子类先例(`CwScreenBattleWait(ctx, st, config)` 构造覆写口径,`_progression_base.py` :43 注)不受影响:构造签名链只经本类 `__init__`。
- 真 modal 红线类(`CwScreenInterruptDialog`:绝不点「放弃并结算」)承载在 `progress_once` 覆写内,零触碰。

### 4. 测试与锁面

- 新增结构锁(模板同构,`test_cw_obs_arch_event_screens.py` 四锁取结构锁一条):`CwProgressionScreenOp` 是 `CwScreenOpBase` 子类 ∧ 11 子类 AST 全量为其后代 ∧ `handle` 含分流判据表达式 ∧ 变体五段钩子在(observe 早退语义 + decide 空申报)。
- 既有行为锁(如仓库在册推进型锁)原样保绿——不改断言;若锁内 assert 基类直继 `SrOperation`(如存在),按「锁钉着已被新设计取代的旧语义」纪律先对照本篇与 重推锁语义,修锁须在报告对照表申报(测试纪律 7;锁红 ≠ 改动错)。
- L1 快速集(`uv run pytest sr-od-test/test/sr_od/app/currency_war -m "not slow and not legacy_baseline"`)全绿。

## 关键取舍

1. **变体重挂 vs 平行并存**(总纲 §2.3-1 同源,本篇落地面):重挂。平行并存使段迹/端口/on_outcome 机制面永久双源,11 屏永远在架构设计 §9 迁移面之外;重挂后变体 = B4「只读/导航屏变体」的落地形态,豁免清单消失(B4 选项②原文)。
2. **变体五段 decide 空申报 vs 预留策略口**:空申报。空决策形态是 已审合同(零策略器问询),预留口 = 悬置面;将来某推进屏长出策略消费时,按总纲 §2.1-2 规则改直迁全五段形态(届时是行为变更批,单独申报)。
3. **收编时机独立成阶段 vs 随阶段三**:独立成阶段(阶段二)。本篇单文件改动、判据纯机械,可与阶段一并行派工;先收编再让收尾屏(阶段三)按总纲 §2.1-2 规则选型时,变体形态已就位可对照。
