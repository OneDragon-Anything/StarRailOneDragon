# 效果域(effect inventory)

效果域 = 在场效果账本(`GameState.effects`,载体 `kernel/cw_effect_inventory.py::ActiveEffectInventory`):记录本局持有的持续效果,三源一账本(投资策略 / 投资环境 portal / 词缀,经 `source` 分源)。本篇管效果**怎么建模、怎么记账、怎么读**;逐张卡是什么效果(触发词怎么读、数值多少、发放走哪条分支)归注册表条目注释(`kernel/cw_investments.py::STRATEGY_EFFECTS` 等各源注册表),不在本篇。

状态容器字段与写入入口的通用规范见 [game-state.md](game-state.md);效果变化的落盘(不设专用域行,随快照行自带)见 [journal.md](journal.md) §6。

## 1. 声明式建模(核心骨架)

- **每张卡一条规格声明** `EffectSpec`:触发时机(trigger)× 持续期(duration)× 效果类别(category)× 机器人职责(duties,predict/respond),payload 承载数值。机制住 `cw_effect_inventory.py`(类型 + inventory 读写端),数据住 `cw_investments.py` overlay 注册表,两边同键空间构建校验防漂移。
- **新增卡 = 注册表加一行声明,接入点代码零改动**:事件接入点只按声明路由,禁写逐卡特判。「谁要记账」的声明单一源 = `EffectSpec.duties.track`。
- **同卡不叠加**:实例按规格键(spec id)唯一,无叠加合并逻辑(游戏保证一局拿不到第二张同名卡)。
- **构建层校验**:孤儿键 / id 与官方数据层漂移 / payload 与 category 不一致 / pending 条目缺保守支,任一命中 import 即炸(防登记笔误与数据漂移)。

## 2. 计数器模型

- 计数器统一**从 0 开始、单调递增、永不递减、永不重置**;驱动事件发生就 +1。
- 倒计时 / 剩余量 / 门槛 / 周期**全部在计算侧导出**(持续 N 节点的效果,剩余 = N − counter;每 N 次触发一次 = counter 整除判断),state 不存第二份——存了就会和算出来的打架。
- 现行载体以递减余期表示(`remaining_nodes`/`remaining_uses`),与单调 counter 语义等价(`remaining ≡ N − counter`),读取按等价式;无动态需求的纯静态 / 即时效果不建计数器。
- 效果需随实例携带的数值(负债额 / 存款余额 / 护盾量)= 实例内 `counters` 键值承载,不设独立 state 字段。

## 3. 写入面

- **账本自身的写法全走 inventory 方法**(登记 / 推进 / 计数 / 移除,不经 `observe()`/`write_logic()`)——全项目唯一以 inventory 方法域为主写渠道的域。
- **效果改写其他域字段**(金 / 免费刷新余额 / 容量)时,按被改域的写入口规则走,归属判据:**确定性两分**——效果结果可准确计算(确定公式 + 已知输入,含机器人自身操作引起的)→ 逻辑写;含概率 / 随机、结果不可预知 → 不建逻辑写入方,交观察收尾。
- **到期尾款禁直写金**:效果到期时的一次性发钱走观察覆盖兜底,禁在到期时点逻辑直写金币(防与游戏自发入账双计)。
- **登记 best-effort 不阻塞**:登记面失败只留证据不挡选卡主链;登记缺位的局,消耗端零动作、不虚构递减。

## 4. 读取面

- 查表读口 = `by_source`(按 source 分源)/ `first` / `counter`(按 `(spec_id, key)` 定点);账本对决策只输出在场事实与进展读数——哪些效果需要决策姿态响应,由规格声明的 duties 承载,读口不解释效果含义。
- **派生值按「何时被问」归位**:随事件必须落账的(计数推进 / 发放 / 倒计时基数)在写入的同一事务内算完;消费时才被问的(买经验折后价)做成读口现算,不占存储。
- **键域边界**:游戏效果键入效果域;策略行为观测键(`StrategyState.cw4_counters`)归策略侧,两键空间零交集,新游戏效果键禁旁落行为观测容器。

## 5. 事件映射(声明 → 事件源)

七类事件源在用,全部经既有接入点路由(实码接入点以各函数注释为准):

| 事件类 | 事件源 | 适用触发面 |
|---|---|---|
| 节点推进 | 推进生效原语尾段 `tick_effect_boundary`(同节点去重守卫在账本内) | PLANE_START / NODE_ENTER / 条件-限时段 |
| 动作落地 | 刷新上报 `record_refresh` / 购买上报 `on_buy` | ON_REFRESH / 购买计数 |
| 装备合成 | 穿戴上报 applied 出口检查 | ON_MERGE |
| 跳过消耗 | 跳过型出战上报 `consume_use` | 次数类余量 |
| 升级 | `on_level_up` | LEVEL_UP |
| 选卡落地 | `register_strategy` + burst 桥 + 板面重写桥 | INSTANT |
| portal 登记 | 获得链 `gain_invest_env` → `register_portal_from_env` | INSTANT(portal 源) |

账本 → 字段桥(效果发放换算成字段写入的固定函数口,`kernel/cw_game_state.py`):burst 授予 / 每节点刷新余额 / 升级窗口 XP / 容量直写 / 板面重写。**不建事件订阅框架**(hook 机制已否决):注册表零条目的触发面不建事件,事件驱动一律走既有接入点 + 单版本事务内派生。

## 6. 边界纪律

- **战力类零响应教义**:战斗内增益 / 减伤 / 速度这类效果,游戏自己算自己显示,机器人只登记效果存在(UNIT_BUFF 类,登记形态为占位零响应),零建模零消费;选卡估值对这类卡恒零承载。
- **词缀源同轨**:词缀效果(注册表 `cw_affix_effects.py::AFFIX_EFFECT_SPECS`)与策略源同纪律同账本,经 `source='affix'` 分源读;词缀扫描与装备改写扫描是效果面完备性判据,新成员入册时同批入申报表。
- **零注册触发面**:在用零条目的触发语义,枚举值不预建(战斗结算 / 出售触发),启用 = 各自建模批先立枚举值与规格条目、再接事件源,启用前按观察收尾兜底。
- 实例生命周期 = 登记 → 推进(计数 / 发放)→ 移除(到期 / 用尽);once 类登记后即历史,无推进维度。
