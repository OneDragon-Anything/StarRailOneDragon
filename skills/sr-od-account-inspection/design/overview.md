# 账号巡检 skill 设计

## 定位

`sr-od-account-inspection` 回答一个问题：**不依赖用户手把手操作，agent 如何摸清一个星铁账号的养成情况**。产出是结构化的账号档案（角色清单、养成深度、动态状态），作为后续托管决策（体力怎么分、培养谁、跑什么）的输入。

## 两条数据路线

| 路线 | 覆盖 | 速度 | 前置 |
|---|---|---|---|
| A. 米游社官方接口（game_record） | 角色清单+养成概要、开拓力/委托/每日实训等动态状态、挑战成绩 | 分钟级，结构化 JSON | 浏览器有米游社登录态；账号在游戏内开通过「漫游签证」 |
| B. 游戏内画面读取（MCP analyze_screen + VLM） | A 拿不到的：活动页面详情、仓库材料明细、以及 A 未开通时的兜底 | 慢（逐屏导航） | 游戏可启动、MCP server 在跑 |

路线决策：**先 A 后 B**。A 一次调用拿全量结构化数据；B 只补 A 的盲区或 A 不可用时兜底。两路线的原始发现都走同一个产出（账号档案文件），不双源。

## 动机

- 账号认知是托管决策的地基：决策质量取决于对角色养成、资源、进度的了解程度，而不是会跑一条龙。
- 官方接口一次调用等价于游戏内几十次截图判读，且无 OCR 误差；优先级天然最高。
- 游戏内读取不只是兜底：激活「漫游签证」授权这个前置本身要靠游戏内操作完成，且部分数据（活动详情）没有接口。

## 关键设计决策

- **cookie 不经过 agent 的手**：登录凭据（`ltoken_v2` 等）是 HttpOnly 的，agent 从网络面板读响应头可见值并写入 `.mihoyo.com` 域，全程不落盘、不进会话文本。
- **浏览器发请求、本地算签名**：DS 签名的 md5 在本地（run_code/Node）算好，fetch 从浏览器页面上下文发（credentials 自动带 cookie），agent 只读响应。
- **错误码分层判别**：`-10001`（头/签名格式错）、`10035`（星铁数据功能未开通，游戏内开战绩展示页可激活）、`10041`（激活后仍拒，未解，走 B 路线规避）、`1034`（风控验证码，可换时间重试）。原神同调用返回 1034 是「链路正确」的对照证据。
- **游戏内扫描用「截图落袋 + 判读外包」两段式**：主会话串行操作游戏只负责滚动截图（快），VLM 判读外包给干净上下文子 agent（省主会话上下文），数据管线（校验合并落档）固化为 `tools/account/merge_profile.py`。
- **扫描脚本不碰游戏操作**：脚本只做数据后处理（JSON→YML 管线）；画面扫描必须由 agent 经 MCP 逐步执行，剧本在 SKILL.md，两者职责分开。

## 深渊联动（2026-10 实测沉淀）

- 账号从未打开过战绩数据时，三大深渊数据在米游社侧不可见；游戏内「漫游签证-战绩展示」页打开一次即激活（`10035`→`10041` 的分界）。
- 忘却之庭实战验证：预设编队上下半分别应用时共用角色会被抢（1 号位缺人），需手动补；游戏自动战斗可靠（第 9 关 0-1 轮速通）；「3 星通关后获得前置关卡全部奖励」+ 快速通关补发——**打能通的最高关即可，无需逐关清**。

## 边界

- 不管「跑一条龙 / 打活动」等执行类操作（其他 skill / application 的职责）。
- 不管账号数据的**消费决策**（该练谁、体力怎么分）——本 skill 只负责把账号状态摸清并落档。
- 签名体系若失效（salt 更换/接口改版），按 SKILL.md 的排障序自查，不阻塞 B 路线。
