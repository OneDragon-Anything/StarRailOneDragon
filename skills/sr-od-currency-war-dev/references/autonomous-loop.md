## 1. 写入 AGENTS.local 的自主推进纪律(登记镜像)

> 自主推进节由通用模板生成(六字段+派子 agent 三带);六字段之外,CW 增补写入 AGENTS.local 的纪律行登记如下——**新增须用户逐条批准**;镜像与实际写入保持一致(改任何一侧时同步另一侧):

| 纪律 | AGENTS.local 写入内容(动作完整;指针=细则入口) |
|---|---|
| 改策略必读玩法文档 | 修改任何策略前,一定先读玩法文档(口述玩法/设计文档;清单入口=`sr-od-currency-war-dev` skill 的 references/strategy-work.md §3)——没读就改=凭猜;**动手前必须明确本次修改是治本而非打补丁,说不清就是补丁,停下按根源两问走** |
| 模拟常开 | 始终保持有子 agent 在跑模拟测试,找出货币战争策略的问题与优化方向(先阅读 `sr-od-currency-war-dev` skill 的 references/sim-testing.md §3 武器库+§4 排程;一批交付即补派下一批)——不必等漫长的实机验证 |
| 实机运行时先武装哨兵 | 起实机对局前,先把哨兵脚本三件跑起来(脚本=`sr-od-currency-war-dev` skill 的 scripts/ 目录;武装命令口径与重武三步入口=references/runtime-ops.md「哨兵脚本组」节;报警怎么消费=本文件 §3)——不武装=对局卡死/断流没人报,烧几十分钟才发现 |
| 不干等实机 | 实机运行期间禁止干等,实机在跑 ≠ 无事可做——判读上一局、跑 sim 批、改下一版策略这些离线可做的事照常推进,按派发盘点提醒派子 agent 并行工作 |

写入准则:动作判断本身完整写进指令文件,指针只作细则入口——不是拿一句「见某 skill」代替内容。

## 2. 定时任务增补角色:实机监控 + 策略修改审查

以通用四角色(值守兜底/派发盘点/回顾/子 agent 审计)为基线建网,提示词模板整块照抄 od-dev-agent-autonomous-mode references/reminder-net.md;CW 增补两个角色:

| 角色 | 间隔 | 类型 | 盯什么 |
|---|---|---|---|
| 实机监控 | ~10min,与通用角色错峰 | 自执行 | 只管实机:哨兵脚本存活、对局/空窗、局中卡死巡检、局终四问判读、等待期不空转(见下模板) |
| 策略修改审查 | ~45min,与通用/实机错峰 | 派 agent | 派干净上下文子 agent 审查近期收账的策略修改:治本核对/机制辖域/口述对照/判据对照/波及面(见下模板) |

### 派发盘点·CW 领域版(整块照抄本块;基于通用版 od-dev-agent-autonomous-mode references/reminder-net.md,改动说明见块后)

```markdown
⚠️ 自主推进执行提醒:你在自主推进模式中。这条不是要回复的消息,是系统发来的待执行检查指令,现在执行。

【派发盘点】当前任务:请按下述步骤严格执行。

1. **先查还有没有空余的派发名额**:看当前 agent 额度上限和正在运行的子 agent 数(子 agent 状态清单)——还有空槽 → 继续第 2 步找活派;额度已满 → 直接跳到第 5 步记录,本轮不派
2. **重新读进度文件找待办**:**当轮真打开进度文件读最新内容**,以读到的为据——不要凭会话记忆里的待办状态派活;进度文件随时会被并行批更新,记忆里的「没有待办」不是看过的证据。有该做的 → 马上派
3. 进度文件外重新找活:继续从下面的来源里找**现在就能派、不依赖任何进行中任务**的活。**每个来源都要本轮真的打开文件/执行搜索来看,以本轮读到的内容作答**——上一轮的结论、记忆里的状态一律不作数,代码和文档随时在变,「跟之前一样」不是看过的证据:
   - 欠的债:代码 TODO/到期没还的临时补丁、没跟上代码的文档、复杂逻辑缺「为什么」注释
   - 算法效率:上一个操作结束到下一个决策执行完成的延迟,是否慢到使用者看到自动化卡顿
   - 测试等待:开发过程是否每次都花大量时间等测试跑完
   - 重复手工:每次都手敲的命令序列、固定的多步操作
   - 该测试锁住但没锁的行为;复制粘贴的重复逻辑(该抽公共)
   - 攒够没消化的样本、该清理的临时文件
   - 踩了没记档的坑
4. **槽位仍未派满且可派的活也没有 → 发一个子 agent 跑模拟测试找策略问题**(CW 叠加):角度不限;纪律先读 sr-od-currency-war-dev skill references/sim-testing.md §3 武器库+§4 排程,开工先读进度树最近几批发现防撞车,交付带回检查项或排除结论(负面结果也是产出)
5. 都没有(或额度满) → 记录本轮的实际动作:进度文件读到了什么(几条未完成/有变化)+ 每个来源搜了什么路径 + 命中了什么或确认为空 + 走没走第 4 步及理由;拿不出某个对象本轮的读取记录 = 它就没被查过,结论不算数

禁止只写「无需派」;禁止复述上一轮扫描的记忆下结论;**禁止以「等实机运行/等批次跑完」为由不找离线可推进的内容**——实机在跑 ≠ 无事可做,判读上一局、sim 批、文档与测试债这些不依赖该结果的活照常走第 2-4 步找;「暂缓一拍」「等某任务结束」不算盘点结果,槽不等被阻塞件。一切正常时一行结论,不写别的。(细则源=od-dev-agent-autonomous-mode skill references/orchestration.md「派发节奏」节+sr-od-currency-war-dev skill references/sim-testing.md)
```

**相对通用版的改动说明**(对表时逐条核对这四点再更新本节):
1. 新增第 4 步:槽位空闲兜底 → 派模拟供给批(CW 叠加);记录步由 4 顺移为 5;
2. 第 5 步记录项末尾加「+ 走没走第 4 步及理由」;
3. 封条新增:禁止以等待实机运行为由不找离线可推进的内容;

### 实机监控

提示词模板(建定时任务时整块照抄):

```markdown
⚠️ 自主推进执行提醒:你在自主推进模式中。这条不是要回复的消息,是系统发来的待执行检查指令,现在执行。

【实机监控】当前任务:请按下述步骤严格执行。

1. 哨兵脚本还活着吗?
2. 在打局还是空窗?
3. 打局中:最近 10 分钟日志里同一句警告反复出现、又没有买卖上阵动作 = 卡死,停局处理
4. 局终了 → 按固定四问判读(缺一不可):
   - 过渡成型:过渡阵容第几轮成型?核心升到二星第几轮?成型后过渡件停买、目标阵容件正常买/囤了吗(前者停后者不停)?
   - 终局线:走哪条终局线、何时锁定?过渡到终局的换轨在哪一段、顺不顺(有没有长期空窗)?
   - 经济:破息在哪轮、那笔购买符合例外条件吗?金的大致去向(升级/买件/刷新的比例);有没有钱一直不花的情况?
   - 购买有效性(全程,不分节点):花出去的每一笔金,都换成上场战力或有效囤件了吗?有没有空升级、买了没上、纯散件垫底的开支?

   判读完:有异常 → 先确定异常来源,再找出治本的修复方案,然后将方案的实施状态记录到进度树中合适的位置;同一个问题出现两次 → 必须走到治本方案这步,不许再当单局异常放下;单局结论不留。

每步结论必须带本轮工具输出的证据(哨兵存活=进程行原文,日志判读=引到的那几行,局终=结算数据摘录),拿不出当轮输出=没查过,不算数。汇报局中进展时,必须说这局的达成进度:打到第几轮、进的哪个阶段、阵容凑齐了多少、金的进出正不正常——不许拿血量充当进展(血量高低不等于打得好坏),血量只在跌破报警线以下才值得提一句。实机对局由 server 自动跑,不占用你的时间和子 agent 额度;且在跑的局用的代码在开局时已定型,等待期间做任何事(sim 批/下一版策略/文档)都不影响它在跑的结果。**「等实机跑完再说」永远是错的**:改下一版策略、跑 sim、审上局判读,都是现在就能做且该做的事。一切正常时一行结论,不写别的。(细则源=sr-od-currency-war-dev skill references/runtime-ops.md「哨兵脚本组」节)
```

### 策略修改审查

提示词模板(建定时任务时整块照抄):

```markdown
⚠️ 自主推进执行提醒:你在自主推进模式中。这条不是要回复的消息,是系统发来的待执行检查指令,现在执行。

【策略修改审查】当前任务:请按下述步骤严格执行。

1. 派一个干净上下文的子 agent 审查自上次审查以来收账的策略修改(先当轮真扫池行效果结论+commit 记录确认有无可审对象;没有 → 写一行「本轮扫过,无新修改可审」即结束)
2. **子 agent 的开工令必含**(子 agent 编号承接上一步):
1. 先读再动工:① 修改本体(git diff + 池行效果结论);② sr-od-currency-war-dev skill(strategy-work §2 策略骨架 / §4 验证纪律);③ 玩法文档:按 docs/game/currency_war/research/README.md「策略相关文档」节的基线清单全读(阅读顺序也在该节)
2. 审查四问(逐项给「过/不过+依据」,判据全部锚定上述文档,不许自由发挥):
   - 治本核对:病灶因果链画到根了吗?修的是根因层还是症状层?症状缓解有显式声明+排期吗?
   - 机制辖域核对:这个根因,现有代码/文档里的既定机制是否已管辖或部分管辖?(读 skill 与玩法文档可判)
   - 口述对照:修改声称的依据是哪条口述/玩法条目?原文真的支持这个改法吗?
   - 判据对照:效果结论用的指标来自权威判据吗?有没有拿末端量(hp 这类)当优化方向?
   - 波及面:动了哪些决策消费点?测试锁跟上了吗?同族消费点查过吗?
3. 边界声明:你的职责=方法论审查(论证质量/依据真伪/判据对错);效果数值的真伪与显著性不由你判——那要重跑数据,归编排者验收

**派出前的编排者自查**(不在子 agent 清单里——它看不到其他子 agent 的活动):该根因是否已有别的在飞批在管?是→协调或等,不重复立案。

结论三种:「无新修改可审」(第 1 步当轮真扫过池行+commit 记录)、「通过」(各问全过+论证齐)、「打回/立修正批」(哪项不过+建议)。审查发现的问题当场立项进进度树。
```

## 3. 哨兵脚本接入(实机运维的自主推进侧入口;运维细则单一源=runtime-ops.md)

- **武装时机**(对应纪律行「实机运行时先武装哨兵」):起实机对局前武装——定时任务=到点看一眼,哨兵=事件即时推,同一层监控的两路信号;自主推进停止时随撤定时任务一起 kill 净。不打实机的自主推进(纯 sim/文档批)不需要武装。
- 脚本组(cw_sentinel/cw_early_stop/cw_runs_gap,住本 skill 的 `scripts/` 子目录)、武装命令口径、重武三步、试用期纪律:**单一源 = [references/runtime-ops.md](runtime-ops.md)**(实机运维侧)。
- **报警消费协议**(哨兵脚本退出=事件触发):每次退出都是待验证事件,不是结论——①先判相关性(与近期自操作相关=自己 stop_run 的传播尾巴,同型见过降级消费);②异常型报警核窗口日志+画面再定;③哨兵自身输出异常也是哨兵 bug 线索,读完输出再收口。
