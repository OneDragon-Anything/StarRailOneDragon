# sr-od-dev-currency-war · 设计总览

## 定位

货币战争(Currency War)自动化的**开发·维护·自主推进操作手册**,项目内 dev skill(跟仓库走,不独立发布)。回答三件事:代码架构与铁律是什么(SKILL.md §1)、任务从分诊表哪一行进入(§2 入口分诊)、知识在哪与行为变更怎么同步文档(§3 单一源地图+§4)。

## 边界

- **不管**:新玩法从零搭建(od-dev-write-application)、迭代流程与迭代内进度(od-dev-run-iteration)、停机钩子生命周期(od-dev-stop-hooks)、画面建档(od-dev-screen-onboarding)、写单个 op(od-dev-write-operation)——CW 场景下按 SKILL.md 入口序路由到它们,本 skill 不复述其内容。
- **不管**:游戏机制知识本身(在哪查由单一源地图指路)、策略的具体行为语义(strategy/01-07 是源)。
- 面向**已存在的 CW app**;若 CW 被推倒重写,本 skill 随之修订。

- `references/runtime-ops.md`:实机运维细则(启动与重启、早停判据、局间交接序、残局画面清单、监控栈与哨兵脚本组)。
- `references/data-collection.md`:数据采集全景(生成器族、图鉴实采、运行时钩子、建模增量层、钩子统一使用与产物路径)。

## 动机记录

- **§1.4 参数规范(用户裁定)**:动作原语最初按 kernel 会话语义设计参数(名称定位/槽位缺省走 game state 现算),暴露三类缺口——名称在重复实体下定位歧义(实拍:装备栏同名多条)、个别分支 game state 缺席即断言崩溃、参数 dataclass 缺 `from_dict` 导致 MCP JSON 通道构造不出(实机局 agent 无法调用穿装 op)。裁定:执行路径零 game state 依赖、参数三分法(固定槽位/半固定/动态坐标)、名称降级语义参数、坐标新鲜度归调用方、迁移按 op 切四角色子代理流水线(设计→review→实施→review)。刻意不采纳:op 落点前校验(违反动作 op 纯机械契约,新鲜度归调用方纪律)、按名称定位(重复实体歧义不可解)。
- **自主推进形态重写为实机探索期(用户裁定)**:旧形态(定时任务提醒+实机监控角色+哨兵报警消费接入+模拟常开+局终自动派复盘)服务 server 自动跑局时代,已整体废弃;新形态 = 编排者派实机探索 agent 按玩家 skill 亲自玩、遇问题停止操作并汇报,走诊断→设计→对抗评审(每轮全新子 agent)→实现与 review→实机验证循环(报告里没有要查原因的问题时,缺动作 op 的发现不经过诊断,直接立修复线),编排者全程只调度与传话不做技术判断。刻意不采纳:在旧文档上保留定时任务模板待将来恢复使用(用户裁定需要时重写,不留尾巴)。
- **自主推进文档按场景组织(用户裁定)**:编排方法跨场景相同(编排者职责/窗口所有权/处置循环/挂账与归位),一个场景一份文档、换期整体重写会让这些恒定件被反复重抄、方法无稳定落点;四个场景(版本适配摸索/流程框架适配/投资策略与环境 sim 适配/策略实现)只决定优先事项与对应场景节,文档不整体重写、各场景节就地维护。场景由用户开启自主推进时说明,编排者不按证据判定、不自行切换:线表表头只抄用户的原话,不随证据更新。刻意不采纳:按日历时间分期(能力未就绪即切换会让场景错位);编排者按追踪文件等证据判定场景并自动切换;维持单场景文档+换期整体重写。
- **场景一的范围(用户裁定)**:场景一管两件事:画面建档与识别、动作 op;实测玩家 skill 的玩法指引。各域数据的更新(注册表、成批生成识别模板)是版本适配时做一次的事,不在场景一里预先排;只有实机探索中发现某一项内容识别不到(比如缺模板),才立修复线去补。画面上有这一局必须做的一步、该有动作 op 而操作表里还没写时,探索 agent 用鼠标把当前画面摸清楚后停在它上面、不往后打:画面留着,新动作 op 写完就能在它上面验证。知识文档在场景一只记待裁知识队列、不直接改,诊断结论是知识修正时不立线、探索线不等它:玩家 skill 的知识文档由用户把关,等裁定不该挡住探索。停在半路的对局留着、修复线期间不放弃:放弃对局收不回来,现场又是验证修复的场景。不做事先的盘点:不到游戏里看,光翻文件看不出缺了什么;目标由用户开启自主推进时说明,缺口在实机局里发现一条记一条,追踪文件开局时不预先建画面章。每局不另派子 agent 核对报告、整理发现、出下一局计划:实机探索 agent 自己在单局报告里写清发现、每条该去哪,编排者照报告登记;下一局任务书的各栏照固定的记录填(目标 = 用户说明的目标,阵容线 = 用户指定的阵容攻略、没指定写「无」,顺带取证 = 待跟进事项文件里等实机取证的条目,顺路验证 = 等实机验证的修复线,难度 = 可解锁的最高难度)。派要操作游戏窗口的活之前不另做画面识别,也不设「画面停在一局中间而占用表没有持有者」的专门规则。刻意不采纳:操作表里没有这一步时,让探索 agent 自己试着点、打完整局再补(没有操作表的指引,自己试容易点错;画面过去后只能等它随机再出现);在场景一里按域预先排数据更新线;开局先派一个不进游戏的盘点任务,预先扫出缺口清单和数据差异清单;每局另派一个判读子 agent 核对报告数字、整理发现、出下一局计划;派发前识别当前画面,发现来历不明的现场就登记待裁。
- **长期追踪目录(用户裁定)**:画面识别、动作 op 的情况要持续跟进,是跨会话的长期记录;开工前不该为了解它们读很多内容。做法:货币战争的长期追踪目录(`.temp/tracking/currency-war/`,不在版本控制里)放长期保存的文件——待跟进事项文件(寿命超过单个迭代的待办)和追踪文件(按画面分章,记识别核对的日期和结论、每个该有动作 op 的动作有没有动作 op、该画面的缺口)。任务书只给路径,不抄内容:实机探索 agent 打到哪个画面读哪一章。记录只写日期和结论,不复述画面文档和画面档里已经写着的细节(两处都写,迟早不一致)。不是画面的缺口(流程缺陷、机制缺失)不进追踪文件,归待跟进事项文件。刻意不采纳:每次自主推进开工新建一张缺口矩阵、把没覆盖的格子原文抄进每一份任务书(每次开工新建一份,以前开工时记下的读不到;任务书越写越长);开工前按文件盘点一遍、预先建好全部画面章(不进游戏看不出缺了什么);记录里写明每次核对了哪些内容(和画面文档形成两份说法)。
- **打法照玩家 skill 的指引,不够用的地方单独登记(用户裁定)**:实测玩法指引是场景一的职责之一。实机探索 agent 自己打局时,打法照玩家 skill `sr-od-currency-war` 的指引、加上自己的判断;开发 skill 不写打法要求。指引不会讲到每一种情况。做判断觉得难而没有指引、有指引但不适合现在的情况、照着做效果不好,这三种由实机探索 agent 当场记进长期追踪目录的玩法指引的不足文件,用户改玩家 skill 的时候看。为什么打法不写在开发 skill:打法只住在玩家 skill,写好了照着做就能通关;开发 skill 另写一套,两处会各说各的。为什么单独一份文件、不由编排者照报告转登:不足是跨局攒的,一局一份的单局报告里翻不起来;当时记最准;同一时间只有一个 agent 占着游戏窗口。单局报告记结果的那一节只留五样(走到哪、难度、照哪条阵容线打、怎么结束的、局内目标):看一局看的就是这几样。刻意不采纳:让实机探索 agent 每一步都先查指引、查到就照做(指引不是对每种情况都有建议,使用者要有自己的判断);把不足并进待跟进事项文件(那份已经很长,它记的是开发待办,和「玩家 skill 的指引够不够用」不是一回事)。
- **阵容线可以由用户指定(用户裁定)**:场景一的任务书多一栏「阵容线」。用户开启自主推进时说了这一轮按哪篇阵容攻略打的,记进线表表头;每一局都照那篇打、不改打别的,不够用的地方记玩法指引的不足。没说的,实机探索 agent 按指引自己定。为什么加这一栏:以前每局照哪条阵容线打全由实机探索 agent 临场定,用户没法专门检验某一篇阵容攻略。刻意不采纳:为它单独建一个场景(活和场景一完全一样,只差这一栏;只想测某几篇攻略的,把这几篇写进进入自主推进时给的目标,流程仍用场景一的)。
- **场景不写死目标和完成条件(用户裁定)**:目标是用户进入自主推进时给的,每次可以不一样;场景只定关注什么、按什么顺序推。什么时候算完,编排者不自己判断,只认两样:执行 agent 的报告里写明目标达到的;用户自己说的(叫停,或者说进入下一个场景)。场景一的「局内目标」由实机探索 agent 每局写:用户的目标里写明了做到什么程度的(打到通关、哪些画面建完档)才写达到,没写明的写未达到。目标达到以后,没收口的线照常走完,追踪文件里的缺口原样留给下一个场景。为什么:固定的条目套不上每次不一样的目标;线和缺口各有自己的记录(线表、追踪文件、待跟进事项文件),不靠完成条件兜底。为什么没写明程度的不写达到:没有可对照的程度,编排者会在第一局以后就停下来问,挂机的时间白等。刻意不采纳:每个场景写死一条完成条件(比如「app 自动流程能稳定打完整局」「对拍一致」);编排者对照记录自己判断目标达到没达到。
- **哪些动作该有动作 op(用户裁定)**:自动打一局用得上的动作,才做动作 op。项目本来的设计就是一条龙和 agent 共用最底下的动作:探索 agent 每用一次,等于替一条龙试了一次;用不上的做了也没人用。老画面以代码为准,一条龙已经会做的动作就是该有的:这一条由修复线看代码时用,实机探索 agent 不看代码。判据落在画面本身:由探索 agent 站在画面上,对每一个能做的动作问三个问题——自动打一局会走到这个画面吗、不点它这一局走不下去吗、点了它后面的对局会不会不一样;判不准的报上来,修复线看代码定。只是看的信息,到程序做决定要用时再做:现在做等于猜以后用不用。刻意不采纳:操作表的每一行都要有动作 op(一条龙不去的画面也做,白费功夫);只有鼠标点不稳的才要(稳不稳要实机试过才知道,开工前判不了)。
- **该有动作 op 的动作还没有时停不停(用户裁定)**:这一局在这里必须做的一步,操作表里写了的,探索 agent 照操作表用鼠标做、继续打,缺口照常写进报告;操作表里没写的,才停在这个画面。不是必须做的一步(比如商店上的「商店锁定」),操作表里没写就不点;该有的记进「缺动作 op」,继续打。为什么:老画面上这样的步骤很多,都是一条龙已经会做的动作,每处停一次,一局要等几十条修复线才打得完。停下来留画面,是给验证用的,留给文档里没写过的新步骤才值得。做好的动作 op,以后几局打到这个画面、用到它的时候就验证了。刻意不采纳:该有、还没有的每一步都停(老步骤也要一局停几十次)。
- **修复线不挡实机探索(用户裁定)**:修复线还是一个画面一条。缺口登记进追踪文件,实机探索线就接着打下一局,不等修复线做完。修复线和知识文档线用探索线以外的空位走;要重启 MCP server、要占游戏窗口的验证放在两局之间;同时能跑的 agent 只有 1 个的时候,每打完一局先让修复线或知识文档线走一步,再派下一局(这一条用户认可)。为什么:缺动作 op 的修复线一个画面一条,有几十条,全做完再打,探索就停住了;探索 agent 照操作表用鼠标做,照样能往下探别的画面,做完的动作 op 以后几局用到的时候再验证。中途停下、画面留着的情形不变:画面是留着给修复线在上面验证的。刻意不采纳:把一份报告里的缺动作 op 合成一条修复线(用户要保留一个画面一条);修复线全做完再派下一局。
- **场景一的运转细节(领域设计,不是用户裁定)**:
  - 有没有动作 op,先看追踪文件里这个画面那一章的动作一栏(它只列该有的动作,和判不准、后来判了不用做的):括号里是 op 名就有;括号里是「鼠标点击」就是该有、还没有;括号里是「不用做动作 op」就是判不准、后来判了不用做。动作一栏里没有这一步、或者这个画面还没有章的,再看玩家 skill 对应画面文档的操作表和三个问题:操作表这一步写的是 op 名(用 run_operation 调用的)就有;写的是鼠标、而三个问题判它该有的,就没有——这一步没有给 agent 调用的动作 op。新动作 op 做出来以后,由编排者在重启 MCP server 以后,照实现报告把操作表那一格和追踪文件里这一步都改成 op 名:探索线不等修复线以后,这几处改动必须跟着挪到重启以后——写在重启以前,中间派出去的那一局会照操作表去调一个还没加载的 op,停在半路。不改,下一个探索 agent 判断这一步还是没有动作 op,会再报一次,也只能照旧用鼠标,新动作 op 没人用。
  - 缺口的建议处置(立修复线 / 现在探不了)由实机探索 agent 在单局报告里写,编排者照抄:不写,这个技术判断会落到编排者头上。
  - 缺口并进已有修复线,只在那条线没过定稿时成立;过了定稿就另立一条线:过了定稿再并,等于绕开设计修订的门,而编排者没有「派设计修订」的机械规则。
  - 闪退、掉线以后对局多半转成挂起存档:恢复时先看模式选择画面有没有「继续进度」,有就续同一局,没有才记中止;启动工具只登到大世界,进货币战争交给重派的探索 agent。
  - 探索 agent 的建档按画面建档 skill 的完整步骤做,含测试仓的归档图和 id_mark 测试:不这样做,局里建档不算完成;留给后面的线补又没有固定的线来接。
  - 修复线连续 3 局没遇到而转去等裁定时,它对应的缺口条目同时登记进待跟进事项文件:那条线在等用户裁定,这几条缺口跟着标成「已登记待跟进事项」,看追踪文件就知道它们在等什么;用户裁定以后再改回去。
  - 中途停下的报告(叫停、连接断开、闪退以后重开)和局终报告一样要登记:一局一派,子 agent 交了报告就结束,这一份不登记,里面的发现就没人再报。
  - 修复线往立绘库、装备库加了模板,或者改了已有的模板,要重启 MCP server:这几个库读进服务进程以后不再重读,不重启新模板不生效,修对了也会验证不达标。
  - 同一条缺口再报一次,不另立线:实机探索线不等修复线以后,一条修复线从定稿走到实现要隔好几局,这几局里同一个画面每局都会把同一条缺口再报一次。照「同一个画面又报缺口就并线」的规则办,过了定稿的会另立一条带序号的重复线。所以先分清「同一条」和「同一画面的另一条」:同一条已经有没收口的线在跟,就什么都不做;靠缺口状态后面记的线名找那条线。
  - 旧口径的章怎么读、怎么转,只用单局报告里的判断:编排者手里只有报告,报告只写这一局用到的动作;让编排者对着没报到的动作判该不该有动作 op,等于让它做技术判断。没报到的行先标「未判」,等报到再定。
  - 核对旧缺口分「还在」「不在了」「核不了」三种:旧缺口多数说的是画面上某个元素没建,不是整张画面认不出;只看「认不认得出」,会把还在的缺口报成不在了、删掉。站在画面上核不了的(要特定局面、要看代码),原样留着。
  - 流程外画面的缺口,每次开启时清一次(开启清单第 3 步):动作 op 的缺口删掉(这些画面的动作都不该有),画面建档、画面识别两层的登记挂账。为什么:这些画面实机探索 agent 走不到,没有哪份报告会来处理它们(用户裁定过:碰不到的内容就是挂账)。随机才出现的画面的缺口不另处理:用户叫停时,没有修复线在跟的缺口本来就统一登记(§3.8)。
  - 修复线判了一步不用做动作 op:这一行由编排者照探索报告写,线里只有这一件事的移入「已结束线」。探索 agent 用的是通用探索模板,不许改文档;没有立项的线也没有迭代目录,谈不上收口。
  - 局终报告有要查原因的问题:诊断 agent 排在修复线前面先派,不挡下一局。诊断结论可能把缺的动作 op 并进别的线,先出结论,免得先立出一条要并掉的线。
  - 已建档的画面上缺的元素,实机探索 agent 站在画面上、补得上的就当场补建:它手里有写档工具;修复线只有验证那一步进游戏,要站在画面上才能建的元素它做不了。
