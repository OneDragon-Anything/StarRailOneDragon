# UI 区域坐标检测 / 验证方法论

检测「画面上一组 UI 元素在哪」时,**别凭 vision 自由问坐标(必幻觉),也别对所有元素用同一种法**。按元素类型选工具,且**必须有 ground truth 数值对拍**。

## 核心判据:vision vs CV,按元素类型选

- **稀疏 / 大 / 独特**(≤ ~6 个、单元素 > ~80px:几个图标按钮、少量大卡槽)→ **vision(VLM grounding)**。
- **密集 / 规则网格**(等距阵列、≥ ~7 个:一排很多小槽、密集等距槽位栏)→ **传统 CV(投影峰值法)**。vision 在密集网格会漏检 / 错位(受 32×32 patch 天花板限制)。
- **带边框 / 底色对比的图标阵列 / 卡牌**(卡牌、装备格、商店牌、头像框)→ **传统 CV(形状轮廓法,见「CV 路径二」)**。这类元素是程序绘制的简单几何形(矩形 / 圆 / 六边形),边框色 / 亮度对比稳定 → 轮廓检测比硬编码坐标鲁棒(硬编码单张截图推断、不适配滚动、易截断)。
- **纯文字** → OCR(`analyze_screen` 的 `ocr_texts`,1080p 直出坐标)。
- **小目标**(< ~50px,图标)无论走哪条,**先裁切到目标区 + 放大**(vision 破 patch 天花板;CV 提信噪比)。

判据一句话:**「稀疏独特找 vision,密集网格找 CV,文字找 OCR」**。两者互补 —— 同一画面里稀疏行用 vision、密集行用 CV(混用)是常态,不是二选一。

## vision 路径:必须用模型原生 grounding 格式

自由问坐标(「描述位置 / 报像素 / 报 0-1 小数」)→ 模型瞎编(全图偏几百 px)。**用模型被训练好的「母语」坐标格式**:

- **GLM-4.5V**(本项目 `mcp__4_5v_mcp__analyze_image`)用**自然语言**要 `[xmin,ymin,xmax,ymax]` 归一化 **0-1000**:
  prompt 例:`"Where is each <目标>? Provide coordinates in [[xmin,ymin,xmax,ymax],...] format normalized 0-1000"`
  还原:`pixel = value / 1000 × 宽(或高)`。
- 换模型**先查其文档确认坐标系**(各代不同:GLM-4.5V=0-1000、Qwen3 系=0-999、Qwen2.5-VL=绝对像素),别混用。
- **vision 的「状态推理 / 计数 / 对齐判断」不可信**(不懂游戏、会基于文字瞎猜;数 overlay 对齐也会数错)—— 只信它**客观描述**(有哪些元素 / 文字 / 大致位置)。坐标对错以**数值对拍 ground truth** 为准,别让 vision 当裁判。
- **vision 的「颜色 / RGB」不可信精确值**:VLM 颜色感知是「人类式分类命名」(说「亮蓝」「暗紫」),**非像素级精确**,且会被色彩错觉骗(2025 学术共识:VLMs inherit human color perception、color illusions fool VLMs)。**用法**:让 vision **定性**描述(够用来选 CV 信号:亮 vs 暗 / 蓝调 vs 紫调)→ **精确阈值 / RGB 由 CV 采样定**(`np.mean(bbox)` 均值 / k-means 主色),别拿 vision 报的「V~85%」当阈值。**分工:VLM 定位(在哪)+ CV 采样(准值)**。

## CV 路径:密集规则网格用「投影峰值法」

一排等距槽位 → 逐列投影 + 局部极大 + NMS(见本 skill 目录 `detect_grid.py` 可复用实现):

1. **裁行带**:y = 槽的 y 范围,x 两侧留余量。
2. **逐列信号** = 该列灰度**标准差**(槽内有立绘 / 边框 = 方差大,缝隙 = 均匀 = 方差小)。框色若与背景可分,也可用 `inRange` mask 列求和;但**框色常与缝隙同色**(如暗框 + 暗缝)→ 标准差更稳。
3. **轻平滑**(核 `slot_w // 4`;**重了会桥接相邻密集槽** → 数量变少)。
4. **阈值 = `median`**(低到能保留**空槽**的微弱峰;空槽没立绘,信号弱,高阈值会漏)。
5. **局部极大**(窗口 `±slot_w*0.4`)+ **NMS**(限距 `slot_w*0.7`)→ 一个槽一个峰。
6. 峰位置 = 槽中心;span = `±slot_w/2`。

**优点**:内容无关(靠「槽内有别于缝隙的任何信号」,空槽也能抓);不依赖槽内角色图,不需模板。
**局限**:大槽 + 复杂立绘(带角色立绘的大卡)内部多峰 → 这类用 vision,或先重平滑塌峰(但会牺牲密集网格分辨,二者权衡)。

## CV 路径二:形状轮廓检测(图标 / 卡牌 / 头像 / 装备槽)

游戏 UI 里**程序绘制的图标类元素**(角色卡 / 头像框 / 装备槽 / 商店牌 / 技能图标)几乎都是**简单几何形状** —— 矩形 / 圆角矩形 / 圆形 / 六边形,偶尔平行四边形(俯视倾斜的牌面),更特殊的极少。它们**边缘锐利** → 传统 CV 形状检测可鲁棒定位,**远胜硬编码坐标**(单张截图推断的坐标脆弱:不适配滚动、易截断 —— 猜浅砍底 / 猜高切顶)。

### 第 0 步:vision 描述客观特征 → 确定性选法(别让 vision 点名算法)

**先让 vision 描述客观特征**(形状是矩形 / 圆 / 网格?颜色是否随属性变?数量?布局?哪些特征跨所有元素恒定?)→ **按「特征 → 方法」确定性映射**选法。⚠️ **别让 vision 直接点名 CV 算法**(它会基于特征瞎推荐);只取它**客观特征描述**,过下表选法:

| vision 看到的特征 | 选法 |
|---|---|
| 矩形 / 圆角矩形阵列(卡牌 / 装备格) | **squares 检测**(多阈值 + 4 顶点几何,第 1 步首选) |
| 圆形(头像框 / 技能图标) | `HoughCircles` / 轮廓圆度 `4πA/P²>0.7` |
| 等距密集小槽 | 投影峰值法(CV 路径一) |
| 倾斜平行四边形(俯视牌面) | `minAreaRect` + `getPerspectiveTransform` 透视矫正 |

**关键:颜色可能随等级 / 星级 / 费用 / 稀有度变化**(常见:低阶冷色 → 高阶暖色),**别假设统一背景 / 边框色**。选法挑**不随该属性变的恒定特征**:颜色随属性变 → 用**形状(几何)**而非颜色阈值。

### 第 1 步:squares 检测(矩形首选,鲁棒于颜色变化)

OpenCV 经典 squares 法(多阈值扫描 + 几何判矩形)—— **判几何不判颜色**,在某阈值层每个元素(任意颜色)都成干净 4 顶点矩形:

1. 灰度,**多阈值扫描**(`cv2.threshold` 扫一个范围步进,`THRESH_BINARY` / `THRESH_BINARY_INV` 各一遍)→ 每个元素在某层成干净矩形 blob。
2. `morphologyEx CLOSE`(核 **< 相邻元素间距**,防粘连;核 > 间距 = 粘连)。
3. `findContours` → `approxPolyDP(0.02·peri)`:**4 顶点 + `isContourConvex` + 面积 + 长宽比**(按目标实际尺寸定范围)过滤 = 矩形。圆角 / 抗锯齿致 >4 顶点时,先 `drawContours(...,FILLED)` 填实再判。
4. **去重**(IoU>0.3 合并;多阈值会重复检同一元素)。
5. **验证**:检测 bbox 与 ground truth 比 **IoU>0.8**;落盘标注图肉眼复核;**多样本**核实稳定性 —— 单屏对上不算过。vision 只用于「描述特征」+「给 ground truth」,不当裁判。

### 第 2 步:亮度 / 颜色阈值(几何法不足时补充,squares 够用就别用)

仅当元素内部颜色均匀 / 边框色跨元素一致时简单好用;**对颜色变化更脆**,先用 vision 确认目标颜色不随属性变:
- **亮度阈值** `cv2.threshold`(亮边框 vs 暗背景)—— 内部亮度均匀时最简单。
- **颜色 inRange**(HSV 抓边框色)—— 边框色跨元素稳定时。
- **背景互补法**(kmeans 找背景色 → 取补集):仅当背景真均匀且能正确定位背景簇;kmeans 易把常见元素色误判成背景 → 失败。**优先 squares**。

### 方法选型判据

多探索几种经典法、量化对比,别只试一种就下结论。矩形阵列实测选型判据:
- **判别量优先查亮度(VALUE)**:背景暗(低 V)、元素更亮 → 灰度阈值有效;饱和度 / 色相常不是判别量(背景可能也饱和)。先 vision 查 + CV 采样确认「背景 vs 目标的判别量是 V / S / H 哪个」,别假设。
- **填洞(`drawContours(..., cv2.FILLED)` 把外轮廓环填实)是阈值 / 边缘法的关键后处理**:亮边框成环、内部深色内容是洞 → 不填洞则环碎裂 / 被面积过滤 → 漏检。**漏检时先查是不是没填洞**,别急着归咎颜色变化。
- **squares 最鲁棒**(纯几何,多阈值扫到每个元素的干净矩形层)→ 跨颜色变化 / 跨屏最稳,首选;单阈值 + 填洞是更简单的次选。
- **kmeans 背景互补慎用**:簇数 / 背景定位不稳时把元素色误判成背景 → 大面积漏检。

### 副产物:标签与裁剪同源 → 消除错标

检测出的每个元素是**独立区域** → 标签和模板从**同一区域**取,不靠"OCR 行 × 列模糊匹配"。做法:对每个检测出的独立区域,从**同一区域**取标签(如 OCR 该元素内文字)与模板(如裁该元素的图),根除「标签贴到隔壁元素」的风险(行 × 列模糊匹配 + difflib 易错标)。

### 验证(数值,不用 vision 当裁判)

- 检测 bbox 与 ground truth(vision grounding / 手圈)**比 IoU > 0.8** 为准(形状检测给矩形,用 IoU 非中心距;投影峰值法给点,用中心距 < 10px)。
- 落盘**标注图**(检测框 + 序号)肉眼复核数量与位置;**多样本核实**(滚动多屏 / 不同内容)稳定性 —— 单屏对上不算过。
- vision 只用于"描述特征"和"给 ground truth",**不当裁判**(计数 / 对齐判断不可信)。

### 何时用形状轮廓法 vs 投影峰值法

- **投影峰值法**(上文):一排**等距小槽**,内容无关抓"有别于缝隙的信号",空槽也抓。适合密集等距小槽阵列(一排很多小槽)。
- **形状轮廓法**(本节):元素**有明确边框 / 底色对比**(卡牌 / 图标按钮 / 装备格),要的是元素**矩形边界**本身。适合卡牌阵列 / 装备格 / 带框图标。
- 同一画面可混用:密集无框槽用投影,带框卡用轮廓。

## 验证:必须有 ground truth,且用数值不用 vision

- **ground truth 来源**:手圈区域 / `click_game` 实锤 / screen_info 已有 `pc_rect`。
- **对拍指标**:逐元素中心距;**< ~10px = 通过**。报告数量是否对上 + 每个的误差。
- **不要用 vision 去「判断 overlay 画得对不对」**(vision 计数 / 对齐判断不可信)—— 直接算 `detected_center` 与 `gt_center` 的数值差。

## 何时根本不需要运行时检测

- **screen_info 已有 `pc_rect`**(建档时圈好)→ 自动化**直接用坐标**,不运行时检测。本 skill 的检测方法主要用于:**建档阶段定位坐标**、**验证已圈坐标是否随版本漂移**、**定位 screen_info 未覆盖的动态元素**(如刷新的商店内容)。
- 别为了「全自动」而在运行时重检测已有 screen_info 的元素 —— 多此一举且更脆。

## 与 `sr-od-dev-screen-onboarding` 的分工

- `sr-od-dev-screen-onboarding`:画面**建档**全流程(analyze → vision 理解 → 写 doc → 建模入 screen_info),其 §5 含图形按钮的 CV(圆 HoughCircles / 轮廓圆度 / 模板)。
- 本 skill:聚焦**「检测 / 验证坐标」的方法论选型**(vision vs CV vs OCR 的判据 + 密集网格的投影峰值法 + 数值验证纪律),不重复建档流程。建模入 screen_info 仍走 onboarding skill。
