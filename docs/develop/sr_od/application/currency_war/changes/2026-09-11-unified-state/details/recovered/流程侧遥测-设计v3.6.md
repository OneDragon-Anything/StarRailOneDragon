## ① 结论

1. **统一 state = BoardState 收编升级**:现役 `kernel/cw_board_state.py` 已具备「唯一
   事实容器」骨架(单例、来源四分类、写入只经 API、预期两步、观察赢、效果账本、
   写点序号心跳)。本设计在其上补:①写入 API 全部带**渠道签名**;②`write_seq`
   升格为**版本 id**;③每次写入落一行**自足状态流水**(行 = 写入说明 + 写入后
   完整 state 快照);④缺域补齐与写点补全。另起新容器否决(双源)。
2. **BoardState 与 GameState 的关系(E2,实码核实)**:统一 state 载体 = BoardState
   (session 旁表单例);现役策略器决策消费的是 GameState(识别链填充
   `session.last_state`,mandate_v1 全部 decide 函数签名 `state: GameState`);BoardState
   现役 = 并行记录(观察喂入口 relay/效果域写点/tick 已部分接线,消费未切换);
   sim 侧 GameState 真值经 `synthesize_from_game_state` 落 BoardState,实机识别主链
   产 GameState、经 `_feed_board_state` 部分同步 BoardState。v3 目标态 = 流水记录
   BoardState 面,GameState 降级为决策读端投影(迁移批次二消费切换),详见 §3.1.5。
   **决策可信位(hp_readable/hp_trusted)保留决策域读面**(正本批次二 hp 帧透传
   申报延续,v3.2-G1;§3.1.2/§3.1.5)。
3. **写入源有且只有三个**(裁定 1),各带渠道签名:①画面 op 观察(`obs`);②动作 op
   逻辑计算(`logic_action`);③状态内部派生逻辑计算(`logic_hook`——族名沿旧;
   逻辑态派生规则是源③的 state 内部形态,实现 = _swap 内管线,无独立 hook
   框架)。carried/prior/synthesized 是 `obs` 族内来源
   子模,非第四源。
4. **状态流水(核心形态)**:流程侧唯一落盘流 `state/journal.jsonl`,每次写入一行,
   行内 = 改了什么 + 渠道签名 + 版本 id + **写入后完整 state 快照**(含逐字段
   来源注记,v3.2-G3;§3.2.3)。行行自足:查询 = 直接读行,零重放、零前溯、零锚、

## ③ 变更面(设计文档本体)

### 3.0 名词与辖域

- **统一 state**:本设计唯一的游戏事实容器(载体 = BoardState,§3.1.5)。「游戏
  事实」= 观察数据 + 效果统计计数 + 逻辑态派生字段。**不入辖**:纯工程性能面
  (op 耗时/重试计数/进程心跳——归日志或专用工程流候裁,§3.6.1 op_journal 行);
  策略器内部状态(归策略侧决策行,§3.5.1);hook 订阅机制(零预留)。
- **状态流水(state journal)**:流程侧唯一落盘流——每次写入一行,行 = 改了什么 +
  渠道签名 + 版本 id + **写入后完整 state 快照**;行行自足,查询直接读行。
- **渠道签名(channel signature)**:每次写入携带的「谁写的、从哪写的、质量如何」
  结构化标注(§3.2.1)。
- **版本 id(version)**:统一写入口给每次写入分配的 run 段内单调整数;写入序 =
  版本序 = 流内行序。版本 id 是全局单调事实序,后续系统自然消费,遥测侧不做
  专门接口。
- **版本钉(state_ref)**:策略侧遥测用 `(run_id, v)` 钉定某时点 state——回溯 =
  直接读该行(§3.5)。
- **逻辑态派生规则(derivation rule)**:game state 内部确定性规则,消费已写入字段,
  产出逻辑态字段;写入走统一写入口源③。规则本体单一源 = 场景一判定方案
  (现行 R4,§3.4.1 一行引用),本正本不复写。
- **两文件模型(E1)**:全局落盘目标 = ①`state/journal.jsonl`(流程侧状态流水)+
  ②策略侧决策行文件(DecisionTrace 演进;文件名/格式归策略侧设计正文,建议与
  现役 decisions 演进承接)。两文件各自行行自足、按 run_id 切段归局。
- **落盘根(建议,终裁落实施批)**:`<现役 live 根>/state/journal.jsonl`(生产 =
  `.debug/currency_war/telemetry/live/state/journal.jsonl`);单文件 + 行内 run_id 列
  (per-run 分文件候选否决,v2-F10 申报延续)。
- **与现役的关系申报(E1 修正)**:现役 decisions 行的「行内全量 GameState」自足
  形态 = 状态流水的直系前身;v3 = 把该形态推广为**流程侧唯一落盘流**(所有 state
  写入同构,补渠道签名与版本 id)。其余各流**不因「一条流」而一句话收编**——
  逐流三类处置评估见 §3.6.1。**流清点方法(v3.2-G2)**= recorder 写入面 /
  match_archive 切片清单 / 全仓落盘调用点三方交叉,禁仅 recorder.py 清点——
  第 13 条流(board_state_archive.jsonl,cw_loop 直写)即调用点扫描发现。

- **行行自足是唯一完整性机制**(v3 根本性纠正):查询 = 按行读;无重放、无前溯、
