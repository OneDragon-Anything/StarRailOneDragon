## 4. 申报点裁决

### ① 重建判据同秒窗口 —— 裁定:可接受并记录,无需处置

核实(权威源 = `telemetry/state.py`):

- run_id 构造:`start_run` 内 `_CURRENT_RUN_ID = datetime.now().strftime('run_%Y%m%d_%H%M%S')`(:105 附近)——秒级时间戳字符串。
- 判据两端的真实时点:重建比对的「当前 run」在 loop `__init__` 的 ensure 铸/认领(先于 handle_init);上一 run 的 created_run_id 铸于上一局 establish 段3。**同值 ⇔ 两 run 铸造间隔 <1s ⇔ 上一局「铸段 → 全局跑完 → close_run 收尾 → 下一 run 铸段」全程压缩进同一秒**——上一局至少含一轮备战交互(框架等待秒级)加收尾,间隔为分钟级,不可达。worker 申报的「框架等待下限跨秒」成立,且可加强:间隔的硬下界是上一局完整时长,比逐点等待更硬。
- 正交事实补充:上一 run **未收尾**的残留(入口链 fail/假局提前 return)走 ensure 认领路径(`_RUN_MATCH is match ∧ not _RUN_CLOSED` → 认领 → created_run_id == current → 保留),不经过「铸新段后同值比对」——该形态是 design §2.4 保留集合括注明确申报的保留语义,与同秒窗口是两回事,窗口唯一可达前提「已收尾 + 两铸造同秒」不存在。
- 处置建议:无需处置(run_id 加单调后缀属判据变更,design 定稿禁变体);已由测试以假钟跨秒显式造出真实时序(test_stale_container_rebuilt_as_takeover 的 _AdvancingDatetime),判据行为有锁。T-4 核签复核时按本节口径复核即可。

### ② ensure 的 difficulty 实参捕获位置 —— 裁定:语义核实一致,落法正确

- 旧铸段时点核实(cc234625a^):旧 ensure 三处全在简报/投资分支,实参 = `ctx.cw_selected_difficulty or ''`;旧时序下该值**未被取走**——旧首次 establish(难度确认屏分支,先于读取段)的吸收段在 ctx 无值时空转,幂等分支(模式选择/简报屏)不重跑吸收段 → 旧铸段实参 = 难度确认屏读存的**真值**。
- 新落法(cw_strategy_manager.py:135):`_run_difficulty` 在吸收段取走 ctx **之前**捕获 → ensure(段3)携带同一真值。若捕获在取走后则恒 `''`(语义断裂)——worker 落法恰是语义保持的必要条件,注释申报(cw_strategy_manager.py:131-133)准确。铸段时点前移(简报/投资分支 → establish 点)为 design §2.4 遥测副作用申报①的定稿内容,非偏差。

### ③ handle_init 惰性 import 收拢 —— 裁定:无行为差

Python 作用域语义核实:函数体内任一分支的 `from X import Y` 把 Y 编译期绑定为局部名;若两分支各自 import 同名而控制流未经其中一支的 import 就引用该名,触发 UnboundLocalError。收拢到分支前单次 import(两分支共用)消除该雷,且 import 时机提前仅是名字绑定提前,模块已加载、零行为差。worker 申报的实现期实证与语义相符。
