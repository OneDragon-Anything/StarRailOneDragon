## ① 结论(一句话)

效果域 = **声明式规格 × 单调计数器笨存储**:state 只按规格声明维护效果实例
清单 `{spec_key(唯一键), 登记节点, counter}`——counter **从 0 起单调 +1、
事件发生就 +1、永不递减永不重置、无动态需求为空**;剩余量/门槛/周期/到零语义
**全部在计算侧按规格算**(如持续 3 节点:剩余 = 3 − counter),state 结构
永不变(新增效果 = 新增规格声明,零 state 改动);效果实例按 spec_key 唯一
(投资策略环境永不重复出现,游戏规则保证,无叠加合并逻辑);生命周期 =
**TriggerKind × DurationKind 声明式**,驱动 `_swap` 派生管线效果域段
(单版本事务内原子生效,关注点派生序 = 节点判定→类型→效果推进)。

### 2.1 计数器模型(用户 2026-09-10 18:44:45 更正版;效力最高)

1. 计数器统一**从 0 开始**;**事件发生就 +1**;**单调递增,永不递减,永不重置**。
2. 倒计时/剩余量**全部在计算侧算**——例:持续 3 节点的效果,剩余 = 3 − counter
   (counter=1 时「3−1=2,还有 2 个节点」)。
3. 门槛/周期也在计算侧:**counter ÷ 阈值整除触发**(如采购专员每 7 次刷新、
   周期性发放效果按周期整除)。
4. state = **纯单调正整数计数器笨存储**;计数器方向/驱动事件/阈值/到零语义
   全部归**效果规格的计算规则**,state 不解释计数含义。

**新旧对照(作废申报)**:18:42:03 曾定「递减/递增混合模型」(躺平递减/
采购专员递增)——**已被 18:44:45 更正作废**:不存在递减计数器,一切「递减/
剩余」语义 = 计算侧由单调 counter 导出(统一推论:原「动态状态三类」
剩余节点/计数器/授予权——18:07:42——在更正版下由 **counter 一项 + 计算侧**
统一承载:剩余节点 = N − counter,授予权余量 = M − counter,不再分设三类
存储;此统一推论依确认模型导出,逐条核对候讨论)。

### 2.5 惰性读口 vs swap 急算决策规则(用户 2026-09-10 确认;派生值归位三件套)

派生值(由 state 内容算出来的值)归到哪一段计算,按「何时被需要」分判:

1. **随事件必须落账 → _swap 效果域段急算**:事件发生当时就要落账的派生值
   (计数器推进/发放/倒计时基数)在 _swap 派生管线效果域段(§2.4 驱动段)单版本
   事务内算完落账。
2. **消费时才被问 → state 内部惰性读口**:不随事件变化、消费时才需要的派生值,
   做成 state 内部读口,消费时现算,不占存储。首两个已确认实例:
   - `effective_node_ord()`(第一实例,节点域生效序读口,node-domain.md §3);
   - `xp_buy_cost()`(第二实例,2026-09-10 折入)= 商业间谍被动腿读口,见下。
3. **_swap 前只放原始读数整理**:依赖 state 内部知识的派生,禁放 _swap 前段。

**`xp_buy_cost()` 实例(商业间谍,2026-09-10 定稿)**:被动腿「购买经验花费−1」
的「−1」本身不写入 state——获得时点效果域实例登记一行(在场标记)即可;读口 =
效果域在场清单驱动,消费时:观察层有显示价 → 用显示价(商业间谍在场时备战画面
显示的即折后价,游戏已算好);观察不到 → 逻辑兜底 = 基准 4−折扣(max 0;基准
恒 4=用户口径,非按等级)。现行同语义实码载体 = kernel `xp_click_cost`
(cw_economy.py:491:level_up_cost OCR 实读优先 + `XP_CLICK_COST_FALLBACK`
兜底 + `xp_buy_cost_discount` 再减),读口归位形态候实施批。
