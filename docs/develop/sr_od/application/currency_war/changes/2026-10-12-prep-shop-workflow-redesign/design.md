# 备战与商店工序流重设计 迭代设计（总纲）

## 0. 元信息

- **迭代目标**：按用户裁定系列（2026-10-12）重新设计货币战争备战画面与商店画面的策略工序流，替换现行 mandate_v1 的两域决策编排。覆盖：备战工序重排、商店会话模型、卖出统一语义（置换账）、升级判据重轴、统一选线函数、节点边界状态重置、溢出自救阶梯。
- **状态**：草案
- **文档清单**：
  - [details/prep_pipeline.md](details/prep_pipeline.md) —— 备战画面工序流：8 步全扫逐条判据、溢出自救阶梯、节点边界状态重置
  - [details/shop_session.md](details/shop_session.md) —— 商店会话模型：一节点一会话、买入序、置换账、筹资、刷新、节末凑息、正常重开触发
  - [details/line_and_upgrade.md](details/line_and_upgrade.md) —— 统一选线函数、升级判据（概率主轴）、方向签名前置段

## 1. 问题与动机

### 1.1 现状症状

1. **备战动作优先序与用户打法错位**。晶矿在席位满时仅探测 2 次即放弃（`entry.py` 晶矿让路段）；部署排在逛店之前（买了立即上阵）；工具消费排位过早；升级动作被多层闸推迟。用户给出的目标工序（用户裁定 2026-10-12）：消耗品最先、晶矿席满时卖 1 个腾位必拿、升级在逛店前、商店按节点一次处理、部署在逛店后、工具靠后、出战兜底。
2. **血本位局买经验截断成部分购买**。现行血本位支付检查按「血够几击买几击」执行（`kernel/cw_economy.py::blood_xp_gate` 逐击支付形态），违反整买纪律（user_playstyle [41]：「需要升级的时候一次买齐，零散买 XP 完全无效益」）。用户裁定 2026-10-12：付不起整级就一击不买。
3. **升级判据主轴偏离**。现行存在三层外围拦截（调度守息门、支出预算闸、危险顾问延迟），主轴被稀释。用户裁定 2026-10-12：升级主判据 = 目标核心费用档的刷新概率账（user_playstyle [3]/[7]），一次买齐；外围拦截层删除。
4. **卖出语义缺位**。卖出候选池只有备战席（场上凑人数垫件遗漏——部署逻辑会让无关角色上阵占位，用户裁定 2026-10-12 卖出候选应含场上）；卖出无「价值比较」语义。用户裁定：店内席满买入 = 商店里新角色的价值与手上已有角色的价值比较，值得换才换。
5. **换线体系散装**。现行 12 号篇的换线机器（证据评估、换线事件、回锁窗、塌缩卖出）是多组件拼盘。用户裁定 2026-10-12：应为一个**统一的选线函数**——计算应选哪个最终阵容，算出新的就更换目标；贯穿件是强信号之一（非一票定音）。
6. **节点变动无显式重置点**。节点作用域的策略状态（商店处理标记、尝试计数等）靠键失配隐式失效，无统一边界处理。用户裁定 2026-10-12：识别到节点变动时，策略层应显式更新相关标识。
7. **溢出告警死局出口违反自动化原则**。现行溢出告警强收窄为单笔卖出，若候选空则停摆。用户裁定 2026-10-12：策略工序不允许「停下来等人」的出口；卖出候选耗尽时按损失递增阶梯逐级下探（含目标件），必然可解。
8. **文档黑话密集**。strategy-docs 正本大量使用无定义自造词（用户裁定 2026-10-12：编号引用如 M1/P40 可保留，其余自造词改正常表述或首次出现给定义）。

### 1.2 根因归层

- **语义层**（主因）：判据主次颠倒（升级主轴、卖出语义、方向语义）；两域动作的时序语义（部署/升级/凑息相对商店的位置）未按用户打法组织。
- **流程层**：备战工序的优先级序错位。
- **架构层**：腾位、卖出、方向三块各自散装多组件，无统一原语。

### 1.3 解决到哪 / 明确不解决

- **解决**：上述 1-7 全部（全部收在策略层 `strategies/impl/mandate_v1/` 与 kernel 状态键）；8 在末阶段正本更新时一并执行。
- **明确不解决**：
  - 流程层画面编排不动：刷新维持「访问终结」语义（op 结束→外循环重识别→商店 op 重新入口观察，规范出处 = strategy-docs/11 §3 决策规则 4 与 02 §7「循环内零读屏」）；开店/关店动作链不变。
  - 画面识别与建档不动（商店画面能力面已由实机归档帧确认，见 details/shop_session.md §1）。
  - 装备策略内容不动（用户裁定 2026-10-12：装备穿戴保留完整版现行实现——合成规划/分配/转移/工具判据照旧，仅其在工序中的调用位置移动）。
  - sim 基建不动（只消费：改前基线批用现有 sim 跑）。
  - 数学证明件不重推（选线函数的概率输入消费既有 P40 期望模型与注册表概率表）。

## 2. 方案

### 2.1 系统级变化（读一遍知全貌）

1. **备战画面 = 8 步全扫工序**：每次回到备战画面从第 0 步向下扫描，执行第一个满足条件的动作后重新扫描。顺序：溢出自救 → 点消耗品 → 晶矿 → 升级检查 → 商店会话 → 部署调整 → 装备与工具 → 节末凑息 → 出战。载体 = `entry.py::emit` 重写。
2. **商店画面 = 一节点一会话**：本节点未处理时进入会话；会话内循环「方向评估 → 买牌（席满走置换账）→ 刷新判据 → 收工」；正常收工打「本节点已处理」标记并记「未消费机会清单」；清单被后续正常事件（部署腾席、资产变现）解拦时清标记重开。
3. **卖出统一为「价值让位」语义**：一个卖出候选评估器服务全部卖出场景（告警自救/晶矿腾位/店内置换/筹资/节末凑息），候选池 = 备战席 ∪ 场上，按持有价值升序让位；店内场景（席满买入）额外过置换账（新牌价值 > 手上最差牌价值 + 置换摩擦才卖买）。
4. **升级判据重轴**：主判据 = 目标阵容缺件在当前等级与升一级后的刷新期望比较（消费 P40 期望模型）；人口位触发并列保留；一次买齐整级；硬闸只留等级帽与血本位支付检查（付不起整级不买）；守息门/预算闸/危险顾问三层删除。
5. **统一选线函数**：加权评分（完成度/获取前景/专属资产/环境四维）输出「未定型」或「目标线」；贯穿件为强信号之一；换目标过「切换成本 + 滞后余量」账防摇摆；评估以方向签名前置段形式挂在备战与商店两个决策入口（签名 = 证据源拼接，变了才重算）。
6. **节点边界重置**：策略入口检测到节点号变化时，显式重置节点作用域状态键（见 prep_pipeline §3）。
7. **溢出自救阶梯**：损失递增序列（消耗品点开 → 无关 1★ → 无关 2★ → 低费 1★ 目标件 → 2★ 目标件），候选池含场上；任何分支无停机出口。

### 2.2 详设划分与跨详设接口契约

| 详设 | 范围 |
|---|---|
| prep_pipeline | 备战 8 步逐条判据、自救阶梯、节点边界重置 |
| shop_session | 会话模型、买入序、置换账、筹资、刷新、节末凑息、重开触发 |
| line_and_upgrade | 选线函数、升级判据、方向签名 |

**跨详设接口契约（唯一必须在总纲定死的深度内容）**：

- **契约 A（prep_pipeline ↔ shop_session：商店会话的进出）**
  - 备战工序第 4 步是商店会话的**唯一入口**：备战决策输出 `CwActionOpenShopParam`；商店决策输出 `CwActionCloseShopParam` 为会话终结，终结时置「本节点已处理」标记（session 键，键含位面+轮次）并写「未消费机会清单」（session 键，内容 = 判据通过但被席满或金不足拦下的牌名列表 + 拦因）。
  - 标记与清单的读写唯一所有者 = shop_session（shop.py）；备战工序只消费标记（第 4 步判据）与清单（部署/卖出后的重开触发在 prep_pipeline 调用，但判定函数由 shop_session 提供）。
- **契约 B（line_and_upgrade ↔ 两域：方向状态）**
  - 方向状态 = session 上的「目标线名或未定型」单值 + 证据签名（字符串）。读写唯一所有者 = line_and_upgrade 提供的两个函数：`refresh_line_if_needed(gs)`（签名比对，变了重算）与 `line_members_view()`（当前方向下的目标名单视图）。
  - 备战工序（部署/凑息/自救）与商店会话（买入序/置换账）消费同一视图，禁各自维护第二份名单口径。
- **契约 C（节点边界重置：键清单唯一所有者）**
  - 节点作用域状态键的清点与重置逻辑唯一所有者 = prep_pipeline 的「节点边界处理」函数；shop_session 与 line_and_upgrade 把自己需要节点级重置的键登记进该函数的清单。触发点 = 策略决策入口检测到节点号（位面+轮次）变化。
- **契约 D（卖出候选评估器：单一入口）**
  - 一个评估函数，输入 =（场景, 当前容器状态），输出 = 排序后的卖出候选或空。五类场景共用同一候选池与价值排序；场景差异只体现为**过滤参数**（店内场景候选仅备战席；节末凑息仅 1★ 全额退件）与**消费方式**（置换场景由调用方比较账裁决，自救场景直接取首候选）。候选资格门（锁定线成员禁卖等）单一源不变（现行 `sell_gate.py` 资格面收编）。

### 2.3 行为验证总则

- 判据/策略层改动 sim 可见：改前基线批先行（任何行为改动落地前跑 sim 基线并归档），全部行为批完成后同参对照（strategy-work §4；A/B 仅确认，采纳判据 = 本设计 + 对抗审收敛）。
- 每个行为批配单帧锁（构造 GameState + 策略入口调用 → 断言动作序列），锁出处 = 本设计对应节。
- 实机验收判据线在行为批全部落地后、A/B 对照批开跑前预注册（载体 = proofs 目录单篇，先 commit 后跑批；必含既有验收线保全清单）。
