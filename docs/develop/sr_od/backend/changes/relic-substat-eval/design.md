# 有效词条计数工具（relic-substat-eval）迭代设计（总纲）

## 0. 元信息
- 迭代目标：练度评估遗器层的计数工具化（项目本地待办「有效词条计数工具化（口径参数化 MCP 工具）」；口径标准与设计决定见 `skills/sr-od-game-coach/references/investment.md`「评估优先级与遗器层」「有效词条计数工具的设计决定」节）
- 状态：草案
- 文档清单：无详设（单文档方案，本文件即完整设计，深度按详设要求执行）

## 1. 问题与动机
- 现状症状：练度评估遗器层（社区口径「命中了多少个有效词条」）目前只能由 agent 对 `mys_get_roster_detail` 的词条明细手数——12 角色 × 6 件 × 4~6 条副词条的计数既慢又易错，且不可复算。
- 根因归层：**能力层缺口**——口径（知识）已在 game-coach 角色档，确定性的计数算术（能力）无工具承载。
- 解决到哪：`sr_od` MCP server 新增一个口径参数化的只读评估工具（入参=每角色有效词条口径，出参=命中计数与毕业线对照）；顺带在 game-coach 角色档落地一行机器可读口径的约定（知识侧配合项，见「跨层依赖」）。
- **明确不解决**：
  - 不内置任何默认口径（设计决定：口径是活知识，写死必与角色档漂移）；
  - 不做强度打分（分数=实战，工具只数数）；
  - v1 不做按词条滚动值域的加权评分（暴击 5.4~6.9%/条等权重表）——属外溢议题，若未来需要自成新迭代；
  - 不解析角色档 markdown（口径行由调用方读取后作为参数传入，工具不读任何知识库文件）。

## 2. 方案

### 2.1 系统级变化
`sr_od` MCP server 工具组新增一个只读工具 `mys_evaluate_relic_substats`，背后是一个纯计算模块（零 IO、零副作用，可独立测试）。数据流：调用方传「每角色口径 + 可选名册明细」→ 工具（缺名册时自调 `mys_get_roster_detail`）→ 逐角色逐件数词条 → 返回计数与对照。

### 2.2 MCP 工具接口（字段名为最终实现名）

**工具名**：`mys_evaluate_relic_substats`（title：评估遗器有效词条；`ToolAnnotations(readOnlyHint=True)`）

**工具描述文本（实现时逐字使用）**：
> 评估遗器副词条的命中情况——按传入的每角色有效词条口径，对名册遗器明细做确定性计数：命中数/浪费分布/主词条核对/毕业线对照。口径由调用方提供（取自 sr-od-game-coach 角色档的「有效口径」行，可按阵容定位调整），本工具不内置任何默认口径；未传口径的角色不评估。`roster_data` 可传 `mys_get_roster_detail` 已拉取的结果避免重复请求；不传则工具自动拉取。

**入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `criteria` | list[object] | 是 | 每角色一条口径，结构见下 |
| `roster_data` | object | 否 | `mys_get_roster_detail` 返回的 `data`；缺省则工具自拉 |

**criteria 元素字段**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `character_name` | str | 是 | 角色中文名，对名册精确匹配 |
| `effective_substats` | list[str] | 是 | 有效词条清单；元素可以是词条标准名，也可以是口径包名（内置表自动展开，见 2.4）；清单的补集一律视为无效 |
| `main_stat_expectations` | object | 否 | 部位中文名（躯干/脚部/位面球/连结绳）→ 可接受的主词条标准名数组；缺省则该角色跳过主词条核对 |
| `stat_thresholds` | object | 否 | 词条标准名 → 毕业线数值（如 `{"效果命中": 120}`）；缺省则该角色跳过毕业线对照 |

**出参**（统一信封 `{"status","message","data"}`，与 mys 工具组惯例一致；依据：`src/sr_od/backend/mcp/mys_tools.py` 各工具返回形态）：

data 结构：

| 字段 | 类型 | 说明 |
|---|---|---|
| `results` | object（角色名 → 评估结果） | 见下 |
| `not_found` | list[str] | criteria 里传了、名册里找不到的角色名（名字写错/未持有） |

单个角色的评估结果字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `total_rolls` | int | 6 件遗器副词条强化次数总和 |
| `effective_hits` | int | 落在 `effective_substats` 内的强化次数 |
| `hit_ratio` | float | 命中占比（total_rolls 为 0 时置 null） |
| `hits_by_stat` | object | 词条标准名 → `{"rolls": int, "value_sum": float}`（仅命中项） |
| `wasted_rolls_by_stat` | object | 词条标准名 → 浪费次数（命中清单的补集） |
| `main_stat_check` | list[object] | `{"slot": "躯干", "actual": "暴击率", "expected": ["暴击率","暴击伤害"], "matches": true}`；未传 main_stat_expectations 则为空数组 |
| `threshold_report` | list[object] | `{"stat": "效果命中", "current": 134.5, "line": 120, "gap_text": "达标 +14.5"}`；current = 该词条名在主+副词条的数值求和；未传 stat_thresholds 则为空数组 |
| `weakest_piece` | object\|null | 浪费次数最多的单件：`{"set_name", "slot", "effective_hits", "wasted_rolls"}`；并列取命中更少者；全零时为 null |
| `verdict` | str | 一行中文结论（模板生成，见 2.3） |

### 2.3 计算规则（确定性，实现者无需再设计）
1. **词条名归一**：入参与名册词条名（`name_cn`）都经内置**别名表**归一到标准名后比对；别名表 = 术语词汇常量，属 MCP 可内置范围（稳定词表，非判断口径）。⚠ 名册词条名的真实全集（尤其「攻击力」flat 与「攻击力提高」% 是否同名异义）实现第一步先拉一次真实名册核对，别名表据此定稿（land 3.1 验收项）。
2. **口径包展开**：`effective_substats` 中的口径包名经内置**口径包表**展开为标准名集合（如「双暴攻」→ 暴击率+暴击伤害+攻击力提高）；口径包表同属词汇常量。已知包：双暴攻/速双暴/双暴生/击破速/命中速/生命双暴；实现时以真实名册核对后定稿枚举。
3. **命中计数**：每条副词条 `name_cn` 归一后 ∈ 展开后的有效集合 → `effective_hits += 强化次数(times)`，并按标准名累加 `value`；否则按标准名累加 `wasted_rolls_by_stat`。
4. **主词条核对**：逐件 `pos_cn`（躯干/脚部/位面球/连结绳）取主词条名归一后与 `main_stat_expectations` 对应部位的可接受集合比对。
5. **毕业线对照**：`stat_thresholds` 的每个键：current = 主词条（若同名）+ 副词条 value 求和；gap_text = `达标 +X` 或 `差 X`（保留 1 位小数）。
6. **最弱件**：单件浪费次数最高者，并列取命中次数更低者；浪费与命中全零（无副词条数据）置 null。
7. **verdict 模板**：`命中 {hits}/{total}（{ratio:.0%}）{主词条穿错 N 件；}{达标/差线摘要；}最弱件：{slot}（浪费 {n} 条）`——无主核对/无阈值时省略对应短句。
8. **跳过与缺名**：名册中找不到 `character_name` → 记入 `not_found`，不影响其他角色；criteria 为空列表 → 全部跳过，`results` 为空对象。

### 2.4 常量表初稿（实现第一步据真实名册定稿）
- **别名表**（口径别名 → 标准名）：攻击%/大攻击/攻击力百分比→攻击力提高；生命%/大生命→生命值提高；防御%/大防御→防御力提高；暴击→暴击率；暴伤/爆伤→暴击伤害；命中→效果命中；抵抗→效果抵抗；击破→击破特攻；充能/回能→能量恢复效率；治疗→治疗量加成；速度→速度（同名直通）。
- **口径包表**：双暴攻=暴击率+暴击伤害+攻击力提高；速双暴=速度+暴击率+暴击伤害；双暴生=暴击率+暴击伤害+生命值提高；击破速=击破特攻+速度；命中速=效果命中+速度；生命双暴=生命值提高+暴击率+暴击伤害。
- 两张表都是常量 dict，放纯计算模块顶部，注释标明「词汇归一/速记展开，非判断口径；条目随真实名册核对更新」。

### 2.5 代码结构与跨层依赖
- 纯计算模块：`src/sr_od/backend/mys/relic_substat_eval.py`——`evaluate(roster_data: dict, criteria: list[dict]) -> dict` 纯函数 + 两张常量表；不做任何 IO（依据：本迭代「明确不解决」与测试规范零副作用要求）。
- MCP 适配：`src/sr_od/backend/mcp/mys_tools.py` 按既有工具工厂惯例注册（依据：同文件 `mys_get_characters` 等既有注册形态与信封惯例）；`roster_data` 缺省时经既有 controller 调 `mys_get_roster_detail` 取数。
- **跨层依赖（知识侧配合项，非本迭代代码面）**：game-coach 角色档需补「有效口径: <口径包名或枚举>」行（`references/characters/<角色>.md`），并随知识库维护流程维护——调用方据此行组装 `criteria`。本迭代仅覆盖候选队 12 角色（星启诊断使用面），全量铺开归 game-coach 维护流程。
- 字段命名原则：英文小写下划线、名词短语自释（`effective_substats` 而非 `eff`/`list1`）；中文只出现在工具描述与输出 `verdict`。

### 2.6 关键取舍
- **口径参数化 vs 内置默认口径**：选参数化。内置默认会与角色档形成双真源必然漂移，且定位差异场景给错数（裁定记录：game-coach investment.md「有效词条计数工具的设计决定」）。
- **v1 按次数计数 vs 按滚动值域加权**：选次数。加权需要词条滚动值域常量表，收益与复杂度未经实战验证——先出次数报告看是否够诊断用，加权列为外溢议题（见 §1 明确不解决）。
- **roster 传入 vs 工具自拉**：两者都支持、传入优先。全量名册载荷大（64 角色数百 KB）且接口有风控消耗，调用方已拉过就不重复拉。
