# 核三·治本核验报告

> 审查对象：本迭代 design.md / landing.md（2026-11-20-ci-build-test-branch）。
> 审查方法：只读核验——两仓 workflow 与脚本文件原文、GitHub 线上实查（分支头、workflow 运行历史、open PR 与标签、SR main 上的文件清单）、ZZZ 仓 git 历史与 PR #2655 原文、本仓 `.debug/temp/` 支持件。未改动两仓任何文件、未触发任何 workflow。
> 名词约定（本文自足）：「测试闭环」= design §1 的说法，指「test 分支重建成功后自动联动 test-check 在 test 分支上跑全量测试」；「消费方」= 机制产出的结果（分支产物 / 测试红绿信号）由谁拿去使用并采取行动。

## 结论摘要

- 阻断 1 / 应修 4 / 存疑 2 / 低级 1。
- 总判定：**打回补设计（不推翻方案骨架）**。B1 是 design 的论证根基——「集成分支的验证闭环即本仓对它的消费方式」这句话在 SR 语境下不成立：测试红了之后没有任何「谁看得到、谁去修」的设计，而姊妹仓 ZZZ 的同款 CI 测试恰恰因为「红告警长期无人处理变成噪音」被其维护者亲手禁用（2026-08-03 至今未恢复）。必须补上红信号的去处与首跑消化方案才能放行。工程骨架（照搬脚本 + 基线参数化）本身没有问题。
- 归层判断（攻击线 1/2 的回答）：design 把根因归「流程层（缺集成验证环节）」在字面上对症状 1 成立，但本仓当前最重的病灶确实是治理层（main 停摆四个月 + 活线直推零覆盖），C 对三项症状的治疗在落地时点全部为零（休眠卡点），生效时点悬空在一件无迭代、无排期、无负责人的治理动作上。这不足以构成打回理由（打回 C 也治不了治理），但构成「带战术权衡放行」必须写明的前提——见 Q1。
- 治的是根还是症状：C 对「PR 之间叠加冲突」这一类问题是治本（机制性防线，激活后自动运转）；对「活线直推零覆盖」只有每日一次的事后全量间接覆盖（design 未点明）；对 main 停摆不治（前置）。落地即休眠的定性：是预备性占位，不是立即生效的治本——可接受，条件是休眠期验收知识入库（F3）。

## 逐条发现

### [阻断] B1 测试闭环缺最后一环——红信号没有去向，且 ZZZ 已用行动证明这类告警会以「噪音」收场

- 位置：design.md §1「解决到哪」（「集成分支的验证闭环即本仓对它的消费方式」）；§2.2-2/3（闭环接线）；§2.3 全节（无任何告警/消化设计）
- 证据：
  1. SR 现行 test-check.yml（活线）的失败出口只有一步 `Test failure notification`（96-106 行），内容是往本 job 日志里打三条 `::notice::`/`::error::` 注解——不建 issue、不打标签、不通知任何人。test 分支上的测试红了，产物就是 GitHub Actions 页面一个红叉。
  2. 定时任务（schedule）触发的运行没有天然关联人：GitHub 对定时任务失败的默认邮件通知只覆盖「watch 了仓库且开了 Actions 通知」的人——本仓无证据存在这样的 watcher。design 全文没有回答「红了谁看到、谁修、多久没人修算失败」。
  3. ZZZ 前车之鉴（ZZZ 仓 PR #2655，2026-08-03，标题「ci: 临时注释跳过 test-check 中的 pytest 测试步骤」）原文理由：「如果一个告警从来都不成功，那它就算噪音，需要降噪」。该「临时」禁用到今天（2026-11-20）已 3.5 个月未恢复——ZZZ 的 test-check 至今跑的是空壳（测试步骤整体被注释，ZZZ test-check.yml 69-85 行）。也就是说：**ZZZ 从未有过「test 分支跑测试」这件事**，它的 test 分支消费方是 CNB 分发（2026-11-20 实查其运行链：Build Test Branch 02:31 success → Sync to CNB 02:31 workflow_run success，由真人在 CNB 侧下载试用）；SR design 把 ZZZ 用在 CNB 同步上的 workflow_run 触发模式挪到 test-check 上造出的「测试闭环」，是一个没有先例、没有消费方、没有失败处置的新机制。
  4. 叠加风险：SR 的 test-check 最后一次真实运行是 2026-08-07（pull_request 触发），结论 failure，此后 3.5 个月零运行（GitHub Actions 运行历史实查，期间全部运行为每日关 issue 定时任务）。休眠解除、机制首跑的那天，面对的是一条四个月没跑过、最后一次跑是红的测试流水——首跑红是大概率事件，而按当前设计，这个红没有去处。
- 建议（打回补设计的具体补法，补完即可放行）：
  1. design 增设「红信号去向」小节，至少落实一条可执行路径，例如：test-check 在 workflow_run 事件下失败时，由脚本向本次集成的各 open PR 评论失败摘要（build_test_branch.py 已持有 PR 列表与写权限，改造点小）；或每日运行失败时自动开/复用一个跟踪 issue；
  2. 增设「首跑消化预案」：机制激活首跑允许红，但必须指定谁负责把首次全量拉绿（写进 landing 的前置满足后核对项）；
  3. 在 §1 如实改写「消费方式」一句：当前设计的消费方式是「每日无人值守的红绿信号」，其价值成立的前提就是 B1.1 的告警路径存在。
- 判定：**打回**（补上述三处设计后放行；工程骨架不动）。

### [应修] F1 「本仓无 CNB 渠道」与仓库事实相悖——main 上存在正在运行的 CNB 镜像

- 位置：design.md §1「解决到哪」括注（「ZZZ 的 test 分支消费方是 CNB 镜像分发，本仓无该渠道」）
- 证据：SR 仓 GitHub main 分支上存在 `.github/workflows/sync-cnb.yml`（GitHub 文件清单 API 实查；内容为 `on: push`（无分支过滤）+ 手动触发，全量镜像到 `cnb.cool/OneDragon-Anything/Star-OneDragon.git`），workflow 状态 active。同会话产出的决策支持件 `.debug/temp/PR612处置分析.md` 自己也记录了「（main）有 sync-cnb.yml——7 月 #610/#611 合入」。「无该渠道」作为「所以只能拿测试闭环当消费方」的论据，前提是错的——需要区分两层事实：镜像管道（存在，main 上 active）与测试者消费人群（是否存在无从查证，且该文件不在活线上）。另一项待解释的观测：该 workflow 注册了无分支过滤的 `on: push` 且活线 2026-11-19 有推送，但全仓最近 30 次运行（覆盖整整一个月）无一次 Sync to CNB——渠道文件存在、近月从未实际流过水，真实可用性存疑，恰说明 §1 该处值得把事实写准而不是一笔带过。
- 建议：§1 该句改写为两层事实陈述：「本仓 main 上有 CNB 镜像管道（sync-cnb.yml，2026-07 合入），但无已知测试者消费人群，且活线上无此文件——故不复制 ZZZ 的 CNB 分发消费方，改用测试闭环（见 B1 的去向设计）」。若作者其实掌握「CNB 分发在 SR 有使用者」的反证，则应重新权衡两种消费方。
- 判定：应修（论证前提纠正，不动方案）。

### [应修] F2 备选取舍面缺失：与 C 同症状的更轻治疗（「活线改走 PR 流」「人工叠加验证」）没有进入 §2.4 的对照

- 位置：design.md §2.4（现有四条取舍：照搬 vs 重写、不写单测、弃常开 PR、时区）
- 证据：
  1. 「活线改走 PR 流」直接治疗症状 2（活线 CI 零覆盖），且 pull_request 类触发不受默认分支限制（design 自己在 §2.3-1 与支持件里都写了这条平台规则）——即它**立即生效、零新代码**，对比 C 的「每日一次事后全量 + 落地休眠」。这是同症状下两种治疗的正面取舍，§2.4 完全缺席。
  2. 「PR 合入前由维护者本地叠加验证」治症状 1（PR 间冲突），本仓 open PR 仅 10 个、全部长期搁置（最新一个 2026-11-13，其余 5-7 月）——流量低到人工叠加成本几乎为零，弃用「每日自动机制」选「人工」并非显然不合理，但 design 没有给出比较。
  3. 现实暴露面：当前 10 个 open PR **无一携带任何标签**（GitHub API 实查 labels 全空）。机制激活后若无人打 `test-branch` 标签，每日重建的 test 分支恒等于基线（活线）——此时每日全量测试实际上变成「活线每日回归」（这对症状 2 反而是唯一的实质治疗路径），但这些联动效应 design 一处都没有点明（§2.3-4 只算了费用账）。
- 建议：§2.4 补两条取舍：①「活线改走 PR 流」——写明为何不选（如单人直推节奏、PR 开销、与 #612 build 标签机制的交互……作者需给出真实理由，而不是缺席）；②「人工叠加验证」——以 PR 流量数据说明为何机器化值得。同时点明「零标签期间 test 分支 == 活线基线，test-check 每日全量即活线每日回归」这枚双面硬币（收益：活线获得覆盖；成本：无人需要结果时每日白跑 10-20 分钟 Windows runner）。
- 判定：应修（补取舍面；这也是 Q1 归层质疑的落地出口——让读者能看到 C 是在什么替代方案下胜出的）。

### [应修] F3 休眠唤醒的验收知识唯一载体不入库——`.debug/temp/TODO.md` 被 gitignore，跨人、跨机、跨时间都不可见

- 位置：design.md §2.3-1（「登记 `.debug/temp/TODO.md` 跟进」）；landing.md 3.1 完成判据同引
- 证据：`.gitignore` 第 50 行 `.debug/`。该 TODO 条目（2026-11-20 建，实查存在）确实写全了背景与完成判据，但：协作者 ShadowLemoon 看不到它；换机器、重克隆即丢失；半年后 main 治理了结时，「C 迭代怎么验收、首跑该看什么」的知识全部押在一个设计上就会消失的文件里。迭代自身的 README.md 进度区与 landing.md 都不承载这条唤醒核对项（迭代按当前结构会在机制从未实跑的状态下走完末阶段正本更新并收尾）。
- 建议：把「前置满足后首跑核对」的三条判据（Build Test Branch 首跑 success、test 分支重建正确、test-check workflow_run 联动跑通——TODO 条目里已写好）固化到入库载体：landing.md 增设「前置解除后核对项」小节（或 README 进度区常驻一行未竟项，迭代收尾义务里明确该项不因正本更新完成而清零）。`.debug/temp/TODO.md` 可继续作本机提醒，但不得是唯一载体。
- 判定：应修。

### [应修] F4 「照搬 ZZZ 已实跑验证的实现」话术掩盖了增量部分恰好是没有先例的新接线

- 位置：design.md §2.4 第一条（「照搬 ZZZ 已实跑验证的实现……SR 侧只动基线参数化三处——重写无收益、引入新风险面」）
- 证据：「已实跑验证」只覆盖 build_test_branch.py + build-test-branch.yml（ZZZ 每日 success 属实，2026-11-20 实查）。而本迭代真正的增量——test-check 的 workflow_run 触发 + 三事件测试仓 checkout 表达式——在 ZZZ 没有对应物：ZZZ 的 test-check 从未被 workflow_run 触发过（其触发只有 pull_request/push main），其测试步骤更自 2026-08-03 起整体禁用（见 B1）。§2.2-2 引的 ZZZ 先例是 sync-cnb 用 workflow_run，不是 test-check。即：参数化三处之外，SR 侧新增的闭环接线全部是未跑过的推断性代码，且按 §2.3-1 落地后还无法实跑验证。
- 建议：§2.4 改为分层陈述：「照搬部分（建分支脚本+workflow）＝ZZZ 每日实跑验证；新写部分（test-check 的 workflow_run 接线）＝无先例推断，验证手段只有前置解除后的首跑核对（见 F3 的入库载体）」。landing 3.2 的完成判据相应承认「本阶段全部判据均为静态对照，行为验证整体后置」。
- 判定：应修（诚实度修正，避免读者误以为整条链有实跑背书）。

### [存疑] Q1 归层与「占位」定性：C 落地时点对全部三项症状的改善为零——可以带战术权衡放行，但前提要写进设计

- 位置：design.md §1（根因归层、「明确不解决」）、§2.3-1
- 证据：
  1. 三症状的治疗路径全部经过休眠卡点：症状 1（PR 间冲突）——触发休眠，且当前 10 个 open PR 零标签，激活后还需有人开始打标签才有效果；症状 2（活线零覆盖）——唯一的机制性治疗是「test 分支=基线时的每日全量」（design 未点明，见 F2.3），同样休眠；症状 3（main 停摆）——不治，是前置。
  2. 分叉规模实查：活线领先 main 6409 个提交、落后 3 个（GitHub compare API）——「治理」不是切一下默认分支那么轻，但落后仅 3 也说明合流工作量可控；治理迟迟未动的原因在支持件里已列（等用户与 ShadowLemoon 协调），无排期。
  3. 「明确不解决」把治理划出边界**是诚实的**（明写了它是前置而非任务，处置归用户与协作者）——但 C 的全部价值兑现压在这个无排期前置上，设计的风险节只用了「落地≠生效」一句带过休眠期的另一半风险：休眠文件无人维护，活线高速演进下（四个月 6409 提交）休眠的 test-check 接线与 BASE_BRANCH 配置可能随活线换代/依赖漂移而失效，且失效要等到首跑那天才暴露。
- 建议：接受「预备性占位」定位（打回 C 并不能治治理，反而丢掉治理了结日的即战力），但 design §2.3-1 补两点：①把 F2.3 的「激活后对症状 2 的实际治疗路径」写明（当前读起来 C 只治症状 1，价值叙述不完整）；②休眠期维护责任一句话（谁在活线换代时改 BASE_BRANCH 那一行——§2.2-1 已说「只改一行」，补上「由谁记得改」，可与 F3 的入库载体合并解决）。
- 判定：**带战术权衡放行**（B1/F 系列修完的前提下）。

### [存疑] Q2 前置件悬空：main 停摆治理没有自己的迭代、排期与负责人，C 的生效时点挂在一个不存在于任何正式跟踪体系里的动作上

- 位置：design.md §1「明确不解决」第一条；`.debug/temp/PR612处置分析.md`（三路线决策支持件，不入 git）
- 证据：本仓 docs/ 全域与 git 历史均无「集成验证缺失」同族前例（git log 按关键词实查，命中全是货币战争玩法的无关「集成」字样）——本件为同族第一件，独立成迭代本身成立（A+B 有 #612 现成实现只需处置、C 需新写，工作面不同，拆分合理）。但真正的母题「main 停摆治理」：无迭代、无设计文档，唯一的过程性分析件（三路线比较）躺在 `.debug/temp/`（不入库）；C 的 design 把它当前置写死，TODO 里等「用户协调后指示」——若协调拖到半年后，B1/F3/F4 所修补的验收知识就是那时候唯一的接力棒，这更加放大了 F3 的载体问题。
- 建议：不必为本件打回；建议在 design §1「明确不解决」处补一句前置件的跟踪位置声明（「处置分析存 `.debug/temp/PR612处置分析.md`（不入库），治理动作由用户与协作者协调，本仓不跟踪其排期」——把「我们知道它悬空」写成显式事实），并把三路线要点以一两行沉淀进本迭代 README 或 design 脚注，防支持件被清理后失忆。
- 判定：存疑（不阻断，与 F3 一并处理成本最低）。

### [低级] L1 引用悬空：「docs/develop/setup 同类记录：ZZZ repositories.md」在本仓不可寻址，且被引文件并无「供测试者使用」的表述
