**证据(代码直调)**:

**附带(任务面②的分层合法性)**:即使改挂 StrategySession,`cap_sup_latched` 是 cw4 判据派生概念(非 `active_strategies` 那类游戏级概念),直入 kernel 共享类需一句分层论证(建议:session 通用「观测锁存注册表」`dict[str, bool]` 或显式论证单字段合理性);设计件当前对该层问题零论证。局态销毁、cw3/legacy 局写该字段(共享 handler 在 cw3/legacy 局同样置位、无消费方)两问在 R74-2(c)/R75-4 只以「行为零影响」一句带过,载体改 Session 后该申报可自洽,但需随载体勘误重述。

R75 批六项中,两项高严重度缺陷(N1 载体错位、N2 sim 注入点不存在)使 R75-1/R75-4 的落位声明在**按文本落码即失效**的意义上不合格:锁存逐帧重置、sim 覆盖恢复声明落空、候选集构成口径的未申报分叉使 sim/实机可比性声明超出证据;N3-N5 使 R75-2 判读与 R75-3 频度申报当前不可实现或内部不自洽。R75 批的「零冲突自查」对本批内部的三处(载体两读、候选集构成、精确/模糊查询)未完成自洽,属八修复批尾巴,建议下一批(落码批前)按 N1-N5 修复方向逐条收口。

**适用域限定**:本报告基于 R75 落位后态的**设计文本**与当前代码注册表/实现直调;cw4 包尚未落码,全部发现为设计级缺陷(实现者按文本落码即触发),非现网行为缺陷。若后续批把载体改挂局级载体(StrategySession 或等价)、sim 注入点改日程注入处并申报 offered-but-not-picked 分叉,则 N1/N2 随之消解;N3/N4/N7 的修复不阻塞落码批开工(观察级),N1/N2/N5 应视为落码批前置。
