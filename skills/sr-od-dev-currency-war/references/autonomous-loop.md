## 1. 阶段定位与编排者职责

- 阶段目标:用真实对局摸清新版本的画面、机制、与旧版本的差异,收集问题。提升对局成绩与策略调优不属于本阶段。
- 运转形态只有一条主线:编排者反复派实机探索 agent 亲自玩货币战争——玩法知识与操作方法按游玩 skill `sr-od-currency-war`(面向玩家的 skill),经项目 MCP 工具执行;每次派发以一局为限(单局限令,§2.1),实机探索 agent 打完当前局即停止汇报,编排者按局间机械条件映射处置(§2.1 第 7 项:有未闭环问题→处置循环;无问题且清单未覆盖→判读批规划建议单照抄续派;全覆盖→收束)。实机探索 agent 遇到问题就停止操作(停止一切游戏操作、保持游戏窗口状态原样,向编排者汇报后等待处置,细则见 §2.3);编排者按 §3 走问题处置循环;处置完让实机探索 agent 继续工作。
- **推进模式映射**:CW 实机探索期=**串行模式**(游戏窗口与 MCP server 单跑道,独占资源天然串行——并行度取值恒为 1;策略迭代期口径见 §6)。探索产出开迭代是默认去向(自主模式 §2-③:挂机下不设「小改直做」出口)——知识产出(补画面档/修正知识文档)与问题修复都立线走 od-dev-run-iteration,最小形态=设计一页+任务一行,门一个不少。
- 编排者只做机械动作(派子 agent+记录三份文件,通用框架单一源,本文件不展开),不参与决策:判断类动作机械规则化或外放子 agent 产出固定节,无判据可依登记待裁、线转等待(自主模式 §2-②)。
- 编排者不做:技术判断(方案倾向、归因结论、评审意见一律由对应角色子 agent 产出)、亲自写代码与文档、亲自操作游戏。编排者夹带技术倾向会污染对抗评审与用户裁决——这是本流程要防的第一件事;用户明确指名要编排者亲手做某事时,以该指令为准。

## 2. 实机探索 agent

### 2.1 任务书构成(CW 实例差异,逐项并入模板实例位)

任务书以 od-dev-agent-autonomous-mode skill 的 references/line-templates.md §1 探索模板为基复制(实例位照填),再按本节条目 1-8 增补 CW 条款(领域增补规则见该模板库头注);CW 实例差异:

1. **操作依据**:游玩 skill `sr-od-currency-war`(面向玩家的 skill)——实机探索 agent 的玩法知识与操作方法从它取;任务书不复制其内容,实机探索 agent 也不依赖编排者的会话历史。
2. **关注清单**:本次要关注/验证的内容——由实机探索 agent 开工步自起草(输入:用户当期指令原文∪跨迭代挂账文件未竟项∪游玩 skill 玩法文档中当期值得核对的面;仍空=按操作依据 skill 的玩法机制文档自选关注点并如实申报来源),每条注来源,零来源条目禁入;每条写清「关注什么、观察到什么算值得关注、怎么记录」。探索阶段的终止判据=交付固定节「清单逐条覆盖状态」全为已覆盖(凭据随附)或用户叫停。
3. **停止操作纪律**:§2.3 整段并入任务书。
4. **现场交接信息**:接管已有对局时,写明交出方(= 上一个持有窗口的 agent,见 §2.2 交接协议)报告的现场信息四项(当前画面 / 对局进度 / 血量与金币 / 未了事项)。
5. **文件面**:探索产物只写知识归档(知识文档/画面档,分层判据见 SKILL.md §3)与探索报告,不动任何代码。
6. **交付**:探索报告与证据截图落自主工作文件夹当线子目录(`<工作文件夹>/<线名>/`),回信格式按通用模板。
7. **单局限令(每次派发最多一局)**:任务书写明本局的局内目标(打到哪里/验证什么)与顺带取证清单——由判读批按跨迭代挂账文件+单局报告给「下一局规划建议单」(判读批任务书要素:输入=跨迭代挂账文件+单局报告;操作依据=本 skill references/telemetry-reading.md;交付=下一局规划建议单,字段=局内目标+顺带取证清单;报告落 <工作文件夹>/<线名>/;回信≤10 行=建议单要点+路径。通用层无此模板,CW 自持),编排者照抄进任务书;实机探索 agent 完成本局(终局或中止)即停止操作、把画面收回大厅待命位、向编排者发单局报告(局账/取证发现/遗留/晶球余额),然后等待——**不获得多局连续授权**。局间处置=机械条件映射:报告有未闭环问题→转问题处置循环(§3);无问题且关注清单未全覆盖→判读批出下一局规划建议单,照抄续派;清单全覆盖→收束窗口。为什么:局间机械步进 = 编排者控制进度的抓手,连续多局授权会让探索方向失控且局间新待办无法插入。
8. **最高难度默认**:实机探索局默认选择当前可解锁的最高难度——探索期目标是暴露新版本问题(画面/机制/策略),难度压力越大暴露面越广,低难度局验不出策略与经济模型的压力面。若最高难度不可达(未解锁/条件不足),如实报告当前可达难度与解锁路径,编排者记档进关注清单并在解锁后上探。新版本初未达最高难度属常态:探索期随解锁逐步上难度,难度选择写进每局任务书。

### 2.2 窗口所有权(串行铁律)

- 一个游戏窗口同一时间只归一个 agent;编排者显式登记「谁、从何时起、干什么」于占用表(occupancy.md)。
- 占用窗口的动作 = 点击/拖拽/输入等驱动游戏的操作;只读识别(analyze_screen)不算占用。
- 派发任何会占用窗口的活(探索/诊断/实机验证)之前:先查窗口登记与项目 MCP 运行状态(get_run_status);窗口已有持有者就把新活排队,不派第二个。
  - 为什么:两个 agent 同时驱动同一窗口会互相干扰(点击落进对方操作的画面、画面被抢),且事后从运行记录难以区分是谁的操作——防患只能靠事前登记,不靠事后归因。
- 交接协议:交出方交窗时报告现场信息四项——当前画面 / 对局进度 / 血量与金币 / 未了事项;接管方开工第一步先识别当前画面(analyze_screen),与交接报告逐项核对,对不上=按遇问题停止纪律报编排者派诊断(现场视为不可信),不先动手。
- **MCP server 重启执行权归编排者**(通用框架规则;CW 重启运维细则=runtime-ops.md「启动与重启」节——重启前四步确认/对局中守卫拒绝/改动集中纪律);探索/诊断/验证 agent 禁自行重启。

### 2.3 停止操作汇报纪律(任务书必含)

- 遇到问题(操作不生效 / 画面异常 / 疑似机制变化 / op 报错)的动作顺序:
  1. 停止操作:一切游戏操作停下,游戏窗口状态保持原样,不试图自行修复或退出当前画面;
  2. 保存证据:截图留档 + 一句话描述 + 发生时间;
  3. 汇报:现象 + 证据 + 发生时点报给编排者,然后等待。
- 禁止:自行改代码;自行绕过问题继续跑(把问题藏进「看起来跑通」);未经交接就把游戏窗口丢在当前状态。
- 为什么:现场就是诊断的证据;修了、绕了、清了,证据就没了,同一个问题还会再来一次。

## 3. 问题处置循环

### 3.1 循环全貌

1. 实机探索 agent 停止操作并汇报 → 编排者派**诊断 agent**定位根因(诊断任务书要素:输入=单局报告+现场交接四项/游戏操作可现场复现但代码只读/交付固定节「处置建议」四值枚举/报告落 <工作文件夹>/<线名>//回信≤10 行=处置建议一行+报告路径;通用层无此模板,CW 自持)。
2. 诊断产出固定节「处置建议」(四值枚举,字段必附),编排者照派:
   - **知识修正**(机制理解错 / 操作方法错 / 画面建档缺口;附目标文件指针+生效方式):立知识文档线(小迭代:补画面档/修正知识文档)走 od-dev-run-iteration,收口后让原实机探索 agent 继续工作;
   - **单点修复单**(改哪+判据):属当前探索线申报面内的=线内任务(当线迭代 tasks.md 加任务,不立新线),派线内修复任务(实现+验证)后继续;
   - **立线建议**(线名+改哪+判据+优先级+原文切片):触设计意图或跨多文件=立新线走 od-dev-run-iteration 完整生命周期(实机验证=复现原故障场景确认已修)→ 重启 MCP server(运维细则见 [runtime-ops.md](runtime-ops.md))→ 让原实机探索 agent 继续工作;
   - **环境处置**(重启/重试+可复跑检查命令):按 occupancy 规则机械执行。
   建议字段缺失=格式缺陷打回重交;**诊断熔断**:同一现象第 3 次=登记待裁(pending-decisions.md),线转等待,其他线继续。
3. 循环期间原实机探索 agent 保持停止状态等待,探索线登记暂停(等处置,恢复点=诊断结论指针),编排者按取活规则接其他排队线;窗口可能被诊断/验证 agent 按 §2.2 接管,窗口归谁以编排者的登记为准。

### 3.2 各角色边界

| 角色 | 游戏操作 | 代码 | 说明 |
|---|---|---|---|
| 实机探索 agent | 可 | 只读 | 按任务书玩货币战争;遇问题停止操作并汇报;问题处置交编排者另派(§3) |
| 诊断 agent | 可(现场复现) | 只读 | 定位根因,不改代码 |
| 设计 agent | 不操作 | 只写设计稿 | 设计与实现分开,防同一个 agent 既定方案又自己验收 |
| 对抗评审 | 不操作 | 只读 | 每轮起全新的、没读过前几轮讨论的子 agent——看过前几轮讨论就会被已有思路带偏,挑不出真问题 |
| 实现 agent | 不操作 | 写 | 按设计稿落地;与设计稿对不上的地方报告编排者,不自作主张改设计 |
| 实机验证 agent | 可(复现验证) | 只读 | 验证后把窗口停回已知稳定状态(大厅或备战画面)再归还 |

### 3.3 传话纪律(约束编排者本人)

- 问题原样带给用户,不加工不筛选;用户裁决原样传给对应子 agent,不夹带编排者的技术倾向。
- 设计争议需要用户裁决时:把双方论点原样并列转达,不排序、不建议。
- 用户未应答时(挂机常态):无判据可依的情形登记待裁(pending-decisions.md),线转等待、其他线继续,禁编排者自行决定(通用框架定义)。

## 4. 进度登记与跨会话接口

- 自主推进不设总的任务清单文件:关注清单由实机探索 agent 开工步自起草(§2.1 第 2 项,用户当期指令原文是输入之一);编排层登记(线表/占用表/待裁登记三份文件)=通用框架定义的自主工作文件夹(SR 项目惯例 .debug/temp/ 下 autonomous/<开工日期-主题>/)。
- 推进期间子 agent 做迭代时,按 od-dev-run-iteration(完整迭代 skill)的 tasks.md 格式在迭代目录内登记进度;编排者不替子 agent 记迭代进度。
- 待办登记:货币战争专用的待办文件 = `.debug/progress/CW跨迭代挂账.md`(定位见 SKILL.md §3「跨迭代挂账」行);条目写明「改哪、判据是什么」——这两样是立线定迭代形态时要对照的原料,入口写齐 = 初判纯文字对照,不强制格式。**完成即删**:条目闭环(清偿/实证/裁决定谳)时当场把该条目从跨迭代挂账文件删除——文件里只留开放项,禁留「已完成/已清偿」划线态或存档句堆积;有长效价值的裁定结论随 commit message 或知识卡固化,不靠文件留尸。为什么:文件混入完成态会让后来者把已完结条目当活待办盘,文件越长真待办越难找。
- 探索发现的归档:知识类结论落对应知识文档或画面档(分层判据见 SKILL.md §3);过程叙事不进本 skill。

## 5. 领域叠加件(通用 skill 的 CW 映射)

通用层机制自含完整默认形态,本节只写 CW 的映射与增量(分层边界见该 skill 的 design/overview.md「边界」节:领域操作归领域 skill):

1. **推进模式映射**:CW 实机探索期=串行模式,见 §1——本领域缺省串行,用户当次明示并行时按通用层取值序生效(实机与 MCP 单跑道的互斥由占用表把关,不随线数放宽);策略迭代期同口径(§6)。
2. **核心面清单**(landing 影响面申报与对抗/review 对照用):CW 的核心/策略面 = `strategies/`(策略行为、量化判据与状态函数)+「决策控制分层」铁律面(流程侧出现决策闸门=分层错误,判据见 SKILL.md §1.3 铁律)。判定口径:画面/流程任务的改动不得触碰策略行为模块(评分/权重/搜索/选择);局内状态对象(GameState)字段定义不算策略面。
3. **共享资产枚举**(影响面申报第二层的 CW 实例):`kernel/cw_vocab.py` 词表、`data/` 全部注册表、`knowledge/` 事实常量、screen_info 的 `currency_war_*.yml` 画面档与 `_od_merged.yml` 合并缓存、模板资产 `assets/template/currency_war/`、立绘/首领头像库(character_avatar/boss_avatar)。任一被列入线的申报面时按共享资产层申报。
4. **MCP 重启窗**:改 `src/sr_od/` 运行时代码的线,申报第三层必带重启标记;重启执行权归编排者,前置确认四步与局间时机 = runtime-ops.md「启动与重启」节。
5. **影响面申报落位**:全线迭代设计的申报节落 landing.md 首节——模板单一源 = od-dev-run-iteration skill 的 references/iteration-docs.md §3(landing 五节,首节即影响面申报)。

## 6. 策略迭代期最小定义(时期切换种子)

本文主体 = 实机探索期细则;进入策略迭代期时按当期需求整体重写,重写以下列口径为种子:

- **线型三类**:策略迭代线(完整生命周期:设计→循环对抗→实施→实机验证→正本更新→收口;探索段跳段判据=领域进度载体已覆盖该线目标面,可指认才跳——探索期通常满足)/挂账修复线(多为小迭代:单点修复+判据机械+不触核心面;挂账条目的改哪与判据逐字可指=可走最小形态——设计一页+任务一行,门一个不少)/知识文档线(纯文档迭代,无实机段)。
- **推进模式**:缺省串行;公共 skill 未提供并行启用判据的领域定义位,本领域亦不定义;要开并行由用户当次明示。
- **设计批规范路径**:策略迭代线按 od-dev-run-iteration 走双层文档流——迭代目录 = `.temp/changes/active/<立项日期-主题>/`,正本区 = `docs/develop/sr_od/application/currency_war/`。
- **恒定项(跨时期不变)**:核心面清单/共享资产枚举/重启窗/挂账与归位(§5/§4)照旧。
