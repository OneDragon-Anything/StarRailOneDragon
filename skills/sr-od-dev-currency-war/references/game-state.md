# game state(局内状态,`kernel/cw_game_state.py`)

> 组件 = `kernel/cw_game_state.py`(GameState 类:局内已知事实的快照,全局同一时间只有一个实例,每局重建)。本篇是 game state(局内状态的唯一存放处)的行为规范:值怎么进来(写入)、怎么算对错(对账)、字段怎么设计。改写入入口、加上报函数、增删字段前先读本篇。

## 1. game state 是什么

一局对局中「此刻我们知道什么」的唯一记录。画面 op 看到东西往里写,动作 op 做完动作往里写,策略器做决策只从这里读。

每个字段的值都带一个来源标记(渠道签名),共三种来源加一个空态:

- **观察态**:画面上读到的值(观察解析后写入);
- **逻辑态**:动作发生后按游戏规则推算的值(例:买一张牌,金币减 40、备战席加一);
- **随机态**:未验证的猜测(见 §4);
- **未观察**:这个字段还没写过。
## 2. 一次完整的值流转(主线)

1. 画面 op 观察 node 读屏,把读数**解析成字段该存的值**(例:顶栏读到「备战阶段 1-3」,存「1-3」;名字类转成标准注册数据),调该屏的观察上报函数写入,来源 = 观察态;
2. 动作 op 执行动作后,调该动作的动作上报函数写入推算结果,来源 = 逻辑态;
3. 下一帧观察来到,新读数覆盖旧值;
4. 覆盖时对账,**只比观察态和逻辑态**:对不上 = 推算代码有 bug,记缺陷行并停机;少数已知机制差异(清单在 `kernel/cw_reconcile.py`)直接采纳新读数;
5. 观察态和随机态对不上**不算错**(随机态本来就是猜的),只记一行随机结果日志;
6. 策略器做决策时,直接读字段现值。

## 3. 写入规范

- **每屏一个观察上报函数**(`kernel/cw_screen_report/` 每屏一文件,`report_screen_<snake>_obs`)。例外两处:节点推进走 `report_node_advance`;选择落地记录(chosen_*)不进观察上报,归动作上报;
- **每动作一个动作上报函数**(`kernel/cw_action_report/` 每动作一文件,`report_action_<snake>_param`)。动作执行后不产生任何逻辑态变化的,也要在 kernel 的零变化清单里显式登记,禁悄悄没有;
- **资产获得走获得链函数**:角色/装备/占席道具/投资资产到手的过程(落位 → 事件回调 → 3 合 1 升星判断 → 升星产物重进)统一走 `kernel/cw_gain_chain.py` 的获得链函数,链式规范住该模块 docstring 与各函数 docstring;获得类效果禁止在效果函数里手写落位与升星时机;
- **一切写入必经统一写入口**(observe / write_logic / write_logic_rand),绕过写入口直改字段 = 违例。每次写入必带渠道签名,来源封闭集:obs(观察读取)/ logic_action(动作推算)/ logic_hook(内部派生逻辑)(签名的完整字段面与流水侧语义见 [journal.md](journal.md) §4);
- **每类属性变化单独一个函数**,函数内处理这个字段变化的连带更新:一次写入分配一个版本号;这次写入引起的连带变化(羁绊计数重算、效果推进)在同一个事务里按固定次序自动执行;连带更新出错,这次写入整笔作废并保留证据;
- **可算出来的不存储**:能从现有字段算出的值(席空数、羁绊计数档位)写成计算函数,读时现算,不落字段——存下来就会和计算结果出现两处不一致;
- **观察层负责解析,禁游戏规则推算**:观察上报的是解析结果(「1-3」、标准名、槽位结构),不是原始整句;「按规则算后果」(买卡扣钱)归逻辑层;
- **字段单值**:一个字段一个值,来源记在渠道签名上,不拆「逻辑值字段 + 原文侧挂字段」双字段;
- **读不到就不写,保留上次好值**:识别质量决定写不写入、它本身不是字段——不可信的读数不进 game state,game state 里只有当前最好的已知值。字段的 None 只表示「这一帧没读到」,不表示「未建模」(未建模的东西根本不建字段);某个画面机制上读不到的字段按字段显式申报,不猜;
- **画面有显示的数值,以显示值为准**:要用某个画面上直接显示的数值(如买经验的单价)时,直接用显示值——它是游戏算好的最终值,再按规则自己推算叠加一次(比如再减一次折扣)就是双扣;画面上读不到时才走逻辑公式兜底,兜底公式全项目只留一份实现,禁止在别处另写第二份独立计算;
- **失读帧的处置**:字段已有值 → 沿用旧值并在来源里标注「沿用」(带来源帧);字段从未读过 → 保持 None。字段一旦有过值,任何失读都不得把它清成 None。现值来源是随机态时失读不沿用——沿用会把猜测标成可信值,宁可保持未验证等观察收尾(画面附加载荷离屏置 None 是结构事实不是失读,见 §5)。

## 4. 随机态的规则

随机态 = 未验证的猜测,两种情况会写入:随机效果动作执行时真的掷了一次随机,把猜的结果记下来;开局阶段预填的值还没被画面确认过。

- **写入时按可靠性选记录方式**(全项目一个统一选择点 `anchor_aware_write`):两种情况记成随机态——写的东西本身是随机采样;这局还在开局阶段(备战画面还没被识别确认过)。随机态的值,下一帧观察直接覆盖,猜错不算对账失败。开局阶段已过、且写的是确定推算,记成逻辑态:对不上就是 bug;
- **随机后果的两档落法**:后果随机的动作(刷新后的牌面、冶金炉产物、晶矿掉落),采样口径已登记的 → 上报函数真掷随机,按采样结果把整条确定链逐步写完,全部写操作标随机态(「安全的不准确」,观察覆盖差异预期内);没有确定真值可写、采样口径也没建的(如刷新后整店铺面)→ 整块跳写不落值,归下一帧观察覆盖——**禁用确定推算写随机结果**(编一个确定值进去会制造假的推算失败记录);
- **要用确定事实做决策时,先补观察**:先查这个字段是不是随机态来源;是,就先补一次观察,把它变成观察态再用(例:备战 op 要用敌人词缀做决策,发现它是开局预填的随机态,先去位面详情屏补观察);
- **随机态会传给后面的确定推算**(写入口自动继承):确定推算建立在随机态值之上时(例:先点了晶矿按猜的角色落位,再买牌把牌摆进备战席),写入口会自动把这次写也记成随机态——直到有一次观察把它覆盖成确认值为止。没有这一步,后面那次观察发现"猜错"时会被误判成推算 bug 而停机(实证:run_20261121_152706 停机死因);
- **开局预填初值的消费例外**:开局预填的初值(与开局未确认期的链写)供未确认期直接消费,消费点 = kernel 计算族——这是「消费前必须重观察」的显式例外;真值由首个备战画面的完整观察静默覆盖收尾,开局阶段过去后恢复纪律。

## 5. 字段设计纪律

- **每局全新创建**:game state 每局重建(挂在 session 上),新局零残留;跨局要记的东西归遥测,不进 game state;
- **画面附加载荷离屏即 None**:商店/遭遇/补给的载荷字段,离开画面就置 None;决策入口拿到 None 载荷 = 观察侧漏了(载荷没观察就离屏),显式报错,禁策略侧兜底;
- **可交互实体字段带坐标**:可选/可点的东西(备战栏条目/装备栏条目/晶矿)的字段必须带画面坐标;坐标由观察上报整表覆盖,禁动作后回填(获得时点没有画面读数);
- **策略私有状态不入 game state**:换一个策略实现就不存在的字段(配方方向、义务清单、信号、旗标)放策略实现层自己的状态(StrategyState),框架层不感知;游戏里能观察、按游戏规则能算的才进 game state。

## 6. 对账与失配处置

对账 = 推算状态(逻辑态)与下一帧实读(观察态)逐项比对,唯一发生点 = 画面 op 上报观察数据进 game state 的观察边界。观察写入覆盖逻辑来源值;失配说明推算代码错了,修推算代码。失配时三种处置(按判定次序):

1. **白名单机制性差异——直接采纳**:三种已知差异不算推算错误,读到新值直接采纳并记一行日志,不触发告警停机:
   - 节点边界把差额金币补回(`boundary_gold_backfilled`);
   - 上阵行内单位只换位置、成员不变(`deploy_slot_reorder`——游戏侧行内重排,无逻辑写入方;同单位多重集仅排列差异时,直接采纳新读数并做纠偏处理);
   - board 羁绊计数与观察不一致(`board_derived_adopt`——派生漂移,如环境卡星徽幽灵计数、未知身份零贡献、徽标坏读;观察覆盖直接采纳收敛)。
2. **逻辑随机态的预期内差异——记录采纳**:logic_rand 来源值的观察覆盖差异 = 随机效果落地的预期表现,落 `logic_rand_outcome` 记录行直接采纳新读数,无告警无停机,不进失配分支;
3. **真失配——记缺陷停机**:记 `observe_vs_logic_mismatch` 缺陷行,保留证据暴露出来,不静默。

- **board 派生量禁独立写**:上阵羁绊计数 = front_row/back_row 单位集合的派生量(「可算出来的不存储」,§3),逻辑写入方经行域挂钩单一源自动重算;非派生写入方手写 board = 违例,失配照真失配停。「上阵单位集合」这一真不变量由行域自身的失配检查独立把守。
- 已知缺口:bench/equips 投资卡随机授予、晶矿随机金现无吸收规则,命中照真失配停(随机对账吸收规则已裁定整体拆除、待重新设计,登记在跨迭代挂账文件)。白名单与处置分支的符号载体 = kernel/cw_game_state.py 失配路由区(`_route_logic_mismatch` 一族)。
