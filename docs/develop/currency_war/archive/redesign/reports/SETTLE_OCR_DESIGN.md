## 1. 屏面拓扑与采集时点(帧证据)

战斗结束后有**两级屏**:

1. **挑战结束屏**(每场战斗都出,掉血动画;输轮最终形态多一颗划叉心 + 前往结算/点击空白加速):
   - ①②③ 三项的**唯一真值来源都在这里**——基础伤害/未完成进度伤害在掉血说明面板,挑战进度是进度条(顶部);
   - 首领胜轮也走此屏(2a443d16 实证:1-9 首领胜,基础伤害 -10 仍结算);
   - 团灭终局(挑战失败屏)是它之后的一屏,新增字段**不在该屏采**(无说明面板)。
2. **挑战成功结算屏**(数据统计面板,damage_dealt 已有 W40 通道读):三项不在此屏,本批不改其采集。

采集时点建议:**沿用 battle_loop 分支 3/1f 的 read_round_outcome 读点**(结算停留期循环读,记录时点同帧)。挑战结束屏在分支 1f(失败结算)已走模板门 `标识-挑战进度+标识-挑战结束`。

### 1.5 读策略(2026-09-01 C1 定谳后重写;出处 = REAL_MACHINE_COLLECTION_1.md C1 反转)

- **C1 定谳(四级终版;2026-09-01 遥测验证批修正——[面板延迟出现后驻留],旧[瞬态]与[立即常驻]均不准)**:
  - **①页 2 整版布局=常驻**:挑战结束屏进入后先有 ~2s 掉血动画期,动画结束后完整结算页常驻在屏,直至点「继续挑战」离屏;不点继续不消失,常驻实测 >1min——**HP 锚(小队生命值行/继续挑战按钮)可靠**。
  - **②「小队生命值结算说明」tooltip=瞬态**:该悬浮子件在新批 40 帧 0 命中(首批 4/7 命中系进页瞬窗)——**B/P 三项数字所在的 tooltip 须窗口内捕获**(读点策略:进页后立即连读该区,或另寻承载面;此为三项遥测字段的实现约束)。
  - **③读点时序约束(遥测验证批铁证)**:面板**延迟 ~2-4s 才渲染**;效率等待压缩(页1 驻留 ~1-2s)后读点早于面板出现=漏读(实测 damage 捕获 0/15,但同帧离线复跑读数全对且 -5/-3/+2 与 hp 精确对账)——**读点必须对齐「面板已渲染」帧**(面板锚点检测或延迟下限),与效率优化共存的条件。
  - **④遭遇节点无动画**:进屏即稳定面板。
  - 原「悬停/瞬态触发」假说(§2.2 旧文)对 tooltip 子件维持、对整版布局作废。
- **读取时序 = 动画期过后读**:面板三行数值在动画期滚动不可读,动画完成(进页 ~2s)后进入稳定态;读点应落在「面板稳定之后、点继续之前」。
- **遭遇节点无动画**:遭遇(非战斗类)结算无掉血动画,进屏即稳定面板,读取无需等动画。
- **败局布局同构**:败轮挑战结束屏与胜轮布局同构,面板读取不需按胜负分形态分支(终败划叉心的大数字位置仍按 §2.3 分形态取区,不受本条影响)。
- **C4 团灭屏仍缺标注**:团灭终局屏(挑战失败)至今无实机帧,其几何与面板有无仍是缺口(§5-C4 待采,本定谳不覆盖)。

## 2. 区域提案(pc_rect,1080p)

证据等级标注:【帧实测】= 直接从归档帧像素读出(标注帧);【几何推导】= 由 yml 既有 area 推导,待窗口校准。

### 2.1 挑战进度(进度条)

```
标识-挑战进度标签   [905, 370, 1015, 402]   【帧实测】(多帧一致,与 settlement_fail.yml
                                            既有 标识-挑战进度 [860,362,1060,410] 相容——
                                            该 yml 矩形更宽,是 label+条头合并区,可沿用不新建)
进度条全槽          [710, 422, 1210, 444]   【帧实测】(end_loss/end_final_fail 两帧条槽
                                            左右端一致:x≈710→1210,条体 y≈424-440)
```

- 数值形态:**这几帧里挑战进度只有条、无数字文本**。现有 `parse_settlement_progress` 消费的「±N」浮字是动画期瞬时 token(live 样本实锤过),不可靠作幅度授权读数。
- **幅度真值提案 = 进度条填充率**:对 [710,422,1210,444] 内红色填充像素做列扫描,`fill_ratio × 总进度格数`。总格数(每位面满条对应的进度上限)未在帧内暴露 → **待窗口校准**(采同一轮前后两帧差分对齐 ±N 浮字可标定总格数;判据见 §5-C2)。
- 与 progress_delta 的关系:±N 浮字保留为**符号与增量真值**(识别成熟),填充率为**幅度绝对值**通道;两者同帧并记,互为对拍。

### 2.2 基础伤害 / 未完成进度伤害(掉血说明面板)

唯一帧证据 = `end_boss_win_with_breakdown_panel.png`【帧实测,单帧;面板出现条件待校准 §5-C1】:

```
面板整体        [1237, 485, 1702, 682]
面板标题「小队生命值结算说明」  [1348, 503, 1590, 534]
行·基础伤害     标签 [1250, 555, 1350, 588]   值 [1630, 553, 1690, 588](帧内 -10)
行·未完成进度伤害 标签 [1250, 588, 1410, 622] 值 [1630, 588, 1690, 622](帧内 -1)
行·长线作战     标签 [1250, 622, 1350, 655]   值 [1630, 620, 1690, 655](帧内 +2,绿色)
```

- 行按标签词定位(OCR 找「基础伤害」「未完成进度伤害」「长线作战」),值取**同行右侧最近带符号数字 token**(行判据 y 中心差 ≤ 20px;沿用 parse_settlement_gold_detail 的同行右取法,勿按绝对 x 硬裁——面板可能随窗口位置漂移)。
- 值恒带符号(负=扣血,长线作战为正/绿);解析规则:符号 + 整数,`-` 常被 OCR 读漏 → 值域守卫(§3)。
- **面板不在场时的诚实缺省 = None**:end_loss(-12)与 end_final_fail(-17)两帧面板均不可见。缺 None ≠ 0;「-12 只有基础伤害分量」与「面板没读到」必须可分(与 gold detail 的 None/0 分离同判据)。
- 出现条件已定谳(2026-09-01,C1 反转,出处 = REAL_MACHINE_COLLECTION_1.md):**面板常驻**——进屏 ~2s 动画期后完整面板驻留至点「继续挑战」,实测 >1min;读取时序=动画期过后读,遭遇节点无动画直进面板,败局布局同构,详 §1.5。原「悬停/瞬态触发」假说作废;end_loss/end_final_fail 两帧无面板的成因按新时序口径复核归档(动画期采帧),非「面板不在场」的稳态证据。

## 3. telemetry 字段设计

落点 1:`cw_performance.RoundOutcome`(kernel,观测回路承载)+ `telemetry/schema.py OutcomeRecord`(outcomes.jsonl 一行)+ `recorder.py record_outcome` 透传。全部**末尾追加可选字段**(`| None`,旧记录缺省 None,schema 不破坏——OutcomeRecord 既有惯例):

| 字段 | 类型 | 语义 | 解析规则 |
|---|---|---|---|
| `progress_fill_ratio` | `float \| None` | 挑战进度条填充率 ∈[0,1](幅度绝对值通道) | 红色填充列扫描 [710,422,1210,444];条不可见/全屏分支未走 → None。只存 ratio,格数换算在校准后由读端乘(避免 schema 绑死总格数) |
| `damage_base` | `int \| None` | 说明面板「基础伤害」带符号值 | 面板行 OCR,同行右侧带符号 token;读到恒负,正值 = OCR 丢负号 → **按 str_utils 相似修复后仍正值则拒信**(见下) |
| `damage_unfinished_progress` | `int \| None` | 「未完成进度伤害」带符号值 | 同上;0 也照记(进度打满时游戏可显 0) |
| `damage_breakdown_visible` | `bool` | 面板标题「小队生命值结算说明」是否命中;False = 两 damage 字段为 None 时可分「面板不在场」vs「解析失败」 | 标题 token 相似匹配(one_dragon.utils.str_utils) |

- **对拍守卫(纯函数,可单测)**:`damage_base + damage_unfinished + heal_longline ≈ 心形总扣血`(心形大数字新通道或 progress_delta 取绝对值)。破约 → 两字段置 None 并落 defect_ledger(surface='settle_damage',kind='perception_conflict')——沿用 DefectRecord 既有通道,不新增流。
- **OCR 混淆修复**(AGENTS「规则修复识别结果」硬规):
  - 负号丢失:面板值应恒 ≤0(长线作战除外)→ 值域先验兜符号;
  - `/`、`×` 类混淆在本面板不出现(纯整数);数字粘连(如 `-1 0`)按 token 合并规则修;
  - 标签词形变走 `str_utils` 的相似匹配(阈值与既有 LCS 用法一致),「未完成进度伤害」长词抗噪好,可只匹配前缀「未完成」+「伤害」双锚。
- **采集时点**:胜轮(分支 3)与败轮(分支 1f)都采;挑战失败屏(团灭终局)不采(面板不存在);`currency_war_battle_settle`(战斗结算动画屏)不采(动画态数值滚动,血量数字区是动画中间值)。
- **P12v2/P15v2 消费接口**:幅度授权需要「该轮实际伤害幅度分布」= damage_base×damage_unfinished 真值;脱删失需要「删失轮(进度未打满)的 unfinished 分量」。两字段齐 → P12v2 授权门开;面板出现率 < 100% 时不阻塞——可用 `心形总扣血 - progress_delta 推导` 的回退估计(估计值打 `estimated=True` 标志是后续批的事,本批只建真值通道)。

落点 2:`cw_match_recorder.py` 无需改(outcomes.jsonl 行由 telemetry.recorder 写,recorder.record_outcome 透传 OutcomeRecord 新字段即可;复核过 recorder.py L349-366 是字段白名单式构造,**需在该构造处补 4 个字段透传**——这是落地时的唯一代码改动点)。
