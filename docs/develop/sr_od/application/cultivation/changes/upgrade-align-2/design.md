## 2. D1 券确认事务式记账对齐(char 口径)

### 2.1 现状:逐分支对照

char 口径三支柱(出处:upgrade_character.py `confirm_ticket_farm` 记账口径 docstring 与 `_settle_farm_accounting`;LC 已按迭代1对齐,upgrade_light_cone.py 同构)对照 trace 现状:

| char 口径支柱 | trace 现状 | 判定 |
|---|---|---|
| ① 幂等判据:确认分支 `_farm_times_set == 0` 才设次数,非零重入轮跳过设次数只重发确认 | 确认分支已有同款判据(确认钮在场段开头) | **已覆盖**,形状一致 |
| ② 成功证据 commit:确认点击后不动账,证据(结果框「按钮-关闭刷取结果」在场 = 领奖完成)才 `_settle_farm_accounting`(判据位非零才 `rounds+1`/`draws+times_set`/log/清零) | **点击即计**:点确认后同轮立即 `_farm_rounds += 1` + log 落账 + `_farm_times_set = 0`,不校验任何成功证据 | **需做**(主缺口) |
| ③ 拦截仅清判据位零回滚 | 无拦截分支(归 D2,§3);现状确认点击即计,若确认被拦(开拓力不足弹窗)则轮次虚增 | 归 D2;D1 落地后 D2 拦截天然零回滚(见 §3.2) |
| ④ `_set_farm_times` 入口先清判据位(设置失败不得残留旧值,否则重入轮拿旧判据跳过设次数直接确认) | 无此句(直接进入设次数流程) | **需做**(小缺口) |

现状「点击即计」的具体风险面:确认点击发出但未生效(点击丢失/被弹窗拦截)时,轮次已计、日志已落、判据位已清——重入轮会重跑 `_set_farm_times`(判据位为零)多点「+」/拉满,且账面虚增一轮。char/LC 的「证据计」消除该风险面:未观察到证据不计账,宁可少计不多计(确认生效但 op 中途 fail 的边界下少计,是事务式口径的固有取向,char/LC 同)。

### 2.2 方案:单节点结构适配

改造点全部落在 `farm_ticket_chain` 节点内(单节点状态机),不动节点编排:

1. **确认分支**(快速刷取弹窗标题命中 + 确认钮在场):保留幂等判据设次数;点确认后改为——置 `_chain_farm_done = True`(该状态位现状已有,语义「确认已点」,继续沿用);**删除** `self._farm_rounds += 1`、记账 log 与 `self._farm_times_set = 0` 三句;`_farm_times_set` 保持非零(语义转为「已设未记账」判据位);仍 `round_wait` 慢询等连刷完成。
2. **结果框分支**(「快速刷取结果弹窗」的「按钮-关闭刷取结果」命中):**新增 settle 调用**(提炼 `_settle_farm_accounting` 式辅助,判据位非零才 `_farm_rounds += 1` + log + 清零;log 内容与现状确认轮一致:轮次/连刷次数/开拓力与券消耗常量),再执行既有关结果框行为。单节点结构下成功证据族只有**结果框在场**一个成员——trace 的确认点击是裸 `controller.click` + `round_wait`(无带 until 的 helper),不存在 char/LC 的「helper success 第二记账点」;且现状链状态机本就逐轮探测结果框,证据轮天然存在,无需新增探测。char/LC「两处共用 settle」的教训(只挂一处则生产时序不可达)在本结构下不适用,但 settle 挂点必须是**探测命中处**(即结果框分支体内),不是关框 helper 返回处——后者带 until 验证,等价性成立,但探测命中处更早、状态机形状更直白,取前者。
3. **`_set_farm_times` 入口补判据位清零**(`self._farm_times_set = 0` 一句,char :722 / LC 同款):改造后判据位语义为「已设未记账」,设置失败残留旧值会让重入轮跳过设次数直接确认,必须入口清零。
4. **预算语义复核**:`_farm_rounds` 的预算核在升级循环路由处(⑤⑥ 分支,`_farm_rounds < farm_rounds_max`)。改造后轮次在结果框轮 settle——券刷链收口回面板交回升级循环重判时,结果框轮已 settle,预算语义不变(确认生效 + 领奖完成才算消耗一轮);确认生效但未到结果框即 fail 的边界下预算少计一,取向与 char/LC 一致。
5. **注释同步**:字段 `_farm_times_set` 与确认分支处「记账读数已入日志,消费后清零备下一轮」的注释改写为新语义(判据位:已设未记账,settle 时落账清零);类 docstring 结果状态段补「记账以结果框为成功证据」一句,并**补 POWER_CAPPED 进结果状态枚举**(:71-73 现仅列 MAX_LEVEL/MATERIAL_CAPPED/不在目标技能面板)。

## 3. D2 开拓力拦截守卫 + POWER_CAPPED 终态

### 3.1 现状

全文件「开拓力」字样仅命中注释 / docstring / log 文案(消耗声明与记账日志共 6 处),**无任何拦截识别代码**——现状开拓力不足时:确认刷取被游戏弹「开拓力补充」弹窗拦截,该弹窗标题不在链状态机四个画面锚(快速刷取弹窗/结果弹窗/资源窗口/面板开关)内,全 miss 落兜底 `round_wait('券刷链过渡态')` 慢询,直到节点 `timeout_seconds=300` 超时 fail——既不可恢复判停,又空烧 300 秒。docstring「开拓力不足时挑战/刷取静默无反应——链路重试预算耗尽即判停」描述的是面板钮静默拒绝场景,不覆盖确认弹窗拦截场景。**需做**。

### 3.2 方案(对照 LC 已实机验证形状 + 单节点适配)

语义对齐 LC(升级_light_cone.py `confirm_ticket_farm` 守卫分支与 `manual_fight` 守卫分支、类 docstring POWER_CAPPED 定义;任务提示的历史行号 :601-607/:681-685/:771-779 在当前文件已漂移,以符号名为准):识别「开拓力补充弹窗」→ 点「取消」→ 原路清场 → POWER_CAPPED 可恢复判停,「确认」钮 = 星琼购开拓力**永不触碰**。

**建档零新增**:`power_replenish_dialog.yml`(screen_name「开拓力补充弹窗」)已存在,area = 「标题-开拓力补充弹窗」+「按钮-取消」两个,由光锥线实机验证落地;弹窗为全局模态居中,行迹上下文复用同一画面档成立(实现时实机跑一次行迹券刷确认被拦场景复核落点即可,见 §7 开放问题)。确认钮**刻意不建 area**——红线沿用,任何实现不得为其建 area 或点击。

**守卫点:链状态机探测序列首位**(farm_ticket_chain 现有四态探测之前插一发「开拓力补充弹窗」标题识别)。理由:补充弹窗是模态,在场时暗遮罩下其余锚大概率全盲,放首位是唯一能保证「弹窗在场不被其他态误分流」的位置;char/LC 的 confirm 节点同样把守卫放探测首位,口径一致。插在首位意味着链节点每轮多一发识别查询(含面板态轮),桩测试剧本逐轮插 miss 格,成本可接受(§3.3)。

**守卫命中分支行为**(一轮内完成):

1. 点「按钮-取消」(补充弹窗画面档);
2. 仅清判据位 `_farm_times_set = 0`(本轮未成交未记账,不动历史账;D1 落地后 `_farm_rounds` 只在 settle 增长,守卫时本轮尚未 settle,**天然零回滚**——char/LC 「禁止对 rounds/draws 减法」的约束在 trace 结构下由记账点后置自动满足,实现仍须注释声明该约束防未来演化破坏);
3. 置判停标志(新增 `_capped: bool`,对齐 char/LC 命名)与 `_final_status = 'POWER_CAPPED'`;置位后链状态机进入**清场模式**;
4. log 带「开拓力随时间恢复,续跑即继续」提示(可恢复判停语义)。

**清场模式**(跨轮,`_capped` 置位期间的链状态机各态变体——「原路清场」,只关不发起):

- 补充弹窗再在场:再点取消(点击未生效重试);
- 快速刷取弹窗(确认框)在场:点其「按钮-取消」(画面档已有该 area,光锥线残留清场同款);
- 结果框在场:关结果框(现状行为复用);
- 资源窗口在场:关窗(现状 `_chain_farm_done=True` 分支同款);
- 面板态:回面板(**复位与等待复用现状收口分支,返回状态改 CLOSE_PANEL,不得回「回面板」交升级循环**——判停后重入升级循环违反可恢复判停语义),此轮读 `_end_level` 一次(判停等级日志对照,此时已在面板态可读——比 LC 「收尾补读」更早,形状更直白),转 CLOSE_PANEL 边;
- 交 `close_panel` 关面板回树态,落账 `_final_status = 'POWER_CAPPED'`。

## 4. D3 补料优先级翻转(通用材料补全 → 快速刷取券 → 手动战斗)

### 4.1 现状

负责人裁定三线统一补料优先级 = 通用材料补全 → 快速刷取券 → 手动战斗(char/LC 行为已符合,迭代1仅做 docstring 声明;trace 翻转归本迭代)。trace 现状与裁定相反:⑤ 分支(「按钮-通用材料补全」在场形态)`farm_dungeon` 授权时**先 NEED_FARM 券刷**(预算内),预算耗尽才回落 `fill_generic` 补全——通用材料非稀缺却被排在券刷之后,且该形态缺口本可由合成覆盖,点面板「快速刷取」会被游戏以「无可刷缺口」拒绝(toast),白烧点击轮次。⑥ 分支(无补全钮形态,仅「按钮-快速刷取」在场)先 farm 是正确形态(缺口不可合成,刷取是唯一补料路线),不受翻转影响。⑤b 分支(「按钮-材料合成」形态)无 farm 路径(原料已足,券刷无收益,既有裁定),不受影响。

### 4.2 方案

⑤ 分支内两授权判断的优先级对调,其余不动:

- 翻转后 ⑤ 分支判定序:`fill_generic` 授权 → 点「按钮-通用材料补全」等确认弹窗(现状行为);未授权 `fill_generic` 且 `farm_dungeon` 预算内 → NEED_FARM(现状行为);均不可用 → MATERIAL_CAPPED 判停(现状行为)。
- 三个出口的形状(点击目标/round 返回/判停落账)全部不变,只改进入顺序——**先补全**(通用材料非稀缺优先消耗),未授权补全时才走券刷(缺口可刷时;不可刷由既有 toast 正判门控 + 连点封顶兜底,见 §1.2 核对结论:两道防线均在,未被动)。
- docstring 同步:类 docstring「路线地位」段与模块 docstring 对应段改写为裁定句 + trace 后缀(措辞对齐 char/LC 已落地形态:「授权补全时优先补全,不刷取;未授权补全时转券刷,由无可刷缺口 toast 探测兜底判停」),并引用裁定出处(负责人裁定的统一优先级,与 char/LC docstring 同句)。

### 4.3 特别核对:翻转与落地版新防线的交互

- **与「按钮带全空连续 3 轮判停」**:无冲突。⑤ 分支命中处复位 `_buttonless_rounds`(现状语句保留,位置随判定序平移);补全确认 → 升级执行 → 反馈遮罩 → 面板回归的全链由 ② 盲点驱动兜住(既有用例 `test_feedback_banner_recovered_then_max_level` 已锁该链,该用例组合 fill_generic=True + farm 未授权,翻转前后行为一致)。
- **与「弹窗识别放宽」**:无时序假设冲突。⓪ 分支(材料补全确认弹窗)在升级循环每轮开头探测、优先于按钮判定,与弹窗从何而来解耦——现状 farm 优先时弹窗出现在券刷回来之后,翻转后弹窗直接出现在第一轮,⓪ 都能接住。放宽(标题/确认/取消三 area 框覆盖一行/两行材料两种布局)只影响识别命中率,不改变弹窗出现时机与流转。
- **与 toast 门控/连点封顶**:券刷链内逻辑零改动,防线原样;翻转只改变链的**进入时机**(从 ⑤ 首选变为 ⑤ 次选 + ⑥ 唯一路线),门控计数/封顶复位点(弹窗/结果框/资源窗口/回面板各态)不受影响。

## 7. 开放问题

1. **补充弹窗取消后的落点**(回确认框还是回资源窗口)未实机确认——清场模式对各态都有变体,实现不依赖该假设;实现后实机跑一次确认被拦场景,按实际落点收敛清场剧本注释。
2. **链入口面板钮静默拒绝的停因可区分性**:开拓力不足与无可刷缺口在面板态表现相同(点击被拒无反应/弹 toast),现状兜底判停词 MATERIAL_CAPPED 可能误导调用方(实际等开拓力恢复可续跑)。若实机发现开拓力不足时点面板钮也会弹补充弹窗,则守卫自然覆盖该态、判停词自动正确;否则保持现状,语义细化留待后续迭代(需实机证据)。
3. **D2 守卫探测的查询成本**:守卫插链节点首位使链内每轮多一发识别查询(含不可能出现弹窗的面板态轮);若实机确认补充弹窗在场时其余锚必然全盲(模态遮罩),可评估守卫探测收窄到非面板态轮——本迭代按首位全探测实现(保守正确),收窄归 align-3 归并时一并评估。
