# sr-od-team-coach 设计总览

## 定位

配队知识库 skill：给「玩游戏的 agent」做配队决策用的公共知识单一源 + 决策工作流。与玩法操作 skill（进本/画面操作/自动化流程）分离，与米游社 MCP（账号数据源）互补——skill 是脑，MCP 是手和数据。

目标使用形态：普通使用者接入本 skill + 项目 MCP，agent 即可完成「读环境弱点 → 选体系 → 选人 → 查练度门槛 → 输出编队」的全流程，不需要读项目源码。

## 边界

- 只含公共游戏知识：任何档案不得出现特定账号的信息（BOX 构成、练度数值、持有星魂等）。账号数据一律运行时拉取。
- 不含玩法操作流程（忘却之庭怎么进、编队画面怎么点）——那是玩法 skill 的职责；本 skill 被玩法 skill 引用。
- 不含自动化开发知识（写 op/app）——那是 od-dev-* 开发 skill 的职责。

## 构成

```
SKILL.md                      # 触发 + 配队决策工作流 + 路由（指令式）
references/                   # 知识语料（agent 按需查阅的数据，不是指令）
  INDEX.md                    # 总路由：机制/体系/角色三层索引
  mechanics/                  # 机制层：跨角色共享的规则（战斗基础/伤害模型与词条/大招资源/欢愉命途/记忆命途）
  teams/                      # 体系层：一类配队一档（骨架/绑定规则/变体/操作轴/替补矩阵）
  characters/                 # 角色层：一人一档（定位/伤害模型/机制/转模上限/词条口径/绑定互斥/星魂档位）
maintenance/                  # 维护者文档（不进 agent 执行上下文）
  doc-writing-guide.md        # 知识档模板与填写方法论（持续总结更新）
design/                       # 本目录：设计记录
```

知识分层的依据是机制本身的归属，不是拍脑袋：

- **机制层** = 对任意持该命途/机制的角色都成立的规则（欢愉伤害乘区规则、忆灵系统、大招资源体系）。
- **角色层** = 单个角色的机制（黄泉的残梦是她的个人机制，别的负面角色不共享）。
- **体系层** = 配队原型（骨架槽位 + 绑定规则 + 替补矩阵）；体系档引用角色档，不重复角色细节。

## 关键设计决策（动机）

1. **知识放在 skill 而非 docs/game**：分发形态决定的——使用者只挂 skill + MCP，不克隆仓库；docs/game 是项目内部知识树（开发者向），skill 是自包含分发资产。两者在玩法规则层面会有少量重叠，各自服务各自读者；skill 的版本维护挂在版本适配流程（新角色/平衡改动 → 补/改角色档）。
2. **「写方法论不写具体事实」规范对本 skill 的适用边界**：该规范约束的是指令文本（SKILL.md 与指导行为的辅助文件）；本 skill 的 `references/` 是被查阅的知识数据语料，不是指令——知识密度正是其价值，规范 4 不适用于语料内容。SKILL.md 本身仍只写方法论与工作流，不塞角色事实。
3. **两个 skill 的拆分（用户裁定）**：知识 skill（本 skill，机制+角色+体系三层）与玩法 skill（忘却之庭等：进本流程/画面操作/湍流判读，引用本 skill 做配队）。基础玩法说明不单独成 skill——基础机制的消费者与配队知识的消费者相同，作为本 skill 的机制层存在。
4. **角色档暂不加机器可读摘要头（用户裁定）**：YAML frontmatter 摘要便于程序化扫描，但引入「正文与摘要双源同步」成本；待真实消费场景（bot 化）出现再议。
5. **档案语言与命名**：全中文（目标用户中文环境）；角色档以游戏内官方中文名为文件名，体系档以「机制 + 锚点角色」命名（例：黄泉负面队）。

## 证据层级与知识纪律

- 知识档统一标注证据层级：【官】官方文本（技能/星魂/行迹/光锥描述）＞【攻】攻略交叉验证（标时效）＞未标注 = 两层一致。
- 机制结论尽量给官方文本锚点（行迹名/技能名），攻略数值（公式系数、面板目标）必须标【攻】。
- 档内「信息缺口」节是诚实清单：官方文本无法取证、攻略分歧的点如实记录，禁止脑补。
