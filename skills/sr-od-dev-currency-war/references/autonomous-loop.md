# 自主推进编排细则(CW 实机探索期)

## 1. 阶段定位与编排者职责

- 阶段目标:用真实对局摸清新版本的画面、机制、与旧版本的差异,收集问题。提升对局成绩与策略调优不属于本阶段。
- 运转形态只有一条主线:编排者反复派实机探索 agent 亲自玩货币战争——玩法知识与操作方法按游玩 skill `sr-od-currency-war`(面向玩家的 skill),经项目 MCP 工具执行;每次派发以一局为限(单局限令,§2.1),实机探索 agent 打完当前局即停止汇报,编排者在局间重新盘点待办(挂账板+当次新发现)后组下一局任务书再派。实机探索 agent 遇到问题就停止操作(停止一切游戏操作、保持游戏窗口状态原样,向编排者汇报后等待处置,细则见 §2.3);编排者按 §3 走问题处置循环;处置完让实机探索 agent 继续工作。
- **推进模式映射**:CW 实机探索期=**串行模式**(游戏窗口与 MCP server 单跑道,独占资源天然串行——并行模式启用判据在本领域恒不满足;策略迭代期口径见 §6)。探索线属「先行线」:立线时落最小申报,无迭代设计段(探索产出直接归档知识/立修复线,不走设计批)。
- 编排者只做三件事:
  1. 调度:派工、窗口所有权管理(§2.2)、问题处置循环推进(§3);
  2. 传话:问题与裁决在用户和子 agent 之间原样转达(§3.3);
  3. 登记:窗口所有权登记(§2.2)、待办与发现的归位(§4);自主推进不设总的任务账本,迭代进度由做迭代的子 agent 按 od-dev-progress-tracking 登记(§4)。
- 编排者不做:技术判断(方案倾向、归因结论、评审意见一律由对应角色子 agent 产出)、亲自写代码与文档、亲自操作游戏。编排者夹带技术倾向会污染对抗评审与用户裁决——这是本流程要防的第一件事;用户明确指名要编排者亲手做某事时,以该指令为准。

## 2. 实机探索 agent

### 2.1 任务书构成(四项,缺一不派)

任务书骨架 = od-dev-agent-autonomous-mode skill 的 references/line-templates.md §2 探索模板(逐字复制,只填实例位);CW 实例差异:

1. **操作依据**:游玩 skill `sr-od-currency-war`(面向玩家的 skill)——实机探索 agent 的玩法知识与操作方法从它取;任务书不复制其内容,实机探索 agent 也不依赖编排者的会话历史。
2. **关注清单**:本次要关注/验证的内容——由用户在开始自主推进前告知,当次指令可补充;每条写清「关注什么、观察到什么算值得关注、怎么记录」。探索阶段的终止判据=关注清单覆盖完毕或用户叫停(通用骨架定义,列表驱动的「探索够了」,不凭感觉)。
3. **停止操作纪律**:§2.3 整段并入任务书。
4. **现场交接信息**:接管已有对局时,写明交出方(= 上一个持有窗口的 agent,见 §2.2 交接协议)报告的现场信息四项(当前画面 / 对局进度 / 血量与金币 / 未了事项)。
5. **文件面**:探索产物只写知识归档(知识文档/画面档,分层判据见 SKILL.md §3)与探索报告,不动任何代码。
6. **交付**:探索报告与证据截图落工作台当线子目录(`<工作台>/<线名>/`),回信格式按通用模板。
7. **单局限令(每次派发最多一局)**:任务书写明本局的局内目标(打到哪里/验证什么)与顺带取证清单;实机探索 agent 完成本局(终局或中止)即停止操作、把画面收回大厅待命位、向编排者发单局报告(局账/取证发现/遗留/晶球余额),然后等待——**不获得多局连续授权**。编排者在局间重新盘点待办(挂账板+单局报告新发现)后决定:续派下一局(组新任务书)/转问题处置循环/收束窗口。为什么:局间盘点 = 编排者控制进度的抓手,连续多局授权会让探索方向失控且局间新待办无法插入。

### 2.2 窗口所有权(串行铁律)

- 一个游戏窗口同一时间只归一个 agent;编排者显式登记「谁、从何时起、干什么」于工作台 occupancy 登记文件。
- 占用窗口的动作 = 点击/拖拽/输入等驱动游戏的操作;只读识别(analyze_screen)不算占用。
- 派发任何会占用窗口的活(探索/诊断/实机验证)之前:先查窗口登记与项目 MCP 运行状态(get_run_status);窗口已有持有者就把新活排队,不派第二个。
  - 为什么:两个 agent 同时驱动同一窗口会互相干扰(点击落进对方操作的画面、画面被抢),且事后从运行记录难以区分是谁的操作——防患只能靠事前登记,不靠事后归因。
- 交接协议:交出方交窗时报告现场信息四项——当前画面 / 对局进度 / 血量与金币 / 未了事项;接管方开工第一步先识别当前画面(analyze_screen),与交接报告逐项核对,对不上先报告编排者,不先动手。
- **MCP server 重启执行权归编排者**(通用骨架规则;CW 重启运维细则=runtime-ops.md「启动与重启」节——重启前四步确认/对局中守卫拒绝/改动集中纪律);探索/诊断/验证 agent 禁自行重启。

### 2.3 停止操作汇报纪律(任务书必含)

- 遇到问题(操作不生效 / 画面异常 / 疑似机制变化 / op 报错)的动作顺序:
  1. 停止操作:一切游戏操作停下,游戏窗口状态保持原样,不试图自行修复或退出当前画面;
  2. 保存证据:截图留档 + 一句话描述 + 发生时间;
  3. 汇报:现象 + 证据 + 发生时点报给编排者,然后等待。
- 禁止:自行改代码;自行绕过问题继续跑(把问题藏进「看起来跑通」);未经交接就把游戏窗口丢在当前状态。
- 为什么:现场就是诊断的证据;修了、绕了、清了,证据就没了,同一个问题还会再来一次。

## 3. 问题处置循环

### 3.1 循环全貌

1. 实机探索 agent 停止操作并汇报 → 编排者派**诊断 agent** 定位根因。
2. 诊断结论分两类:
   - **非代码问题**(机制理解错 / 操作方法错 / 画面建档缺口):做知识修正(补画面档、修正知识文档),然后让原实机探索 agent 继续工作;
   - **代码问题**:设计 → 对抗评审 → 修订设计 → 实现 → review(全审档) → 实机验证(复现原故障场景确认已修)→ 重启 MCP server(运维细则见 [runtime-ops.md](runtime-ops.md))→ 让原实机探索 agent 继续工作。代码问题的修复按通用骨架的分界处置:属当前探索线申报面内的单点修复=线内任务(不立新线);触设计意图或跨多文件=立新线走全流程(设计→对抗→实施→review),拿不准=立新线。
3. 循环期间原实机探索 agent 保持停止状态等待;窗口可能被诊断/验证 agent 按 §2.2 接管,窗口归谁以编排者的登记为准。

### 3.2 各角色边界

| 角色 | 游戏操作 | 代码 | 说明 |
|---|---|---|---|
| 实机探索 agent | 可 | 只读 | 按任务书玩货币战争;遇问题停止操作并汇报;问题处置交编排者另派(§3) |
| 诊断 agent | 可(现场复现) | 只读 | 定位根因,不改代码 |
| 设计 agent | 不操作 | 只写设计稿 | 设计与实现分开,防同一个 agent 既定方案又自己验收 |
| 对抗评审 | 不操作 | 只读 | 每轮起全新的、没读过前几轮讨论的子 agent——看过前几轮讨论就会被已有思路带偏,挑不出真问题 |
| 实现 agent | 不操作 | 写 | 按设计稿落地;与设计稿对不上的地方报告编排者,不自作主张改设计 |
| 实机验证 agent | 可(复现验证) | 只读 | 验证后把窗口停回已知稳定状态(大厅或备战画面)再归还 |

### 3.3 传话纪律(约束编排者本人)

- 问题原样带给用户,不加工不筛选;用户裁决原样传给对应子 agent,不夹带编排者的技术倾向。
- 设计争议需要用户裁决时:把双方论点原样并列转达,不排序、不建议。
- 用户未应答时(自主推进常态):按指令文件「状态」字段授权以子 agent 对抗收敛代裁决,结论与依据记录在案(通用骨架定义)。

## 4. 进度登记与跨会话接口

- 自主推进不设总的任务账本:关注内容由用户在开始自主推进前告知编排者,编排者写进任务书派发(§2.1);编排层登记(在飞线/占用/子 agent 计数)=通用骨架的编排者工作台(.debug/autonomous/<日期-主题>/)。
- 推进期间子 agent 做迭代时,按 od-dev-progress-tracking(迭代进度 skill)的要求在迭代目录内登记进度;编排者不替子 agent 记迭代进度。
- 待办登记:货币战争专用的待办文件 = `.debug/progress/CW跨迭代挂账.md`(定位见 SKILL.md §3「跨迭代挂账」行);条目写明「改哪、判据是什么」——这两样是立线时初判轻线要对照的原料,入口写齐 = 初判纯文字对照,不强制格式。
- 探索发现的归档:知识类结论落对应知识文档或画面档(分层判据见 SKILL.md §3);过程叙事不进本 skill。

## 5. 领域叠加件(通用 skill 的 CW 映射)

通用层机制自含完整默认形态,本节只写 CW 的映射与增量(od-dev-agent-autonomous-mode skill「通用写全、领域叠加」契约):

1. **推进模式映射**:CW 实机探索期=串行模式,见 §1——通用层「并行模式启用判据=领域 skill 定义」,本领域定义为「探索期恒不启用;策略迭代期不定义并行判据,缺省串行,开并行由用户明示(§6)」。
2. **核心面清单**(通用 skill 轻线核查/裁判官输入用):CW 的核心/策略面 = `strategies/`(策略行为、量化判据与状态函数)+「决策控制分层」铁律面(流程侧出现决策闸门=分层错误,判据见 SKILL.md §1.3 铁律)。口径跟随 SR 仓 AGENTS.md「测试规范·产物落点校验」:画面/流程任务的改动不得触碰策略行为模块(评分/权重/搜索/选择);局内状态对象(GameState)字段定义不算策略面。
3. **共享资产枚举**(影响面申报第二层的 CW 实例):`kernel/cw_vocab.py` 词表、`data/` 全部注册表、`knowledge/` 事实常量、screen_info 的 `currency_war_*.yml` 画面档与 `_od_merged.yml` 合并缓存、模板资产 `assets/template/currency_war/`、立绘/首领头像库(character_avatar/boss_avatar)。任一被列入线的申报面时按共享资产层申报。
4. **MCP 重启窗**:改 `src/sr_od/` 运行时代码的线,申报第三层必带重启标记;重启执行权归编排者,前置确认四步与局间时机 = runtime-ops.md「启动与重启」节。
5. **影响面申报落位**:全线迭代设计的申报节落 landing.md 首节——SR 落地文档模板已内置该节(推荐格式,见 docs/develop/harness/iteration-design.md 附录 C)。

## 6. 策略迭代期最小定义(时期切换种子)

本文主体 = 实机探索期细则;进入策略迭代期时按当期需求整体重写,重写以下列口径为种子:

- **线型三类**:策略迭代线(全流程:设计→循环对抗→实施→review→实机验证;探索段视该线信息充分度可跳——探索期通常已覆盖)/挂账修复线(多为轻线:单点修复+判据机械+不触核心面,三件在挂账条目写齐=初判轻线)/知识文档线(纯文档线,无实机段)。
- **推进模式**:缺省串行;本领域不定义并行启用判据(通用 skill 的领域定义位空缺),要开并行由用户明示。
- **设计批规范路径**:策略迭代线设计批的「结构细则」实例位 = `docs/develop/sr_od/application/currency_war/` 双层文档流(changes/ 迭代设计→对抗→落地→正本更新)。
- **恒定项(跨时期不变)**:核心面清单/共享资产枚举/重启窗/挂账与归位(§5/§4)照旧。
