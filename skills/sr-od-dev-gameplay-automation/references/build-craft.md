| 玩法特征 | 参照兄弟(读其源码作骨架) |
|---|---|
| 肉鸽推进 + 选择决策 + 自动战斗 | `sim_universe` |
| 体力刷本 + 配队 + 自动战斗 | `trailblaze_power` |

**复用对的、丢掉不对的**(如节点制玩法用不上大世界 `move_v1/v2` 寻路)。杠杆 = "在既有代码里找结构同构的兄弟",比从零设计省一个数量级,也符合项目"先复用现有 Application/Operation 模式"的硬约束。

读三处看模式怎么串:`ApplicationFactory` 怎么注册、`SrApplication` 怎么编排 `Operation`、配置怎么走 `YamlConfig` 子类 + GUI setting card(`YamlConfigAdapter`)。

## §设计:范围 + 前置 + 拆 op + 状态机 + 配置(阶段 4)

- **先定自动化范围**:核心目标是**帮使用者完成大量游戏日常**(每日重复、量大的),其次才是极端复杂场景(成就/挑战/极限难度)。日常没稳之前别钻极端场景。
- **前置条件**:自动化可能有前提 —— 使用者需先解锁某玩法/完成某任务/达到某等级。把这些列清楚(写进 doc + 配置说明),别假设所有人一开始就能跑。
- 把一局拆成**可独立验证的 Operation**(每个 op 一个职责:一类画面/一类动作)。
- 主循环画成**状态机**:每轮读屏 → 按优先级匹配画面 → 分流处理。
- 配置(难度选择、策略开关、优先角色…)走 `YamlConfig` 子类 + GUI setting card(`YamlConfigAdapter`),别散落硬编码。

## §实现:先零件后整体(阶段 5)

**激进拆成多个小 op,每个 op 只负责一个特定操作(一类画面/一个事件/一个动作),别写巨型 op**。工程化好的代码 = 很多个职责单一的小 op,而不是一个塞满分支的大 op。

- **理由(前期尤甚)**:按 op 执行(`run_operation '<op_id>'` 单独跑)能最快定位每一步的问题 —— op 粒度小,失败就锁在那一个 op 的那一步,修那一步、单独重跑该 op 确认、再往下走;不用每次跑整条 app 才撞到问题、再从一堆内联分支里猜哪步坏了。
- **反例(别这样)**:主循环 op 的 `loop()` 里内联 N 个事件 handler → 任一 handler 坏了,都得跑整局才碰到,且无法 `run_operation` 单独复现 → 只能靠实机手动 click 一步步试(慢、浪费)。**正确**:每个事件 = 独立 op,主循环按画面分流 `run` 各 op;坏了单独跑那个 op 定位。
- **判据**:op 的某个方法(如 `loop`)里 if-elif 分支 ≥ 3 个不同画面/事件 → 拆成独立 op;一个 op 超过 ~80 行 / 职责含"或"(买牌**或**选人**或**结算)→ 拆。
- 拆完仍守「先零件后整体」:每个小 op 单独 `run_operation` 实测通过,再串成 app 主循环。

Operation 用 `@operation_node` / `@node_from` 编排状态机;`round_by_ocr_and_click` / `round_by_ocr` 做画面判定 + 重试。

### TDD 从入口(逻辑先于运行时)
入口流线性(大厅→…→备战),每步输入 = fixture、输出 = 检测/动作明确 → **先写 fixture 测试断言期望,再实现/改**。存量 op 先补**刻画测试**锁现状;新改先写期望测试再改。

⚠️ TDD 锁的是**逻辑回归**(检测对/该点哪/纯函数),**锁不住运行时 bug**(click 时序被截图吞、MCP 异步、真机 OCR 抖动)→ 绿测试 ≠ 实机能跑,仍靠阶段 6 实机验。流程 op(跨多屏)用 `add_mock_screenshot` 喂**序列 fixture** 测整条推进。

### 实现-测试流水线(写一个 op → 后台测 → 等待时写下个)
别"写完一个 op → 干等它测完 → 再写下一个"(串行浪费等待时间)。改成**写完一个 op 立刻 `run_operation '<op_id>'` 后台跑(`block=false`)测试它,趁后台测试的等待时间写下一个 op**;然后 `get_run_status` 查前一个结果,有问题就修、没问题继续往下。**实现与测试重叠,等待时不闲着**。

- 判据:只要**跑道空**(无 op 在跑)且**有待测 op** → 立刻后台提交测试,自己转去写下一个;op 跑完(成功/失败)再回来收尾。
- 约束:单跑道(同时只能一个 op 在跑)+ LLM 并发 ≤ 2;后台 op 期间**别再起第二个 op**(撞跑道报错),写代码/读文档/沉淀经验这些不占跑道的活随便做。
- 配合「激进拆小 op」:op 越小、单个测试越快、流水线越顺;巨 op 测一次耗时久,流水线优势发挥不出来。

每步实机验证(短闭环:分钟级 跑→看→改→再跑)是快速推进的关键。

## §验证:串成 app 端到端(阶段 6)

`SrApplication` + `XxxAppFactory`(注册进 `ApplicationFactory`),`run_standalone_app('<app_id>')` 端到端跑。跑通 = 能从入口走到结算回大厅,不卡死、不死循环。

## §测试 + 文档(阶段 9)

- `sr-od-test/` 加测试(纯逻辑部分:策略评估、OCR 解析、数据类;fixture 截图 → 期望输出)。
- **测试覆盖具体画面,不只是纯逻辑**:每个 reader/op 测试用**真实截图 fixture**(每状态 1-2 张典型)断言具体输出;改 reader/解析前把所有相关状态 fixture 跑一遍 → 改完重跑 → **无回归才提交**。只测纯逻辑(无截图)防不住"某状态 OCR 读不到/读错"的回归。
- **TDD:测试前置**(见上):新 reader/op/改 → 先写 fixture 测试再实现;改前跑、改后跑,锁回归。刻画测试(存量 op)+ TDD(新改)搭配 fixture 覆盖。
- `docs/game/gameplay/<play>.md` 写玩法 + bot 流程 + 踩坑。
- 改动同步 `docs/develop/`(若涉及框架)。
