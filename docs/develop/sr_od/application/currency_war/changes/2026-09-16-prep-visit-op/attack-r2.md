## 新发现清单(自找角度)

### R2-1 F1 修复未同步:被证伪口径残留在行为变化申报与 landing 派工面
- **位置**:design.md:34(行为变化申报);landing.md:34(3.3 范围)。对照 design.md:21,29、landing.md:12。
- **问题**:方案 2/4 已把浮层闸改为「不退役、整建制内嵌统一执行器」,但①行为变化申报仍声明「浮层闸:显式预检门 → op 清场职责 + 零判效重判(对外行为等价:弹窗帧不发射)」——这正是前轮 F1 用注册表自身声明与实测病例证伪的替换方案(cw_screen_prep.py:162-168 注册表显式排除交互 overlay;遭遇面板无关闭钮);②landing 3.3 范围(阶段 = 账本唯一源,iteration-design.md §3.1)同句残留。实现者同时读到两处:按方案做 = 保留闸,按 landing 做 = 退役闸,交付契约段停手令必然触发;更坏形态是 worker 只读阶段小节落码,无声实现回被证伪行为。
- **严重度**:重要(阻断定稿;前轮同内容曾定致命,此处是同一证伪结论的残留面而非新证伪)。
- **建议**:design.md:34 行为申报改写为「浮层闸:loop 侧显式预检门 → 统一执行器内嵌浮层安全检查(捕获面与判据原样,宿主迁移)」;landing.md:34 同步改「浮层闸内嵌统一执行器(见 3.1)」。

### R2-2 前置发射位与 S1 开店闩的冲突形态未定义,且「禁绕过」与旧形态不等价
- **位置**:design.md:25(「访问意图走既有 OpenShop 节流与 S1 开店闩(禁绕过)」)。
- **问题**:旧仲裁的受限访问**不过** S1 闩——cw_loop.py:570 直调 `open_shop(op)`,全程无 `cw4_shopped_phase` 检查。新形态声明「走既有节流与 S1 闩(禁绕过)」后:S1 闩发射位 = `_emit_open_shop`「闩命中 = 跳过 + 分站计数」(mandate.py:1222-1230),而 M-chain 常规商店访问(凑息/压库/缺员)同相位先访即置闩、闩键 = (位面,轮次) 相位内长存(mandate.py:813,855-880)。于是同相位内「先常规访 → 后 armed∧gate 命中帧」是常态路径,此时前置位的访问意图被闩吞,**吞掉之后本帧产出什么设计未定义**:若空手落入后续 pass,⑥ 兜底「无动作 ⇒ StartBattle」(entry.py:943-944)会在 gate 命中帧直接发射未消费的金——恰是仲裁要防的 P70 反形态;若直接改发 StartBattle,等于「闩活帧放弃溢出消费」,同样与旧形态(旧仲裁无视闩照访照发)不等价。两条路都未选,等价申报(design.md:33)在此形态为假。
- **严重度**:重要。
- **建议**:设计显式钉死「前置位访问意图遇闩活」的行为(三选一:无视相位闩、以武装段已访旗自为节流并申报与旧形态的差、或闩活帧的显式降级出口),并把该差异补进行为变化申报。

### R2-3 统一执行器钉死内部序漏「部署原子序」,armed 帧发射存在丢部署通道
- **位置**:design.md:21(方案 2 内部序 =「屏态复验(双锚)→ 浮层安全检查 → 出战点击链」);landing.md:12(3.1 审计清单五项,无部署项)。
- **问题**:旧达标臂发射 = 复验 → G1 显影 → **部署原子序** → StartBattle(cw_loop.py:346-411 → launch_prepared_battle :300-310「达标臂面:每帧部署原子序(部署面现读重建)」;恢复局面面同步步同源 :285-299)。新形态下 armed 帧由前置位短路「任何 pass 之前」(design.md:22)——④ 骨架 pass 的 M1/M5 部署发射位不再运行,**发射路径上唯一的部署机制只剩执行器内部步**;而钉死序里没有它。实现者按字面落码 = armed 帧发射不部署(板满换血/bench core 上场场景行为破坏);补进去则常规 ⑥ 出战面(passes 已逐帧发过 DeployMove)也过一遍部署现读——逐面部署语义(op 面是否含部署步、loop 面同步步闩 `_cw_locked_sync_done` 如何进执行器)全未钉。3.1 审计判据清单(屏态复验/重发长按/失败计数复位/连败停机/免战子态)恰好不含部署项,审计兜不住。
- **严重度**:重要。
- **建议**:方案 2 内部序补「部署原子序(现读重建,逐面语义:op 面 = 每帧现读零 move 形态;loop 面 = sync_once 闩语义原样)」;3.1 审计清单补部署项。

### R2-4 失败分轨引用已整删的「连败停机/重发长按」语义,并继承漂移正本
- **位置**:design.md:21(方案 2「`_start_battle`(重发长按/连败停机)」「失败语义按调用面分轨(loop 恢复局面面 = C1 三振计数;op 策略面 = 连败停机)」);landing.md:12(审计清单含「重发长按」「连败停机」)。
- **问题**:`重发长按下 / launch_dead 连败停机` 已随出战域重设计(T-286)**整删**——cw_start_battle_action.py:20-24 模块头明文「旧发射家族(……重发长按下/失焦守卫/launch_dead 连败停机)随出战域重设计整删:op 不判效,交回后画面状态由外循环下一帧重判」;现 `_start_battle` = 三行薄委托(prep_actions.py:855-859)。op 策略面**不存在**可承接分轨的连败停机机制;设计要么是在给 op 面新造一套停机(未申报为新行为),要么是把已删语义当现存语义合并。上游成因 = start-battle.md §1 正本漂移(:7 仍写「发射 → 未落地原样重发长按下 → 仍败计连败停机留证」,与代码矛盾),设计引用漂移正本当作合并语义权威(硬规则 1 防的事故:信任二手转述与真值不符)。
- **严重度**:重要。
- **建议**:方案 2 分轨改按真值:op 策略面 = 发出即交回、零计数(start-battle.md §3-3 现行口径),如需停机防线须显式申报为新机制并给判据;3.1 审计清单把「重发长按/连败停机」改标「已随 T-286 整删,不参与合并」;start-battle.md §1 漂移挂入正本更新清单。

### R2-5 遥测分键申报账实不符:7≠8 键、两个写点宿主消亡未申报、跨阶段判据悬挂
- **位置**:design.md:37(「`launch_arbitrage_*` 7 键 + `readiness_*` 4 键 + 质量闸实机 sink 的写点随宿主迁策略前置发射位(键名与语义不变,零静默)」);landing.md:27(3.2 判据「遥测分键族随迁写点就位(launch_arbitrage_\*/readiness_\*/质量闸 sink)」)。
- **问题**:①`launch_arbitrage_*` 现役 KEY_ 共 **8** 个(cw_launch_arbitrage.py:62-81:frames/inband_closed/zero_consume/gate_blocked/abandoned_launch/cross_line/open_failed/precheck_skip),非 7;②`KEY_PRECHECK_SKIP` 唯一写点 = `_prep_anchors_hit` 预检(cw_loop.py:511-514),随方案 5 预检退役而消亡;`KEY_ABANDONED_LAUNCH` 写点 = 仲裁消费后 stale 弃射分支(cw_loop.py:1977-2009),随达标臂拆除与跨帧形态消亡——两键命运未申报,与「键名与语义不变,零静默」自相矛盾;③「写点随宿主迁策略前置发射位」只对判定核消费键(质量闸两键,写点 = 判定返回消费位,cw_loop.py:1918-1927)成立;`readiness_stale_screen`(执行器屏态复验内,cw_loop.py:386-393)、`readiness_overlay_hold`(执行器浮层检查内,:1955-1963)、`open_failed/gate_blocked/zero_consume/cross_line`(op 受限访问执行内,:570-632)的新宿主分别是执行器与 op 访问,不在策略层——一刀切表述误导 3.2 落点;④landing 3.2 判据把 3.1(执行器)/3.3(op 访问)阶段的写点绑进 3.2 验收,该判据在 3.2 时点不可满足。

- **建议**:design/landing 补逐键迁移对照表(键 → 旧写点 → 新写点/显式退役申报);3.2 判据收窄为「策略前置位辖域键就位」,执行器/op 辖域键分挂 3.1/3.3 判据。

### R2-6 帧级判定单一源钉错 kernel 函数:gate 是逐动作闸,帧级「金>息线」单一源是 in_launch_spend_zone
- **位置**:design.md:25(「仲裁判定**直调 kernel 既有 `launch_arbitration_gate`**……gate 命中 → 产出受限商店访问意图……gate 未命中 → 产出 StartBattle」);landing.md:19(「armed ∧ 金 > 息线 → 产出受限商店访问意图序」)、:26(判据「仲裁判定直调 kernel `launch_arbitration_gate`」)。
- **问题**:`launch_arbitration_gate(action, gold, session)` 是**单动作预算闸**(cw_launch_arbitrage.py:107-132),入参要一个动作、零成本动作恒放行(:128-129)——前置位在「是否发起访问」的帧级分支上没有动作可传;照字面实现要么无处取 action、要么凑哨兵动作得到恒「命中」(armed 帧全变访问帧,发射消失)。帧级「金>息线」的判定单一源是 `in_launch_spend_zone(gold, session)`(cw_economy.py:306-320,明文「仲裁段区判,两面直调本函数,禁各自内联 gold > g* 字面量式」「新增消费点须回 DESIGN §5 对账表」),旧代码帧级判定用的正是它(cw_loop.py:554);gate 只在访问内部逐动作消费(cw_loop.py:590-595)。前轮 F3 建议本已区分「域判定 = in_launch_spend_zone 直调、闸 = launch_arbitration_gate 复用」,本轮修订把两者合并成了一个错误符号。landing 判据「grep 禁内联金息线比较」拦不住此错(错实现同样不含内联字面量)。
- **严重度**:重要。
- **建议**:design.md:25 与 landing.md:19,26 改钉:帧级域判定 = 直调 `in_launch_spend_zone`(消费点回金出口族 DESIGN §5 对账表登记),访问内逐动作闸 = 复用 `launch_arbitration_gate`。

### R2-7 「每武装段恰一次」的状态载体未钉
- **位置**:design.md:25(「每武装段恰一次(段 = armed 持续期,失武装即复位;段内已访问则次帧无条件产 StartBattle)」)。
- **问题**:段语义已定,但「段内已访问」旗的存储宿主未定(策略器状态对象/`cw4_counters`/GameState 容器域三选),复位观察点(只存在于备战帧 decide)与跨节点/跨局生命周期、sim 面可见性随之未定。载体选择有现成约束可依(session.md:26 目标态「策略器状态 = 实现包自定义的状态对象,所有权归策略器」),不钉则由实现者拍板(hard rule 2);入 GameState 还会牵 sim 建模面(设计只申报了意图的 sim 映射,未申报状态面)。
- **严重度**:次要。
- **建议**:接口契约补一句:载体 = 策略器状态对象(与既有备战旗标同宿主),生命周期 = 局级、失武装帧复位,sim 零新增建模。

### R2-8 「对外行为等价(受限访问恰一次、发射恰一次)」存在具体反例形态未定性
- **位置**:design.md:25,33。
- **问题**:访问内 LevelUp/买经验抬 `max_units` → `defer_by_quality = not load_bearing_full` 翻转(cw_launch_admission.py:211-212)→ 次帧非 armed → 段复位;若 LevelUp 后金仍 > 息线(大金差场景),重武装帧 gate 再命中 → **再访一次**——旧形态一访一发,新形态两访(且首段发射被推迟到常规链)。design.md:25 的「跨帧等价」论证只覆盖段内路径,design.md:33 的等价申报是无限定全称命题。
- **严重度**:次要(形态窄,但申报为承重结论,须显式收窄或论证)。
