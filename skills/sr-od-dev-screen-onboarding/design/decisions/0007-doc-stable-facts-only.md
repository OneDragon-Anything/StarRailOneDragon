# 0007. 建档文档只写画面事实,过程产物不进描述章节

- **Status**: accepted
- **Date**: 2026-08-04(形式化;原始踩坑 2026-07-28)

## Context
onboard「战斗失败」画面时,把排查 / 修复过程的产物塞进了画面描述 —— 「✅ 两种布局均识别 GREEN」(测试结果)、「原 bug... 现已修」(修复历史)、「实测强队也是 3 按钮」(调研开放问题)混在描述里,稳定的画面事实(两种按钮布局 / 识别特征 / 流转)被淹没,doc 变得像排查日志。根因:SKILL §3 定义了 doc 结构但没强调「描述章节只写事实、过程产物不进」。

## Decision Drivers
- **doc 稳定可参考**:画面事实(长啥样 / 元素 / 识别 / 流转)稳定;过程产物(测试结果 / bug 历史)易变、属别处。
- **职责分离**:测试结果归测试仓(`sr-od-test`);bug / 修复历史归 commit / PR;开放问题归 doc 备注节。

## Considered Options
1. **描述章节混写事实 + 过程产物**:doc 变排查日志,稳定事实被淹没。
2. **描述章节只写画面事实,过程产物分流**(选中):事实归描述章节,产物归对应 owner。
3. **完全不写过程产物**:开放问题 / screen_info 缺口也没处记 → 选 2 但开放问题进「备注」节。

## Decision
选 2。**建档文档 = 稳定的画面参考(事实),不是建档过程的日志**。描述类章节(何时出现 / 状态流转 / 识别特征 / 可交互元素 / 识别快照)只写**画面本身的事实**;建档 / 排查过程的产物不混入:
- **不进 doc**:① 测试结果(通过 / 失败 —— 测试归 `sr-od-test`,doc 不跟踪测试状态);② bug / 修复历史(「原 bug... 现已修」归 commit / PR,doc 只写现状)。
- **进「备注」并与事实分开**:开放问题(如某元素触发条件未知)、screen_info 现状缺口、易变点。
- **判据**:每句问「这是画面本身的事实,还是建档 / 排查过程的产物?」后者不进描述章节。

## Consequences
- **正向**:doc 稳定可参考,不被过程噪声污染;职责分离清晰。
- **负向**:过程经验需另存(commit / PR / design ADR),不能顺手塞 doc。
- **边界**:多子态画面的识别快照,每子态用 `### N. 子态名(source_image)` 编号子标题(`## 识别快照` 下一级,符合 markdownlint MD001;原用 `####` 跳级触发 MD001)而非加粗(加粗在 6+ 子态里扫不出层次)—— 这是格式约定,不是过程产物。
