> 质疑:「每轮 5 秒不可能」——本报告用实测数字拆解一轮轮询里 OCR 与睡眠各占多少。
> 基准脚本:`ocr_bench.py`(同目录),原始数据:`ocr_bench_result.json`(同目录)。
> 运行口径:`PYTHONPATH=src; uv run python .debug/temp/currency_war/redesign/ocr_bench.py`,每样本预热 1 轮 + 计时 5 轮取中位数。

## 二、配置现状:跑的是 GPU(DirectML),不是 CPU

- `config/model.yml` 实际内容:`ocr_use_gpu: true`(另 `world_patrol_gpu: true`、`sim_uni_gpu: true`)。
- 读取链:`BasicModelConfig.ocr_use_gpu` → `OneDragonContext` 初始化 OCR 时传 `use_gpu` → `ONNXPaddleOcr` → `onnxocr/inference_engine.create_session`。
- 运行时实证(本次基准日志):det/rec 会话 providers = `['DmlExecutionProvider', 'CPUExecutionProvider']`,即 **DirectML GPU,本机无 CUDA**。
- 模型:ppocrv5(`config/model.yml` 未设 `ocr` → 默认),det_limit_side_len=960,use_angle_cls=False——与 battle_loop 生产链路(`ctx.ocr_service` → `OnnxOcrMatcher` → 同参数 `ONNXPaddleOcr`)完全同源。

因此「OCR 走 CPU、切 GPU 有收益」的前提**不成立**——生产已经是 GPU。

## 三、GPU vs CPU 实测对比(既然两种都跑了)

| 场景 | GPU(DML) | CPU | GPU 优势 |
|---|---|---|---|
| det(全帧) | ~0.05-0.06s | ~0.08-0.10s | **快 ~35%** |
| rec 63 框 | 0.604s | 0.509s | **慢 ~19%** |
| rec 28-30 框 | 0.27-0.28s | 0.25-0.28s | 持平 |
| 全帧总耗时(30 框级) | 0.33s | 0.34-0.37s | 快 ~5% |

结论:DML 只在 det 上有实打实收益;rec 反而略慢(rec 是小图多次小 batch 推理,DML 提交开销吃掉收益)。两者总耗时差距在 ±10% 内,**切换方向都没有值得动手的收益**。兼容性方面无新风险:DML 会话本来就走 `gpu_executor` 单线程串行化(`run_session` → DML 检测 → 串行队列),现有机制已兼容,无需改动。

## 四、轮询周期重构:5 秒里 OCR 占多少

battle_loop 一轮轮询的实际构成(生产代码 `battle_loop.py`):

```
一轮 ≈ 截图(约 0.03-0.06s,mss/gdi)
    + 全图 OCR 一次(同帧多查询共享 OcrService 缓存,不重复跑)
    + 节点判定/点击逻辑(纯内存,毫秒级)
    + round_wait 睡眠(time.sleep 直睡)
```

battle_loop 里 round_wait 的实际取值(代码逐处数过):战斗中 `wait=2`;各事件/结算/弹窗分支 0.8~3s 不等,最常见 1.5~2s;个别 `time.sleep(1.2)`、`time.sleep(0.2)`。

用实测 OCR 数字对照「每轮 ~5 秒」的体感:

| 构成 | 耗时 | 占 5s 周期占比 |
|---|---|---|
| 全图 OCR(密文本在局面面,28-63 框) | 0.33~0.67s | **7%~13%** |
| 全图 OCR(结算页/稀文本,8-15 框) | 0.14~0.22s | 3%~4% |
| 截图 | ~0.05s | ~1% |
| round_wait 睡眠 + 若干轮空转 | 其余 4s+ | **80%~90%** |

即:**OCR 本身 0.14~0.67s,5 秒周期里睡眠(以及跨多轮的等待)占八成以上**。若体感周期是 5s,通常是「一轮 round_wait 2s + 画面未定型再空转一轮」叠加,不是 OCR 慢。

## 五、结论与建议

1. **OCR 本身多快**:全图一次 0.14~0.67s(取决于文本框数,~10ms/框 + det 固定 ~0.05s)。远够快,不是 5s 周期的主因。
2. **5 秒里睡眠占多少**:80%~90% 是 `round_wait`/`time.sleep`;OCR 只占 3%~13%。
3. **GPU/CPU**:生产已是 DirectML GPU(`ocr_use_gpu: true` 实证);DML 与 CPU 总耗时持平(det 快/rec 慢相互抵消),**没有切换价值,维持现状**。DML 单线程限制已由 `gpu_executor` 串行化兜住,无兼容问题。
4. **要压周期该动哪**:动 round_wait,不动 OCR。若目标是更快反应(如结算窗口出现即响应),把对应分支 `wait` 从 1.5~2s 降到 0.5~1s,周期立即缩 ~一半;OCR 端无需任何改动(密文本帧 0.67s 是上限,降睡眠后单轮总耗时仍 <1.4s)。
