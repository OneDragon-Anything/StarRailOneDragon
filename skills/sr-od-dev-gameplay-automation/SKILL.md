# 新玩法自动化开发 playbook(OneDragon 框架)

把「自主开发一个新玩法的自动化」拆成可复现阶段。**全程守「看(analyze)→ 动(click/key/run)→ 等(sleep)→ 验」循环**;**别凭猜硬写** —— 凭猜只覆盖一种情况、漏另一种,必回归。

> 通用方法论(不绑具体玩法)。每阶段达标再进下一个。

## 总流程(按序;每阶段达标再进下一个)

| 阶段 | 做什么 | 达标判据 | 深度细则 |
|---|---|---|---|
| 0 | 先验现实约束 | 确认玩法常驻/限时、能实机、未过期 | — |
| 1 | 玩法建档(理解玩法)= 一切的起点 | 能口述机制 + 一局流程 + 决策点 | — |
| 2 | 找结构同构兄弟 + 读现有代码 | 定下复用/丢弃清单 | `references/build-craft.md` §找兄弟 |
| 3 | 画面建档(核心环节) | 每画面定识别方式(OCR/CV/YOLO)+ screen_info/模板 | `references/screen-identification.md` |
| 4 | 设计:范围+前置+op 链+配置 | 定范围/前置 + op 链 + 配置项 | `references/build-craft.md` §设计 |
| 5 | 实现:先零件后整体 | 每个零件单独 `run_operation` 实测过 | `references/build-craft.md` §实现 |
| 6 | 验证:串成 app 端到端跑 | `run_standalone_app` 跑通 | `references/build-craft.md` §验证 |
| 7 | 策略设计(若有决策) | 客观指标 + A/B,迭代到目标 | 见下「策略设计」 |
| 8 | 事件长尾:遇预料外补逻辑 | loop 覆盖已知全部事件类型 | `references/runtime-iteration.md` |
| 9 | 测试 + 文档 + 成文 | ruff 干净 + sr-od-test + docs/game | `references/build-craft.md` §测试 |

**阶段 0**(最易漏):钻机制前先确认外部依赖还在不在 —— 常驻 or 限时(限时可能已结束 → 只能"研究+骨架",没法实机验证);能实机打开(客户端版本/入口还在);有无反作弊/锁光标/全屏独占(影响 controller 能否操作)。

**阶段 1**:面对全新玩法,**第一件事是搞懂玩法本身,不是急着写代码**。先搜官方+攻略/wiki 理清类型(肉鸽/自动战斗/手动/节点制)、一局流程、决策点、自动 vs 手动部分、胜负奖励;再实机跟一遍(或看视频),边走边记每画面进出条件 + "玩家在此做什么"。输出:机制口述 + 画面清单。实机跟走本身就是画面建档(阶段 3)的开始。

**阶段 3 是核心环节**:它决定每步怎么识别、要不要 screen_info、要不要裁模板,进而决定整个流程能不能流转。**画面建档/逻辑设计时就该想好每步识别什么、用什么手段**(文字→OCR;固定 UI/图标→screen_info+CV;动态/稀有/多实例→YOLO)。马虎建档 = 后面每步在猜。**主动建档玩法流程经过的每个画面**(入口/备战/各类事件/战斗/各结算子页/失败/大厅回归…),别只建 op 当前要点的那几个 —— 信息源/决策点/反馈信号常在建档读三层(截图/screen_info/代码)时才浮现。判据:**流程经过的画面 = 都要建档**(每画面定识别方式 + 存 fixture)。深度细则见 `references/screen-identification.md`。

**阶段 7 策略设计**(玩法有玩家决策时):
- 用**客观指标**衡量(到第几轮/剩血/金币/激活羁绊层数/胜负),别凭感觉。
- **A/B 对比**比直觉可靠;优化找**甜点**不是极端化。
- **"打不过"先精确诊断卡在哪一步**(警告?锁阵?出战禁用?被某机制阻塞?),别笼统归因"策略差" —— 往往一个具体小动作(升等级/卖弱角色)就破墙。
- 策略**给配置口**(优先角色/阵营偏好/激进度),别写死。

## 跨阶段不变量(每阶段都守)

**证据纪律(下结论别凭单点)**:
1. 验证 OCR 读取器/运行时行为**跨多样本**,别凭一张图 —— 跑实机后看 telemetry/日志的统计分布(如 `grep -o '"<field>": [0-9]*' file | sort | uniq -c`);`analyze_screen` 全屏 OCR 与区域 OCR(`get_ocr_result_list(rect=...)`)可能行为不一致,要分开验(全屏命中 = 该处有字,不等于区域 OCR 读得到);异常值(garbage)是误读信号,别忽略。
2. 逻辑推断也要**交叉验证**,别拿未证实假设当论据("某读数不可能是 X,所以读到 X 必是 bug" —— 可能有你没考虑的状态/机制理解错);结论立在硬证据(诊断 + 代码流)上。
3. 写 docstring/结论/文章前分清"多样本观察到"还是"单次推断";单次的标"待核实",别写成既成事实。

**知识维护(边干边补)**:文档没写、或与实际矛盾、而你在干活时又需要它 = 知识缺口,补上 —— 能查官方文档/工具说明的**先查,别凭猜试错**(API/模型用法/坐标系/grounding 格式,查文档比反复试错快得多);能确定答案的提议补 docs(只补会重复用到的);确定不了的问用户。**游戏数据/描述/原生数值优先官网(米游社)和游戏内(图鉴/词条)**(权威源);只有"攻略/玩法技巧"这类主观总结才信第三方网站。**遇工具/API/模型行为反常,先查文档** —— 这条比任何具体技巧都重要。

**调试纪律**:bot 卡死/失败时**先读日志再动手**,别凭猜改或盲点坐标 —— 日志(`.debug/sr_od_mcp/main_server.log`)常直接暴露根因(OCR 没读到锚点/节点循环/命中错屏);日志解释不了就**在决策点补日志**(OCR 摘要 + 点击坐标 + 分支结果)+ 临时存图(`screenshot()`);再结合日志客观事实 + 玩法知识形成假设验证。深度(意外屏调研、运行时不确定性、重复操作建 op)见 `references/runtime-iteration.md`。

**框架级踩坑**(bug #1 截图吞 click、MCP 异步、ONNX 异步、配置生效、录屏、GBK 日志等)见 `references/framework-pitfalls.md` —— 遇 op 点不中/行为怪先查这里。
