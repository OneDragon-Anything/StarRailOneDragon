# 货币战争自主推进·编排者手册

> 读者 = 自主推进会话的编排者(负责派活和登记的主 agent)。开线派发前、处理子 agent 汇报时读。
>
> 读法:先按 §1 确认当前场景(用户开启自主推进时会说明)。§2 所有场景都适用。场景一走 §3 到 §7;场景二到四见 §8;领域叠加件见 §9。
>
> 适用前提 = 货币战争自主推进的任何场景。
>
> 分工:开启和停止自主推进的做法,以及通用框架(编排者职责、线的调度与放行、挂机〔用户不在场,由 agent 自己推进〕时和平时有什么不同、失败后怎么重派、游戏窗口的占用互斥、传话纪律〔编排者在用户与子 agent 之间如实转交、不加工〕),单一源是公共 skill od-dev-agent-autonomous-mode 的 SKILL.md;任务书模板是它的 references/line-templates.md(实机探索任务书除外,见 §4.1)。迭代流程和迭代内进度的单一源 = od-dev-run-iteration。本文件不复述这两份,只写两样:货币战争在各场景下的不同做法(§3 到 §8),货币战争对通用框架的补充(§9)。
>
> 实机探索 agent 自己的工作方法(打一局的步骤、局内情况处理、单局报告)在 [exploration.md](exploration.md)。编排者不用通读它,派实机探索任务书时按 §4 写就行。
>
> 名词:
>
> - 线 = 一条独立推进的需求(公共 skill 叫需求线)。本文件出现四种线,见 §1.5。
> - 验证载具 = 当前场景用来暴露缺口、验证改动的运行形态:场景一 = 实机探索局,场景二 = app 自动流程跑局,场景三 = sim 对拍局,场景四 = 策略迭代线的实机验证局。
> - 执行 agent = 当前线操作验证载具的那个子 agent。在飞 = 已经派出去、还没交活的。
> - 线表 = 公共 skill 的线登记表。占用表 = 它的占用登记(occupancy.md)。待裁登记 = 它的 pending-decisions.md,放等用户裁定的事项。
> - 自主工作文件夹 = 公共 skill 定义的文件夹,放线表、占用表、待裁登记。本项目的位置见 §2.5。
> - 单局报告 = 实机探索 agent 每次停下时交的报告,构成见 exploration.md §7。局账 = 单局报告里记这一局各项结果的那一节。
> - 现场四项 = 当前画面 / 对局进度 / 血量与金币 / 未了事项。
> - 追踪文件 = 画面识别与动作 op 的追踪文件,按画面分章,格式见 [screen-tracking.md](../screen-tracking.md)。
> - 待跟进事项文件 = 货币战争专用的待办文件(§2.5)。
> - 待裁知识队列 = 放等用户裁定的知识发现的文件(§5.6)。
> - 转登 = 编排者照子 agent 报告的原文,抄进别的记录文件,不加工。
> - 玩法指引的不足 = `.temp/tracking/currency-war/玩法指引的不足.md`,放实机探索 agent 照玩家 skill 的指引打的时候、感到不够用的地方(exploration.md §6.4)。
> - 玩家 skill = `sr-od-currency-war`。
> - 知识文档 = 玩家 skill 的玩法文档(各画面的文档和各篇总览)和 `docs/game/currency_war/research/` 各篇。归位分层的判据见 SKILL.md §3。
> - sim = 项目内置的单局模拟器(`src/sr_od/application/currency_war/sim/`,只模拟环境,不评判策略)。对拍 = sim 局与实机局跑同一对局内容后逐项比对读数。

## 1. 场景与线

### 1.1 四个场景

货币战争自主推进分四个场景。场景 = 开启自主推进时设定的一组「这段时间要关注什么」。方法骨架跨场景不变(§2 和 §9),场景只决定优先事项:编排者让当前线按对应场景节运转。

| 场景 | 关注什么 | 优先事项 |
|---|---|---|
| 场景一 版本适配摸索期 | 新版本的画面:建档与识别、动作 op。实测玩家 skill 的玩法指引。玩法上的新发现靠实机局收集 | 实机探索局 → 修复线 |
| 场景二 流程框架适配期 | 把场景一的识别成果与动作 op 接入 app 自动流程 | app 自动流程跑局循环(run→暴露缺口→修→再跑);策略可以坏、随机乱选——不看对局成绩,只看流程推进与缺口收敛 |
| 场景三 投资策略/环境 sim 适配期 | 投资策略与环境效果在 sim 里的建模 | sim 与实机对拍 |
| 场景四 策略实现适配期 | 策略实现 | 策略迭代线(真实策略代码迭代) |

四个场景都不写死目标和完成条件:目标是用户进入自主推进时给的,每次可以不一样。场景只定关注什么、按什么顺序推。什么时候算完,见 §1.2。

### 1.2 场景怎么确定、什么时候算完

**场景的确定**:

- 场景由用户在开启自主推进时说明。编排者不按证据判断现在处在哪个场景,也不自行切换。
- 编排者把用户说明场景的原话整句抄进线表表头,包括用户有没有说「接着做下一个场景」。中断重开的会话以这行记录为准接续。
- 上一个场景完成、用户说过「接着做下一个场景」→ 表头另起一行,写「按用户原话〈…〉顺延进入场景 N」,旧行保留。

**场景什么时候算完**(四个场景一样):

- 目标由用户进入自主推进时给。编排者不自己判断目标达到没达到,只认两样:
  - 执行 agent 的报告里写明目标达到的。场景一指单局报告「局账」里的「局内目标」(§3.1);别的场景进入时细化;
  - 用户自己说的(叫停,或者说进入下一个场景)。
- 认到其中一样,按表头记的原话处理:
  - 说过「接着做下一个场景」→ 按 §1.1 的顺序进入下一个场景。场景四是最后一个:它完成时,在待裁登记写一条「四个场景都已完成,等用户说明」。
  - 没说过 → 在待裁登记写一条「本场景已完成,等用户说明下一个场景」,不自行开始下一个场景。
  - 这两条待裁登记没有对应的线。待裁登记的模板每条要写线名,这两条的线名一栏写「场景收尾」。
  - 进入下一个场景的时候,线表里没收口的线不用等,照 §9.1 照常走完;追踪文件里的缺口原样留着,下一个场景接着用。
- 场景一完成以后进入场景二怎么做,见 §8.1 开头的说明。

### 1.3 开启清单在本领域怎么填

公共 skill 的开启清单照走,只有下面两处不同:

- 「确认需求入口」这一步:需求入口 = 用户开启时说明的目标和场景的原话,加上本文件对应的场景节(场景一就是 §3)。用户只说了场景、没有说明目标 → 登记待裁请用户补,不自造目标(公共 skill 这一步的规则)。
- 「立线并派首个探索」这一步:场景一按 §3.4 走。

### 1.4 跨场景恒定项

任何场景都成立:

- §2 通用编排与 §9 领域叠加件在所有场景生效;
- 知识文档线和挂账修复线是跨场景常驻的线型,任何场景都可立(§8.3)。场景一里知识文档线只在用户裁定知识发现以后才立(§5.6);
- 推进模式缺省串行(§9.1)。

### 1.5 线的叫法

立了迭代的线,迭代内每一步怎么走都一样,见 od-dev-run-iteration。实机探索线只走到探索这一步(§3.2)。

| 线型 | 做什么 | 定义在 |
|---|---|---|
| 实机探索线 | 实机探索 agent 亲自打对局,收集画面和机制上的发现 | §3.2;任务书见 §4 |
| 修复线 | 改识别代码、补识别模板、改动作 op、补完没做完的建档 | §6 |
| 知识文档线 | 只改知识文档,不进游戏 | §5.6、§8.3 |
| 策略迭代线 | 改策略代码 | §8.3 |

从待跟进事项文件里取条目来修的线叫挂账修复线,它是修复线的一种(§8.3)。

## 2. 通用编排

本节对所有场景生效。

### 2.1 编排者职责

编排者做的事分三类,都是机械动作:

1. 派子 agent。
2. 登记记录文件。通用框架定义的三份:线表、占用表、待裁登记。货币战争另有三份:
   - 待跟进事项文件(§2.5)和追踪文件(screen-tracking.md),这两份长期保存;
   - 待裁知识队列(§5.6),场景一才有。

   登记的内容照子 agent 报告的原文抄,不加工。
3. 按本文件写的固定步骤做的几件事:武装资产哨兵(§2.2);重启 MCP server(§6.4);对局丢失后的恢复(§7.2);子 agent 被中断以后替它提交文件(§7.1)。

- 判断类动作,编排者要么按本文件写的机械规则做,要么交给对应的子 agent 在它交付的固定节里给结论。两边都没有依据 → 登记待裁,线转等待(公共 skill §2-②)。
- 编排者不做三类事:
  - 技术判断(方案倾向、归因结论、评审意见,一律由对应的子 agent 产出);
  - 亲自写代码与文档;
  - 操作游戏(§7.2 固定步骤里的 open_game 除外,它只负责把游戏打开并登到大世界)。
- 有两样看着像编排者在写,其实都是照子 agent 的报告抄,不算上面的第三类:登记各份记录文件(第 2 类);修复线接上动作 op 以后,照实现报告改画面文档「操作」章的那一格和追踪文件的动作一栏(§6.7)。
- 例外:用户明确指名要编排者亲手做某事时,以该指令为准。

### 2.2 窗口所有权(串行铁律)

- 一个游戏窗口同一时间只归一条线,由这条线在飞的 agent 操作。编排者登记「谁、从何时起、干什么」于占用表(occupancy.md)。
- 操作窗口的动作 = 点击、拖拽、输入这些驱动游戏的操作。只读识别(analyze_screen)不算占用。
- 派发任何会操作窗口的活之前,做派发前检查:
  1. 查占用表。窗口已有持有者 → 把新活排队,不派第二个。两种情况不算别人占用:持有行就是本次要派的这条线自己的;接管窗口的是同一条线的诊断 agent 或实机验证 agent(§2.4)。
  2. 查项目 MCP 运行状态(get_run_status)。运行状态是「运行中」→ 排队。
  3. 登记占用表:谁、从何时起、干什么。登记先于派发。
- 交接协议:交出窗口的 agent 报告现场四项,接管方核对以后才动手。条文在 exploration.md §5.1。派接管窗口的 agent(实机探索 agent、诊断 agent、实机验证 agent)时,任务书写明先读它。
- **资产哨兵**:资产哨兵是一个后台脚本,盯着识别模型、立绘库这些运行时资产还在不在,缺了就报警。做法见 runtime-ops.md「哨兵脚本组」表。
  - 每个会话(包括接手中断的会话)第一次派实机探索 agent 之前,先查它还在不在(查旧的办法见同一张表)。在,就不用再管;不在,按 runtime-ops.md 同一节的「重新启动三步」武装(把它放到后台跑起来)。武装以后,把后台任务的编号记进线表备注栏。
  - 它报警退出(证据在 asset_hit_alert.md)→ 编排者把报警原话转给在飞的实机探索 agent,让它停止操作、交报告;登记待裁(附证据文件路径),实机探索线转等待。资产怎么恢复由用户定(同一张表「只报不修」一栏)。
  - 用户叫停时不用专门停它:它是长驻脚本,随会话走。

### 2.3 MCP server 重启执行权

重启 MCP server 归编排者;执行、诊断、实机验证 agent 禁自行重启。重启前先查运行状态,没有运行中的 run 才重启。重启办法见项目入口文件 §6。四步确认、改动集中纪律见 runtime-ops.md「启动与重启」节;场景一怎么适用见 §6.4。

### 2.4 问题处置循环

**循环全貌**

1. 执行 agent 停止操作并汇报 → 编排者派**诊断 agent**定位根因。一份报告里有多条未闭环问题,一次只派一个诊断 agent:任务书把全部未闭环问题列上,它的报告逐条给处置建议。

   诊断任务书的要素(通用层没有这个模板,货币战争自己定):

   - 输入:当前线的报告。场景一 = 这一份单局报告;中途停下的那份带着现场四项,局终的现场四项填「无」。另带本线此前的诊断报告(有就带上)和追踪文件的路径(「处置建议」第 5 样要指认里面的缺口条目)。
   - 权限:代码只读。游戏操作:现场还在(出问题的画面还停在游戏窗口里)才可以复现;现场不在了,不进游戏、不开新局,只凭报告、截图和代码定位。
   - 报告:格式用 od-dev-run-iteration 的探索报告格式(判断结论 / 活跃迭代影响 / 现状 / 没摸到的现状 / 澄清记录 / 问题定义)。「现状」一节写复现步骤和证据,「问题定义」一节写根因。另加两节:「处置建议」;「结束时的现场四项」(动过游戏窗口才写)。
   - 「处置建议」逐条写五样:
     1. 处置方式(下面第 2 步四个值里选一个,必附字段);
     2. 合并建议(并入哪条已有的线,或新立);
     3. 现象指认(和本线哪一份此前的诊断报告是同一现象,没有写「无」);
     4. 修正办法(给下一个执行 agent 看的做法,有才写);
     5. 对应追踪文件里哪个画面的哪几条缺口(不对应任何一条写「无」)。
   - 查不清也是合法结论:凭现有证据定位不了根因的,报告结论写「查不清,要等现场」,不硬选处置方式。
   - 落点:报告落 `<自主工作文件夹>/<线名>/`。回信不超过 10 行:结论一行(处置方式,或「查不清」)+ 报告路径。

2. 诊断产出固定节「处置建议」,编排者照派:

   - 先改追踪文件:照第 5 样找到那几条缺口。
     - 查出来属于三层里哪一层的,把开头的「待查原因」改成那一层。
     - 处置方式是立线建议、单点修复单的,状态改成「等修复线」。
     - 结论是「查不清」的,按下一小条登记,状态改成「已登记待跟进事项」。
     - 处置方式是知识修正、环境处置的,和写「无」的,删掉那几条状态是「等诊断」的缺口(这次的问题不是画面上的缺口)。
     - 它指的画面和缺口原来记的画面不一样,把缺口挪过去(一条缺口怎么写,见 screen-tracking.md §2)。
   - 结论是「查不清」(场景一)→ 编排者把这条问题登记进待跟进事项文件,标「等现场再现」。以后每局任务书的附加信息节带上它;实机探索 agent 再遇到就停下来,现场留给诊断。诊断报告写出以后,编排者删掉这条「等现场再现」的条目:结论不是查不清的,问题有了处置建议,照建议走;还是查不清的,原样再登记一条,由诊断熔断计数;追踪文件里对应缺口的状态,改成新条目的编号。
   - **知识修正**(知识文档要改;附目标文件指针和生效方式):立知识文档线走 od-dev-run-iteration。它是小迭代:步骤少、文档短,内容是修正知识文档。收口后让原执行 agent 继续工作。场景一例外:知识文档等用户裁定,不立线,登记进待裁知识队列(§5.6),原执行 agent 不等这一条;编排者把「修正办法」原文放进重派任务书的附加信息节。画面档、模板要改的,不算知识修正,按单点修复单或立线建议走(修复线的范围含补完建档,§6.1)。
   - **单点修复单**(改哪 + 判据):编排者拿「改哪」对照当前线 landing 文件首节的影响面申报(§9.5)。影响面申报 = 落地申报文件(landing.md)的第一节,声明本线会改哪些文件;下文说的「申报面」就是它。
     - 在申报范围里的 = 线内任务:当前线迭代 tasks.md 加任务,不立新线。派线内修复任务(实现 + 验证)后继续;
     - 不在申报范围里的,和没有迭代目录的线(如场景一的实机探索线)一样,按立线处理。
   - **立线建议**(线名 + 改哪 + 判据 + 优先级 + 原文切片〔从报告里原样抄出来的一段话〕):立新线走 od-dev-run-iteration 完整生命周期 → 实现并过了 review → 改了运行时代码的重启 MCP server(§6.4)→ 实机验证(复现原故障场景确认已修;什么时候验见各场景节,场景一 = §6.5)→ 让原执行 agent 继续工作。
   - **环境处置**(重启、重试 + 可复跑检查命令):执行者是编排者。
     - 动作限于三种:重启 MCP server、重新打开游戏、重派原执行 agent。每种做一次。
     - 检查命令由编排者跑,限于不操作游戏的命令(git、pytest、查日志这类)。要操作游戏的检查,写进重派任务书交实机探索 agent。
     - 场景一里对局停在半路时,「重新打开游戏」不直接做:那等于放弃对局,改为登记待裁。
     - 做完还不行 → 登记待裁。场景一里对局丢了怎么恢复,见 §7.2(不派诊断,按固定步骤走)。

   建议字段缺失 = 格式缺陷,打回重交。

   **诊断熔断**:编排者按「现象指认」连起来的链条计数,同一现象第 3 次 = 登记待裁(pending-decisions.md),线表等待条件记「等待裁定」,追踪文件里对应缺口的状态写「等用户裁定」,其他线继续。

3. 对局停在半路(§5.2 路 A)时,循环期间原执行 agent 保持停止状态等待。线表里这条线的「在飞 agent」一格改记诊断 agent,「当前步骤」不变。编排者按公共 skill 的放行规则(其 §4.1)接其他排队线;窗口可能被诊断、实机验证 agent 按 §2.2 接管,窗口归谁以编排者的登记为准。诊断 agent 不立线;它用窗口期间,占用表仍记在原线名下,备注「诊断 agent 在用」。这一局已经结束(§5.3 路 B)时不一样:没有停下等这回事,诊断 agent 和别的线一样照 §3.3 排着走,不挡下一局;派出去的诊断 agent 同样记在实机探索线那一行的「在飞 agent」一格。

**诊断报告当修复线的探索报告用**:按处置建议立线时,立项与设计任务书里的「探索报告」填诊断报告的路径,修复线不另派探索。本领域和迭代 skill 有一点不同:迭代 skill 写的是把探索报告移进迭代目录;这里复制一份进迭代目录、改名 explore.md,原报告留在原处(后面的诊断和线表还要引用它)。这一句写进立项与设计任务书的附加信息节。没经过诊断的修复线(§6.1),自己的探索报告照迭代 skill 的做法移进迭代目录。报告里没有未闭环问题时,「缺动作 op」不经过诊断,见 §6.1。

**各角色边界**

| 角色 | 游戏操作 | 代码 | 说明 |
|---|---|---|---|
| 执行 agent | 可 | 只读 | 按任务书操作当前场景验证载具(场景一 = 亲自玩货币战争);遇问题停止操作并汇报;问题处置交编排者另派(§2.4) |
| 诊断 agent | 现场还在才可(复现) | 只读 | 定位根因,不改代码 |
| 设计 agent | 不操作 | 只写设计稿 | 设计与实现分开,防同一个 agent 既定方案又自己验收 |
| 对抗评审 | 不操作 | 只读 | 每轮起全新的、没读过前几轮讨论的子 agent——看过前几轮讨论就会被已有思路带偏,挑不出真问题 |
| 实现 agent | 不操作 | 写 | 按设计稿落地;与设计稿对不上的地方报告编排者,不自作主张改设计 |
| 实机验证 agent | 可(复现验证) | 只读 | 验证后把窗口停回已知稳定状态(大厅或备战画面)再归还;要把窗口交还给半路对局的原执行 agent 时,停在验证结束时的画面归还,并在报告里附现场四项(§6.5) |

**传话纪律(约束编排者本人)**:用户消息与子 agent 问题原样转交、不加工、不筛选——通用框架定义,单一源 = od-dev-agent-autonomous-mode §4.3「传话原样」。货币战争加一条:设计争议需要用户裁决时,把双方论点原样并列转达,不排序、不建议。

### 2.5 记录文件与待跟进事项的写法

**哪件事记在哪**

- 自主推进不设总的任务清单文件。当前线还有哪些事没做完,记在下面这些地方:
  - 画面识别、动作 op 的缺口:记在追踪文件(screen-tracking.md),哪个场景发现的都记这里;
  - 其余待办:记在待跟进事项文件(本节下文);
  - 等用户裁定的知识发现:记在待裁知识队列(§5.6);
  - 玩家 skill 的指引不够用的地方:记在玩法指引的不足文件(exploration.md §6.4)。
- 编排层的登记(线表、占用表、待裁登记)= 通用框架定义的自主工作文件夹(SR 项目惯例 .debug/temp/ 下 autonomous/<开工日期-主题>/)。
- 追踪文件、待跟进事项文件、玩法指引的不足文件不放自主工作文件夹,会话结束了也留着。位置见 screen-tracking.md §1、本节下文、exploration.md §6.4。待裁知识队列放自主工作文件夹。
- 谁写:
  - 追踪文件、待跟进事项文件、待裁知识队列这三份,由编排者照子 agent 的报告登记;
  - 玩法指引的不足文件,由实机探索 agent 自己写(exploration.md §6.4);
  - 修复线做出新的动作 op、或者判了一步不用做动作 op 以后,追踪文件的动作一栏和玩家 skill 画面文档的「操作」章,也由编排者照修复线的报告改(§6.7、§6.8)。
- 推进期间子 agent 做迭代时,按 od-dev-run-iteration 的 tasks.md 格式在迭代目录内登记进度。编排者不替子 agent 记迭代进度。
- 发现的归档:知识类结论落对应知识文档或画面档(分层判据见 SKILL.md §3;场景一先记待裁知识队列,见 §5.6)。过程叙事不进本 skill。

**待跟进事项文件** = `.temp/tracking/currency-war/待跟进事项.md`。它是运行时产生的文件,不进版本控制。文件不存在就按「没有未竟项」处理,第一次登记时新建。

- 条目写四样:事项、证据指针(截图文件名)、状态标签、编号。编号在全文里顺延,删掉的编号不复用。
- 状态标签六种:等实机取证 / 已取证 / 等现场再现 / 等用户裁定 / 等随机遇到 / 等外部条件(等游戏版本这类不由本项目控制的条件)。
- 立过修复线或迭代目录的条目,再写「改哪、判据是什么」,照它的申报抄。
- 从追踪文件转登的条目,写上画面名,抄缺口条目原文和证据;追踪文件里那条缺口的状态后面写上这个条目的编号(写法见 screen-tracking.md §2)。编排者不自己编技术内容。
- 按旧记法写的条目(分节存放、每一节自己编号、多数没写状态标签)怎么读,见 screen-tracking.md §6。
- 迭代做多大,由设计 agent 在设计文档里定。
- **完成即删**:条目闭环(清偿、实证、裁决定谳)时,当场把该条目从待跟进事项文件删除。文件里只留开放项,禁留「已完成」「已清偿」的划线态或存档句堆积。有长效价值的裁定结论随 commit message 或知识文档固化,不靠文件留尸。

## 3. 场景一:关注什么与开局

### 3.1 关注什么与范围

- 关注两块:
  - 新版本的画面建档与识别、动作 op;
  - 实测玩家 skill 的玩法指引。实测的办法:实机探索 agent 每一局都照它的指引打,不够用的地方记进玩法指引的不足文件。玩法上的新发现靠实机局收集。
- 四层覆盖:

| 层 | 内容 | 覆盖判据 |
|---|---|---|
| 画面建档 | bot 会遇到的画面建档到 screen_info | 画面能被识别框架认出(产物形态见 od-dev-screen-onboarding) |
| 画面识别 | 已建档画面的关键读数接入识别器 | `analyze_screen` extras(结构化读数扩展)能读出该画面的关键数值 |
| 动作 op | 自动打一局用得上的动作有对应动作 op | 该不该有,按 exploration.md §3.2 的三个问题判。该有的里面,玩家 skill 对应画面文档的操作表这一步「用什么」的主做法写着 op 的类名(用 run_operation 调用的)算有,其余算没有 |
| 游玩指导 | 玩家 skill 有该画面的决策知识 | 玩家 skill 对应玩法文档覆盖该画面的决策面 |

  - **标杆 = 商店的买卖闭环**:商店画面上买、卖这一组动作,四层全部在役(建档可识别 / extras 可读数 / 买卖的动作 op 可执行 / 玩家 skill 有买卖的决策指导)。新画面与新节点的覆盖验收以它为参照:前三层缺任何一层 = 未闭合,缺口登记进追踪文件;第四层缺了,记进待裁知识队列(§5.6)。商店画面上不在买卖这一组里的动作(比如免战跳过),该有动作 op 而还没有的,照常登记缺口,不算在标杆里。
- 目标来自用户,缺口边做边记。实机局任务书由用户说明的目标驱动(§4.2)。追踪文件里已知的缺口只带路径:实机探索 agent 打到哪个画面,读那一章,顺手核对章里的缺口。禁不带目标进局。
- 不属于本场景的事:
  - 更新各域的数据(角色、羁绊、装备这些注册表,以及成批生成识别模板)。这是版本适配时做一次的事,走 version-update.md 的清单,不归自主推进。探索中发现某一项内容识别不到(比如缺模板),才立修复线去补(§6.1);
  - 调 bot 的策略代码(场景四,§8.3)。实机探索 agent 自己打局用的打法不在此列:照玩家 skill 的指引打(exploration.md §2.1);
  - 单局复盘。它的输入是 bot 自动打局留下的运行记录;本场景的对局由实机探索 agent 自己手动打,没有这种记录;
  - 改写知识文档。本场景里知识文档等用户裁定(§5.6)。
- 范围:
  - 画面建档、画面识别、动作 op 三层的缺口,记在追踪文件;
  - 第四层(游玩指导)靠实机局实测,实测出的不足记在玩法指引的不足文件。第四层的知识文档本身要等用户裁定才改,它的缺口登记进待裁知识队列或待跟进事项文件。
- 本场景不设固定的完成条件,什么时候算完见 §1.2。「局内目标」由实机探索 agent 每局写:
  - 用户说明的目标里写明了做到什么程度的(比如打到通关、哪些画面建完档),达到的那一局写达到,别的局写未达到;
  - 没写明程度的,都写未达到,写到用户叫停或者用户说进入下一个场景为止。

### 3.2 有哪几类活

| 类别 | 进不进游戏 | 做什么 | 改哪些文件 |
|---|---|---|---|
| 实机探索线 | 进 | 实机探索 agent 按玩家 skill 亲自打,一局一派 | 建档内容、画面文档前两章、玩家 skill 入口列表加一行、玩法指引的不足文件、单局报告 |
| 修复线 | 验证时进 | 改识别代码、补识别模板、改动作 op、补完没做完的建档 | 代码、测试、模板资产、画面档、画面文档(前两章)、设计正本。接上动作 op 的线,画面文档「操作」章那一格由编排者照实现报告改(§6.7) |
| 诊断 agent(一次性任务) | 现场还在才进 | 定位一个问题的根因,给处置建议 | 不改文件,只写诊断报告 |

- **实机探索线**:一开始只立这一条。它停在迭代的探索这一步。产出是单局报告和上表列的文件,不做设计与实现;要改代码、补模板的发现都另立修复线。
- **修复线**:探索中发现要改代码、补模板才能解决的问题才立。什么时候立、怎么走,见 §6。
- **诊断 agent**:不立线,做完即止。任务书要素见 §2.4。

**追踪文件** = `.temp/tracking/currency-war/画面识别与动作op.md`,长期保存,不随会话或迭代重建。它按画面分章,记三样:识别核对、动作一栏、这个画面的缺口。开局时编排者不预先建章。格式和记法见 [screen-tracking.md](../screen-tracking.md)。

### 3.3 谁先走

实机探索线不等修复线,也不等知识文档线。

- 缺口登记进追踪文件,实机探索 agent 照操作表用鼠标做,就能接着打下一局。
- 并行度大于 1 的,多出来的位子给修复线和知识文档线,走它们不占游戏窗口的步骤(探索、立项与设计、对抗、实现、review)。
- 要重启 MCP server、要占游戏窗口的验证,放在两局之间(§6.4、§6.5)。
- 并行度是 1 的,每打完一局、报告登记完,先推进一步修复线或知识文档线,再派下一局。一步 = 一张任务书:派出去、等它交活、登记完,算走了一步。
- 这一局有要查原因的问题的,先派诊断 agent(§2.4)。它排在修复线、知识文档线前面;诊断报告处理完,再走这一步。

### 3.4 场景一的开启清单

按顺序做。公共 skill 开启清单的四步都在里面,最后一步是自验。

1. ☐ 确认需求入口:用户说明的场景和目标,整句抄下来。只说了场景、没说目标 → 先做完第 2 步,在待裁登记里登记请用户补,然后停下等用户,不往下走。
2. ☐ 建自主工作文件夹,复制线表、占用表、待裁登记三份模板。要填的:
   - 场景原话抄进线表表头(§1.2):线表模板的标题下面加一行「场景(用户原话):〈…〉」。
   - 用户指定了阵容线的(开启时说了这一轮按哪篇阵容攻略打):线表表头另加一行「阵容线:〈攻略名〉」。以后每一局任务书的「阵容线」都从这里取(§4.2);没指定的不加这一行。
   - 并行度:用户当次明示了并行就按用户的,没明示取 1(§9.1)。向用户报一句。
3. ☐ 核对两处:
   - 第一处,只在接手中断的会话时(已有同主题的文件夹)做:按公共 skill 核对三份文件。另外,追踪文件里标着「卡在用户叫停」的缺口,状态改回「等修复线」;待跟进事项文件里对应的条目删除(叫停时登记的,§7.1)。
   - 第二处,每次开启都做:追踪文件里有流程外画面的章(旧口径的章怎么认,见 screen-tracking.md §6)的,动作一栏写「- 动作:无」,「没有动作 op」的缺口删掉。这些画面的动作都不该有(exploration.md §3.2 第 1 问),实机探索 agent 也走不到,没有哪份报告会来转它。画面建档、画面识别两层的缺口,登记进待跟进事项文件,状态标签「等用户裁定」;追踪文件里这几条的状态写「已登记待跟进事项(编号 N)」。
4. ☐ 立实机探索线:登记线表,建 `<线名>/` 子目录。
5. ☐ 派第一局之前做三件事:查占用表和运行状态;查资产哨兵还在不在,不在就武装(§2.2);登记占用表。
6. ☐ 拼任务书,派实机探索 agent(§4)。分两种情况:
   - 上次是用户叫停的(交接记录、追踪文件或线表里写着)→ 先派活,再拼任务书。
     - 派活:最后一份单局报告里登记过、还没派活的发现,该立修复线的立修复线(追踪文件里已经有同一条缺口的,照 §5.3 第 2 步办),用户已经裁定的知识发现派知识文档线。未闭环问题不派诊断:叫停时已经登记成「等现场再现」(§7.1 第 3 步),再遇到才停、才诊断。叫停时在飞的修复线、知识文档线,照公共 skill 恢复中断会话的办法接着走。
     - 占用表里有留存的半路对局(交接记录里写着「用户叫停」):停下原因是「操作表里没有这一步」的,等那条修复线验证通过再重派(§5.2 路 A 第 3 步);别的停下原因,派完活就重派。续打的任务书按 §4.4 更新,附加信息节带「叫停后恢复」的说明(§7.2 的恢复类说明里,用户叫停那一种)。交接记录写了「现场未知」的,任务书带公共 skill 的接棒前言。
     - 没有半路对局(叫停发生在两局之间):派完活,拼下一局的任务书。
   - 不是叫停以后(第一次开启,或者因为别的原因中断以后重开)→ 占用表里有留存的半路对局,拼续打的任务书(§4.4);没有,拼下一局的任务书;还没有打过的,照 §4 拼第一局。
7. ☐ 自验:场景原话在线表表头;用户指定了阵容线的,线表表头里有「阵容线」那一行;线表里有实机探索线;占用表有登记;资产哨兵在岗;探索 agent 已派。有缺回那步重做。

## 4. 场景一:实机探索任务书

### 4.1 模板

实机探索任务书只用下面这个模板,公共 skill 探索模板的条款对它不适用:那份模板是按「摸清现状、不推进游戏」写的,步骤、报告格式都和「打完一局」对不上。别的任务书照模板库头注。

任务书写全这一局的全部内容,不写「同前」「按上次任务书」。任务书不复制玩家 skill 的内容;实机探索 agent 也不依赖编排者的会话历史。

```markdown
# 任务书:<线名>·实机探索·第 <局号> 局

开工前先通读 sr-od-dev-currency-war 的 references/autonomous/exploration.md
(实机探索 agent 作业手册),照它打这一局。

## 需求
- 局内目标:<§4.2>
- 阵容线:<§4.2>
- 顺带取证清单:<§4.2>
- 顺路验证清单:<§4.2>
- 难度:<§4.2>
- 这一局:<开新局 / 接着打,从停下的画面继续>

## 操作依据
- 打法、画面上的操作、对局决策:玩家 skill `sr-od-currency-war`
- 打这一局的工作方法:references/autonomous/exploration.md

## 禁止事项
- 能写的文件只有 exploration.md §6 列的四样,不动 `src/` 下的代码
- 对局之外的东西不碰(exploration.md §2.2)
- 遇到问题停止操作并汇报,禁自行修复(exploration.md §4.1)

## 回信
不超过 10 行,内容见 exploration.md §7.3

## 附加信息
<按 §4.3 填>
```

### 4.2 五样的来源

「需求」节的五样,每次派发都照当时的记录重新填,编排者不自己判断:

| 样 | 来源 |
|---|---|
| 局内目标 | 用户开启自主推进时说明的目标(原话),每一局都一样 |
| 阵容线 | 用户开启自主推进时指定的阵容攻略。取线表表头「阵容线」那一行(§3.4 第 2 步);没指定的写「无」 |
| 顺带取证清单(本局顺路可取的条目) | 待跟进事项文件里标「等实机取证」的条目(按旧记法写的条目怎么算,见 screen-tracking.md §6) |
| 顺路验证清单(等实机验证的线里本局顺路能验的) | 线表里等待条件是「等实机」的修复线,每条写线名 + 它 landing 文件「验证需求」节的路径 |
| 难度 | 当前可解锁的最高难度(exploration.md §1.4) |

- 某一样没有内容,写「无」。
- 排序判据:覆盖缺口优先,机制取证次之。每局只背一个主目标,顺带清单只收顺路可取的条目,不要求绕路取证。
- 这一局是开新局还是接着打,也写在「需求」节。

### 4.3 附加信息节

编排者照抄、不加工。

- 每次派发都带:
  - 待裁知识队列全文和队列文件路径。第一局时队列文件还没有,写「无」;
  - 待跟进事项文件的路径;
  - 追踪文件的路径;
  - 玩法指引的不足文件的路径。

  追踪文件、玩法指引的不足文件只给路径,不抄内容:实机探索 agent 打到哪个画面,自己读哪一章;玩法指引的不足文件它开工前自己读一遍。
- 有才带:
  - 诊断报告里给的修正办法(§2.4);
  - 待跟进事项文件里标「等现场再现」的问题(再遇到就停下来,现场留给诊断);
  - 上一份单局报告的关注清单里「没看到」的条目(原文;实机探索 agent 起草关注清单时从这取);
  - 恢复类的说明:写明上一份报告是哪一种停下原因(连不上、掉线、闪退、叫停四种之一),做法见 exploration.md §5.2 对应的一段。

### 4.4 现场交接信息与重派时改哪里

**现场交接信息**:接管已有对局时,任务书写三样:

- 交出方(最后一个动过窗口的 agent)报告的现场四项;
- 它的报告路径;
- 这一局此前全部单局报告的路径。

局账和关注清单接着这些报告续记。

**重派时改哪里**:重派实机探索 agent 接着打这一局时,任务书 = 原任务书,更新下面几处:

- 五样按当时的记录重新填(§4.2)。停下这段时间新走到「等实机验证」的修复线,这时才进得了任务书;
- 现场交接信息里的现场四项,取自动过窗口的最后一个 agent 的报告。诊断 agent、实机验证 agent 动过窗口的,取它们的报告;都没动过,取最后一份单局报告;
- 附加信息节更新(§4.3),其中带两句:「从停下的画面继续」;修复线给这个画面接上了新动作 op 的,「这个画面的这一步已经是动作 op〈名字〉」(§6.7);
- 上一份报告缺了栏目的,在附加信息节写明要补写哪一栏,让接手的实机探索 agent 补写。

## 5. 场景一:局间流程

### 5.1 三条路

实机探索 agent 停下并汇报以后,看单局报告的「停下方式」,分三条路:

| 停下方式 | 走哪条路 |
|---|---|
| 中途停下(这一局没打完) | §5.2 路 A |
| 局终(这一局结束) | §5.3 路 B |
| 中止(对局丢了) | §5.5 路 C |

实机探索线什么时候停,由用户决定(§7.1):编排者不因为「连着几局没盖到新条目」自己收线。

### 5.2 路 A:中途停下

1. 停下原因是 MCP server 连不上、游戏掉线、游戏闪退 → 不派诊断。先按第 5 条登记,再按 §7.2 的固定步骤恢复。恢复以后直接重派(§4.4)。
2. 停下原因是用户叫停 → 按 §7.1 处理。
3. 其余原因:先按第 5 条登记,再走下面四小步。
   1. 报告里有未闭环问题 → 走 §2.4 派诊断。报告里同时有「缺动作 op」的,也先派诊断:未闭环问题和缺的动作 op 可能是同一个原因。诊断报告到了,按它的合并建议决定缺的动作 op 并进哪条线。
   2. 没有未闭环问题,只有「缺动作 op」,或者建议处置是「立修复线」的缺口 → 不派诊断,直接立修复线(§6.1)。追踪文件里已经有同一条缺口的,照 §5.3 第 2 步办,不另立。
   3. 立起来的修复线按 §6 走到验证通过,或者转成顺路验证(现场不在了的时候)。修复线自己的探索报告认为不用改代码的 → 登记待裁(附报告路径),线表等待条件记「等待裁定」,这一小步停在这里等裁定。两种除外,照 §6 办:这一步已经有现成的动作 op 能用、只差操作表没写;一条龙的代码不点这一步,修复线判它不用做动作 op。
   4. 重派实机探索 agent 接着打这一局,任务书按 §4.4 更新。

   中途停下期间没有局在打。停下原因所在画面的那条修复线,连续走到验证通过;并行度是 1 的时候,位子先给它。这一局前面几个画面立起来的修复线都是顺路验证,等重派以后再照 §3.3 走。
4. 停下原因是「模式选择画面有存档」→ 登记待裁(附报告路径),线表等待条件记「等待裁定」。用户裁定以后,把裁定原话写进重派任务书的附加信息节,重派实机探索 agent。
5. 中途报告怎么登记(第 1、3、4 条共用):照 §5.3 第 2 到 4 步里登记的部分做,三样:
   - 追踪文件(§5.3 第 3 步,做法见 §5.4);
   - 待裁知识队列、待跟进事项文件(§5.3 第 2 步);
   - 顺带取证和顺路验证的结果(§5.3 第 2、4 步)。

   登记这一步不派活:不派诊断、不立修复线、不派知识文档线。第 3 条的派活在登记以后按它的小步走。第 1 条恢复以后不派:没闭环的问题由这一局后面的单局报告接着报(「未闭环问题」只列还没处置的);顺路验证不达标的,记进那条修复线在线表的备注栏。这两样都等下一次停下或者局终,再按对应的路处理。

### 5.3 路 B:这一局结束

按顺序做,最后一步是自验。

1. ☐ 收这一局的全部单局报告,以局终那份为准。不另派子 agent 核对报告里的数字,数字照报告登记。局终报告缺了哪一栏,在线表里实机探索线那一行的备注栏记「〈报告文件名〉缺〈栏名〉」,不补写。
2. ☐ 处置这一局的发现:
   - 未闭环问题 → 走 §2.4 派诊断。诊断 agent 不挡下一局:并行度是 1 的时候,它排在修复线、知识文档线前面,先派它(§3.3)。同一个问题已经有诊断 agent 在查的,不另派:新报告的路径写进它的任务书附加信息节(在飞的,直接转话);
   - 「缺口」里建议处置是「立修复线」的、「缺动作 op」→ 逐条先查追踪文件,分两种:
     - 这一条已经有了(有一句说的是同一件事):不另起、不派活、不往线表备注栏追加;报告有新证据的,追加到那一条的证据里。再看它的状态。「等修复线」后面写着线名的:线表里这条线还没收口 → 什么都不做;已经收口了,或者线表里找不到这条线 → 照下面新缺口的办法立线或并线,把线名换成新的。「等修复线」后面没有线名的 → 照下面新缺口的办法立线或并线。「等用户裁定」「已登记待跟进事项」→ 只核对状态还在不在(那一头的条目还在、裁定还没到),不派活;
     - 这一条是新的(追踪文件里没有)→ 立修复线,或者并进已有的修复线(§6.2「攒批」)。登记进追踪文件是第 3 步的事;
   - 「缺口」里写明现在探不了的 → 登记待跟进事项文件,状态标签照报告写的条件选:等某个随机局面的写「等随机遇到」;等游戏版本这类外部条件的写「等外部条件」。追踪文件里这条缺口的状态在第 3 步一起改;
   - 知识发现 → 编排者照每条的建议去处登记(§5.6):进待裁知识队列,或登记待跟进事项文件;
   - 顺带取证采到的项 → 把数值和证据指针照报告抄进待跟进事项文件的对应条目,状态标签改成「已取证」。之后由谁拿它改代码或文档,登记待裁由用户定;知识文档线在等的条目除外,照 §5.6;
   - 这一轮立起来的修复线、知识文档线,登记进线表就行,不挡下一局:它们照 §3.3 的先后顺序走。诊断 agent 不立线,记法见 §2.4 第 3 步。
3. ☐ 照单局报告更新追踪文件,做法见 §5.4。
4. ☐ 顺路验证的结果照单局报告处理(§6.6)。达标与否以报告写的为准,编排者不另核。
5. ☐ 待裁知识队列里有用户已经裁定的 → 立知识文档线(§5.6)。它不挡下一局。
6. ☐ 按条件决定下一步:
   - 局终报告「局账」里的「局内目标」写着达到 → 这一局有要查原因的问题的,先派诊断 agent(第 2 步);然后按 §1.2 处理,不派下一局;
   - 其余 → 这一局有要查原因的问题的,先派诊断 agent(第 2 步)。然后按 §3.3 让修复线或知识文档线走一步。然后拼下一局的任务书(§4),派发前过 §2.2,派下一局。验证通过的修复线,剩下几步(全局对照、正本更新、收口)和别的修复线步骤一样,照 §3.3 排着走,不挡下一局。
7. ☐ 自验:这一局报告里的每条发现都有去处——追踪文件、待裁知识队列、待跟进事项文件、线表,四份文件里至少一份记了它;线表和占用表是最新值。有遗漏回去补。

### 5.4 照单局报告更新追踪文件

记法见 screen-tracking.md。

- 要更新的章还是旧口径的,先照 screen-tracking.md §6 转好再登记。
- 第 12 节「画面核对」,报告写到过的每个画面,按顺序做四样:
  1. 这个画面还没有章的,新建一章。
  2. 识别核对那一行,改成报告日期和报告写的结论。
  3. 报告写用过的动作里,用 op 做的,或者用鼠标做并且报告写了「该有」或者「判不准」的:动作一栏里还没有这一步的,加一行。括号里写操作表这一步的做法:是 op 的类名就写类名,是鼠标就写「鼠标点击」;操作表里没有这一步的,写「鼠标点击」。新加的行括号是「鼠标点击」的,缺口小节同时加一条「动作 op」,状态「等修复线」,发现的日期写报告日期,证据写这份报告的文件名。报告写照括号里的做法做、并且正常的,日期改成报告日期。原来标着「未判」的行,报告写了该有的,去掉「未判」,照上面的办法加缺口;报告写了不用做的,删这一行。
  4. 报告写不正常的动作:日期不改。它的问题按下面「未闭环问题」那一条处理。

  报告写某一章原有的缺口已经不在了的,删掉那一条缺口。写「核不了」的不动。写「已补建」的,删掉那一条缺口;状态里写着线名的,把「已补建」记进那条线的线表备注栏,下一张任务书的附加信息节带上它,由那条线决定还做不做。
- 第 2 步立了线或者并了线的,这一步把线名写进对应缺口的状态:「等修复线(〈线名〉)」。
- 第 4 节「缺口」、第 7 节「缺动作 op」→ 写进对应画面那一章的「缺口」小节,状态「等修复线」。
  - 已经有一条说的是同一件事,不另起一条;它的状态只在上面写明的情况下改。
  - 报告写这一步是三个问题判不准的,把理由和拿不准的地方抄进这一条缺口:做不做动作 op 要靠它判。
  - 报告写这一条现在探不了的,按 §5.3 第 2 步登记进待跟进事项文件;这里的状态写「已登记待跟进事项(编号 N)」,N 是那个条目的编号。
- 第 8 节「未闭环问题」→ 每个问题在报告写的那个画面的「缺口」小节里先写一条,开头写「待查原因:」,后面照报告写的现象写,状态「等诊断」。诊断报告到了以后按 §2.4 第 2 步改。
- 第 9 节「遗留」里写着追踪文件的括号和操作表对不上的 → 照操作表把括号改过来。
- 原来标「已登记待跟进事项」的缺口,这一局又遇到了(第 4 节里有它),待跟进事项文件里那一条标的是「等随机遇到」→ 删掉那一条待跟进事项,缺口的状态改回「等修复线」。
- 第 3 节「没看到」→ 不动追踪文件,按 §4.3 抄进下一局任务书。
- 第 9 节「遗留」里的文件名 → 记进线表备注栏。以后给这个画面立修复线时,写进任务书的附加信息节,由修复线的探索 agent 核对:改动全属于那次建档的,由修复线提交;混有别人改动的,不动。

### 5.5 路 C:中止

1. 这一份中止报告和这一局此前的各份单局报告,照 §5.3 第 2 到 4 步登记,内容以最后一份完整的单局报告为准。
2. 开新局 = 派下一局:五样照记录填,派发前过 §2.2。有修复线或知识文档线在排队的,并行度是 1 的时候先让其中一条走一步(§3.3)。

### 5.6 待裁知识队列与知识文档线

**待裁知识队列** = `<自主工作文件夹>/pending-knowledge.md`,放等用户裁定的知识发现。

- 谁写:编排者。实机探索 agent 把知识发现写进单局报告的「知识发现」;编排者照原文转登,不加工。
- 每条四项:编号(K-1、K-2 顺延,删掉的编号不复用)、发现内容、证据指针、建议落点(改哪份文档的哪一节)。已经入队的发现再次出现,只在原条目上追加证据指针,不另起一条。
- 证据还不够、要等实机取证的发现不进这个队列:登记待跟进事项文件,由顺带取证清单携带。
- 用户裁定以后:编排者先把裁定原话记在这条队列条目下面,再派知识文档线按裁定更新。
- 用户裁定「不改」→ 删除队列条目,不立线。
- 用户一次裁定好几条 → 合并成一条知识文档线。

**知识文档线**(小迭代:步骤少、文档短,内容是修正知识文档):

- 走 od-dev-run-iteration。它和修复线一样,不挡实机探索线,照 §3.3 的先后顺序走。
- 它不进游戏,核实靠第二来源:官方配置、wiki、以前实机局留下的截图,三样里有一样和这条发现对得上,才写进文档。
- 核实的三种结果,各有收场:
  - 对得上 → 更新知识文档。更新线提交后,删除队列里对应的条目。
  - 第二来源证明它不对 → 知识文档线回报编排者;编排者把这一条从待裁知识队列移到待裁登记(一个事项只挂在一处),由用户再定。
  - 三样都查不到、要再打一局才能核实(知识文档线走到哪一步查到,都按这条办)→ 知识文档线回报编排者;编排者把这条发现登记进待跟进事项文件,标「等实机取证」,删除队列条目。这条知识文档线不结束,线表等待条件记「等实机」。顺带取证采到以后,编排者清掉等待条件,重派它的立项与设计这一步,附上采到的证据。
- 可靠性纪律见 exploration.md §8。

### 5.7 知识文档的改动范围

- 实机探索 agent 不经用户裁定就能写的只有四样(exploration.md §6):建档内容、画面文档的前两章、玩家 skill 入口列表加一行、玩法指引的不足文件。前三样是改文档;第四样只是登记,不改任何文档。
- 实机探索 agent 别的都不写,也不删除任何文档:
  - 画面文档的「玩法指引」章;
  - 玩家 skill 的指引文档(references/ 下的必读三篇、阵容图鉴、阵容攻略、机制各篇);
  - `docs/game/currency_war/research/` 各篇。
- 本场景里,另外会改到文档的只有三处:
  - 修复线改设计正本,走它迭代的正本更新步;
  - 接上动作 op 以后画面文档「操作」章的那一处,由编排者照实现报告改(§6.7),不进修复线的申报面;
  - 知识文档,按用户裁定由知识文档线改(§5.6)。

**玩法指引的不足怎么收场**:

- 用户改玩家 skill 的时候看这份文件,改不改、谁来改由用户定。自主推进里的各条线不替用户处理它。
- 改进玩家 skill 的那一次改动,顺手删掉对应的那一条;用户裁定不改的,也删掉。
- 写的是「指引说的和实机不一样」的,改文档以前按 exploration.md §8 第 2 条核实一次。

## 6. 修复线

### 6.1 什么时候立、范围

**什么时候立修复线**:来源两个,都照报告写的办,编排者不自己判断:

- 实机探索 agent 的单局报告:「缺动作 op」一节;「缺口」一节里建议处置是「立修复线」的;
- 处置循环的处置建议(§2.4):单点修复单、立线建议。

**修复线的范围**:改识别代码、补识别模板、改动作 op、补完没做完的建档(比如没点的按钮的跳转关系)。

**立线分两种**:

- 经过诊断的:按 §2.4 走,诊断报告当探索报告。
- 没经过诊断的(单局报告的「缺动作 op」和「缺口」里报的):直接立线,按通用流程从探索这一步开始。探索任务书照通用模板,附加信息节加两句。
  - 第一句,「只读识别、不操作」:现场还在的,画面留在原地不动,连画面一起读;现场不在了的(实机探索 agent 照操作表用鼠标做完了这一步、已经往下打了),只凭单局报告、截图和代码。
  - 第二句:一条龙的代码不点这一步的,探索报告里写明画面名、步骤名和理由。这一行由编排者照报告写进追踪文件(§6.8),探索 agent 自己不改文档。

修复线的申报面不得碰策略面(§9.2)。

### 6.2 线名、攒批、半路的对局

**线名**:按画面归并的,线名用画面名。按诊断的立线建议立线、诊断另起了线名的,用诊断起的线名,线表备注栏记「对应画面:<画面名>」。以后同一个画面再报缺口,找这个画面最近一条没收口的线(线名是这个画面名的,或者备注栏「对应画面」写着这个画面的)。

**攒批(按画面归并)**:一个画面一条修复线。同一个画面又报了一条新的缺口(追踪文件里原来没有的),按这个画面最近一条没收口的线在哪个状态办:

- 还没进定稿(还在探索、立项与设计、对抗这三步)→ 并进去。编排者把新缺口的报告原文切片记进线表备注栏;这条线定稿以前的每一张任务书,附加信息节都带上它(这一步在飞的,直接转话)。并进设计由设计 agent 做,对抗 agent 不做。这条缺口登记进追踪文件时,状态写「等修复线(〈线名〉)」。不同画面的缺口各立各的线。
- 在等待裁定(诊断熔断、规则没覆盖)→ 不另立。把新缺口的原文追加进同一条待裁登记,等用户一起裁;这条缺口的状态写「等用户裁定」。
- 已经进了定稿这一步,或者过了定稿(在定稿、实现、review、等实机验证,或者已经收口)→ 不并,另立一条线,线名加序号(比如「商店-2」)。
- 诊断报告的合并建议说要并入某条线的,同样看那条线在哪个状态。诊断给的是单点修复单、在场景一按立线处理的,也照这三条找该并的线。

同一条缺口再报一次(追踪文件里已经有,说的是同一件事)不走这里,照 §5.3 第 2 步办。

**半路的对局留着**:诊断、实现期间,游戏窗口停在现场不动,占用表把窗口记到这条修复线名下。不替用户放弃对局。

### 6.3 最小形态

改哪和判据都能逐字指出来的小修复,迭代可以很小(设计一页 + 任务一行),门一个不少。够不够小,由设计 agent 在设计文档里定。

### 6.4 重启 MCP server

**什么改动要重启**:三种之一就要。

1. 改了运行时代码(`src/sr_od/` 下);
2. 往立绘库、装备库里加了模板。立绘库 = `assets/template/cw_character_avatar`;装备库 = `assets/template/currency_war/` 下的 `equip_plaza`、`equip_legacy`;
3. 改了已有的模板文件。

不用重启的:只改了画面档、测试、文档;或者只新加了立绘库、装备库以外的模板。

**怎么判这条线要不要重启**:

- 先看这条线 landing 文件首节「影响面申报」的「共享资源面」有没有「重启」标记(§9.4);
- 没有标记的,再看回信增补第 1、2 样(模板的改动不带标记);
- 要重启的,实现完成并过了 review 以后,由编排者重启(§2.3)。

**场景一的实现任务书另加一条回信增补**,写明四样:

1. 本线改没改 `src/sr_od/` 下的运行时代码;
2. 本线动没动模板文件(加了还是改了,在哪个目录);
3. 本线改动直接影响的测试有哪些(测试文件路径);
4. 本线给哪一步接上了动作 op:画面文档的路径、这一步的名字,操作章里这一格要写的内容(op 的名字和用法)。画面文档还没有「操作」章的,给新建这一章的全文。没接动作 op 的写「无」。

**什么时候重启**:

- 画面停在半路时立的修复线:等它们都到了验证点,合并成一次重启,派一个实机验证 agent 一次验完。同现场还有修复线在实现的时候,先到验证点的那条不先重启,等它到了再一起;转去等裁定的不算,不用等它。
- 实机探索 agent 在打局的时候不重启。
- 到了验证点的修复线,等这一局打完,在两局之间合并成一次重启。重启以后照常派下一局,新动作 op 由实机探索 agent 顺路验证(§6.5 第 2 种时机)。

**重启前确认**:照 runtime-ops.md「启动与重启」节做,其中三项在本场景这样判,其余照做:

- 「游戏在大厅」不要求:中途停下的时候,对局可能停在半路。
- 「工作区干净」:本线申报面里的文件都已提交,就算过。工作区里别的会话的改动不挡重启,编排者把剩下的文件名记进线表备注栏。
- 「全量测试 0 失败」:全量测试有失败时,只跑回信增补第 3 样列的直接影响的测试。这些全过 → 把全量里失败的测试名记进线表备注栏,照常重启。直接影响的测试也有失败 → 不重启,回 §2.4 处置循环。

**重启以后**:

- 编排者调一次 get_run_status,调通了才算连接恢复。
- 调通以后,这条线接了新动作 op 的,先照 §6.7 把两处改掉,再派下一个 agent。
- 调不通 → 按所在环境的办法重连 MCP 客户端再调;仍不通 → 登记待裁,两处也不改(新代码没加载,改了实机探索 agent 也调不了)。

runtime-ops.md 的「改动集中纪律」(局中不改代码)针对的是 MCP server 自己在跑的对局。实机探索 agent 自己打的对局,它停下以后就可以改代码并重启。

### 6.5 等实机验证

实现完成、过了 review 以后,线表记等待条件「等实机」(线表模板里的「等实机」,就是本文件说的等实机验证)。

收口这一步的任务书加一句,两种时机都用:回信里写明本线修掉了追踪文件里哪个画面的哪几条缺口,验证时哪些识别核对和动作是正常的,并附验证报告的路径。编排者在验证达标时已经照验证报告更新过追踪文件(§6.6);回信里这两样用来核对更新有没有漏。

验证分两种时机:

1. **现场还在**(出问题的画面还停在游戏窗口里):重启以后立刻派实机验证 agent,在这个画面上验。同现场还有修复线在实现的,等它们都到了验证点再重启、再派(见 §6.4「什么时候重启」)。
   - 主验证和次要验证:线表里先记「等实机」的那条线是主验证。同一个现场其余等实机验证的修复线,进验证任务书的「次要验证」一节。
   - 验证任务书开头加一句声明,替换模板「禁止事项」的第二条:「本任务书里,模板『专跑趟次不做消耗性 / 不可逆的游戏内操作』这一条,替换为——允许执行被验的动作 op,它会改变对局,这就是验证本身;和验收标准无关的操作不做。」
   - 附加信息节带五样:
     1. 交接协议(exploration.md §5.1),写明先读;
     2. 交出方的现场四项和报告路径;
     3. 同现场其他等实机验证的修复线(每条写线名和验收标准,模板「次要验证」一节的填法);
     4. 追踪文件里这个画面那一章的原文;
     5. 这个画面上标了「未点」的按钮清单(exploration.md §6.1)——验证时点到了哪个,报告里就写明点了哪些、点后到了哪个画面。
   - 验完把窗口停在验证结束时的画面归还,报告里附现场四项。验完交还实机探索 agent(§5.2 路 A 第 3 步)。
   - 验证要打一段对局的,打法照 exploration.md §2.1;感到玩家 skill 的指引不够用,也记玩法指引的不足(exploration.md §6.4)。
2. **现场不在了**(出问题的画面不在游戏窗口里:这一局已经结束;对局已经往前走、回不到那个画面;或者缺的动作 op 是照操作表用鼠标做的,实机探索 agent 没有停下):编排者每局拼任务书时,把等实机验证的修复线写进「顺路验证清单」(§4.2)。实机探索 agent 顺路遇到就验:对照那条线的验收标准,把结果写进单局报告。编排者照报告处理。

### 6.6 验证结果怎么处理

两种时机相同。

- 达标 → 清掉线表的等待条件,派后面几步(全局对照、正本更新、收口)。编排者同时照验证报告更新追踪文件:删掉本线修掉的缺口条目;验证时用着正常的动作、核对一致的识别,日期改成验证那天。验证报告里写明点过「未点」的按钮的,修复线在正本更新这一步补录:把画面文档「交互效果」一栏改成实测结果,goto_list 用写档工具补上,写进本线的落地申报。线收口以后,状态里还写着这条线名字的缺口,是这条线没修的:去掉线名,照 §5.3 第 2 步立线或并线。
- 不达标 → 回 §2.4 处置循环。
- 没遇到 → 在线表这条线的备注栏记一局。连续 3 局没遇到 → 做三样:
  1. 登记待裁,线表等待条件记「等待裁定」;
  2. 把它对应的缺口条目登记进待跟进事项文件,状态标签「等用户裁定」;
  3. 追踪文件里这几条的状态写「已登记待跟进事项(编号 N)」,N 是第 2 步那个条目的编号。

  用户裁定以后:要修的,这几条改回「等修复线」,删掉待跟进事项文件里对应的条目;不修的,两处都不动。

  怎么数「连续 3 局」:局终报告算一局,中途停下的报告不算;中间出过一次不达标的,重新从 0 数。

### 6.7 接上动作 op 以后改操作章和追踪文件

这两处改动排在重启 MCP server 以后、派下一个 agent 以前,由编排者照实现报告的回信增补第 4 样改。这是照报告抄,不算编排者自己写文档。操作章不进修复线的申报面(实现 agent 不改它)。

- **操作章**(玩家 skill 对应画面文档的「操作」章):
  - 画面文档已经有「操作」章的:只改这一步「用什么」那一格,别的章不动。操作表里没有这一步的,加一行。
  - 画面文档还没有「操作」章的(新画面:前两章是实机探索 agent 写的,后两章没人写):照报告给的全文新建这一章,只写接上动作 op 的这一步。「玩法指引」章仍然不写。
- **追踪文件里这个画面的动作一栏**(记法见 screen-tracking.md):这一步的括号里改成新 op 的名字,日期写「还没用过」;动作一栏里没有这一步的,加一行。
- 改完,操作章这一处按项目提交规范单独提交:逐文件点名;这个文件里混着别人没提交的改动的,不提交,文件名记进线表备注栏。
- 不用重启的线(这一步已经有现成的动作 op 能用、只差操作表没写,修复线的探索看代码发现的):不用改代码,过了 review 就做这两处改动,线照常走验证。

### 6.8 判了一步不用做动作 op 以后改追踪文件

三个问题判不准的步骤,修复线的探索看过代码,一条龙不点这一步的,判它不用做动作 op。这一行由编排者照探索报告写:

- 在追踪文件这个画面的动作一栏里给这一步加一行(原来有这一行的,改括号),括号写「不用做动作 op」,冒号后面写判的日期和理由;
- 对应的缺口删掉。

线怎么记:线里只有这一件事的,不往下走,移入线表的「已结束线」,注明「探索判不用做动作 op」。这不是收口,没有立项,也没有迭代目录。

新画面没有代码可对,修复线认为不该做的,不自己判:登记待裁(§5.2 路 A 第 3 步)。

用户裁定哪一步不用做的,编排者照裁定写这一行。裁定过的现在有一条:模式选择画面的「切换模式页签」,2026-11-24 裁定。追踪文件里模式选择那一章没有这一行的,补一行;括号不是「不用做动作 op」的,改过来;对应「没有动作 op」的缺口里写到它的,去掉。

## 7. 叫停与恢复

### 7.1 用户叫停

实机探索线什么时候停,由用户决定:用户叫停;用户说进入下一个场景;或者用户给的目标按 §1.2 算达到了。除此之外,编排者不自己判断「再打下去没收获」而收线。

用户叫停时,按顺序做,之后接着做公共 skill 停止清单的其余步骤:

1. 把用户的原话转给此刻持有游戏窗口的 agent(实机探索 agent、实机验证 agent 或诊断 agent),让它停止操作、交报告。实机探索 agent 交的是单局报告,附现场四项和这次写的文件清单;先提交这次派发写的文件,再发报告。
   - 转话以后 10 分钟没有交报告 → 用中断手段中断它。
   - 中断导致文件没提交,分两种:
     - 报告里有「这次写的文件清单」的:编排者只按清单逐文件点名提交,提交说明写线名和「叫停时未完成」。同样先核对该文件的改动全是这次派发写的,混有别人改动的不提交。
     - 没有清单的:编排者不替它提交。把工作区里还没提交的路径(`git status` 的输出)全部记进线表备注栏,标「未经核对」。下次开启重派时,让新的实机探索 agent 核对:改动全是那次派发写的才提交。
2. 收到报告以后,最后一份单局报告照 §5.3 第 2 到 4 步登记:追踪文件、待裁知识队列、待跟进事项文件、顺路验证的结果。叫停时只登记、不派活:不派诊断、不立修复线、不派知识文档线。这几样留到下次开启再做(§3.4 第 6 步)。
3. 最后一份单局报告里有未闭环问题的:登记进待跟进事项文件,状态标签「等现场再现」。追踪文件里这几条「等诊断」的缺口,状态改成「已登记待跟进事项(编号 N)」。下次开启时它们跟着任务书的附加信息节走(§4.3);实机探索 agent 再遇到就停下来,现场留给诊断。
4. 对局停在半路 → 对局留在原地,不放弃。占用表的持有行保留,交接记录写明现场四项(取自最后一个动过窗口的 agent 的报告)和「用户叫停」。那个 agent 被中断、没交报告的,交接记录写「现场未知」。线表「在飞 agent」一格记「停止时中断」。
5. 追踪文件里的缺口条目,分三种:状态是「已登记待跟进事项」「等用户裁定」的不动(叫停以前就卡住了,待跟进事项文件里已经有条目)。有修复线在跟的不动。其余的,登记进待跟进事项文件,状态标签「等随机遇到」;追踪文件里这几条的状态写「已登记待跟进事项(编号 N),卡在用户叫停」。
6. 汇总给用户时,待裁登记和待裁知识队列两份都汇总;玩法指引的不足文件里现在有几条,报个数和文件路径。
7. 自验:没有在飞的 agent;线表、占用表、待裁登记、追踪文件是最终值;最后一份报告里的发现都登记了;待裁已汇总。有缺回那步重做。

线表里实机探索线怎么记结束:

- 用户叫停 → 线不结束,「在飞 agent」一格记「停止时中断」,下次开启接着推。
- 用户明说这条线不要了(砍单)→ 移入「已结束线」,注明砍单。
- 用户给的目标达到、按 §1.2 进入下一个场景,或者用户自己说场景一做完了 → 注明收口。

### 7.2 对局丢了或者连接断了以后怎么恢复

由编排者按固定步骤做,不派诊断。

按上一份报告的停下原因,在重派任务书的附加信息节写明是哪一种,做法见 exploration.md §5.2 对应的一段(连不上、掉线、闪退、叫停,各有一段)。

1. MCP server 连不上 → 重启(§2.3)。
2. `check_game_window` 显示窗口无效 → `open_game`。它只负责把游戏打开、登到大世界,到不了货币战争大厅。
3. 重派实机探索 agent,任务书按 §4.4 更新。之后按原因分三种:
   - MCP server 连不上:它核对现场,对得上就接着打。
   - 游戏掉线:它先识别画面,有重新连接的提示就点它;连不上,停下回报。编排者再重派一次;还连不上 → 登记待裁。
   - 游戏闪退:它按玩家 skill 进货币战争,走到模式选择画面。有存档 → 点「继续进度」,续上原来那一局;没有存档 → 回报编排者「对局已丢」。
4. 收到「对局已丢」→ 这一局记「中止」,走路 C(§5.5)。
5. 某一步做不成 → 登记待裁。

恢复期间,占用表的持有行保留在实机探索线名下,备注「恢复中」。

## 8. 场景二到四

### 8.1 场景二:流程框架适配期(app 自动流程跑局)

> 本节只立了骨架:关注什么、验证载具、缺口的去处。进入本场景时立哪些线、由谁发起第一局,本节没有写——编排者在待裁登记写一条「已进入场景二,怎么开工等用户说明」,不自行立线。

**关注什么与优先事项**:

- 关注什么:把场景一的识别成果与动作 op 接入 app 自动流程——对局由流程框架自主推进,不再靠 agent 逐帧代理操作。
- 优先事项:app 自动流程跑局循环——「跑一局→暴露缺口→修→再跑」。
- 策略无关性:本场景策略质量不设标准(可以坏、可以随机乱选)。流程框架的验证看「对局推进与缺口收敛」,不看胜负与成绩;对局成绩与策略调优是场景四的事(§8.3)。

**验证载具与工作节奏**:

- 验证载具 = app 自动流程跑局:经项目 MCP 工具发起 run_standalone_app(货币战争);一次 run 一局,run 结束即停——与场景一「一局一停」同型,载具不同。逐局发起,不获多局连续授权。
- 跑局暴露存量识别、建档、流程的缺口是常态,暴露即覆盖工作在生效,逐条登记后继续。连续两局零登记 → 登记待裁(已知的缺口可能都补完了,下一步等用户说明)。本节没有「重新找缺口」的做法,编排者不自己找。
- run 卡死、中途停止 → 按停止操作汇报纪律处置(exploration.md §4.1),走 §2.4 问题处置循环。run 跑完但暴露读数、行为缺口 → 不停线,按下面「缺口分诊与修复路由」登记缺口后继续下一局。

**缺口分诊与修复路由**:

- 按缺口类型路由:
  - 识别缺口(建档过期、OCR 能力不足、模板缺失)→ 画面建档与识别修复走 od-dev-screen-onboarding;
  - 流程缺陷(重试语义、分发接线、循环结构)→ 小修复批(线内单点修复攒批实现与验证,每条带「改哪 + 判据」);
  - 机制缺失(动作 op 缺失、机制建模缺)→ 立线走 od-dev-run-iteration(迭代形态按挂账条目的改哪与判据是否逐字可指,口径见 §8.3)。
- 缺口记账:画面识别、动作 op 的缺口,记进追踪文件里该画面的「缺口」小节(screen-tracking.md);其余缺口逐条登记待跟进事项文件(§2.5),条目写明「改哪 + 判据」。修复批从两份文件的开放条目取活逐个清偿,完成即删。
- 根因不明的缺口先走 §2.4 处置循环(诊断 agent 定位)再归入上述路由。修复改运行时代码的,重启窗纪律按 §9.4。

### 8.2 场景三:投资策略/环境 sim 适配期

> 本节先立骨架:进入本场景时按当期需求就地细化本节(本文不整体重写,各场景节就地维护)。

- 关注什么:投资策略与环境效果在 sim 里的建模。sim 局与实机局跑同一套循环、op、策略,只换环境(SKILL.md §1.3 铁律);环境面失真会直接污染场景四的策略结论,所以先对拍再开工策略迭代线。
- 优先事项:sim 与实机对拍。
- 方法单一源 = [sim-testing.md](../sim-testing.md)(sim 能信什么、找问题三步、种子段分配纪律、单局复盘素材采集)。本节不复制其内容。进入本场景时,以它「先知道边界」一节为对拍口径基线。
- 对拍差异的处置:走 §2.4 处置循环分诊,缺口按 §8.1「缺口分诊与修复路由」的口径登记(画面识别、动作 op 的进追踪文件,其余进待跟进事项文件)。

### 8.3 场景四:策略实现适配期(策略迭代线)

**关注什么与优先事项**:

- 关注什么:真实策略代码迭代。场景一到三的产物(画面档、动作 op、自动流程、sim 建模)是既有地基,本场景在其上做策略实现与调优。策略工作的方法主线与验证阶梯 = [strategy-work.md](../strategy-work.md)(分诊表「改策略 / 迭代算法」行),本节不复制。
- 优先事项:策略迭代线。

**三种线**:

- **策略迭代线**:完整生命周期(设计→循环对抗→实施→实机验证→正本更新→收口)。探索段跳段判据 = 设计开工前确认本线目标面已被既有探索产出覆盖,逐条指认出处才跳(追踪文件里对应画面那一章的缺口小节写着「无」、知识文档结论、画面档;追踪文件的格式见 screen-tracking.md)。指认不了,按完整生命周期走探索。场景一的探索产出通常已满足。
- **挂账修复线**(修复线的一种,§1.5;任何场景都可立,不只本场景):多为小迭代(单点修复、判据机械、不触核心面)。挂账条目的改哪与判据逐字可指 = 可走最小形态(§6.3)。
- **知识文档线**(跨场景常驻的线型,§1.4):纯文档迭代,无实机段(§5.6)。

**推进模式与设计批规范路径**:

- 推进模式:缺省串行(§9.1)。
- 设计批规范路径:策略迭代线按 od-dev-run-iteration 走双层文档流。迭代目录 = `.temp/changes/active/<立项日期-主题>/`,正本区 = `docs/develop/sr_od/application/currency_war/`。

## 9. 领域叠加件

通用层机制自含完整默认形态,本节只写货币战争的映射与增量。分层边界:领域操作归领域 skill,通用层只管调度。

### 9.1 推进模式

- 货币战争自主推进的各场景缺省串行(并行度取 1)。游戏窗口与 MCP server 一次只给一个 run 用,独占资源的互斥由占用表把关,不随线数放宽。
- 用户当次明示并行时,按公共 skill 的取值顺序生效。公共 skill 没有给出什么时候该开并行的判据,本领域也不定义:要开并行,由用户当次明示。
- 并行度大于 1 时,多出来的位子走不占游戏窗口的步骤;要重启 MCP server、要占游戏窗口的验证,放在两局之间。场景一的先后见 §3.3。

### 9.2 核心面清单

landing 影响面申报与对抗、review 对照用。货币战争的核心面(策略面)= `strategies/`(策略行为、量化判据与状态函数)+「决策控制分层」铁律面(流程侧出现决策闸门 = 分层错误,判据见 SKILL.md §1.3 铁律)。

判定口径:

- 画面、流程任务的改动不得触碰策略行为模块(评分、权重、搜索、选择);
- 局内状态对象(GameState)的字段定义不算策略面。

### 9.3 共享资产枚举

影响面申报第二层 = 共享资产面。货币战争的共享资产:

- `kernel/cw_vocab.py` 词表;
- `data/` 全部注册表;
- `knowledge/` 事实常量;
- screen_info 的 `currency_war_*.yml`、`cw_*.yml` 画面档与 `_od_merged.yml` 合并缓存;
- 模板资产 `assets/template/` 根级 cw_ 前缀模板目录(currency_war 类目已退役上移;装备库 equip_legacy、equip_plaza 暂留该类目);
- 立绘库、首领头像库(cw_character_avatar、cw_boss_avatar)。

线动到其中任一项,申报面按共享资产层申报。

### 9.4 MCP 重启窗

- 改 `src/sr_od/` 运行时代码的线,申报第三层(= 共享资源面)必带重启标记。
- 重启执行权归编排者(§2.3)。前置确认四步与局间时机 = runtime-ops.md「启动与重启」节。
- 模板文件的改动不带这个标记(标记只管运行时代码)。场景一的修复线动了模板要不要重启,见 §6.4。

### 9.5 影响面申报落位

全线迭代设计的申报节落 landing.md 首节。模板单一源 = od-dev-run-iteration 的 references/iteration-docs.md §3(landing 五节,首节即影响面申报)。

### 9.6 交接对不上的去向

公共 skill 写的是登记待裁(其 §4.2)。货币战争改为报编排者派诊断。交接协议见 exploration.md §5.1。
