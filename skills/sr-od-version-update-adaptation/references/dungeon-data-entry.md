# 副本数据更新(星际和平指南注册表)

版本新增/调整副本——拟造花萼(金/赤)、凝滞虚影、历战余响、侵蚀隧洞、饰品提取等生存索引玩法入口变化时,把副本数据更新进指南注册表 `assets/game_data/interastral_peace_guide_data.yml`。目标:新副本能进 GUI 体力计划下拉、能被指南导航 OCR 匹配选中、材料→副本反查能定位到实例。

**顺序约束:本适配项先于「新角色数据录入」执行**——角色数据管道生成「材料→刷取副本」映射时,以本注册表的分类/关卡/区域字段做 join 与锚点校验;注册表落后 = join 报警或新角色材料查不到刷取点。

**没做完下面 5 步不算完成。**

## 数据来源

三类源合并;冲突时仲裁序:**仓库权威表 > 实机画面 > 官方 wiki 词条 > srmap 点位**(wiki 词条有错字与滞后,srmap 点位为编辑者手标覆盖不全——两者都只作线索,存在性以实机为最终裁决)。

1. **官方 wiki 材料频道**——接口打法见 sr-od-dev-official-api。逐条养成材料详情的「获取途径」原文,产出「副本类型【区域】」「boss名•历战余响【区域】」两类来源串:拟造花萼(赤)、凝滞虚影、历战余响的实例清单来源。判据:来源串带【区域】才有实例信息,裸分类名(如只写「拟造花萼（金）」)只证明分类可刷、不产实例;新实装材料的 wiki 词条常滞后,缺源材料走实机核对。
2. **遗器权威表 obtain 字段**(`src/sr_od/mys/sr_relic_sets.py`,遗器数据管道维护的单一源):「X·侵蚀隧洞」→ 隧洞副本名;「X·差分宇宙」→ 饰品提取副本名。同 obtain 值下的套装组 = 该副本 display 用的套装名。判据:每个隧洞副本对应两个隧洞套装、每个饰品提取副本对应两个位面套装,成对不齐 = 清单有漏。
3. **srmap 大地图点位**(交叉验证)——接口见 sr-od-dev-official-api 的 references/map.md。副本点位 label 即「关卡名·副本类型」,楼层沿地图树回溯得区域归属。判据:只用于补区域线索与查漏,不作为存在性权威。

## 注册表口径

- 三级结构 tab → category → mission。`category_name` 是跨模块 join 键(生成器副本产出表、配置层、材料反查都按它路由),**禁改名**;tab 清单与实机对齐,实机已移除的 tab 不留。
- mission 字段:`mission_name` = 指南列表 OCR 匹配的关卡名;`display_name` = GUI 展示文案;`region_name` = 区域(进 unique_id,用户配置存了引用,定了不改);`power` = 单次开拓力;`show_in_power_plan` = 是否进体力计划下拉。
- display 口径与既有条目一致:凝滞虚影「属性-名」;侵蚀隧洞 / 饰品提取「套装A/套装B」;历战余响 mission_name 带「·历战余响」后缀、display 用裸 boss 名。
- 新条目插入位置与实机指南列表顺序一致(新版本条目在分类内靠前 / 对应属性组内);旧条目仅在实机确认消失时删,不凭单一来源缺失删。
- 存量文本修正在同一轮做完(老格式 display、错别字),不另开批次。

## 验证

1. 注册表加载:`SrGuideData` 构造后 tab / 分类 / 关卡计数与本轮意图一致,无解析告警。
2. 体力计划下拉:`get_category_list_in_power_plan` / `get_mission_list_in_power_plan` 能列出新副本。
3. 导航匹配:对每个新 mission_name,`best_match_mission_by_name` 在对应分类下命中唯一条目。
4. 材料反查不回归:实例级映射(生成产物 `dungeon_drop_const.py` 的 MATERIAL_MISSIONS)逐条经 `get_mission_by_guide_info` 命中——本轮没重跑生成器时,至少验既有映射不因本轮改动断链。
5. 实机冒烟(本机可登录时):指南里选中新副本分类与条目、传送成功。
