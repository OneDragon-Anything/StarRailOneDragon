# sr-od-game-coach 设计总览

## 定位

配队知识库 skill：给「玩游戏的 agent」做配队决策用的公共知识单一源 + 决策工作流。与玩法操作 skill（进本/画面操作/自动化流程）分离，与米游社 MCP（账号数据源）互补——skill 是脑，MCP 是手和数据。

目标使用形态：普通使用者接入本 skill + 项目 MCP，agent 即可完成「读环境弱点 → 选体系 → 选人 → 查练度门槛 → 输出编队」的全流程，不需要读项目源码。

## 边界

- 只含公共游戏知识：任何档案不得出现特定账号的信息（BOX 构成、练度数值、持有星魂等）。账号数据一律运行时拉取。
- 不含玩法操作流程（忘却之庭怎么进、编队画面怎么点）——那是玩法 skill 的职责；本 skill 被玩法 skill 引用。
- 不含自动化开发知识（写 op/app）——那是 od-dev-* 开发 skill 的职责。

## 构成

```
SKILL.md                      # 触发 + 配队决策工作流 + 路由表（唯一顶层索引，路由直达文档或子目录索引）
references/                   # 知识语料（agent 按需查阅的数据，不是指令）；多文件子目录各带 INDEX.md 二级索引
  mechanics/INDEX.md          # 机制层索引：跨角色规则 + 养成操作路由档（装备/升级/叠影/遗器）说明
  teams/INDEX.md              # 体系层索引（为什么这么组）
  lineups/INDEX.md            # 阵容层索引（这四个人怎么打）
  characters/INDEX.md         # 角色层索引：按命途分组 + 覆盖追踪表（新增角色加行/转正的唯一入口）
  mechanics/                  # 机制层：跨角色共享的规则（战斗基础/伤害模型与词条/大招资源/欢愉命途/记忆命途/遗器套装速查）
  teams/                      # 体系层：一类配队一档——管「为什么这么组」（引擎机制/绑定规则/成员池/替补矩阵）
  lineups/                    # 阵容层：一队一档——管「这四个人怎么打」（成员/绑定逻辑/攻略参考轴：开局秘技序/回合轴/配速参考/SP预算——参考向非强制）
  characters/                 # 角色层：一人一档，三段式（命途属性与技能说明 / 推荐遗器与原因 / 推荐配队与原因）
maintenance/                  # 维护者文档（不进 agent 执行上下文）
  doc-writing-guide.md        # 知识档模板与填写方法论（持续总结更新）
design/                       # 本目录：设计记录
```

知识分层的依据是机制本身的归属与消费路径，不是拍脑袋：

- **机制层** = 对任意持该命途/机制的角色都成立的规则（欢愉伤害乘区规则、忆灵系统、大招资源体系）。
- **角色层** = 单个角色的机制（黄泉的残梦是她的个人机制，别的负面角色不共享）。
- **体系层** = 配队原型（骨架槽位 + 绑定规则 + 替补矩阵）；管「为什么这么组」。
- **阵容层** = 具体四人组的打法（配速/回合轴/SP 预算）；管「这四个人怎么打」——体系与阵容两层分离（用户裁定的方案二）是因为消费路径不同：配队决策走体系档，实战操作走阵容档；阵容档随版本增删独立演进。阵容档的配速/回合轴一律标【攻】并声明参考向非强制（用户裁定）。
- **玩法层**（modes/，三期新增，用户裁定）= 一玩法一档（规则/轮换/环境增益/适配体系），头部标注受众定位（主流/较新/小众/一次性）——小众玩法明确标注（货币战争·活动期、锄大地、回忆持久层），提示不必为其优化配队。
- **多轮调研制**（三期，用户裁定）：每档显式标注调研轮次——R1=官方文本+首轮社区调研；R2=米游社+B站（源限定：miyoushe/bbs.mihoyo.com/sr.mihoyo.com + bilibili.com 及 B站系 BWIKI）；前瞻角色情报记在对应体系档 R2 节，实装后转正。
- **结构治本（v12，用户裁定「全面思考逐类型优化」）**：①角色档标准节序（标题导语→一技能[表/资源循环/满级数值]→二装备[光锥/套装条件式/主副词条/转化]→三配队[表/官方阵容/硬否决/通用性]→星魂→调研轮次→信息缺口）全库统一；②maintenance 三分（templates/methodology/research-status）；③体系档去重（操作轴归阵容档、成员池只记定位）；④官方数据快照入库 `references/data（skill 自包含）/`（换机不丢/版本 diff/管道可重跑）；⑤SKILL.md 路由按五问题域+维护域组织，数据源优先级=百科官方表>视频实证>推导。

## 关键设计决策（动机）

1. **知识放在 skill 而非 docs/game**：分发形态决定的——使用者只挂 skill + MCP，不克隆仓库；docs/game 是项目内部知识树（开发者向），skill 是自包含分发资产。两者在玩法规则层面会有少量重叠，各自服务各自读者；skill 的版本维护挂在版本适配流程（新角色/平衡改动 → 补/改角色档）。
2. **「写方法论不写具体事实」规范对本 skill 的适用边界**：该规范约束的是指令文本（SKILL.md 与指导行为的辅助文件）；本 skill 的 `references/` 是被查阅的知识数据语料，不是指令——知识密度正是其价值，规范 4 不适用于语料内容。SKILL.md 本身仍只写方法论与工作流，不塞角色事实。
3. **两个 skill 的拆分（用户裁定）**：知识 skill（本 skill，机制+角色+体系三层）与玩法 skill（忘却之庭等：进本流程/画面操作/湍流判读，引用本 skill 做配队）。基础玩法说明不单独成 skill——基础机制的消费者与配队知识的消费者相同，作为本 skill 的机制层存在。
4. **角色档暂不加机器可读摘要头（用户裁定）**：YAML frontmatter 摘要便于程序化扫描，但引入「正文与摘要双源同步」成本；待真实消费场景（bot 化）出现再议。
5. **档案语言与命名**：全中文（目标用户中文环境）；角色档以游戏内官方中文名为文件名，体系档以「机制 + 锚点角色」命名（例：黄泉负面队）。

## 证据层级与知识纪律

- 知识档统一标注证据层级：【官】官方文本（技能/星魂/行迹/光锥描述）＞【攻】攻略交叉验证（标时效）＞未标注 = 两层一致。
- 机制结论尽量给官方文本锚点（行迹名/技能名），攻略数值（公式系数、面板目标）必须标【攻】。
- 档内「信息缺口」节是诚实清单：官方文本无法取证、攻略分歧的点如实记录，禁止脑补。

- **skill 家族架构（v13，用户裁定）**：本 skill=基础玩法知识（任何场景成立）；特殊玩法专项 skill 分立（逐光捡金 sr-od-treasures-lightward / 货币战争 sr-od-currency-war-guide，待建）——modes/ 只留框架+按 skill 名称指针；skill 间引用一律用 skill 名称不用路径；官方数据不留原文快照（v14，2026-11-12 用户裁定同 CW 底稿先例：结论进知识档、原文按需重拉,拉取缓存落 `.debug/game_data/`）。
- **索引架构（v15，用户裁定）**：顶层索引唯一在 SKILL.md 路由表，不设独立总路由文件——agent 触发加载的只有 SKILL.md，索引放在它读不到的位置（原 `references/INDEX.md`）等于第一跳路由断链（实际案例：装备操作路由存在于 mechanics/light-cone-enhancement.md §2，但 SKILL.md 装备行只指决策侧、总路由文件没人翻到，操作问题找不到落点）；多文件子目录（characters/teams/lineups/mechanics）的枚举索引放各自子目录 `INDEX.md` 二级索引，SKILL.md 路由直达子目录索引。同次补齐：路由表新增「装备与养成操作」问题域行（怎么装/换/查占用/升级 op 消耗门）。
- **description 触发口径可机械判断化（v16，2026-11-14 实测驱动）**：v15 在路由表加「装备与养成操作」域时未同步 frontmatter description，导致实机案例漏触发——用户让 agent「用 op 领取角色升级后的奖励并测试该 op」，agent 把任务判为「开发执行」未加载本 skill，靠画面红点自行脑补了「晋阶奖励」概念（结论碰巧正确，但概念对齐靠猜）。两条修法：①触发口径从「凡涉及崩铁玩法理解与决策」（不可机械判断，agent 会把「理解」窄化成决策类问题）改为「凡任务中出现崩铁游戏内容概念词——哪怕只作宾语、哪怕任务本体是执行或开发测试操作」；②补齐 description 与正文的路由同步缺口（养成操作/基础信息查询两域此前无触发词）与全部易混兄弟指路（consume/lightward/cw-dev/version-update/write-operation，写全名）。兄弟指路的分工语义：op/app 开发测试场景为双触发——开发方法归 od-dev-write-operation，其中的游戏概念对齐仍归本 skill，二者互补不互斥。
- **攻略知识常态化巡检（v17，用户裁定）**：攻略知识的时效性跟社区共识演进走而非版本更新日——新内容对旧角色环境的影响渐进显现，版本初期/中期/末期的社区理解深度不同（首周口径→实测修正→盖棺口径），所以「版本更新日做一次攻略更新」覆盖不了这条演进曲线。分工：版本更新适配日只做时点确定的硬事件（数据录入/首周建档/平衡性改动/往待复核清单登记复核条目），持续演进（到期复核/环境波及探测/共识漂移）归 `references/maintenance/patrol.md` 定义的常态化巡检——任务书自包含（可交定时任务拉起的干净 agent 执行），建议每周一轮、实际节奏由执行方环境决定；巡检是清单驱动+定向深调研，禁全量重调研。**落盘分界（2026-11-14 用户裁定「给使用者总结好的东西，不是我们的进度记录」）**：skill 仓库只放给使用者的最终知识（知识档本体）；一切维护进度与状态——research-status（待复核清单/调研轮次记录）与每轮巡检过程记录——落巡检工作区 `.debug/temp/game-coach-patrol/` 不进 git（原 `references/maintenance/research-status.md` 已按此裁定移出，工作区丢失时从知识档的调研轮次与信息缺口节重建待复核清单）。刻意不采纳的备选：把巡检做成版本更新 skill 的又一个路由项——那是事件驱动、一版一次，与「持续演进」的诉求错位。
