# 实机探索 agent 作业手册(打一局货币战争)

> 读者 = 实机探索 agent:自己动手打一局货币战争的子 agent。每次派发,开工前通读本文件。
>
> 本文件只写打这一局的工作方法:开工前读什么、每个画面做哪三件事、遇到情况怎么处理、能写哪些文件、单局报告怎么写。打法、画面上的操作、对局决策归玩家 skill `sr-od-currency-war`。
>
> 适用前提 = 实机探索 agent 自己动手打货币战争的实机探索局。
>
> 第 4.1 节(停止操作汇报纪律)和第 5.1 节(交接协议),任何操作游戏窗口的 agent 都照做,不只实机探索 agent:诊断 agent、实机验证 agent 也一样。
>
> 派活、登记、修复线、叫停和恢复的编排归 [orchestrator.md](orchestrator.md),实机探索 agent 不用读。画面识别与动作 op 的追踪文件的格式见 [screen-tracking.md](../screen-tracking.md),待跟进事项文件的写法见编排者手册 §2.5。
>
> 名词:
>
> - 玩家 skill = `sr-od-currency-war`。
> - 操作章 = 玩家 skill 对应画面文档的「操作」章。多数画面是一张表,叫操作表,写每一步用什么做。
> - 追踪文件 = 画面识别与动作 op 的追踪文件,按画面分章。路径在任务书的附加信息节里。
> - 单局报告 = 实机探索 agent 每次停下时交的报告(第 7 节)。局账 = 单局报告里记这一局各项结果的那一节。
> - 现场四项 = 当前画面 / 对局进度 / 血量与金币 / 未了事项。
> - 知识文档 = 玩家 skill 的玩法文档(各画面的文档和各篇总览)和 `docs/game/currency_war/research/` 各篇。
- 转登 = 编排者照子 agent 报告的原文,抄进别的记录文件,不加工。

## 1. 开工前

### 1.1 读什么

- 本文件。会话记忆被压缩过、记不清早先读过的内容时,重读本文件和任务书。
- 玩家 skill:读什么、什么时候读,照它入口文件的规定。
- 玩法指引的不足文件(路径在任务书的附加信息节里)。以前登记过的不足,这一局再遇到,在原来那条后面补,不另起一条(§6.4)。
- 进游戏的授权已含在自主推进授权内,不用再问用户。用户不在场:问题原样记进报告,不等回复。

### 1.2 任务书里这一局的内容

任务书的「需求」节写着这一局的五样:局内目标、阵容线、顺带取证清单、顺路验证清单、难度。它还写明这一局是开新局,还是接着打。

每次派发最多一局。打完这一局,或者按 §4 中途停下,就停止操作、交单局报告,然后等待。不获得连续打多局的授权。

### 1.3 关注清单

关注清单 = 这一次要关注的内容。每次派发各有一份,由实机探索 agent 开工时自己起草,写进单局报告。

- 起草的输入四样:
  - 用户开启自主推进时说明的目标(任务书「需求」节);
  - 附加信息节里上一份单局报告「没看到」的条目和待裁知识队列;
  - 待跟进事项文件的未竟项(路径在附加信息节里);
  - 玩家 skill 玩法文档里当期值得核对的面。
- 每条注来源,零来源的条目不进清单。
- 每条写清「关注什么、观察到什么算值得关注、怎么记录」,以及对应哪个画面(按玩家 skill 的画面名写;哪个画面都不是的写「跨画面」)。
- 关注清单只管这一局。这一局没看到的条目,编排者照原文抄进下一局任务书的附加信息节,下一局起草时从那里取。
- 待裁知识队列里已有的发现,这一局再遇到,不算新发现:在单局报告的「知识发现」里写「同队列 K-N,本局再次出现」,附证据指针。

### 1.4 难度

- 用当前可解锁的最高难度。
- 最高难度不可达(未解锁、条件不足)时,用可达的最高难度,并在单局报告里写明可达的难度和解锁路径。

## 2. 打这一局

### 2.1 打法

- 照玩家 skill 的指引打,加上自己的判断。指引不会讲到每一种情况,没讲到的自己判断。
- 任务书指定了阵容线的:这一局照那篇阵容攻略打,不改打别的阵容线。每个阶段照攻略上的阵容去凑。照不了、效果不好,记一条「玩法指引的不足」(§6.4),按自己的判断继续往下打。
- 没指定的:按指引自己定阵容线。
- 修复线派来的实机验证 agent,验证时要打一段对局的,也照本节办。

### 2.2 对局之外的东西不碰

晶球、门票、充值、放弃对局都不碰。对局里正常的买牌、刷新、出战是打一局的一部分,可以做。

### 2.3 步骤

1. **开工先识别当前画面**(只读),分四种情况:
   - 在货币战争大厅 → 开新局。
   - 在一局中间的画面(接管已有对局)→ 先按 §5.1 交接协议核对现场,对得上就从停下的画面继续。
   - 已经在货币战争的开局流程里(模式选择、难度确认这些画面;上一局对局丢了以后会停在这里)→ 按任务书的目标走。
   - 在大世界或别的玩法 → 按玩家 skill 的导航办法进货币战争,走到模式选择画面。
2. **走到模式选择画面时**,上面几种情况都一样:
   - 任务书写明开新局:没有存档 → 开新局。是「进行中」形态(有存档)→ 不点任何东西,停下回报编排者(开新局要先放弃旧局,放弃对局要用户点头)。
   - 任务书写明接着打:是「进行中」形态(有存档)→ 点「继续进度」,续的是上一局,算同一局。没有存档 → 回报编排者「对局已丢」。
3. **每到一个画面,做三件事**:
   - 动手以前,先看操作章里有没有这一局在这里要做的动作。操作章里没有的,按 §4.2 的表处理,先别点。
   - 读追踪文件里这个画面的那一章(路径在附加信息节里;没有这一章就跳过)。章里有缺口的,顺手核对:
     - 按这条缺口说的缺什么来核。画面建档那一层的:缺的是整张画面,看认不认得出;缺的是画面上的某个元素,看那个元素建档了没有。画面识别那一层的,看识别结果和自己读图还对不对得上。动作 op 那一层的,按 §3 判断。
     - 核对的结果写三种:还在的,记进「缺口」;不在了的,在「画面核对」这个画面那一条后面写一句;这一局核不了的(要特定局面才出现、要看代码才知道的),在「画面核对」里写「核不了」和原因。
     - 画面建档那一层的缺口,说的元素此刻就在画面上、自己补得上的(比如给一个没建档的按钮建 area):当场补建,做法同新画面建档,在「画面核对」里写「已补建」。
     - 卡在特定局面上、核不了的,在「缺口」里报一条,建议处置写「现在探不了」,写明等的是什么局面。
   - 把画面识别的结果和自己读图对一遍;每做一个动作,记下用的是哪个 op 还是鼠标点击、有没有生效。用鼠标做的,按 §3 判该不该有动作 op:该有、还没有的,写进「缺口」。这些写进单局报告的「画面核对」。
4. **打完这一局,或者按 §4 中途停下** → 停止操作,提交(§7.4),发单局报告,然后等待。

局终以后把画面收回大厅;中途停下时画面留在原地不动。接着打同一局不算新的一局。

### 2.4 结算画面留证

每场战斗的结算画面截图存档。截图放当前线的子目录,文件名列进单局报告的证据文件清单。

## 3. 动作 op:哪些该有、怎么判有没有

### 3.1 动作 op 指什么

本文说的动作 op,指实机探索 agent 能用 run_operation 单独调用的一次动作。开发 skill 入口文件 §1.2 按代码目录把动作分成「动作 op」「动作原语」,那是讲代码怎么分层,和这里不是一种分法。新做一个动作 op 该放哪一层,按 od-dev-write-operation。

### 3.2 哪些动作该有动作 op

自动打一局用得上的动作,才做动作 op。对画面上每一个能做的动作(点按钮、拖拽、点某个物品都算)问三个问题,按顺序问:

1. 自动打一局会走到这个画面吗?
   - 自己弹出来的画面,和玩家 skill 入口文件「各阶段与画面的处理方案」列表里不在「流程外画面」一组的画面,答「会」。
   - 「流程外画面」一组里要点按钮才进得去的(攻略、图鉴、优势布局这些),答「不会」:这个画面上的动作都不该有,不用再问下面两问。进这些画面的按钮(大厅里攻略、图鉴、优势布局的入口)长在流程内的画面上,也算「不会」。
2. 不点它,这一局走不下去吗?走不下去的该有。比如开新局、确认难度、简报的下一步、关掉挡路的弹窗。不点它,后面该做的动作就做不了,也算走不下去,比如商店开着时不先收店就出不了战。
3. 点了它,后面的对局会不会不一样?会不一样的该有。比如买、卖、刷新、选卡、穿装备,勾了「本局不再提示」以后不再弹这个窗。只是换一页给自己看的算「不会」,比如切换页签、展开详情。

第 1 问「会」,并且第 2、3 问里有一个「会」= 该有动作 op。第 1 问「会」、第 2、3 问都是「不会」= 只是看,不用做动作 op,照操作表用鼠标。

- 例外:只是看的信息,程序做决定时要用到(比如位面详情里的节点情报)。到要用的时候再做。
- 实机探索 agent 不看代码,每个画面都按三个问题判。代码归修复线看(orchestrator.md §6.1):一条龙自动打局已经会做的动作,就是该有的;一条龙不做的动作,修复线可以判它不用做。
- 三个问题答不准的,照该有的处理;报上来时写明理由和拿不准的地方,留给修复线判。
- 用户裁定过不用做的,以裁定为准。现在有一条:模式选择画面的「切换模式页签」不用做动作 op。追踪文件里它记成「不用做动作 op」,读到就照操作表用鼠标,不报。

### 3.3 有没有动作 op,按顺序看

1. 追踪文件里这个画面有章、动作一栏里有这一步(路径在附加信息节里),看括号里写的是什么。
   - op 的名字 = 有动作 op。
   - 「鼠标点击」= 该有、还没有(缺口小节里记着它)。
   - 「不用做动作 op」= 这一步判过不用做,照操作表用鼠标,不算缺口。
   - 「鼠标点击,未判」= 这一步还没判过该不该有:按第 2 条看操作表起判;操作表这一步是 op 名的,写进「遗留」。
   - 括号里是「鼠标点击」、操作表里这一步却已经是 op 名的,以操作表为准,写进「遗留」报上去,编排者把括号改过来。
2. 别的情况(动作一栏里没有这一步,这个画面还没有章,括号是「鼠标点击,未判」)→ 看玩家 skill 对应画面文档的「操作」章(多数画面是一张表,就是操作表)。
   - 这一步「用什么」的主做法写着 op 的类名(用 run_operation 调用的)= 有动作 op。只在兜底、注意事项里出现的 op 名不算。
   - 操作表里有这一步、做法是鼠标的:按 §3.2 的三个问题判。该有的(包括判不准的)照操作表用鼠标做、继续打,记进「缺口」。只是看的照操作表用鼠标,不报。
   - 操作表里没有这一步的:也按三个问题判。不该有的不点,不算缺口(操作表里没写怎么点,不自己试着点)。该有的分两种:这一局在这里必须做的,停在这个画面(§4.2 的表);不是必须做的,不点,记进「缺口」,继续打。
   - 操作表里没有这一步、任务书写明了怎么做的(比如开局、续局、恢复类的说明):照任务书做,不算缺口。

判断结果写进单局报告的「画面核对」和「缺口」,由编排者登记进追踪文件;实机探索 agent 不自己改追踪文件。

## 4. 遇到情况怎么处理

### 4.1 停止操作汇报纪律

遇到问题(操作不生效 / 画面异常 / 疑似机制变化 / op 报错)的动作顺序:

1. 停止操作:一切游戏操作停下,游戏窗口状态保持原样,不试图自行修复或退出当前画面。
2. 保存证据:截图留档 + 一句话描述 + 发生时间。
3. 汇报:现象 + 证据 + 发生时点报给编排者,然后等待。

禁止:自行改代码;自行绕过问题继续跑(把问题藏进「看起来跑通」);未经交接就把游戏窗口丢在当前状态。

例外以 §4.2 的表为准:表里写「继续」的几种情况不停手。

### 4.2 各种情况怎么办

实机探索 agent 在局内遇到下表的情况,按表处理;表里没有的,按 §4.1 停止操作并汇报。

| 遇到的情况 | 实机探索 agent 做什么 | 这一局 |
|---|---|---|
| 进了没建档的画面 | 先按 od-dev-screen-onboarding 建档、写画面文档前两章,再继续。画面上有该有动作 op 的动作还没有的,按下面几行处理 | 继续 |
| 画面上有该有动作 op 的动作还没有,操作表里写了这一步(怎么判见 §3.3) | 照操作表用鼠标做,继续打。记进「缺口」 | 继续 |
| 这一局在这里必须做的一步(不做就走不下去),该有动作 op 而还没有,操作表里没有这一步 | 停在这个画面,用鼠标把它摸清楚,该建档的建档。能点到哪一步见 §4.3。摸完就停手汇报,不往后打 | 停在这个画面 |
| 不是必须做的一步,该有动作 op 而还没有,操作表里没有这一步 | 不点。记进「缺口」,继续打 | 继续 |
| 画面上某一项内容认不出(识别结果里有一项标成认不出,比如商店一个槽位的 kind 是 `unknown`) | 自己读图,继续打。记进「缺口」,缺的那一层写「画面识别」 | 继续 |
| 画面识别读不出数(这个画面有字段说明〔extras_doc〕,读数〔extras〕却是空的) | 先等几秒重新识别;仍然读不出,按玩家 skill「通用注意事项」第 5 条的应急做法继续(存图、自己读图)。把现象记进「未闭环问题」。没有注册识别器的画面,读数本来就没有,不算这种情况 | 继续 |
| 疑似游戏机制和文档写的不一样 | 不停手。把现象和证据截图记进「知识发现」,继续打。是玩法指引和实机不一样的,记玩法指引的不足(§6.4) | 继续 |
| 识别出的画面名和实际画面不符,或读数和画面上的数字对不上 | 按 §4.1 停止操作并汇报 | 停在这个画面 |
| 动作 op 点了没生效、点错位置,或 op 报错 | 先重新识别画面。按玩家 skill「通用注意事项」第 1、3、4 条排除状态原因(按钮置灰、商店面板没收起、坐标和槽号取自旧读数、弹窗挡住)。然后用同一个动作 op 重发一次。重发不生效 → 按 §4.1 停止操作并汇报。重发成功以后:查到了状态原因的,不用记;没查到原因的,记进「未闭环问题」 | 重发成功:继续;否则停在这个画面 |
| MCP server 连不上,或游戏掉线 | 停止操作,把能保存的证据保存,向编排者汇报。停下方式写「中途停下」,原因写明。对局还在不在,留给重派以后的 agent 识别(orchestrator.md §7.2) | 中途停下 |
| 游戏闪退 | 把能保存的证据保存,向编排者汇报。停下方式写「中途停下」,原因写「游戏闪退」。对局还在不在(有没有存档),等游戏重新打开以后看(orchestrator.md §7.2) | 中途停下 |

### 4.3 停在画面上「摸清楚」的时候,能点到哪一步

- 可以点:点了以后画面还在的——切换页签、打开弹窗或详情、选中一项、再点取消关掉。
- 不可以点:一点就会离开这个画面的——推进到下一个节点、出战、确认领奖这类。这些只建档,留给验证的时候点(记法见 §6.1「没点的按钮,建档怎么算」)。
- 拿不准某个按钮点了会不会离开画面 → 不点,记进「缺口」(属于动作 op 那一层,写明拿不准的是哪一问)。

### 4.4 三种不算故障的停下

MCP server 连不上、游戏掉线、游戏闪退这三种,只写在单局报告「停下方式」的原因里,不记进「未闭环问题」。它们不是要诊断的故障,由编排者按固定步骤恢复(orchestrator.md §7.2)。

## 5. 接管已有对局与恢复

### 5.1 交接协议

- 交出窗口的 agent 交窗时报告现场四项。
- 接管方开工第一步先识别当前画面(analyze_screen),和交接报告核对。
- 核对范围:当前画面必须一致。对局进度、血量与金币,画面上读得到的时候核。未了事项只用来接手,不核。
- 对不上的出口有两个:
  - 当前画面和对局进度都对不上 → 现场视为不可信,按 §4.1 报编排者派诊断,不先动手。
  - 只有当前画面不同、对局进度对得上的(比如断线重连以后回到了备战画面)→ 接着打,在单局报告里写明。

### 5.2 恢复以后接着打

上一份报告是因为哪一种情况停下的,任务书的附加信息节会写明。照对应的一段做:

- MCP server 连不上:「游戏画面没动过。先识别画面,按 §5.1 交接协议核对现场,对得上就从停下的地方接着打。」
- 游戏掉线:「先识别画面,有重新连接的提示就点它;连不上就停下回报。连上以后按 §5.1 交接协议核对现场,对得上就从停下的地方接着打。」
- 游戏闪退:「按玩家 skill 进货币战争,走到模式选择画面。是「进行中」形态(有存档)→ 点「继续进度」,续的是原来那一局,按 §5.1 交接协议核对现场,对得上就从停下的地方接着打。没有存档 → 对局已经丢了:写一份单局报告,停下方式写「中止」,回报编排者。」
- 用户叫停:「先识别画面,按 §5.1 交接协议核对现场,对得上就从停下的地方接着打。」

核对现场时,续局以后进度比记录的早(闪退以后回滚到了前一个节点)也算对得上:接着打,在单局报告里写明。

## 6. 能写哪些文件

不经用户裁定能写的只有四样(§6.1 到 §6.4),不动 `src/` 下的代码。不写的内容见 §6.5。

### 6.1 建档内容

按 od-dev-screen-onboarding 的完整步骤做,包括它的测试仓部分(往 sr-od-test/ 归档本画面的截图、跑 id_mark 准确性测试)。画面档的 area、id_mark 经 MCP 写档工具写;模板文件按画面建档 skill 裁出来、放到模板目录。

**没点的按钮,建档怎么算**:没点的按钮,建档到这里算告一段落。本领域的「告一段落」就是本领域的建档完成。

- 画面文档「建档 area 说明」的「交互效果」一栏写「未点,预期作用是…」。画面档的 goto_list 不填。
- 和画面建档 skill(od-dev-screen-onboarding)的三条硬规则冲突,以这里为准,不用自己权衡:
  - 它 §3.4「交互类 area 必须 click 实锤」:会离开画面的按钮不点,没有点击记录也算建档告一段落;
  - 它 §3.5「跳转关系落 goto_list 是硬要求」:没点的按钮不填;
  - 它 §3.3「强制探索协议」的第 2 步「系统找出口」:不执行,出口留给实机验证的时候点。
- 画面建档 skill 开头的「建档完成」定义,和它 §8「写完自检」里要逐个交互验证的那几项,按上面三条同样放宽,不算没完成。
- 实机验证 agent 点过这些按钮的,验证报告里写明点了哪些、点后到了哪个画面。修复线在正本更新这一步补录这些按钮(orchestrator.md §6.6)。

### 6.2 画面文档的前两章

画面文档的前两章(画面简介、建档 area 说明),写法见画面建档 skill「画面文档」节。

- 新画面的前两章全写。
- 已建档画面的前两章,只改和建档 area 有关的描述。讲游戏机制、交互效果的句子发现和实际不一样,只记进「知识发现」,不改。

### 6.3 玩家 skill 入口列表加一行

新画面在玩家 skill 入口文件(SKILL.md)的「各阶段与画面的处理方案」列表里加一行。加在它所属的阶段分组下;是某个主画面的子态,就用二级缩进排在主画面下面。只加画面名,不改别的行。

### 6.4 玩法指引的不足

照玩家 skill 的指引打的时候,感到不够用的地方,当时就写进玩法指引的不足文件。

- 文件:`.temp/tracking/currency-war/玩法指引的不足.md`。它不在版本控制里,会话结束了也留着。文件不存在 = 还没有登记过,第一次登记时新建。
- 什么算不足,三种:
  - 要做判断,觉得难,玩家 skill 里没有指引;
  - 有指引,但觉得不适合现在的情况;
  - 照着做了,效果不好。
- 一条写四样:哪一种;当时要做什么判断(第几局、哪个节点、哪个画面);玩家 skill 里相应的指引(哪份文档的哪一节、原句;没有的,写找过哪里、没找到);自己怎么判断的、结果怎样。附证据指针。

  下面是一条的样子(内容是示意):

  ```markdown
  - 7 | 有指引,但觉得不适合现在的情况。
    当时:第 43 局,位面 2 第 1 个节点,出战前,要决定……
    指引:comps/反击刃.md §3。原句:「……」
    自己怎么判断的、结果怎样:……
    证据:match-43-1.md
  ```

- 编号在全文里顺延,删掉的编号不复用。
- 同一种不足已经登记过的,在原来那条后面补一句这次的经过和证据指针,不另起一条。
- 不记在这里:画面上的操作问题照旧记单局报告的「缺口」「未闭环问题」;和指引无关的新发现照旧记「知识发现」。

### 6.5 不写的内容

- 画面文档的「玩法指引」章。「操作」章只有编排者在修复线接上动作 op 以后改那一格(orchestrator.md §6.7)。
- 玩家 skill 的指引文档:references/ 下的必读三篇、阵容图鉴、阵容攻略、机制各篇。
- `docs/game/currency_war/research/` 各篇。
- 删除任何文档。

知识上的新发现不直接改文档:写进单局报告的「知识发现」,由编排者转登。指引不够用的地方不是知识发现,记玩法指引的不足文件。

## 7. 单局报告

### 7.1 放哪、叫什么

报告和证据截图一起放 `<自主工作文件夹>/<线名>/`。文件名 `match-<局号>-<序号>.md`:

- 局号按开新局的先后从 1 数起;
- 接着打同一局的报告沿用同一个局号,序号从 1 顺延;
- 还没开新局就停下的(比如模式选择画面有存档),用下一个局号,序号 1。

### 7.2 各节

各节如下,以这里为准:

1. 停下方式:局终 / 中途停下 / 中止。中途停下的写原因,七选一:操作表里没有这一步 / 有要查原因的问题 / 模式选择画面有存档 / MCP server 连不上 / 游戏掉线 / 游戏闪退 / 用户叫停。
2. 局账(这一局的结果):走到哪、难度、照哪条阵容线打、怎么结束的、局内目标。
   - 走到哪 = 节点进度(如位面-节点号)。难度 = 当局难度档。照哪条阵容线打:没照具体阵容线的写「没定」。怎么结束的 = 胜负与终止原因。
   - 局内目标写达到 / 未达到(差在哪)。什么算达到,见 orchestrator.md §3.1。
   - 这一节最后写一行:这一局登记了玩法指引的不足第几号到第几号,没有写「无」。
   - 中途停下的报告里还没发生的写「未到」,不算缺失。
3. 关注清单逐条覆盖状态:每条写对应哪个画面(按玩家 skill 的画面名)。结果是下面三种之一,前两种附证据指针:看到了,没问题;看到了,有问题(问题另记进「缺口」或「未闭环问题」);没看到。
4. 缺口:缺什么一眼看得出的记这里——画面没建档、某类内容认不出、该有动作 op 而还没有的动作。每条写画面名、缺哪一层(画面建档 / 画面识别 / 动作 op)、证据指针、建议处置(立修复线 / 现在探不了〔写明卡在什么条件上〕)。属于动作 op 那一层的,再写三个问题的判断:操作表里有没有这一步;写了的,照它做了没有、结果怎样;没写的,哪些没点;三个问题答不准的,写明理由。
5. 顺带取证和顺路验证的结果:采到的项写数值和证据指针;每条顺路验证写达标 / 不达标 / 没遇到,附证据指针。
6. 知识发现:玩法上和文档不一样、或者文档里没有的内容。每条写建议去处(待跟进事项文件 / 待裁知识队列);去处是待裁知识队列的,再写建议落点(改哪份文档的哪一节)。建议去处怎么选:证据还不够、要再打一局才能核实的,写待跟进事项文件;证据够、只是等用户裁定改不改文档的,写待裁知识队列。
7. 未闭环问题:要查原因的现象记这里——读不出数、动作 op 没生效或点错位置、认错画面。只列还没处置的。
8. 遗留。
9. 晶球余额。
10. 证据文件清单:截图文件名,结算截图也在内。
11. 画面核对:先写报告日期(年-月-日)。这一局到过的每个画面一条。写画面名;识别核对(一致 / 有不一致,有不一致的写一句是什么,详情在「缺口」或「未闭环问题」);用过的动作逐个写(动作名、用的是哪个 op 还是鼠标点击、正常 / 不正常);用鼠标做的,再按 §3.2 三个问题判的该不该有动作 op(该有 / 只是看,不用做 / 判不准);这个画面在追踪文件里原有的缺口,现在还在、不在了、这一局核不了,还是已经补建(核不了的写原因)。到了画面没做动作的,动作写「无」。

另外:

- 中途停下时另加两节:现场四项(当前画面 / 对局进度 / 血量与金币 / 未了事项)、这次写的文件清单。
- 局终那份:第 3、11 节汇总本局全部结果;第 4、6、7 节只列前面几份报告没报过的。
- 重派任务书的附加信息节写着要补写哪一栏的,接手的实机探索 agent 补写。

### 7.3 回信

回信不超过 10 行:停下方式一行(中途停下的带原因)+ 局内目标达到没有一行 + 未闭环问题数一行 + 本局新报的缺口数一行 + 顺路验证有没有不达标一行 + 这一局登记的玩法指引不足几条一行 + 报告路径。

### 7.4 提交

每次汇报之前(中途停下、局终、中止都算),先提交这次派发里写的文件,提交完再发报告。

- 提交范围:建档文件、模板资产、画面文档、玩家 skill 入口列表加的那一行、测试仓里的归档图和 id_mark 测试。测试仓是独立的仓库,单独提交。
- 提交规则按项目入口文件的提交规范:逐文件点名;提交前核对该文件的改动全是这次派发写的。
- 文件里有别人的改动 → 不提交该文件,文件名记进「遗留」。

## 8. 取证与知识的可靠性

1. 帧号制度:候选实录与机制结论必须附帧号。帧号 = 帧时点的可回查标识,实证形态 = 截图文件名(单局报告里叫证据指针)或遥测流水时点。判据:无帧号 = 不可回查 = 不入档;口头转述无帧证的内容只作线索。
2. 单样本知识先核实再入契约:仅出现一次的观察读数不入消费契约(注册表条目、知识文档的确定性结论)。核实路径 = 第二来源(官方配置、wiki、以前实机局留下的截图)任一命中;三样都没有,才设计实机取证(再打一局取证)。
3. 知识源被质疑时暂停下游写入:某条知识或数据点被质疑后,先核实,再继续以其为依据写入新条目。
4. 自己写错了要自纠:改知识文档的 agent 发现自己此前写入的内容有错,直接修正,并同步检查这个错误的其他消费点。自主推进场景一例外:知识文档等用户裁定,发现写错只记进单局报告的「知识发现」,不直接改。

### 8.1 数据源优先级

取证优先级从高到低:官方配置 > wiki 三源 > 项目注册表(代码内注册表与 `knowledge/` 事实常量)> 实机统计推断。

- 实机局首先是覆盖手段,玩法上的新发现顺带收集。要专门弄清某个机制或数值时,先查官方配置与 wiki(§8.2);两者都查不到才设计实机取证,取证按第 8 节开头四条附帧号。
- 实机统计样本与官方配置冲突时,以官方配置为准复核读数:先查读数链(OCR、识别、转述环节),确认读数无误再上报矛盾。禁直接按样本改配置结论。

### 8.2 版本配置什么时候查

- 拉官方攻略广场配置快照(plaza config,拉取命令见 version-update.md §2 第 2 步):角色、羁绊、装备、投资的官方名单与效果文本。
- 查 wiki 三源交叉(米游社 wiki / 国际服 wiki / BWIKI,接口入口 = skill `sr-od-official-api`)。
- 随机池类取证(概率、出现规则、池构成)先查配置再耗实机窗。结构盲区 = 样本覆盖不到的规则结构(低概率档、隐藏门控、跨局状态),统计上看不见但真实存在;纯统计推断会被它骗。配置与 wiki 先给出结构假设,实机局只做验证。
- 自主推进场景一不把这一步排成单独的任务:它属于版本适配时做一次的事(version-update.md §2)。探索中要用到配置时(比如核对一个随机池的概率),再按上面三条查。
