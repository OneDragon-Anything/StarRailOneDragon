# 0002. L0~L4 分级验证架构(L1 总做 / L4 游戏流程硬性)

- **Status**: accepted
- **Date**: 2026-08-04(形式化日;决策本身随 skill 创建 ~2026-07)

## Context
不同 PR 需要不同验证深度:纯框架代码 L1(静态)就够;画面识别要 L3(离线截图喂识别);游戏流程要 L4(live 运行)。一刀切要么过重(全做 L4)要么不足(只做 L1)。功能没在游戏里跑过 = 没验 —— 但 live 要消耗游戏资源,需优先可逆低消耗路径。

## Decision Drivers
- **对症**:不同 PR 类型配不同深度,避免一刀切。
- **功能可信**:游戏流程类 PR 的功能必须在游戏里跑过才算验。
- **资源节约**:live 避开消耗周限/体力/日限的动作,优先导航类可逆路径。

## Considered Options
1. **一刀切全 L4**:最稳但过重(纯框架 PR 不需要进游戏)。
2. **一刀切只 L1**:不足(游戏流程 PR 功能没验)。
3. **L0~L4 分级,逐级有则记无则跳**(选中):L0 分诊判适用 → L1/L2 总做(不依赖环境)→ L3/L4 按 PR 类型决定。
4. **L4 作可选项**:游戏流程 PR 可能被跳过 live → 功能没验。不可接受。

## Decision
选 3:
- **L0 分诊**:前端/CI/纯 git 启动逻辑 → skip;业务逻辑/画面识别/操作流程 → 继续。
- **L1 静态审查**:总是做(查逻辑错/回归/死循环/泄漏 + 框架语义,见 [ADR-0003](0003-framework-semantic-checklist.md))。
- **L2 背景核实**:PR 描述/issue 提到的游戏行为/bug 是否属实。
- **L3 离线运行**:测试仓截图喂 `analyze_screen`;自定义识别管线复刻;PR 自带测试 `pytest`。
- **L4 live 运行**:**游戏流程类 PR 硬性要求**(不是可选);优先可逆低消耗路径(导航,不消耗周限/体力);真无法 live(纯消耗且无低消耗切入 / 需特定账号地区 / 需外部凭据)→ 明确标「无法 live 验证」并写明缺什么,**不假装验过**。

## Consequences
- **正向**:深度配 PR 类型,不浪费也不漏验;游戏流程功能必验。
- **负向**:分级判据有主观性(L0 判「游戏流程类」靠人);L4 live 受游戏环境限制。
- **follow-up**:无。
