## 1. 问题与动机

- **现状症状**:现行 sim(engine_p1 3606 行单文件)是「策略 A/B 评估器」(`sim/sim-design.md` §1.1 自述「sim 只做一件事:在 shop 决策面上评估策略 A/B」),不是「游戏」。三个结构性偏离:
  1. **随机面靠预置注入**:投资策略/环境按 plaza 帖频次表注入(`sim/cw_sim_invest.py` 的 `SIM_STRATEGY_PICK_SCHEDULE` = 63 局 replay 统计频次,不是游戏机制)、开局 bench 按遥测校准分布抽(`START_BENCH_COUNT=4`/费用权重 65/35,engine_p1 `START_BENCH_COST_WEIGHTS`)、战斗结算按实机经验分布 Δ池采样 + 胜率阶梯查表(`kernel/cw_battle_calib.py`、`sim/pool.py` Δ池)——都是「用统计镜像代替机制」。
  2. **评判机器混进游戏本体**:`sim/checks/` 子树 11 模块(约 435KB:calib/corpus/ledger/pool/runner/runtime/segments/selfcalc/suspects/t190_c/launch)与 runner 的批量/A-B/账本落盘,使「游戏」与「裁判」无法分开替换。
  3. **策略逻辑长进引擎**:引擎内含 sim 视图注册表、M1P 部署计划面、围栏/残余部署代理、投资双臂(基线臂/频次臂)授权标签等策略侵入点(明细见 §2.4),策略器与游戏不可独立演化。
- **根因归层(语义层)**:sim 的职责定义错了——被定义为「策略评估器」(评判语义),而已裁定的职责(§0 已裁边界①)是「模拟实机环境」(游戏语义)。职责错位派生出注入式随机面(评估器只需分布像,不需机制对)与评判机器混入。
- **解决到哪**:按「游戏」语义重写 sim 的模块边界、随机面建模口径、策略器接口;逐模块规格化;未知机制收集成议程。
- **明确不解决**:策略效果评估体系(A-B/批量/检查器)不在本迭代重建,只删不建;实机操作链(operations/obs)零改动;kernel 单一源注册表零改动;P3 节点序列等无观测机制不发明回退(照 `research/plane_schedule_observed.md` 裁定,以实机补采为准)。

## 2. 方案

### 2.0 设计总纲

#### 2.0.1 职责定义与交互模型

```
策略器(mandate_v1:全函数 f(期望态)→动作,strategy-docs/02 §7)        sim(游戏本体,本迭代重做)
        │  观测帧(容器 GameState 快照 + 相位)                            │
        │ ◀──────────────────────────────────────────────────────────────┘
        │  动作(统一动作词表 kernel/cw_vocab.py CwAction 族)              │
        │ ──────────────────────────────────────────────────────────────▶ │
        │                                                                 │ 按游戏规则转移状态
        ◀── 转移结果(applied/reason)+ 下一观测帧/相位(节点结算、offer 弹出等)──│ 随机面按机制概率采样
```

- sim 是唯一的状态推进者与随机量产生者;策略器是纯决策函数,**不消费 sim 的随机流、不感知 seed**(策略自带随机时用独立流键 `strategy/*`,§2.0.4)。
- sim 输出的「观测帧」= 容器 `GameState`(`kernel/cw_game_state.py`)快照 + **相位(phase)**。相位枚举 = 实机画面对应的交互状态机:`opening_env`(投资环境选卡,环境在场参数为真时)/`prep`(备战:商店/买/升/部署/卖)/`invest_offer`(局中策略选卡)/`encounter_offer`(遭遇选档)/`supply_pick`(补给 3 选 1)/`box_pick`(补给箱)/`reward_ball`(奖励球)/`event_overlay`(巨星/伙伴/专家邀请/Fate/骇入等)/`settlement`(结算)/`plane_transition`(位面过渡)/`game_over`。相位与实机画面建档(`docs/game/screens/currency_war_*.md`)一一对应,策略器据此路由决策(与实机 flow 层同构)。
- sim 对动作的应用分两类,单一源纪律不变(`sim/sim-design.md` §2.1 契约平移到新架构):
  - **玩家动作**(买/卖/刷/升级/部署/穿戴/选卡/点球/工具)→ 经单一转移函数 `kernel/cw_game_state.apply_shop_action_logic` 及其动作族腿应用,拒绝语义在腿内(`LogicOutcome`);
  - **环境事件**(发牌/收入/结算/offer 生成/位面推进)→ sim 机制面按本稿 §2.2 各模块规格执行,以 obs 渠道写容器。
- **保真度分层声明**(逐模块标注,判读外推纪律沿用 `sim/sim-design.md` §1.3 三档):真代码层(注册表/概率表/策略本体)可直接信;机制层(本稿按游戏规则建模的转移)信机制文档;校准层(战斗结算等不可复刻面,§2.2 M13)结论带免责;sim-only 差异面禁外推(重做目标是把此档压到最小,残留面逐条申报)。

#### 2.0.2 三条硬约束的落地口径

1. **随机元素按游戏真实概率/效果建模**:每个随机量的概率源必须是(a)游戏内可读真值表(如 `data/cw_shop_odds.py REFRESH_PROB` = 商店概率弹窗 OCR);(b)已收案的机制口径(如牌池副本数 27/9,`research/economy.md` §1);(c)§2.3 裁决清单收敛后的定案值。**禁止**以 replay/语料统计分布充当机制概率(现行 `SIM_STRATEGY_PICK_SCHEDULE`、Δ池无条件采样、开局 bench 权重均属此列,§2.4 删改);已收敛的定案值(开局手牌形状采样、第一期战斗随机输出面)属 (c) 通道,不属统计镜像。
2. **逐模块规格化**:§2.1 全清单 × §2.2 逐模块规格,每模块写实机逻辑(引机制文档依据)/sim 状态与转移/概率源/复用面/随机流键。
3. **裁决清单**:§2.3 逐条「已裁决(定案 + 依据)」或「第一期定稿口径」;数据缺口标注「候实机数据」,回填参数不阻塞落地批。

#### 2.0.4 随机种子语义(全局)

- 单局 = 一个 `seed: int`。**全部随机量按流键派生子流**:`random.Random(f'{seed}#{stream_key}')`,流键 = 模块号 + 局内坐标(如 `M06/p1/r3` 发牌、`M02/env-offer`、`M13/p1/r7` 战斗、`M17/ball-1`)。
- 动机:现行引擎单 rng 实例按消耗序耦合,任何模块加/删一次采样就扰动全流(回归门被迫写「rng 消耗序不变」);流键化后各模块随机序独立,模块规格可独立演化。
- 可复现承诺 = `(seed, 开局参数, 注册表指纹)`。开局参数(职级/敌人难度档/词缀/对局类型)是**局级输入**,由调用方给定(§2.5),不是 sim 的随机量——sim 内不猜开局条件分布(现行 `START_BENCH_COST_WEIGHTS` 即违反本条;开局手牌现按定案规则生成,§2.2 M01/U28,不属「猜开局」)。
- 禁令:模块间共享 rng 实例;策略器读 sim 流;用未裁定的经验分布替代机制概率。

### 2.2 逐模块模拟规格

> 每节固定五件:**实机逻辑**(引依据)/ **sim 模拟**(状态与转移)/ **复用面** / **随机量与流键** / **未知指针**(→§2.3 裁决清单)。已裁决条目照定案实现;候实机数据参数回填不阻塞落地批。

### 2.5 单局运行的外层接口(定稿:候选 B)

- **前提**:策略器 = 全函数(期望态→动作,永不返回 None;「无动作」=选终结动作,strategy-docs/02 §7);实机 flow 层已是「单动作画面 op 架构」。sim 的外层接口本质 = **把「画面」换成「相位观测帧」**。
- **候选 A·引擎内嵌循环(现行形态改良)**:`simulate_run(seed, run_config, strategy)` 在 sim 内逐相位调 `strategy.decide_*(观测帧)`,返回局结果。优点:与现行 `simulate_p1` 调用习惯连续、改造量小;缺点:策略接口面多(decide_shop_screen/decide_invest/decide_encounter/…)由 sim 枚举,加新相位就要扩策略接口,sim 与策略耦合仍偏紧。
- **候选 B·显式步进协议(推荐)**:sim 暴露两个原语——`reset(seed, run_config) → 观测帧`、`step(action) → {LogicOutcome, 新观测帧 | 局结果}`;相位在观测帧里。策略器是外层驱动者:`while not done: act = policy.observe(frame); frame = sim.step(act)`。优点:①与 mandate_v1「逐动作提案」天然同构,实机 flow 层与 sim 驱动层可共用同一策略函数(真代码层复用最大化);②加相位 = 加观测帧字段,策略接口稳定;③「将来在 sim 外再包一层(批量/评估)」不动 sim 本体;④测试桩策略零成本。缺点:现行 `simulate_p1` 调用面要包一层适配壳。
- **定稿口径**:选 B(与 mandate_v1「逐动作提案」同构、策略接口稳定、批量外包不动 sim 本体、测试桩零成本);A 的入口函数保留为 B 之上的薄包装(兼容既有测试写法)。局结果 = `{final_hp, plane_reached, rounds, hp_trail, unmodeled 披露面}`(纯结果,无评判)。
- **记录**:策略器/sim 的逐动作轨迹经容器统一 state 流水落盘(同构);sim 不自建第二账本。
