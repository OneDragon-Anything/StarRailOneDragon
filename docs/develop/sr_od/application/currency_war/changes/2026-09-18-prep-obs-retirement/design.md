## 1. 问题与动机

### 现状症状

1. **实机事故**（2026-09-18 定谳，依据 `.debug/temp/incidents/20260918-reconcile/rootcause-reopen.md` 案一）：备战阶段板满（3/3）时决策仍产出第 4 个拖拽，游戏侧静默拒收（零像素变化、无弹窗），账实失配触发对账安灯停局。同机制跨局三次拒收全部发生在板=cap 时刻（match_g_20260918_023823/054257/055133 三局 journal 实证；023823 局 v117 容器 front_row 已含新上场角色而 14.387 决策帧黑板视图缺它，v122 投影把被拒收角色记成超员、v147 战后实读纠漂揭穿）。
2. **架构契约偏离**（对照用户口述规范逐条）：
   - 违反「策略器唯读 game state」：策略器读挂在 gs 上的黑板帧视觉字段——部署名单（`obs.bench_chars`/`obs.deployed_chars`，entry.py:607-608 组装）、装备（`obs.owned_equips`/`obs.occupied_equips`，cw_equip_wear_plan.py:164-182 与 entry.py:793）、晶矿（`obs.spheres`，entry.py:507-509）、宝箱/典籍（`obs.boxes`/`obs.tomes`，entry.py:458-461）。
   - 违反「写端唯二」：动作后存在第三写端——`_project_prep_obs` 的黑板名单/晶矿推进腿（cw_screen_prep.py:974-1092），既非画面op 观察上报、也非动作op 的 kernel 逻辑态写口。其中名单推进含静默失效分支：新上场者须在黑板名单按槽号精确命中才推进，命中失败静默不推进（cw_screen_prep.py:1030-1052 `moved is None` 分支）；容器腿（kernel 写口 `apply_prep_action_logic`，:1021）无此依赖。事故帧即两腿分叉：容器对（v117）、黑板错（14.387 帧 M7 视图 2 人）。

### 根因归层

**契约层**。名单的双重身份（画面识别产物 / 逻辑事实）未拆分：部署上限判定消费的是逻辑事实（板面几个人），却从识别链（黑板帧）取输入；黑板帧的推进走第三写端、无对账显影、可静默丢更新——两本账无双写同步硬约束，分叉是结构允许的，消费面读哪份决定了对错。

### 解决到哪 / 明确不解决

**解决到哪**：`gs.prep_obs` 槽退役；名单、装备、晶矿读端全部切容器（含坐标契约，见 §2）；占用/空位改名单现算；动作后名单/装备/晶矿写端收敛为 kernel 逻辑态写口唯一；瞬态物与控制信号降级备战环内部传递。

**明确不解决**：
- kernel 部署谓词语义（`select_deployments_reasoned` 判据式不动，只换输入源 + 前置显式门）；
- 停买/线状态/升级授权的判据式（只换输入源，行为变化仅来自数据源更准）；
- 板满时的自动卖出规划（卖谁、何时卖是 M4/M6 策略行为，本迭代只拦截+落账，交决策循环既有步骤序）；
- 商店域（已容器化）、tracked 执行账（执行器记账，不在策略输入面）、识别 reader 本体（SIFT/OCR 算法不动）。

## 2. 方案

### 系统级变化（终态图）

| 事实 | 唯一账 | 现状 |
|---|---|---|
| 备战席名单（含宝箱/典籍占席） | 容器 `bench`（BenchView，`BenchSlot.kind ∈ unit/supply_box/tome/empty`，cw_game_state.py:540-548） | 枚举已有；**box/tome 区分写端现缺**（读链 `is_item_slot` 布尔统一映射 supply_box，cw_game_state.py:1446-1451），细分补齐随批 5；读端未切完 |
| 上场名单 | 容器 `front_row`/`back_row`（Unit 定长槽表，读口 `deployed_slots_of`） | 已有；读端未切完（事故源） |
| 装备拥有 | 容器 `equips`（owned 全量含工具） | 已有；M7 读端未切 |
| 装备穿戴位置 | 容器新域（批 2 立，schema 见详设） | 无，观察产物只落黑板 |
| 晶矿 | 容器新域 `spheres`（批 4 立，像素坐标+颜色+半径） | 无，只落黑板 |
| 席空位/前后排占用 | 名单现算（批 3） | 黑板独立记账（双本） |
| 宝箱/典籍点击坐标 | 不落盘：动作参数=槽号，执行器按槽号→画面坐标固定映射现算（`row_area_centers` 簇，1080p 布局既有前提） | 黑板存像素坐标（冗余，删） |
| 事件 overlay/子态可读性/帧识别元信息 | 备战环 op 内部局部对象（控制信号：bail 交外环、对账日志），非决策输入 | 黑板字段（降级保留局部） |

### 跨详设接口契约（总纲定死，两份详设共同遵守）

1. **批间边界**：批 1 只做读端切换 + 显式门 + 拒因落账，**禁预删黑板字段**（删除是批 5 面）；批 1 落地后决策帧名单已是容器源，黑板名单剩余读者在批 2–5 清零。
2. **失读方向统一**：容器失读语义 = carry（保旧值，P2-1 空集守卫族，cw_screen_prep.py:683-720）；读端切换后禁止再引入「空集=失读」语义（黑板空集守卫随批 5 消亡）。批 1 等价性论证见 `details/cap-fix.md` §方案-6。
3. **坐标契约**：bench/front_row/back_row 槽位号 = 1-based 画面物理槽（既有约定）；商店 = 槽号 + 画面 x；晶矿 = 像素坐标（晶矿无槽号）；一切槽号→点击坐标换算在执行器现算，禁止落盘像素。
4. **写端唯一**：动作后名单/装备/晶矿的逻辑态更新 = `apply_prep_action_logic`（kernel 写口）唯一；观察上报 = 入口 `observe` 链唯一。批 4 将「容器零写（视觉域推进）」的晶矿语义翻转，正本 `game_state/logic-updates/collect-ore.md` 同步。

### 详设划分

- `details/cap-fix.md`：批 1（阶段 3.1）——事故修复主体，读端换源 + cap 门槛 + 拒因。
- `details/obs-retirement.md`：批 2–5（阶段 3.2–3.5）——装备归位、占用现算、晶矿域、黑板退役；内含 `PrepObservation` 全字段去向表（批 5 的删除清单以它为准）。
