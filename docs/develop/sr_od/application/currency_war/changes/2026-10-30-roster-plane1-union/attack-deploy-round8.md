## 结论

**打回（阻断）**。2 阻断 / 2 中 / 1 中低 / 2 低：

- **D7-4 处置的事实基础与代码相反**——处置宣称「『一次识别多动作零读屏』是商店会话形态，备战域不是：备战 op = 观察节点与决策动作节点交替循环（cw_screen_prep.py:713/:774，每动作一观察帧）」，并以此为据宣告 D6-2/D6-3/D7-4 的形态矛盾消解；但被引代码白纸黑字是「入口 heavy **一次观察** → 逐动作『决策→执行→逻辑态直写』循环，**循环内零读屏**」（cw_screen_prep.py:779-789 docstring + :801 `while True` + :705-711 模块注释 + :862-864「对账归下一入口 heavy reconcile」）——备战域现行形态恰恰就是七轮声称要修正掉的零读屏多动作形态。级联「逐帧驱动」的强制载体（差分动作后 Obs(outer_loop) / 统一拖动 terminal 化 / 决策循环单动作化，三路均零登记）、「连续 2 帧不增」的帧观测数据源在零读屏循环下的取数路径，双双悬空——D7-4 的修复被一个失实的代码引用盖住，原矛盾（判定载体 vs 执行形态）未消解（D8-1）；
- **D7-1 组得分的增量口径只写给了核心键组（L1 域）**——「增量口径（补后 L1 分 − 骨架基线，防双计骨架成员）」的括号没有落到 sub_tiers 组（L2 域「Σw×档位完成度 × 10⁶」）与 L3 组（「L3 单位序」）上，而骨架基线是「骨架成员按 §1 全量计分（含其全部标签跨层贡献）」——绝对读法下骨架成员的 L2/L3 贡献被双计。实存反例件非构造假设：**三月七/花火 ∈ 姬子线 core_chars/shared_chars（cw_comps.py:577,591）∧ ∈ CROSS_LINE_KEEP_NAMES 万金油名单（protection.py:49-51）**——骨架内三月七的 ×2 已进基线，DP 万金油组按板面绝对计数再计一遍；瓦尔特（姬子线 core，cw_chars.py:190 flows=「减益」= 该线 sub_tiers 键）同款垫底 L2。DP 度量系统性偏差 → 候选漏板，且不在 D7-2「次标签贡献不可见」的已申报近似边界内（这是主归属组自身的口径错误）（D8-2）。

## 发现清单

### D8-1｜D7-4 处置事实基础失实：被引代码就是「一次观察 + 零读屏多动作循环」，与「每动作一观察帧/观察-动作交替」相反——级联逐帧载体与「2 帧不增」判定数据源双悬空，D6-2/D6-3/D7-4 的形态矛盾未消解
- 攻击点：详设 :94 宣称「（七轮 D7-4 修正——『一次识别多动作零读屏』是商店会话形态，**备战域不是**）：备战 op = 观察节点与决策动作节点交替循环（cw_screen_prep.py:713/:774，**每动作一观察帧**……『连续 2 帧不增』的帧 = 观察-动作周期，拖拽未效经真实观察可检出〔零读屏形态下该判定不存在、会误判收敛〕）」。代码实况与之正面相反：① 模块注释（cw_screen_prep.py:705-711）「决策动作 node = 单动作决策循环(决策→执行→逻辑态直写，**循环内零读屏**;终结 op 返回主循环)」「稳定性由**外循环每轮**重识别保证」；② 决策动作 node docstring（:779-782）「形态:入口 heavy **一次观察** → 逐动作……循环，循环内零读屏」；③ 循环体 :801 `while True` 逐动作调 decide_prep_screen（:805），只有终结动作（terminal 集 = 换画面类，:860）、CwActionObs(outer_loop)（:813-821）、overlay pending（:875-880）、异常才退出；④ 直写与对账注释（:862-864）「假账风险由**下一入口** heavy reconcile 以实读纠逻辑态承担」——观察频率 = 每 op 访问一次。两 node 是「每访问各进一次」的顺序结构，不存在「交替循环、每动作一观察帧」。后果链：级联待完成态的差分动作（统一拖动，非终结、不换画面）落入该循环即被**连续执行、零读屏**——自上报按推演直写逻辑态 → 容器板面「已就位」→ diff 空 → 清槽，而真实板面可能纹丝未动（拖拽未效）——这恰是 D7-4 处置自己承认「零读屏形态下……会误判收敛」的形态，即现行代码的默认行为。要得到处置宣称的形态，需要显式改造：差分动作后强制发 CwActionObs(outer_loop) 逐帧退出（现仅用于「无动作可发帧」，design.md:69）、或统一拖动进 terminal 集、或决策循环单动作化——三条路径在详设收编清单/总纲实现边界（design.md:70「禁动流程框架」）均零登记，且各条与总纲约束的相容性不同（terminal 化改注册表类属性 = 动作语义变化；Obs 逐帧化 = 每动作一次外循环 heavy 重观察的成本申报缺失）。「连续 2 帧不增」的「帧」在零读屏循环内无观察数据可取（:94 声称「帧 = 观察-动作周期」的前提不成立）。实现者按 :94 给的坐标去读代码，读到的是与详设相反的形态——必须自决改造路径，任一选择的行为与成本都不同。
- 证据：详设 :94/:122（「级联态下逐帧发差分动作，见 §3.5」）vs cw_screen_prep.py:705-711,779-789,801,805,813-821,860-864,875-880；design.md:69-70（逐帧驱动/单动作契约/Obs 仅无动作帧/禁动流程框架）。
- 严重度：高（**阻断**：七轮处置以失实代码证据宣告矛盾消解——级联执行形态与失败检测（同一机制两面）的载体悬空；按现行代码字面落地 = 零读屏连发 + 误判收敛清槽 = 真实板面烂在半路，D7-4 攻击的事故形态原样保留）。
- 是否阻断：是。
- 处置建议方向：写死级联逐帧化的实现载体并登记改造面——推荐 = 前置步每发一个差分动作后紧跟 CwActionObs(outer_loop) 强制交回外循环（下一入口 heavy 观察即「帧」，与 :862-864 对账机制天然衔接，不动流程框架）；「2 帧不增」的帧定义改锚「op 访问（入口 heavy 观察轮）」；第 6 步常规部署是否同款逐帧化或保留零读屏连发（连发形态下无失败检测，靠下一入口对账）分别申报。

### D8-2｜D7-1 组得分增量口径只写 L1 域：sub_tiers 组（L2）与 L3 组绝对/增量零文——绝对读法与「骨架基线全量计分」双计骨架成员的 L2/L3 贡献（三月七/花火/瓦尔特实存反例），DP 度量偏差致候选漏板且不在 D7-2 申报边界内
